# 05 · The project file

One logical document per project, stored and edited as YAML. The Zod schema in `packages/core/src/schema` is the single source. The JSON Schema, builder forms, reference docs and LLM context are all generated from it. The shapes below are checked against the schema by tests (`packages/core/src/schema`, `fixtures/golden`). If they disagree, the schema wins; the lead records the schema's key choices as a later topic (`docs/decisions/later/`), and the owner reviews after the build.

## Rules for the format
- `schema: ueberblick/<n>` goes on the first line. Platform migrators upgrade older files.
- **ID-keyed maps, never lists** for entities (`types`, `properties`, `tasks`, `auto` (the automatic actions of a task), `views`, `roles`). Diffs, merges and overlays address everything by key path, e.g. `types.baum.properties.vitalitaet`.
- **Keys are the contract.** They match `^[a-z][a-z0-9_]*$` and are never renamed. Labels are `LocalizedString` (`"Baum"` or `{ de: "Baum", en: "Tree" }`). **Fallback chain (WP-588, one function: `localize(value, locales)` in `core/locale`):** a plain string is used as is; for a map, each requested locale in order (its exact tag, then its base language: `de-AT` then `de`), then the first key present, so a non-empty value never resolves to nothing. There is no project default-locale field (decision 0019's "default-locale fallback" is met by the caller): a caller that knows a default appends it to `locales` (the OGC API appends `de`, `en` after the request's `Accept-Language`). `localizeExact(value, locale)` is the editing variant: that language only, `''` when missing, never another language. The builder, the app and the OGC output all resolve through these two; local adapters may only shape arguments.
- **Platform keywords carry the `$` sigil** (`on: $map`, `on: $none`, `see: $all`, `write: $all`). Keys can never start with `$`, so a new keyword can never collide with a project's own key.
- **Option keys follow the key pattern** (letter first), so object order equals authored order: a vitality scale is `v0` … `v4` with the labels `0` … `4`.
- **Order is a change (A-042).** The key order of the maps in `ORDERED_MAPS` (`types`, `tasks`, `views`, `roles`, `types.*.properties`, `types.*.relations`, a select's `options`, `tasks.*.form`, `roles.*.app.views`, `shortcuts`, `tools` and `filter_presets`, `views.*.layers`, `map.layers`, `map.packs`, `tasks.*.auto`, the top-level `tools`, `info_pages`) is served config. `diff` reports a map whose shared keys changed order as one non-breaking `order_changed` entry (`before` and `after` are the key lists), and the version hash covers those key lists, so a draft that only reorders is a new version and the publish bar offers Veröffentlichen. Equal content in equal order has the same hash.
- Expressions are strings in the rule language (`06-rule-language.md`), and are type-checked by `compile()`.
- **No status in the file.** Deploy time, hashes and counts live in `config_versions`.
- Round trips preserve comments and key order (`yaml` Document API). Every save carries a revision hash, and a save based on a stale revision is refused.

## A template (sketch)
```yaml
schema: ueberblick/1
template: { key: baumkataster, version: 1.0.0 }

inputs:                                   # intended customisation points
  kontrollintervall_monate: { type: integer, default: 12, label: { de: Kontrollintervall (Monate) } }

lock:                                     # overlay may not touch these
  - types.baum.properties.stage.options

roles:
  kontrolle:
    label: { de: Baumkontrolle }
    description: { de: Kontrolliert Bäume }  # optional (WP-346): what the role is for, shown on the Rollen page
    quota: 50                             # optional: most features a participant with this role may create (WP-639)
    app:                                  # per-role app profile (H3): what this role's app looks like
      home: karte                         # default view
      views: { karte: {}, meine_aufgaben: {} }       # keyed maps: an overlay adds or hides single entries
      tools: { measure: { availability: offered }, search: { availability: active }, photo: {} }  # availability: offered | active (default active); `settings:` holds per-role tool settings
      shortcuts: { kontrolle: {} }        # tasks pinned for one-tap access
      filter_presets:                     # filters this role finds ready in the filter sheet (WP-640)
        meine: { label: { de: Meine Bäume }, filters: { baum: "self.zustaendig == actor.id" } }   # one rule-language expression per type, over `self`
      activity_names: true                # false: this role sees no names for other people's changes (default true)
  bauhof:
    label: { de: Bauhof }
    app: { home: meine_aufgaben, views: { meine_aufgaben: {} }, tools: { photo: {} } }

types:
  flaeche:
    label: { de: Fläche }
    geometry: umriss                     # the primary geometry: the key of a geometry property
    properties:
      umriss:           { type: geometry, geometry_type: polygon, required: true }
      name:             { type: text, label: Name, required: true }
      letzte_kontrolle: { type: date, label: { de: Letzte Kontrolle } }
  baum:
    label: { de: Baum }
    geometry: standort
    permissions:
      see: { intern_notiz: [kontrolle] }      # per property: unlisted properties stay visible; `$all` or roles for the whole type
      visible_when: "self.zustaendig == actor.id || !('bauhof' in actor.roles)"   # row level, compiled to SQL
      create: [kontrolle]
      write: { vitalitaet: [kontrolle] }
    process: { property: stage, start: erfasst, end: [erledigt] }   # the one process of the type (below)
    properties:
      standort:   { type: geometry, geometry_type: point, required: true }
      stage:      { type: select, options: { erfasst: Erfasst, kontrolliert: Kontrolliert, massnahme: Maßnahme, erledigt: Erledigt } }
      vitalitaet: { type: select, options: { v0: "0", v1: "1", v2: "2", v3: "3", v4: "4" } }
      befund:     { type: text }
      beschreibung: { type: localized_text }  # stores a LocalizedString per observation (F12)
      intern_notiz: { type: text }
      foto:       { type: file, accept: [image/*], max_files: 10 }   # a list of { sha256, name, mime }
      zustaendig: { type: participant, index: true }
      beteiligte: { type: participant, cardinality: many }   # Mehrfachauswahl: a list of participant ids (WP-443, A-048)
      faellig_am: { type: date, index: true }
    relations:
      flaeche: { to: flaeche, derive: "within(self.standort, other.umriss)", cardinality: one }   # one: traversal yields a feature
      massnahmen: { to: massnahme, inverse_of: massnahme.baum, label: { de: Maßnahmen } }   # read-only reverse set of a reference; many by default; optional label

tasks:
  kontrolle:
    label: { de: Kontrolle durchführen }
    on: baum                                             # where it is offered: a type key, [type keys], $map or $none
    # creates: massnahme                                 # the feature type a task creates; required for `on: $map`
    when: "'kontrolle' in actor.roles && self.stage != 'erledigt'"
    bind: { area: self.flaeche }                         # declared relations only
    form:
      vitalitaet: { calculate: "self.vitalitaet" }       # prefill = calculate from current value
      befund:     { required: true, constraint: "value != self.befund", constraint_message: { de: Befund muss sich ändern } }
      foto:       { tool: photo, relevant: "form.vitalitaet >= 'v3'" }
      area.name:  { readonly: "form.vitalitaet < 'v3'" }   # `<bind>.<property>`: a property of a bound Objekt (A-047), see below
      # befund: { page: { label: { de: Befund }, hint: { de: Bitte beschreiben. } } }   # `page` starts a new page at this field; label = tab and heading, hint = description (v3 FormPage)
      # name:   { placeholder: { de: z. B. Linde }, appearance: multiline }              # placeholder in the empty input; appearance = space-separated tokens of FORM_APPEARANCES (multiline, email)
    # steps: [{ kind: form }, { kind: location, property: geometrie }]   # a multi-step task, one run (see "Task steps")
    # button: { label: { de: Kontrolle }, color: success, icon: clipboard-check }   # how the task shows in the action row
    # confirm: { de: Kontrolle abschicken? }             # asked before the run is submitted
    then:                                                # a string value is always an expression; a literal option key is quoted
      - set: { "area.letzte_kontrolle": "today()" }
      - { set: { stage: "'massnahme'" }, when: "form.vitalitaet >= 'v3'" }
      - { set: { stage: "'kontrolliert'" }, otherwise: true }
      - set: { faellig_am: "today() + months(inputs.kontrollintervall_monate)" }
      # an erasure task instead has: - redact: { subject: actor, of: form.subject }

  # An automatic action is an `auto` entry of the task it runs (C-004). The task carries the form values, steps and permissions;
  # the entry says when the system runs it (`after`, `change`, `elapsed`, `schedule`, or no timing key: an edge on its `when`).
  melden:
    label: { de: Meldung anlegen }
    on: baum
    then: [{ set: { art: "'meldung'" } }]
    auto:                                                # no `who`: no person runs it, only the system (C-004 step 3)
      spielplatz_melden:                                 # the entry name; with the task it is the action's identity `melden.spielplatz_melden`
        after: kontrolle                                 # timing: the system runs `melden` right after the task `kontrolle` ran on the same Objekt
        when: "self.flaeche.name.startsWith('Spielplatz') && self.vitalitaet >= 'v2'"
  erinnern:
    label: { de: Erinnern }
    on: baum
    then: [{ set: { art: "'meldung'" } }]                # an automatic run has no form: its values come from `then.set`
    auto:
      kontrolle_wird_faellig:
        elapsed: { from: self.faellig_am, offset: "-days(14)" }   # timings (at most one): after: <task> | change: <type>.<property> | elapsed: { from, after?, offset? } | schedule: "<cron>" (+ idle) | none = an edge on `when`

views:
  karte:
    label: Karte
    camera: { center: [13.4, 52.5, 34.0], zoom: 17, pitch: 60, bearing: 0 }   # optional; center is [lon, lat] or [lon, lat, z]
    layers:
      baeume:
        source: { type: baum }                           # a feature type, optionally with a filter
        renderer: maplibre-2d                            # registry; 3D renderers later (H1)
        style: { $ref: styles/baum.json }                # style format belongs to the renderer (MapLibre Style Spec here; maplibre-2d: see note below)
      rathaus:
        source: { asset: "blob/models/rathaus/", format: 3dtiles }   # an external asset: a blob prefix or URL, never a filter
        renderer: maplibre-2d
  meine_aufgaben:
    source: { type: baum, filter: "self.zustaendig == actor.id && self.faellig_am <= today()" }
    sort: [faellig_am]

tools:
  measure: {}
  search: { sources: [baum.befund] }

migrations:                                             # shipped with major versions, executed as system runs
  "1 -> 2":
    - rename_option: { property: types.baum.properties.stage, from: kontrolliert, to: geprueft }
```

**Role property (WP-455, A-051).** `type: role` holds a role key of the file (v3's selector source "Rollen"); options are `cardinality: one|many` (many = a list of keys) and `select: { all?: [role], self?: [role] }` (WP-481, A-055, the participant shape: a role in `all` may pick any role, one in `self` only roles it holds, any other none; no `select` offers every role; `registry/participant-select.ts` `allowedRoles`, used by the device form and by plan, which refuses with `not_permitted` for a participant, never for an import, rule or the system). The device and the server check the shape (`typeFits`); plan refuses a key that is not in `roles` (`invalid_input`, path `form.<property>`, `plan/role-choice.ts`). In expressions it is a string (a list of strings with `many`). The participant form offers the file's roles by label, cells and the feature sheet show the label (an unknown key as it is).

**Mehrfachauswahl and Anzeigefeld (WP-443, A-048).** A `reference` or `participant` property takes `cardinality: one|many` (the same key and values as a relation; default `one`). With `many` the value is a list of ids (`typeFits`, the form's multi pick, reference edges for each id) and in expressions a list of features (`reference`) or of strings (`participant`). A `reference` also takes `display_property`, a property of the target type (compile: `dangling_reference` of kind `property_of` otherwise): pickers and admin cells show that property of the target, else the display name (B-014). The one function is `displayName(type, feature, locales, via?)` in `@ueberblick/core/locale` (`via` is the reference property). `display` stays the read-view object of a property.

**Layer styles and tool settings (WP-577).** A layer `style` is an inline object or `{ $ref: styles/<name>.json }`, a file of the project bundle (template plus overlay files). `compile(file, { assets })` takes the bundle as a resolver port, `assets(ref)`, and embeds the JSON in the compiled config. `assets` is required (R11, no default): ingestion points (a fixture loader, an import) pass a real resolver, and everything that compiles a stored or exchanged file passes `NO_ASSETS`, which refuses any `$ref` (B-013: a stored project file is self-contained, `$ref` assets are embedded once, at ingestion): `CompiledConfig.file`, `serialize` and `hydrate` never hold a `$ref` (`COMPILED_FORMAT` 2). The resolver is not style-specific: a 3D model asset (H1) or an external GIS source (H5) resolves through the same port. An unresolvable `$ref` is `asset_unresolved` at `views.<view>.layers.<layer>.style`; a style that fits no shape is `style_invalid` at the same path. Core checks only the structure of a `maplibre-2d` style (`{ layers: [{ id }] }`, no `$ref`); the Style Spec check stays in the builder (`validateViewStyle`, `@ueberblick/ui/view-style`), because core may not import ui. `tools.search.sources` entries are `<type>.<property>` naming a property of a type in the file whose type is in the registry `SEARCHABLE_PROPERTY_TYPES` (`text`, `select`, `number`, `integer`; not `localized_text`, whose value the device text index cannot hold): anything else is `tool_source_invalid` at `tools.search.sources["<n>"]`. **Tools (WP-613, tool API 2).** `roles.<r>.app.tools.<key>` is `{ availability?, settings? }`. `availability` is from the registry `TOOL_AVAILABILITY`: `offered` (off at first, the person may switch it on) or `active` (on at first, the person may switch it off; the default). There is no "required" level. A tool the role does not list does not exist for it. `settings` are the role's settings of the tool; the project-wide ones stay in `tools.<key>`. A tool declares a settings schema (what the admin sets) and a preferences schema (what the person may change, with defaults) as option schemas (`ToolOptions`: `boolean`, `string`, `number`, `integer`, `select`, `string_list`, from the registry `TOOL_OPTION_TYPES`, with `default`, bounds or `options`). `compile` checks `tools.<key>` and every role `settings` of the four shipped tools against `BUILTIN_TOOL_SCHEMAS` (registry `tool-options.ts`, the same objects the tool packages pass to `defineTool`): an unknown option or a value that does not fit is `tool_setting_invalid` at `tools.<key>["<option>"]` or `roles.<r>.app.tools.<key>.settings["<option>"]`. A tool without a known schema stays unchecked. Effective values = schema defaults, then project settings, then role settings, then (for preference keys only) the person's preferences (`effectiveToolValues`). The tool is on for a person = `toolIsOn(availability, prefs.tools[key])`.

**maplibre-2d view styles:** a layer added by a new id on `ub-clusters` draws single features only (the renderer adds `['!', ['has', 'clusterId']]` to its filter), and the cluster circle and count layers are drawn last, so counts stay readable. A layer with a default id replaces that default verbatim; that is the seam for styling clusters. A layer added over `ub-clusters` must use an expression-syntax filter (e.g. `["==", ["get", "art"], "x"]`), since the renderer combines it with its own filter.

**View sources and camera.** A layer `source` is either a feature type (`{ type, filter? }`) or an external asset (`{ asset, format? }`, H1). An asset source carries no `filter`; `asset` is a blob prefix or a URL and `format` comes from the `ASSET_FORMATS` registry (`3dtiles`). The view-level `source` stays a feature type because lists, exports and the sync scope need one. `camera` sets the initial view: `center` is `[lon, lat]` or `[lon, lat, z]`, plus optional `zoom`, `pitch` and `bearing`. The renderer host mode (`interleaved` or `own-canvas`) belongs to the UI renderer registry, not to the file.

**Map backgrounds (WP-614).** The optional top-level `map` section declares where the map opens and which background layers exist (Q22, v3 map settings):
```yaml
map:
  start: { center: [10.45, 51.16], zoom: 10 }      # [lon, lat]
  layers:
    osm:   { label: { de: Straßenkarte }, kind: base, source: { type: preset, preset: osm }, on_at_start: true }
    flur:  { label: { de: Flurkarte }, kind: overlay, opacity: 0.7, roles: [verwaltung],
             source: { type: wms, url: "https://…/wms", layers: flurstuecke } }
  order: [osm, flur]                               # optional draw order, lowest first; default is authored order
```
`kind` is `base` (one active) or `overlay` (any number), from `MAP_LAYER_KINDS`. `source.type` comes from `MAP_SOURCE_TYPES`: `xyz` (`url` with `{z}/{x}/{y}`, optional `tile_size`), `wms` (`url`, `layers`, optional `version`, `format`, `transparent`), `geojson` (`url`), `pmtiles` (`url`, `tile_type` raster or vector, `source_layer` for vector) and `preset` (`preset` from `MAP_PRESETS`: `osm`; no commercial imagery). A URL is http(s) or a path starting with `/`. A new source type is a registry entry plus a shape in `schema/map.ts` (H1 3D tiles and H6 external GIS use the same list). Optional per layer: `attribution` (presets bring their own), `opacity` (0 to 1), `minzoom`, `maxzoom`, `roles` (absent means every role), `on_at_start`, and `advanced: { paint, layout }`, MapLibre Style Spec properties applied to the layers whose type the key names (`line-color` to line layers). Core checks the shape of `advanced`; the Style Spec check is `basemapErrors` in `@ueberblick/ui` (`map/maplibre/basemaps.ts`), like view styles, because core may not import the spec. The default base is the first base with `on_at_start`, else the first base (`defaultSelection`, in `@ueberblick/core/registry` so participant code can use it without Zod). The participant's compiled config keeps only the layers for their roles (`layersForRoles(map, roles)`). The renderer (`applyBasemaps`) draws one source `bm-<key>` per layer below every `ub-*` feature layer, adding sources before layers; switching the base replaces only the base layer. `uploaded` rasters are later (offline packs: next paragraph); the renderer registers the `pmtiles://` protocol itself, once, before the first pmtiles layer draws, and loads the `pmtiles` library only then (`map/maplibre/renderer-basemaps.ts`). The participant app keeps the choice (`sheets/layer/layer-controller.ts`: the layers of the person's roles, the start selection, and the choice, which is the personal preference `ui.map_layers` of WP-612 and so follows the person to another device) and hands it to `MapHandle.setBasemaps`. A project with no base layer is drawn on the OSM preset (v3's `default-osm`, `MapCanvas.svelte:203,357`). The reserved key is the registry value `DEFAULT_BASE_LAYER` (`MAP_RESERVED_LAYERS`, `@ueberblick/core/registry`); client and tile proxy both read it there. The tile proxy answers `tiles/default-osm/…` through the `osm` preset (same upstream, host policy and cache as a declared `preset: osm` layer) only for a caller who sees no base layer (`hasBaseLayer` on `layersForRoles`); with a visible base layer it is 404. The default layer carries no attribution of its own: the credit comes from the preset and shows while that source is drawn, as in v3 (the attribution sits on the raster source, `MapCanvas.svelte:324`). It is not listed in the Layer sheet and not part of the config. A project cannot declare a layer under a reserved key: reserved keys contain a hyphen and layer keys match `^[a-z][a-z0-9_]*$`, so the file is refused (spec in `schema/map.spec.ts` keeps every `MAP_RESERVED_LAYERS` key outside the key pattern). There is no per-project opt-out of the default base (owner 2026-10-03: the tile proxy keeps users private from OSM). `compile()` runs the Style Spec check of `advanced` through the optional `CompileOptions.mapStyles` port (pass `basemapErrors` bound to the Style Spec): a bad style is a `style_invalid` problem at `map.layers.<key>.advanced` that names the layer.

**Map zoom bounds (WP-375, A-036).** Next to `map.start`, `map.min_zoom` and `map.max_zoom` (optional integers 0 to 24) bound how far a participant may zoom. `min_zoom <= start.zoom <= max_zoom` is part of the file schema, so a file that breaks it is a `schema_invalid` problem at `map.min_zoom` or `map.start.zoom`; the Standardansicht section of Projekteinstellungen writes all three and refuses the same values in the form. The participant map applying the bounds is the renderer's job (`packages/ui/src/map`).

**Branding (WP-375, A-036).** The optional top-level `branding` is how participants see the project:
```yaml
branding:
  name: { de: Stadtwerke Meldungen }   # LocalizedString; absent = the project name
  icon: 3f9a…                          # sha-256 of an image blob in the project's blob store
```
The participant bootstrap's `project.displayName` and `project.icon` read the deployed config's `branding.name` and `branding.icon` (`projectInfoOf`), falling back to the project name and no icon. The icon is uploaded with `POST /api/admin/p/<project>/assets` (admin only; body is the image, `Content-Type` one of `BRANDING_ICON_TYPES`: png, jpeg, webp, svg; at most `BRANDING_ICON_MAX_BYTES`, 2 MB; the bytes must match the type; answers `201 { sha256, bytes, mime }`, `400 invalid_body` with `issues[0].path` `content-type` or `body`, `413 payload_too_large`, 401, 403). The blob is then an ordinary content-addressed blob, and the blob read check lets every participant of the project download the sha the deployed config names as `branding.icon`, besides the existing rules. An overlay sets `branding.name` and `branding.icon` as `add` entries (`branding` is one of the sections an overlay may start).

**The tile proxy (WP-369, A-033).** Layers of type `xyz`, `wms`, `pmtiles` and `preset` (registry flag `proxied`) are not fetched by the browser from the provider: the server fetches, caches and serves them at `/api/p/<project>/tiles/<layer>/<z>/<x>/<y>` (WMS: `/api/p/<project>/wms/<layer>?bbox&width&height&crs`), `<layer>` being the key in `map.layers`. The config needs nothing for it: the URL in `source` stays the upstream address the server uses, a changed `source` gets a new cache, and the layer's `roles` decide who may fetch it (a hidden layer is 404). Only `geojson` layers are loaded by the browser from their own URL.

**Offline packs (WP-349, A-032).** `map.packs.<key>` declares a region of the map layers that devices download for use without network:
```yaml
map:
  packs:
    innenstadt:
      label: { de: Innenstadt }
      bounds: [7.08, 50.70, 7.14, 50.75]   # [west, south, east, north], WGS84
      min_zoom: 12
      max_zoom: 17
      layers: [luft]                       # keys of map.layers; one PMTiles file per layer
      roles: [kontrolle]                   # optional audience; absent = everyone who sees the layers
```
Packs are config like everything else: they go through the draft and Veröffentlichen, and a template can ship them. Only layers whose source type is `packable` in `MAP_SOURCE_TYPES` may be packed: `pmtiles`, `xyz` and `preset` (the tile proxy caches the last two, A-033, owner answer P5), so a pack that lists a `wms` or `geojson` layer is `pack_layer_not_packable`. A pack of OpenStreetMap tiles (`preset: osm` or an `xyz` URL on `tile.openstreetmap.org`) may hold at most `TILE_HOST_POLICIES.osm.pack_max_tiles` (10,000) tiles per layer because of the OSM tile usage policy; the build fails the layer with that reason, the checker does not know it yet. The limits live in the registry `PACK_LIMITS` (`max_tiles` 250000 and `max_bytes` 1 GB per pack, zoom 0 to 22); `PACK_TILE_BYTES` holds the average tile weight per `PACK_TILE_TYPES` key (raster, vector) the byte estimate uses. The estimate is `estimatePack(bounds, min_zoom, max_zoom, layers)` in `core/geo` (`tilesAtZoom`, `tileCount`: standard web-mercator XYZ math, O(zoom levels), tiles that only touch the box edge are not counted). Each layer is estimated to its own maximum, `min(pack.max_zoom, source max)`, where the source max is the preset's own or the layer's `maxzoom` when declared (`sourceMaxZoom`); the admin dialog ("estimated tile count") and the build job (WP-350) use the same function. For a `pmtiles` layer the real maximum is known only from the archive's header, so the config-side estimate is an upper bound: the build job caps the layer from the header, and the manifest's per-layer `max_zoom` is authoritative (A-032). Problems, with messages in English and German:

| Code | Raised when. Path |
|---|---|
| `pack_unknown_layer` | a `layers` entry is not a key of `map.layers`. `map.packs.<p>.layers["<n>"]` |
| `pack_layer_not_packable` | the layer's source type is not packable. same path |
| `pack_zoom_range` | `min_zoom` above `max_zoom`, or a zoom outside 0 to 22. `map.packs.<p>.min_zoom` |
| `pack_bounds` | west not below east, south not below north, or outside WGS84. `map.packs.<p>.bounds` |
| `pack_too_large` | the estimate is above `PACK_LIMITS` (checked once layers, zoom and bounds are valid). `map.packs.<p>.max_zoom` |
| `pack_unknown_role` | a `roles` entry is not a role of the file. `map.packs.<p>.roles["<n>"]` |
| `select_unknown_role` | a role in a participant property's `select.all` or `select.self` is not a role of the file. `types.<t>.properties.<p>.select.<all\|self>["<n>"]` |

### Form fields of a bound Objekt (A-047)
A form key is a property of the task subject, or `<bind>.<property>`: `<bind>` is a key of the task's `bind` and `<property>` a property of the Objektart it yields. Only `form` keys have this shape (`FormKeySchema`); every other key stays a plain key.
- **Compile.** The bind must be declared and yield one feature (a list is an `expression_type` problem), and the property must exist on that Objektart (`dangling_reference`: `bound_feature`, `property_of`). A computed property is `computed_written`, the process property `process_property_written`.
- **Value.** The field starts at the bound Objekt's current value (a preset or `calculate` wins). `constraint`, `required`, `relevant`, `choice_filter` and `readonly` see it as the field's own value; other expressions read it as `form['<bind>.<property>']`. `self` stays the subject.
- **Write.** The run writes an observation on the bound Objekt in the same run, only for a changed value (an emptied one writes `null`). The actor needs write permission on that property, as for a `then.set` on a bound feature; a refusal is `not_permitted` with the path `form.<bind>.<property>`. `readonly: true` shows the value and never writes it. Editable is the default.
- **Missing Objekt.** A bind that has a form field is optional: if it yields nothing, or the Objekt is not on the device, the task stays available and the field is not relevant (not shown, not written). A bind without a form field keeps `bind_unresolved`.

## Shapes worth knowing (A-004, A-005)
- **Info pages (WP-660).** `info_pages: { <key>: { title, content, sort_order? } }` at the top level: v3's Infoseiten. `title` and `content` are localized strings; `content` is HTML, sanitised on display on the device with the same sanitiser as the legal pages. `sort_order` orders them (lower first). No per-role visibility (as in v3). They reach the device with the bootstrap.
- **Primary geometry is a property.** `types.<t>.geometry` names a property of type `geometry`; its `geometry_type` (registry `GEOMETRY_TYPES`, default `any`) is the kind. A type may have more geometry properties; the primary one is the feature's map geometry (stored `geometry`, anchor, area; `FoldType.primaryGeometry`), while the spatial index covers all of them (the union of their 2D bboxes, docs/04, B-009). No `geometry` key: features of that type have no map geometry.
- **Permissions.** `see`, `create`, `delete`, `write` take an audience (`$all` or role keys); `see` and `write` also take a property-key-to-audience map. In the `see` map, properties not listed stay visible to every role that sees the feature; in the `write` map, properties not listed are denied. `visible_when: <expr>` is the row-level filter (compiled to SQL); `see` stays an audience.
- **Display name.** A type has no name property (R4). A feature's name in lists, the sheet title and relation links is its first `required` `text` or `localized_text` property (declaration order) that has a value, else the type label plus `#` and the last 4 id characters (`Baum #4f2a`); an optional text is never used. One function, `displayName` in `@ueberblick/core/locale`; see [B-014](decisions/later/B-014-feature-display-name.md).
- **Relations.** `cardinality: one | many` (registry `RELATION_CARDINALITIES`). Default `one` for a picked reference, `many` for `derive` and `inverse_of`. `inverse_of: <type>.<key>` declares a read-only reverse set of a reference on the type named in `to`; no edge is stored twice. A relation is derived or an inverse, never both. `inherit_position: true` (only with `inverse_of`; B-019) says the children have no position of their own: the map draws a child at the anchor of its parent (the far end of its reference edge, up the chain for grandchildren), so a moved parent moves its children with nothing written or copied, and a relation opened in the feature sheet fans the children out above the parent. Creating such a child needs no pin ("{name} anlegen" from the parent, or tapping the parent from +). Compile refuses (`inherit_with_own_geometry`) a child type that also declares a primary `geometry`, and (`dangling_reference`) a child property that is not a reference to the parent type. The anchor is one function of the map layer (`packages/ui/src/map/family.ts`); an export (H6) or a 3D renderer (H1) derives the same position from it. `label` (LocalizedString, optional) names the relation in the feature sheet (the schema's description): the sheet (WP-647) names a group by the `label` of the relation that declares it through `inverse_of`, else the label of the type on the other side, else the key. **Conjunction rule:** a `derive` may combine attribute conditions with the spatial predicate (`self != other && self.datum == other.datum && intersects(self.geometrie, other.geometrie)`) only through top-level `&&`; the predicate under `||`, `!` or `?:` is a compile problem, as is any use of `now`/`today()`. A derive condition reads only own properties of `self` and `other`; reading through a relation is `derive_traverses_relation`.
- **Tasks.** `creates: <type key>` names the feature type a task creates. It is required for tasks on `$map` and optional on `$none` (A-004 items 5 and 12, amended by lead-a).
- **Step kinds (`THEN_STEP_KINDS`).** A `then` step has one kind: `set` (above), `redact` or `lifecycle`. `lifecycle: <state>` (`active`, `completed`, `archived` or `deleted`, registry `LIFECYCLE_STATES`) sets the system lifecycle of the task's subject by writing `$lifecycle`; `when` and `otherwise` apply as for `set`, and `$lifecycle` is not a `set` key. Setting `deleted` needs `permissions.delete` for a bound actor (`not_permitted` otherwise). `completed` to `active` is the reopen step; a run on an archived or deleted feature is refused `case_closed`. An OGC `DELETE` runs the unique task on the type that has at least one step without `of` and whose every step without `of` is `lifecycle: deleted`; steps with `of` (which act on other features) may sit beside them (else 422). `redact: { subject, of? }` erases personal values (B-005). `subject` is one of the personal subject kinds (`actor`, `feature`, `property:<key>`, the same as `personal.subject`); `of` is an expression: the participant id for `actor` and `property:<key>` (required, for example `form.subject`), a feature for `feature` (default: the task's feature). The step blanks every personal property whose `personal.subject` equals `subject`: for `actor` those the participant's runs wrote, for `property:<key>` those on features whose `<key>` holds the participant, for `feature` those of the feature. `when` and `otherwise` apply as for `set`. A step with both `set` keys and `redact` is a schema error; `property:<key>` naming no personal property is a `dangling_reference` at `...redact.subject`. The task writing the erasure needs write permission on the blanked properties like any `set` (admin actors are not bound by allowlists).
- **Task steps (WP-616, `TASK_STEP_KINDS`).** A task may chain several steps before it submits once: `steps: [{ kind: form }, { kind: quick_edit, properties: [art] }, { kind: location, property: geometrie }]`, in the admin's order, as v3's multi-step tasks. All steps are **one run**: the input carries the values of every step, and a refusal in any step refuses the run. `form` is where the task's `form` runs (its fields and pages stay in the keyed `form` map, not in the array, because overlays, locks and breaking-change checks address entities by key path and never descend into an array); at most one `form` step, and `steps` is omitted for a task that only has its form. `quick_edit` lists properties of the task subject the participant edits inline: a value equal to the current one writes nothing, an emptied one (`null`, `''`, `[]`, `{}`) writes an explicit `null` and so clears the property (v3 could not), and a required property cannot be emptied (`required_missing`). `location` names a geometry property of the subject (move the pin or redraw the shape). A property is written by one step only (schema error otherwise); `quick_edit` and `location` properties must exist on the subject (`dangling_reference`), a `location` property must be a geometry (`task_step_property_invalid`) and none may be the process property (`process_property_written`). Their values are submitted as input keys like form fields and are checked by `core.form` (`FieldState.step` tells the owner step), without `relevant`, `required` or `calculate` of their own. The participant UI of the steps is built (WP-636): "Schritt n von m" in the task sheet, the quick edit inline in Daten for a task whose only step is a quick edit, the location step on the map (the pin for a point, the draw tool for a line or an area); `button.icon` is a `TASK_BUTTON_ICONS` key. `button: { label?, color?, icon? }` is how the task shows in the action row (`label` is the short label, `color` a `TASK_BUTTON_COLORS` key or `#rrggbb`, `icon` an icon key of the design system), and `confirm` is the text asked before the run is submitted: for a task with several steps when the last step is sent (Absenden), for any other task on the tap that starts it (B-023; v3 never asked); both are data for the UI and change nothing in planning.
- **`of` on `set` and `lifecycle` (WP-374, A-035).** `of: <expression>` names the features the step acts on instead of the task subject: a feature or a list of features, such as `self.kinder` (a to-many relation) or `self`. Anything else is an `expression_type` problem at `tasks.<t>.then["i"].of`. The step applies to each distinct target in list order. With `of`, `set` keys are properties of the target type (`dangling_reference` otherwise) and a bound-feature key (`area.x`) is refused; the value is evaluated once and stored per target. Each target is checked as if the actor ran the step on it (`permissions.delete` for `lifecycle: deleted`, property write permission for `set`); one refused target refuses the whole run. A step may name at most `THEN_STEP_TARGETS_MAX` (100, registry `limits.ts`) features, else the run is refused `too_many_targets`. Relation options of v3 are written with it: mitlöschen is `{ lifecycle: deleted, of: self.kinder }` before the parent's own `{ lifecycle: deleted }`, trennen is `{ set: { eltern: null }, of: self.kinder }`, blockieren is `when: self.kinder.size() == 0` on the delete task. Rules still fire once per run subject.
- **Values.** In `then.set`, a string is always an expression and other scalars are literals. A literal option key is written `"'massnahme'"`. `compile()` hints when a bare identifier equals an option key of the target.
- **Who (`tasks.<t>.who`, C-004 step 3).** A list of role keys; the reserved words `admin` (any admin account) and `import` (import runs) are also allowed (`TASK_WHO_RESERVED`). A person may run the task only when one of their roles is in `who` (an admin: `admin` or one of their roles; an import: `import` or a listed role; a task without `who` refuses it). **No `who` means no person may run it**: only the system, through its `auto` entries. There is no `actor.kind == 'system'` condition any more; the system skips `who` only for the run of one of the task's own `auto` entries (`Run.auto`, set by `fireOne` and the timers; any other system run of a task is checked like any actor, so a task with `who` and no matching entry refuses it). The reserved `$` tasks (seed, move, lifecycle, import-zip) are not planned through a task and stay as they are. `who` is one check in `plan` (`not_permitted`, path `who`) and what `availableFor` reads. `tasks.<t>.when` is one condition for every run, person or system (`whoAdmits`, `core/perms/who.ts`). An `auto` entry with an edge fires when (task `when` AND entry `when`) turns false → true. **Write rights** (`permissions.create/write/delete`) are kept: `deriveRights(config)` (`core/perms/derived.ts`) shows what the tasks alone would grant, and for every golden template that is a subset of the stated rights (the stated ones also cover direct admin edits and reading-only roles); dropping the keys is a later decision.
- **Automatic actions** (`tasks.<t>.auto.<name>`, C-004; registry `AUTO_TIMING_KINDS`). An automatic action is an entry of the task the system runs; there is no top-level `rules` section. The entry is `{ label?, when?, <at most one timing> }` (`AutoEntrySchema`). Its identity is the pair (task, name), written `<task>.<name>` (`AutoId`); a problem path is `tasks.<t>.auto.<name>.<field>`, so the builder can jump to it. `compile()` builds one table of them (`CompiledConfig.autos`, with the trigger index `autosByTrigger`, `schema/compile/autos.ts`); plan, timers, deploy, the builder and the migrator read it, never the raw maps. The timing is one of: `after: <task>` (the system runs the task right after `<task>` ran on the same Objekt; the old `task.<key>` trigger), `change: <type>.<property>` (a run changed the property; `<type>.*` any), `elapsed: { from, after?, offset? }` (server only), `schedule: "<five-field cron>"` with an optional `idle: <duration>` (server only), or **none**: the entry is an **edge** and its `when` is the condition that fires it once when it turns false → true on a feature a run touched (A-045: docs/06 "Edge trigger"; `compile()` checks it is `bool` with `self` = the type the task is offered on, and warns `when_trigger_uses_time` when it reads `now` or `today()`; use `elapsed` for time). An entry without a timing and without `when` is refused by the file schema; more than one timing is the compile problem `auto_timing_conflict` (with a path and a fix). With a timing, `when` is the condition judged when it fires. With `idle` (WP-469, owner A10 b, v3 "Nur wenn inaktiv ≥ Tage") the schedule is a **sweep**: at each cron match it visits the served Objekte of the Objektart the task is offered on, in id order and in batches (the server's `limit` per tick, with a cursor kept across ticks), and fires the entry (its `when` over `self`, then the system run) only for those whose last change (`self.$changed_at`) is at least `idle` ago (core `idleEnough`, `rules/timing/idle.ts`); `idle: days(0)` visits every Objekt. `compile()` checks `idle` as a `duration` in the scope of the task (`self` is its Objektart; a task not offered on one is `expression_type`) and stores it as `tasks.<t>.auto.<name>.idle`. A `schedule` without `idle` has no subject: on a task offered on an Objektart it is `auto_schedule_without_idle`; on `$none` it fires once. An automatic run has no form: its values come from the task's `then.set`, and `compile()` refuses (`auto_value_missing`) a task with an `auto` entry whose required form field gets no `set` value. `compile()` checks `from` (a timestamp) and `after`/`offset` (durations) as rule-language expressions in the scope of the task (`self` is the feature type the task is offered on) and stores them by key path `tasks.<t>.auto.<name>.elapsed.from`, `.after`, `.offset` in `CompiledConfig.expressions`; the due time is `from + after + offset`. `compile()` also runs the cron parser on every `schedule`: a value the parser refuses (range, step, list) is `expression_parse` at `tasks.<t>.auto.<name>.schedule` with the position of the fault (a wrong field count is already refused by the file schema at the same path). Further checks: `after` names a task that exists (`dangling_reference`) and is offered on the same Objektart (`auto_after_other_type`); an edge entry needs a task offered on an Objektart (`auto_edge_without_subject` on `$map` and `$none`). Problems: `expression_parse`, `expression_type`, the `auto_*` codes. The server timer reads the table and calls `PlanApi.fireRuleFor` (docs/03). **Overlay, hide and lock:** an overlay may `add` `tasks.<t>.auto.<name>` to a task of the template (the `auto` map is created on the first add) and hide or override a single entry. A `lock` on `tasks.<t>` covers everything below it, but a project may always **add its own** entry: an `add` of `tasks.<t>.auto.<new name>` that the template does not define is accepted under a lock on `tasks.<t>` or any ancestor (owner rule: a lock stops changing or removing what the template defines, not adding). Changing, hiding or re-adding the template's own entries stays `lock_violation`, and a lock on the new entry's own path still applies. One function decides it for merge and the builder (`lockedBy` in `template/lock.ts`). **Deploy:** an edit of an entry is a change of its task: the deploy offer counts it for the task's Objektarten (`deploy/pins.ts`), and timers are rebuilt on deploy (the timers table keys a timer by `<task>.<name>`, so rows written before this change are dropped, and development databases need a re-seed).
- **Computed properties (WP-312, "Berechnet", owner Q29).** `computed: <expression>` on a property keeps its value up to date from other values (v3's "Vom Server berechnet"): the expression reads `self.<property>` of the same feature (own properties, other computed properties, `self.$lifecycle`, `self.$created_by`, `self.$created_at`) and `inputs`, and must produce the property's type. **Nobody writes the property** (a task `form` may list it: it is shown read-only, never submitted, and a run input carrying its key is refused with `invalid_input`; B-027): after a run's observations are known, plan evaluates every computed property of each touched feature whose inputs include a changed key (all of them on create), in dependency order, and appends an observation to the **same run** when the value differs, so the value is in the history and the device predicts it exactly as the server computes it (R3). A value that cannot be computed (an input is empty) clears the property instead of leaving a stale one. The participant's permission to write the property is not asked: they changed an input. Compile problems: `computed_default` (a `default` next to it), `computed_written` (a `quick_edit` property, `location` step or unprefixed `then.set` key names it), `computed_cycle` (computed properties read each other or themselves), `computed_input_unsupported` (a relation, a reference's feature, another feature, `actor`, `now`, `today()`, `self.$changed_at`: values plan cannot watch), `expression_type` (the expression does not produce the property type) and `dangling_reference` (a `self` read of a property that does not exist). A deploy that adds `computed` or changes an expression records one `deploy_moves` row per type; the move executor runs the reserved system task `$recompute` for every live feature of it (`packages/core/src/plan/computed.ts`, only the `system` actor; idempotent). Relations and other features as inputs are a later extension (no schema change).
- **Participant choices (WP-725, B-022).** `select: { all?: [role], self?: [role] }` on a `participant` property says who may choose whom, as v3's `any_select_roles` / `self_select_roles`. A role in `all` is offered every participant of the project by name; a role in `self` only itself; a role in neither nobody (v3's default deny). With no `select` every role may choose only itself. `select` is allowed on type `participant` only (a schema error on any other type). The server ships the choosable participants (id and name, never an email, disabled ones left out) only to callers whose role is in some `select.all`; the list is sent only when it changed for that device (`docs/07`), and the device offers it offline (`choicesFor`, `apps/web/src/lib/participant/form/choices.ts`). The golden maengelmelder (`zustaendig` of `meldung` and `einsatz`: sachbearbeiter) and baumkataster 2.0.0 (`zustaendig`: verwaltung) set it.
- **Display setting (WP-659, "Anzeige in Daten").** `display: { tab?, tab_order?, row?, column?, hidden?, condition?, history? }` on a property says how the participant's Daten view shows it (v3 `display_config`). `tab` (a localized string) names the Daten sub-tab; the distinct names are the type's sub-tabs, the properties without one form the default tab ("Daten"), which sorts first; the others sort by the smallest `tab_order` among their properties (default 0), then by name. `row` (a number) places a property inside its tab, ascending; properties with the same `row` share one line, and properties without a `row` follow in type order, one per line (v3's row index). `column` is a registry key (`PROPERTY_DISPLAY_COLUMNS`): `full` (default), `left` or `right`; two half-width cells of one row sit side by side, also on a phone, and inside a row `left` sorts before `right` before `full` (v3 `getColumnClass`, `state.svelte.ts` 686-692). Display only: the Daten view reads it, no form does (each form has its own `column` and `row` on its form entry, A-049). `hidden: true` never shows it. `condition` is a rule-language expression over `self` and `actor` (R5, type-checked to a bool by `compile()`, kept at `types.<t>.properties.<p>.display.condition`): the property shows only while it is true; an error or an empty value counts as false. `history` is a registry key (`PROPERTY_HISTORY_HINTS`, `registry/property-display.ts`): `changes` (default, "n Änderungen") or `measurements` ("n Messungen"). A sub-tab with no value left after hiding is not offered (v3's "hide tab, collapse rows"). Who may read a property stays `permissions.see`; the display setting only arranges what the role can already read. An overlay sets it like any other key: `add: { "types.baum.properties.x.display": { tab: Kontrolle } }`, then `override` or `add` on `...display.<field>`. The layout is built on the device (`apps/web/src/lib/participant/feature/data/layout.ts`).
- **Marker and classifying property (WP-674, B-018, v3's per-value icons).** `types.<t>.marker: { color?, icon? }` is the type's own look on the map (v3 `marker_color` and `icon_config`); `types.<t>.classify: { property, values }` names one `select` property (the stage property is one; a multiselect is not) and, per option key, `{ color?, icon? }` (v3 `filterable` tag and `filter_value_icons`). `color` is `#rrggbb`. An `icon` is `{ key }` (registry `MARKER_ICONS`: camera, check, circle-alert, clipboard-check, flag, house, info, leaf, map-pin, pencil, trash-2, tree-deciduous, triangle-alert, wrench), `{ svg }` (an inline SVG) or `{ $ref: icons/name.svg }` (a bundle file, embedded at ingestion like a layer style, so the compiled config holds `{ svg }` only), each with an optional `size` in px (8 to 128, default 32). A registry icon is stroked in the colour; an inline SVG keeps its own colours. The resolution chain is v3's: the value's colour and icon, then the type's `marker`, then the default dot (`resolveMarker`, `markerLooks` in `packages/core/src/marker/index.ts`; `markerLooks` gives a renderer the same). One property groups the type's features everywhere: `classifyingProperty(type)` is `classify.property`, else the stage property of the process. It drives the marker icon and colour per value (the maplibre-2d renderer draws `ub-single` as a symbol layer with a `match` on `icon-image` and shapes with a `match` on the fill and line colour; a view style that replaces a default layer keeps its own), the Einfach value switches, the cluster-detail rows and the per-value counts the cluster worker keeps for every cluster (`ClusterItem.counts`). The cluster circle itself stays grey (owner question M3). `compile()` checks that `classify.property` is a select property of the type (`classify_property_invalid`), that every `values` key is one of its options (`classify_value_unknown`), and every inline SVG (`marker_icon_invalid`: at most 50 KB, an allowlist of elements, no event attributes, no external `href`; one function, `checkMarkerSvg`, which the builder uses too); an unresolved `$ref` is `asset_unresolved`. An overlay addresses it by key path, e.g. `override: { types.baum.classify.values.massnahme.color: "#c05621" }`. A role that may not read `classify.property` (`permissions.see`) sees the type unclassified (WP-1075): its own `marker` or the default dot, and no per-value switches, rows or counts; `classifiedFor(config, actor)` (`packages/core/src/perms/classify.ts`, the sync's `readable` call) decides, and the participant device hands every consumer that config as `device.classified`. Only an explicit `classify` is dropped, never the stage property.
- **What is on when a participant first opens the map (WP-397, A-040, v3 'Sichtbare Workflows').** `types.<t>.on_at_start: false` hides the type at first (absent or true: on, so every type is on, v3's 'Alle'); `types.<t>.values_at_start: [value, …]` lists the values of the classifying property (`classifyingProperty`, the one the participant filter groups by) that are on; absent means all. `compile()` refuses an entry that is not an option (`start_value_unknown`) and the key on a type with no such property (`start_values_without_property`). `startFilter(file)` (`packages/core/src/filter/start.ts`) returns the participant filter's start state in the filter's own shape (`hiddenTypes`, `hiddenValues`): a type off is hidden with all its values, as the filter's master switch; all its values off hides the type. It is the one reader, so a per-role start set (H3) is added there. The admin edits it in Projekteinstellungen, Erststart.
- **Personal properties.** `personal: { subject: <kind> }` on any property marks it as personal data and names whose it is (registry `PERSONAL_SUBJECT_KINDS`, `registry/privacy.ts`): `actor` (the participant who submitted the run), `property:<key>` (the participant named in a participant property of the same type), `feature` (the feature itself is about a person). No new property type (R4). Erasure and export (B-005) read the flag. `compile()` reports `dangling_reference` when `property:<key>` names no participant property of the type, and warns `personal_indexed` (personal plus `index: true`), `personal_without_redact` (a project has personal properties but no task with a `redact` step, so it cannot honour an erasure request; one warning per project, listing the `<type>.<property>` keys; only a warning, because a project may be mid-authoring), and `personal_public` (a view carries a personal property whose effective `see` audience is `$all`; there is no separate "public" audience yet, so `$all` is the widest one). The effective audience is the whole-type `see` audience, or in a `see` map the entry for the property, or `$all` when the map omits the property (it stays visible to every role that sees the feature). An absent `permissions.see` denies everyone (F6), so it never warns.
- **Property type `localized_text`** stores a `LocalizedString` per observation; there is no `localized` flag.
- **Date types (owner Q8).** `date` is `YYYY-MM-DD`, `datetime` an ISO 8601 instant with offset, and `time` (WP-637) a wall-clock time of day, `HH:MM` (24 h, zero-padded, no seconds, no date, no zone), as v3's time mode stored it. In expressions a `time` is a `string`: zero-padded `HH:MM` orders as text, so `form.von < form.bis` compares times and needs no function (SQL pushdown compares the same text).
- **Property type `file`** (WP-603) holds a list of `{ sha256, name, mime }` (`FileRef[]`; a single object is refused). `max_files` (integer >= 1, default 10) caps the list; `accept` is a list of MIME types (`image/*`, `application/pdf`) or extensions (`.pdf`), absent means any type. The form type check refuses a malformed entry, more than `max_files` entries or an entry matching no `accept` pattern (registry `FILE_FAULTS`: `malformed_file`, `too_many_files`, `file_not_accepted`; the form issue stays `type`, refusal `invalid_input`).

## Upgrade semantics (key-wise three-way merge)
| Template old → new | Overlay | Result |
|---|---|---|
| changed | untouched | new wins |
| untouched | changed | overlay wins |
| changed | changed | **conflict**: the builder asks |
| removed/renamed | referenced | resolved by a shipped migration, otherwise a compile error |

- **Tools are not data (A-041).** Removing or changing a `tools.<key>` is never a breaking change: a tool holds no Objekt values, and a tool's own data (for example chat messages) lives outside the config. A tool that later stores data in Objekt properties declares that, and the check then applies to it.
- **Minor versions** may not remove keys, change types or remove options. `template.breakingChanges()` enforces this at publish time, through `checkPublish` (core) in `publishTemplateVersion` (server).
- **Data migrations** are system runs. They add observations and never rewrite history.
- There are three version axes: platform `schema`, template `version`, and project `config_versions`.

## compile() (WP-013)
Code: `packages/core/src/schema/compile`. `compile(file, { assets })` takes the **effective** file (`template.merge` output) and the bundle resolver for `{ $ref }` layer styles (above; `NO_ASSETS` for a file without a bundle) and returns `{ ok: true, config, warnings }` or `{ ok: false, problems }`. Every `Problem` has a `path` (a key path: dot-separated, non-bare segments in brackets, A-005), a `code` (registry `PROBLEM_CODES`), a `message`, a `hint` phrased as an instruction, `params` (the flat values the message is made of, WP-416: the builder words the problem in German or English from them, docs/08) and, inside expressions, a `span`. `message` and `hint` stay English. All problems are collected, not just the first.

Conventions the checker relies on:
- **Process (WP-304, A-028 item 1).** A type declares at most one process, `types.<t>.process: { property, start, end: [..] }`; `property` is a `select` property of the type and `start` / `end` are its options. A new feature of the type gets an observation `property = start` in its creating run; a `then.set` of the creating task that sets the property wins (it comes later). `processesOf(type)` in `core/process` returns a list (0 or 1 entries) so a second process stays additive. Which type or property is "the stage" is never guessed from a `select` (R4): the template says it.
- **Set values (A-004 item 9).** In `then.set`, a string is **always an expression**; numbers, booleans and null are literals (checked against the property type). A literal option key is written `"'massnahme'"`. A bare identifier equal to an option key of the target (`stage: massnahme`) is an `expression_type` problem whose hint is the quoted form. A string literal that is not an option of the target is a `dangling_reference`. A quoted literal counts for `dead_option` as setting that option; any other expression counts as possibly setting any option.
- **Choice filter and option hints (WP-392, A-039, ODK `choice_filter`).** A form entry over a `select` or `multiselect` property may carry `choice_filter: <expression>` (`tasks.<t>.form.<p>.choice_filter`): a bool evaluated once per option of the property, with `option` (the option key, a string) next to `form` and `self`. Options for which it is true are offered; the others are not. It sits on the form entry, not on the property, because ODK keeps it per form, it reads `form.*` answers that exist only in a task form, and two tasks may filter the same property differently. `compile()` checks it as a bool (`expression_type` otherwise) and refuses it on any other property type (`choice_filter_invalid`). `option_hints: { <option key>: <LocalizedString> }` on the property is the explanation text of an option (v3 "Antwort, Erklärungstext"); a key that is not an option is a schema error, and only `select` and `multiselect` take it. `core.form` applies the filter: `FieldState.options` lists the offered options (`{ key, hint? }`, property order) for a field with a filter (absent without one); an answer outside it (a multiselect: any element) has the issue `option`, `submitValues` leaves it out (ODK clears an answer the filter removes), and `plan` refuses it `invalid_input` at `form.<p>`, so the device and the server agree (R1). The value of a removed answer is dropped from `form` for the fields after it, so dependent dropdowns chain in form order; `dependents` includes the filtered field when a field its filter reads changes. The builder (later, after the field config panel) writes one expression per source field in this shape, so it can generate and parse it: `form.<source> == '<value>' ? option in ['<a>', '<b>'] : <next branch>`, ending in `false`; a source value with no checklist offers nothing. v3's Smart Dropdown (Quellfeld, "Optionen wenn „…“ ausgewählt ist") is exactly this.
- **Form semantics (`core/form`, decision 0015).** `relevant` false: the field is not validated and its value is not submitted. Relevance cascades in the ODK way: a non-relevant field is dropped before the fields that read it evaluate, so a reader sees it as empty (evaluated in dependency order). `required` (literal or expression) counts only while relevant and fails on an empty value: an absent value, `null`, `''`, an empty list, or an object whose values are all empty (an empty `LocalizedString` `{}` counts as empty). A missing required geometry refuses with `geometry_required`. `constraint` runs on a non-empty value with `value` bound to it; on failure `constraint_message` is shown. `calculate` prefills once when the task opens (presets override it) and is never re-run for an editable field; with `readonly` it is recomputed on every evaluation and on submit, and a supplied differing value is refused (not when the `calculate` reads `now`: device and server differ by design, the recomputed value is stored). An expression that errors counts as false and is reported.
- **Select types.** A `select` is a string in expressions (option keys start with a letter, so `form.vitalitaet >= 'v3'`); a `multiselect` is a list of strings. There is no numeric special case.
- **Relation types by cardinality (A-004 item 3).** `cardinality: one` (the default for a picked reference) is a feature: `self.flaeche.name`. `many` (the default for `derive` and `inverse_of`) is a list of features: use `size()` and the macros (`self.auflagen.all(a, a.erfuellt)`); `bind` needs a `one` relation. `self` of a task on several feature types has only the properties they share with the same type.
- **`creates`.** With `creates: <type>`, the form fields and the unprefixed `then.set` / `with` keys address the created feature (`then: [{ set: { baum: self } }]` sets the reference on the new feature); `self` stays the feature the task is on (absent for `$map` and `$none`). The rule `when` of `on: task.x` reads `self` as the feature that run created, else the one it was on. `creates` must name a feature type.
- **Keywords carry the `$` sigil** (`$map`, `$none`, `$all`); keys can never start with `$`. `reserved_key` covers only `RESERVED_KEYS` (rule-language names, literals, `in`), so `map`, `none` and `all` are ordinary keys.
- **Key paths** of problems, `diff` entries and `expressions[].path` are built with `formatKeyPath` (grammar below). A list position is a segment: the first `then` step's condition is `tasks.kontrolle.then["0"].when`. Permission maps address `types.baum.permissions.write.vitalitaet`.
- `permissions.visible_when` is checked like a view filter (`self` of the type, must be bool). It runs as SQL on the server, so compile also translates it with `toSql` under `visibleWhenMapping` (`compile/visible.ts`, the mapping perms uses) and warns `visible_when_not_sql` (path `types.<t>.permissions.visible_when`, span and reason of the unsupported part) when that fails: the server then hides every row of the type (fail closed).

`CompiledConfig.hash` is SHA-256 (hex) over RFC 8785 canonical JSON of the file, computed in pure TypeScript (`compile/hash.ts`). `serialize(config)` gives the stored `CompiledConfigData` (file, hash, `{path, source, ast, types}` per expression; `types` is the checked type of every AST node in pre-order; a node the checker left untyped is an error, never `dyn`). `hydrate(data)` rebuilds the runtime form with no Zod, no parser and no checker (a spec asserts the imports of `hydrate.ts`, `indexes.ts`, `views.ts`, `kp.ts`). Hydrated expressions carry the AST, the result type and the per-node types, restored from that list. `hydrate` throws a `CompiledConfigError` with `code: 'format'` for another `format` (the caller recompiles from the stored file) and `code: 'types_mismatch'` when `types` does not match the number of AST nodes. `expr/ast.ts` is a persisted format: `AST_HASH_BY_FORMAT[COMPILED_FORMAT]` records its hash (comments and whitespace ignored) and `format.spec.ts` fails when `ast.ts` changes without a format bump.

**Derived views** (`compile/views.ts`) are the only producers of what fold and evaluate need from the config; both `compile` and `hydrate` build them from the file, and nothing of them is stored. `CompiledConfig.foldTypes` and `foldSchema(config, configVersion)` give the `FoldSchema` (geometry properties, the primary geometry, reference properties with the edge relation named as the property, derived relations); `CompiledConfig.relations` gives `EvalContext.relations` (declared relations and reference properties per type). A derived relation reaches fold when its `derive` has a spatial predicate `predicate(self.<a>, other.<b>)` as a top-level `&&` operand: the predicate prefilters through the bbox index and, when `derive` is more than that one predicate, `FoldDerivedRelation.condition` (the key path of the whole checked expression) decides each candidate pair. `FoldType.derivedInputs` lists the non-geometry properties any condition reads; a change to one is reported as `FoldResult.derivedInputsChanged`, and the adapter then recomputes like after a geometry change. compile refuses a `derive` without such a conjunct (`derive_no_prefilter`) or one reading `now`/`today()` (`derive_uses_time`) or reading through a relation (`derive_traverses_relation`).

`diff(a, b)` reports `added`, `removed` and `changed` entries by key path (an entity that appears or disappears is one entry; a list is atomic). `breaking` comes from the one rule, `template.breakingChanges`: a removed entity (type, property, relation, task, form field, rule, view, layer, input, role) or select option, or a changed `type` or `geometry_type` (kind `type_changed`).

### Merge and upgrade in `packages/core/src/template`
- **Key paths** (`parseKeyPath` / `formatKeyPath` in `template/paths.ts`, the one implementation): segments joined by `.`; a segment matching `^[a-z][a-z0-9_]*$` is bare, any other is a bracketed JSON string appended without a dot: `style["circle-color"]`, `label["en-GB"]`. The same grammar is used by `override`, `add`, `hide`, `order` and `lock`. Lists are atomic: an override replaces the whole list, and an upgrade where both sides changed the same list is a conflict.
- `merge(template, overlay)` applies inputs (as the `default` of the input), `override`, `add`, `hide`, `order` in that order. It returns the effective file, a provenance map (`changed` / `added`; everything else is `template`) and issues. Issues never throw: an entry that touches a `lock` path (equal, ancestor or descendant), addresses a missing path, or adds an existing path is reported and skipped. `add` may create a missing top-level section (`views.x` into a template without `views`, `map.layers.x` or `map.start` into a template without `map`; a created `map` starts with an empty `layers`).
- **Overlay `order`** (WP-333): `order: { <key path of a map>: [key, …] }` reorders the keys of any map: tasks, properties, form fields, options, views. Listed keys come first in the given order (duplicates count once); keys not listed keep their template order after them, so keys a template upgrade adds appear last. A key the map does not have (also one the overlay hid) is an `unknown_path` issue at `<map>.<key>` and is skipped, as is a path that is not a map. An entry whose path equals or lies under a `lock` path is a `lock_violation`; a lock on an entry *inside* the map does not block reordering the map. A reordered map has provenance `changed` at the map path. `upgrade` drops listed keys the new template removed and the whole entry when the map is gone, silently. The key order of the effective file is what the sheet buttons, form fields, dropdown options and data table columns follow (the first property is the "Hauptspalte").
- Hiding removes the entity from the effective file. `hidden_referenced` is reported once per structural reference that remains (task `on`, view source, view `properties`, `sort` and `layers`, role app, rule `run`, form fields, permissions, property and relation `to`). References inside expression strings are left to `compile()`, which type-checks against the effective file.
- `upgrade(old, overlay, new)` decides per overlay entry, comparing the old and new template at its path. Both changed to different values: conflict, the overlay value stays. Both changed to the same value: the entry is dropped. New template removed the path: `unresolved`, unless a `migrations` entry for that major step names the path or one of its ancestors or descendants. A hide whose target the new template already removed is dropped. Input values always win over a changed default. `extends` is rewritten to the new major. `autoApplied` lists template changes (excluding `template` and `migrations`) that no overlay entry touches; labels, descriptions, `constraint_message` and `options` count as one unit.
- `breakingChanges(a, b)` compares entity maps (`inputs`, `roles`, `types` with `properties` and `relations`, `tasks` with `form` and `auto`, `views` with `layers`; not `tools`, A-041): removed key, changed `type` or `geometry_type`, removed select option.

**Filter presets (WP-640).** `roles.<r>.app.filter_presets.<key>` is `{ label, filters }`: `filters` maps a feature type key to a rule-language expression over `self` (a distinct key from `presets`, which holds default values). A participant's saved filter (`prefs` `filters.saved`, `SavedFilter`) is the same shape without the label: `{ id, name, filters }`. `checkFilterPresets(file)` (`core/filters`) type-checks every preset expression as a boolean over `self` of its type and returns problems at `roles.<r>.app.filter_presets.<k>.filters.<type>`: `expression_parse`, `expression_type`, or `dangling_reference` for an unknown type. A filter is always clipped by permissions (`applyFilter`): only features the actor can see are returned, and a filter that reads a property the actor cannot read matches nothing. The filter builder offers `filterFields(config, type, actor)`: declared properties the actor can read, with the operators of the registry `FILTER_OPERATORS_BY_TYPE` (`is_me`, "ich", only on participant properties); `filterTerm(field, operator, value)` writes one clause as rule-language source (the operators are v3's: `eq`, `between`, `older_than_days`, `newer_than_days`, `in`, `not_in`, `contains`, `not_contains`, `is_empty`, `is_not_empty`, `is_me`); an empty clause writes nothing (null) as in v3, and `joinTerms` joins clauses with AND. System metadata fields (created by/at, last changed) join the field list when WP-306 lands them.

# 03 · Architecture

## Stack
- **TypeScript** end to end, with `strict` and `noUncheckedIndexedAccess`.
- **SvelteKit 2 + Svelte 5 (runes)** as the app *and* the only server process (adapter-node). The Node-or-Bun question is open.
- **SQLite** on the server: one file per project plus `control.db`, R*Tree for spatial queries.
- **IndexedDB** on the device (ported from v3 dbperf). SQLite-WASM is allowed later behind the same ports.
- **MapLibre GL**, Supercluster in a worker, PMTiles for basemaps and offline packs.
- **Zod** for schemas (single source, exported as JSON Schema). **Vitest** + **fast-check** for tests. **Playwright** for e2e.
- UI: Tailwind 4, bits-ui/shadcn-svelte as ported from v3 into `packages/ui/src/components/ui` (decision B-015; usage in `packages/ui/README.md`), Paraglide for UI strings. Project content uses `LocalizedString`.

## Packages and allowed dependencies

```
packages/core      ← depends on nothing but zod and vetted pure libs (jsts or geos-wasm, proj4, a cel parser if chosen)
packages/server    → core
packages/client    → core
packages/ui        → core            (types, registries, expr for previews)
packages/builder   → core, ui
packages/tools/*   → core, ui        (via the tool API only: `@ueberblick/ui/tool-api`, `defineTool`, see packages/tools/README.md)
apps/web           → everything
apps/migrate       → core             (v3 exports → v4 project files; data import runs later)
reference/         ← nobody imports this, ever
```
`dependency-cruiser` (`.dependency-cruiser.cjs`) enforces the graph, and `npm run check` fails on any violation. Deep imports across packages are banned: import from the package entry or its declared subpath exports only. `@ueberblick/core` declares subpath exports (packages/core/README.md); participant-facing code (client, ui, participant routes) imports subpaths only, so the shell never bundles Zod, the checker, the parser or JSTS.

## The life of a run

```
Device                                   Server
──────                                   ──────
ui builds Run {id: uuidv7, task, input}
core.plan(run, localFacts, config) ──► prediction or refusal (shown immediately)
queue.store(run); fold prediction locally
                        ── POST /runs ──►  ledger: seen id? → return stored result
                                           core.planFor(runs, serverFacts, configFor: each feature's version)
                                           one SQLite transaction:
                                             append runs + observations (rule runs included, seq++)
                                             fold → features, edges (+ derived edges, edge tombstones)
                                             hooks: outbox rows, timers
                        ◄── result ─────   accepted | refusal
queue: accept → drop prediction; refuse → rebase the remaining runs on the new state
                        ◄── SSE doorbell ─  device pulls the delta since its seq
```

## Where state lives
- **Truth:** `runs` plus `observations` (server).
- **Derived:** `features`, `edges`, `feature_bbox` (server and device, both via `core.fold`).
- **Config:** `config_versions` (compiled, immutable once deployed). Templates are in `control.db`.
- **Blob routes:** `PUT|HEAD|GET /api/p/<project>/blobs/<sha256>` (`packages/server/src/http/blobs`): bytes on the local disk, authorised through `blob_refs`, or, for a blob the deployed config names (`branding.icon`), to every participant of the project (docs/07).
- **Uploaded tile archives (A-044):** an admin uploads a ZIP, MBTiles or PMTiles in chunks (`/api/admin/projects/<key>/tiles/uploads`, `packages/server/src/http/tile-upload`); `packages/server/src/tiles/upload` converts it, one job at a time with yields, into one PMTiles archive under `<dataDir>/blobs/tiles/<project>/` (`runtime.tilesDir(key)`, next to `packsDir`; project delete removes it with `removeProjectFiles`) through the pack writer and reader, and `GET /api/p/<project>/tiles/archives/<archive>.pmtiles` serves it with range requests to the project's participants. Limits: `TILE_UPLOAD_MAX` (registry).
- **Device-only:** the run queue, predictions, the blob cache, offline packs (OPFS).

## Device runtime threads (B-012, WP-567)
The browser app runs the sync pipeline (pull, `planPage`, the chunked IndexedDB writes) in a **dedicated Web Worker** (`packages/client/src/host`). The **main thread** holds a read replica of the same `DeviceStore` (memory index plus its own IndexedDB connection): all reads (`facts`, `searchText`, `near`) answer from it, and it does the run queue's own writes (runs, blobs, predictions, config versions). The worker is the only writer of the cache (features, edges, history, `runMeta`, `people`, cursor). Each page the worker commits reaches the main thread as one notice (the applied page plan, applied with the same `commitPlan`), after which `DeviceStore.onChange` fires with the changed feature ids. `createAutoSync` (doorbell, `online`, `visibilitychange`) stays on the main thread

## Server run transaction (WP-104)
`createStore(db, deps)` (`packages/server/src/store/run`, contract `run/contract.ts`) executes runs. Order inside the one transaction: ledger lookup (a seen run id returns its stored result), `core.plan` (`planFor` with the server's `configFor`: each feature under its pin, else the deployed version; creates under the deployed one; a database without a deployed version refuses with `NoDeployedVersion`), allocate seq, append `runs` (with `caused_by` for rule runs) and `observations`, fold the touched features (each under its own version) and persist them with `createFoldWriter(db).apply`, recompute derived edges for features whose geometry or derive input changed, run the hooks (outbox, timers), commit. A refused run commits only its `runs` row (`outcome = rejected`); a batch is atomic with one contiguous seq range (H2). Details and the seq rules: `packages/server/README.md`.

## Server runtime wiring (WP-137)
`apps/web/src/lib/server/runtime.ts` is the composition root. One `Store` per project comes from `projectStoresFor(runtime())` and from nowhere else: the run endpoints, the timers loop and sync share it. Its hooks are the timers hook (`runtime.hooks`, per project database, inside the run transaction) and, later, the outbox hook; its `runtime.doorbell` rings the project's doorbell after every accepted run (`withDoorbell`), whoever submitted it, so a device that listens on `sync/events` hears about a run within milliseconds, and about a run a timer fired too. The **timers loop** (`startTimersLoop`, `packages/server/src/timers/loop.ts`) starts with the runtime: per project `syncSchedules()` once, then `tick(now)` at start and every `TIMERS_INTERVAL_S` seconds (default 30, `0` = off); it stops on `sveltekit:shutdown`. A **deploy** calls `services.afterDeploy(project)` (rings the doorbell once, timers `rebuild()` and `syncSchedules()`; the `$pin` runs of a `keep` are written through `services.pins(project)`, whose store never rings, so a rolled-back deploy rings nothing), so a changed rule does not keep stale schedules. `configCacheFor(db)` holds each stored config version compiled once (versions are immutable), for the store, sync and timers alike. Rows the loop or a deploy writes are runs too (R3).

**Timers and derive per version (A-029, WP-318).** Both take the project's version resolver (`VersionResolver` in `store/run/config-for.ts`: `configFor(version)` plus `deployed()`, backed by the one config cache) instead of a single config. An `elapsed` row records the version it was scheduled under (`timers.config_version`, migration 20) and is scheduled, evaluated and fired under its subject's effective version, `coalesce(features.pinned_version, deployed)`; the fired run is stamped with it. The timers hook sees a pin or an unpin as the `$version` observation of the run and rebuilds that feature's rows under the new version (a rule the new version lacks loses its row); a deploy's `rebuild()` rebuilds the floating features per live version (the deployed one and every pin) and removes rows whose rule their version lacks. A due row whose `config_version` is no longer its subject's version (a deploy between schedule and tick) is rescheduled, never fired stale; a pin to a version that is gone fails that row (it stays for the next tick), with no fallback to the deployed config (R11). A `schedule` rule has no subject and stays on the deployed version. The dropped-rule warning (`timer.dropped`) is kept per rule per version. A tick resolves each version once (one config per version per tick, `bench/timers`). `createDeriveFor` groups the features of a `recompute` by effective version and runs each group with its version's schema and condition; with no pin that is one group, the deployed one.

## core.plan (WP-041)
`createPlan(form)` returns `{ availableFor, availableTasksFor, fireRuleFor, planFor }` (`packages/core/src/plan`, contract in `plan/contract.ts`; `form` is core.form's `formApi`). One call builds one **overlay** over the `Facts` port: observations planned earlier in the batch, by earlier `then` steps and by earlier rule runs are folded with `core.fold` on top of `facts` and are visible to later checks. `facts` is never mutated, and a refused batch leaves nothing behind (H2: atomic, the refusal names the failing submitted run).

Order of checks for one run (`availableFor` is steps 1 to 5, and `planFor` calls it, so "offered" and "refused" cannot disagree):
1. the task exists (`unknown_task`) and the target fits its `on`: a feature of a listed type, `$map` (the run's `featureId` is then the id of the feature it creates), or `$none` (`unknown_feature`, `not_available`);
2. a participant may see `self` (`Perms.canSee`, `not_permitted`);
3. each `bind` resolves to a related feature (`bind_unresolved`);
4. `when` (`not_available`, with `explain` output as `explanation`; `not_permitted` instead when every decisive failed term reads only `actor`, i.e. the person's roles, kind or id, WP-787);
5. input keys are form fields; `bind.property` outside the declared binds is `bind_undeclared`, any other unknown key `invalid_input`; a key starting with `$` is a reserved system key (`$version`, `$lifecycle`, ...) and is refused `not_permitted` before the form sees it, so a participant form can never write one (only system and admin runs do);
6. the form: `initial(input)` fills omitted `calculate` fields, `evaluate` validates (`required_missing`, or `geometry_required` when the missing field is a geometry property; `constraint_failed`, `readonly_field`, `invalid_input`), `submitValues` drops non-relevant fields, except that `hiddenClears` lets an explicit null clear a stored hidden field (owner Q5). Plan does not implement any of it;
7. observations: for a created feature `$type`, property defaults, then the form values; `Perms.canCreate` (created) or `Perms.canWrite` (existing features, every step and bound feature). For a participant every existing feature written (a bound feature, a `then` `of` target, a `redact` `of` target) must be served and pass `canSee`, and a `reference` value must name a served, visible feature of the relation's `to` type (`unknown_feature` for a missing id, `case_closed` for an archived or deleted one, `not_permitted` for a hidden one, `invalid_input` for the wrong type); `plan/targets.ts` decides, by id lookup. A `lifecycle` or `set` `of` goes through the same check. The task's own expressions (availability, bind, form, `then`) read a feature the participant may not see as absent (`plan/guard.ts`), and a relation list read there holds only visible, served features, so `size(self.kinder)` never counts hidden ones (WP-765; `of` and bind read the unfiltered list, so a hidden id there is still refused loudly); computed properties and rules are not guarded. System, import and admin actors stay unbound (WP-755). Required properties of the created type must have a non-empty value (the one emptiness definition of core.form, `form/empty.ts`) after `then` (`geometry_required`, `required_missing`);
8. `then` steps in order, each step visible to the next (`when`, `otherwise`; a `date` property stores the date part of a timestamp);
9. automatic actions (`tasks.<t>.auto.<name>`, the compiled table `config.autos`): `after: <task>` first, then property changes (`change: <type>.<property>`, `<type>.*`), each as a system run of the entry's task through steps 1 to 9 with `causedBy` set, depth-first. More than `ports.limits.ruleDepth` nested rule runs is `depth_exceeded` (`PlanPorts.limits` is required; callers pass `PLAN_MAX_RULE_DEPTH`, 8, the platform default, unless the platform overrides it; further platform limits join this object) and refuses the submitted run. An entry without a timing (an edge on its `when`) is judged for every feature the run touched (and created): it fires when the expression is false before the run (or the feature did not exist) and true after it (A-045; docs/06 "Edge trigger"). Time-based entries (`elapsed`, `schedule`) are not fired by runs but by the server clock, one at a time, through `PlanApi.fireRuleFor({ rule, subject?, configVersion, dueAt }, configFor, ports, options?)`: it shares step 9's code (`when`, `with`, depth, the system run planned by steps 1 to 8) and returns `{ ok, runs }` (empty when `when` is false) or a refusal; `self` is `subject`, `form` is empty, `actor` is the system actor, `causedBy` is absent.

Only **participants** are bound by role allowlists (`see`, `create`, `write`); `system`, `import` and `admin` actors are not, and `when` applies to everyone (golden semantics 2). Refusal codes are the registry `REFUSAL_CODES` (`registry/refusals.ts`); `plan: false` entries are raised by the batch, import and view layers around plan. `featureAccess(facts, config)` is the one `FeatureAccess` over `Facts`: a reference property reads as a relation, and inverse relations follow `sqlInverse`.

**Rule trace.** `planFor(batch, configFor, ports, { trace: true })` also returns `trace`, a list of `RuleTraceEntry` (its `rule` is the automatic action's id `<task>.<name>`, `AutoId`) in chain order (depth-first), from the same code path as planning (rules.ts, no second evaluator). After every run (submitted or rule-caused) each event rule gets one entry: `reason` from the registry `RULE_TRACE_REASONS` (`fired` with the planned `run` id; `trigger_not_matched`; `already_true` (a `{ when }` trigger held before the run and still holds); `when_false` with the `expr.explain` `explanation`; `depth_exceeded` with the refusal; `refused` with the refusal when the rule's `with` or its run was refused), plus `depth`, `trigger` and `subject`. `trigger` says why the rule was considered and is discriminated on the registry `RULE_TRACE_TRIGGER_KINDS` (not the config timings of `AUTO_TIMING_KINDS`): `{ kind: 'run', causedBy }` for the run whose changes were checked, `{ kind: 'timer', dueAt }` for a time-based rule that came due. A new kind (import, external event, dispatch) is one more registry entry and one more case where the trace is read. A refused batch returns the trace up to the refusal: the rules above the failing one show `refused` with the child's refusal. Without the option no trace is built or allocated. Cost with trace on: within noise of the plain `kontrolle` bench (about 0.15 to 0.2 ms). `PlanApi.fireRuleFor(..., { trace: true })` returns the same kind of trace: its first entry is the timer rule (depth 0, `trigger.kind === 'timer'` with the `dueAt` it was given, `when_false` or `fired`), and the event rules its system run causes follow below it with `trigger.kind === 'run'` (depth 1 and up).

**Erasure in plan (B-005).** A `redact` `then` step (`plan/redact-step.ts`, `plan/redact`) resolves the subject's personal (feature, property) pairs from config (`personal.subject`) and `Facts` (`observationsByActor(actorId)` for `actor`, `featuresWith(type, property, value)` for `property:<key>`), and `planRedaction` yields one `null` observation per pair. `PlannedRun.purge` (required, `[]` for every other run) lists the pairs the server blanks **in place** in the run's own transaction, `PlannedRun.erased` has one entry per `redact` step, `{ subject, purge }`: the subject id for `erasure_subjects` and that step's own pairs (`purge` is the deduplicated union of the entries' pairs). plan reads committed state for these two lookups (what earlier runs of the same batch wrote is not included), and a device answers `observationsByActor` with nothing: an erasure run is authoritative on the server. Refusals name codes and paths and never a submitted value, because a refusal is stored and survives an erasure (`plan/redact-step.spec.ts`).

Derived edges are recomputed in the overlay against every candidate: `Facts.near` for stored features, shadowed by the features the batch changed (judged by their planned state), so a created feature has its derived edges before its rules read them. `PlannedRun.rule` names the rule of a rule run and is absent for user runs. Benchmark `bench/plan-run`: a `kontrolle` run with a rule run about 0.2 ms, a plain run about 0.02 ms (budget 5 ms).

## API tokens and project delete (WP-388, A-037)
**API tokens** (QGIS / GIS access, Q18): `Auth.apiTokens` (`packages/server/src/auth/api-tokens.ts`, control table `api_tokens`) issues, lists, revokes and authenticates `ubk_` tokens per participant. Only the SHA-256 is stored; the secret is returned once by `issue`. `readSessionCookie(request, 'participant')` returns the participant session cookie, else `api:<token>` from `Authorization: Bearer` or HTTP Basic (user name or password), and `authenticate` resolves it to the participant principal with their live roles, so every project endpoint (OGC, sync, runs) takes a token and one permission check serves both. `exchange` refuses a token; a revoke, an expiry, a disabled participant and `revokeParticipant` stop it. `last_used_at` is written at most once a minute per token. `scope` (`API_TOKEN_SCOPES`, today `full`) is the seam for narrower tokens (H4). Admin endpoints (`apps/web/src/lib/server/handlers/admin-tokens.ts`): `GET|POST /api/admin/p/<project>/tokens`, `DELETE …/tokens/<id>`. OGC Part 4 writes run as the caller (A-043): a participant token or session writes under the participant's own permissions, with actor kind `participant`; an admin token is not built (A-037).

**Project delete:** `DELETE /api/admin/projects/<project>` with `{ "confirm": "<key>" }` (`packages/server/src/http/admin-projects/delete.ts`, wired in `admin-project-delete.ts`) closes the preview and project handles, removes the control rows in one transaction, then the files (database, blobs, packs, tile cache, preview). `GET` on the same path answers the counts the confirm dialog lists. The key goes into `retired_projects` and is never handed out again (`freeKey` skips it, a trigger refuses an insert), because per-key caches of the running process would otherwise serve a new project from the closed database. If the file removal fails, `sweepRetiredProjects` finishes it at the next runtime start (`removeProjectFiles` is shared with the delete; only retired keys are swept; WP-404). Allowed for any project membership (A-008; `authorizeProjectDelete` is the seam for an owner role).

## Admin feature list (WP-313, E-7)

`GET /api/admin/p/<project>/features` and `…/features/distinct` (`packages/server/src/http/admin-features`, behind `authorizeAdmin`) are the query behind the admin data table: one feature type, searched, sorted, filtered per column and paged by keyset, with every lifecycle state (`deleted` hidden unless asked for) and the audit columns. The request is parsed into a plain `FeatureQuery` (`query.ts`, a saved view can store it), turned into SQL by pure functions (`sql.ts`: list, count, distinct, empty count) over the columns of the type (`columns.ts`, from the deployed config; properties are read with `propertySql`; system columns are core's `SYSTEM_FIELDS` under their sigil key (`$lifecycle`, `$created_by`, `$created_at`, `$changed_at`) plus `$id`, the same key in `sort=`, `filter.`, `column=`, the cursor and a row, and a property key can never start with `$`). Paging is keyset on (sort value, id) with an opaque cursor that names its sort; no OFFSET. Every text column sorts `COLLATE NOCASE` (ids and timestamps stay binary), so the order never depends on whether a property has `index: true`; for a text-kind property with `index: true` deploy builds a second expression index on the same expression with `COLLATE NOCASE` and the id (`cfg_idx_nc_*`, `deploy/index-ddl.ts`; `sortSql` and the DDL share `noCase`), next to the binary one that serves equality lookups (rules, sync). Search is a LIKE over the text properties with a cheap LIKE on the raw `properties` in front (no FTS table needed: the rare-term search over 60k rows measures 65 ms). Distinct values ignore the column's own filter and are capped at 500. It is a separate path from OGC items (H5 and H6 may reuse the query builder). `bench/admin-features`: every shape at 60k features of one type stays under 110 ms p95 (budget line `admin-features-p95`, 300 ms, in docs/12). Reference: `docs/user/admin/reference/features-api.md`.

**Feature history (WP-362, E-9)**: `GET /api/admin/p/<project>/features/<id>/history?cursor=` (same module, `history.ts`) is the Objekt page's Aktivität: the runs on one feature, newest first, 50 a page, any lifecycle state, accepted and refused. A refused run has no observations, so migration 21 adds `runs.feature_id` (a projection like `features.pinned_version`: the run's `featureId`, for an accepted create run the created feature, null for a refused create run; written by the ledger in the run transaction, back-filled from the run's first observation) with the partial index `runs_by_feature (feature_id)`, whose implicit trailing rowid is the insertion order: newest first is an index walk and the keyset cursor is the rowid, no OFFSET. The page's observations come from one range read of the feature's own rows (`observations_by_feature_seq`, new in 21; the run's stored seq range bounds it). Nothing scans runs of other features. `bench/admin-features/history`: line `admin-feature-history-p95` in docs/12.

**Protokoll of a run (WP-372, owner A3)**: `GET /api/admin/p/<project>/features/<id>/runs/<run>` (`protokoll.ts`, `protokoll-handler.ts`, new files of the same module) returns one accepted run of the feature as `{ run, type, form, properties, values }`: the form entries and properties of the task **in the run's own config version** (`versionCacheFor(db).get(runs.config_version)`, A-029; 404 when that version is gone), and the values are the run's own observations on the form's properties (the run's stored seq range, `run_id`). The server decides what the viewer may read: `visibleProperties(perms, type, viewer, keys)` gives an admin every key (as the Daten tab and the data table, golden semantics 2) and a participant `perms.forType(type).readable(subjects)`, the sync's call (R1); hidden fields are absent from `form`, `properties` and `values`, and the client never filters. A refused run, a run of another feature or an unknown run is 404. ## Preview store and isolation (WP-340, A-031)
A project can have one **preview**: a second project database `<dataDir>/preview-<project key>.db`, served under the key `<project key>__vorschau`, registered in `control.db` `previews` (`project_id`, `id`, `key`, `generation`, `status` = `ready | stale | dropped`, `last_good_version`) and **not** in `projects` (`packages/server/src/preview/registry.ts`: `ensurePreview`, `dropPreview`, `previewDbPath`, `findPreview`). `ensurePreview` is idempotent. `dropPreview` removes the file, the blob dir `<dataDir>/blobs/<key>__vorschau`, the preview's sessions and (unless `keepLogins`, which the reset's `POST` passes) its login tokens, and bumps `generation`; the row stays (`dropped`), so a re-created preview carries the higher generation. Isolation by construction: `rt.project(key)` and `projectKeys()` read only `projects`, so OGC, MCP, runs, sync, blobs, exports, export-subject, erasure and the admin routes cannot resolve a preview; only `rt.participantProject(key)` (real project, else live preview) does, and only participant routes may call it (`apps/web/src/lib/server/runtime.spec.ts` greps for any other use). A preview session's project id is the preview's `id`, so `authorizeProject` refuses it on the real project and a real session on the preview. A project key never contains `__` (`assertProjectKey`), the file name does not match the backup's `project-*.db`, and the timers loop ticks live previews from its second list (`previews`). **The preview follows the draft (WP-341).** The draft `PUT` route calls `rt.previews.schedulePreviewRefresh(project)` after an accepted save (a 409 or 404 does not). It is debounced (`PREVIEW_DEBOUNCE_MS` = 1 s, the timer is injected) and coalesced per project, so typing deploys at most once a second and two saves inside the window give one deploy. `refreshPreview` (`packages/server/src/preview/refresh.ts`) reads the saved draft from the real project database (read only), ensures the preview, parses the overlay and runs `plan` against the preview's deployed version. `previewMappings` (`packages/server/src/preview/mappings.ts`) turns every breaking removal into a mapping: a removed option goes to the first remaining option of its property (the process `start` for the process property), a removed property is `{ discard }`. Then `deployProject(previewDb, overlay, 'preview', deps, mappings)` runs, and its `afterDeploy` lets the value-move executor run the `$move` runs. A draft that does not parse, merge or compile changes nothing in the preview: its status becomes `stale` and the status route reports the problem count; the next good save gives `ready`. `GET /builder-api/<project>/preview` returns `{ status, problems, version, updatedAt, logins }` (`dropped` = no live preview; the problem count and `updatedAt` are held in memory and start empty after a restart; `logins` below). The refresh writes only the preview database and the preview's row in `previews`: the real project's runs, observations and `config_versions` are untouched (`apps/web/src/routes/api/p/[project]/preview-wiring.spec.ts` compares them before and after). The participant routes resolve a preview key through `rt.participantProject`: bootstrap, config, sync (and its events), runs, blobs and prefs (`apps/web/src/routes/(participant)/participant-api/wiring.ts`, `apps/web/src/routes/api/p/[project]/wiring.ts`, `apps/web/src/routes/api/p/[project]/sync/wiring.ts`); OGC, MCP, admin, export and the builder routes keep `rt.project`. Demo data is WP-342; the logins and the carry-over instead of a discard on deploy are WP-373 (A-034, below). Budget: a refresh of the 500-entity template takes about 0.3 s (`bench/preview-refresh`, limit 2 s).

## Preview logins and carry-over (WP-373, A-034)
**No deploy path drops the preview.** Publish, rollback, upgrade and admin deploy end in `ProjectServices.afterDeploy` of the real project; the runtime wraps it and calls `previews.carryOver(projectKey)` for a project with a live preview (`preview/refresh.ts`). `carryOver` deploys the draft (without a draft: the live config) into the preview database with the automatic mappings plus the `{ to }` mappings the live deploy recorded (`recordedMappings(db, version)` reads its `deploy_moves` rows, `deploy/moves.ts`), so preview and live move values with the same mappings and the same executor (R1). It never throws into the live deploy (`onError`). Only project delete drops the preview for good. **Preview logins** (`preview/logins.ts`): every refresh syncs one preview participant per role of the deployed draft plus "Keine Rolle" (`preview-g<generation>-r-<role>` / `preview-g<generation>-none`, rows in the preview's `participants`) with one reusable token each under the preview's id as project id (`Auth.issueCredential` accepts a live preview id). A removed role's token is revoked (`Auth.revokeParticipant`). `GET /builder-api/<project>/preview[?locale=]` (`handlers/preview.ts`, project admin only, `no-store`) answers `{ status, problems, version, updatedAt, logins: [{ role, label, participantId, token, link }] }`. A reset (`POST .../preview/reset`) calls `dropPreview(..., { keepLogins: true })`, so the tokens survive, bumps the generation and moves the tokens to the new participants (`Auth.reassignCredentials`); the runtime also tells `services.forget(key)` and the store source to let go of the closed handle. **The device flag:** `GET /participant-api/bootstrap` answers `project.preview` (`isPreviewKey(project key)`, server side), the one place that knows it.

## Tile proxy (WP-369, A-033)
The browser never talks to a tile provider. `GET /api/p/<project>/tiles/<layer>/<z>/<x>/<y>` (xyz, preset, pmtiles layers) and `GET /api/p/<project>/wms/<layer>?bbox&width&height&crs` (wms layers) are answered by `createTileHandlers` (`packages/server/src/http/tiles`) over one `TileService` per process (`packages/server/src/tiles`, `runtime.tiles`). Auth is a participant or admin session; the layer must be visible through `layersForRoles` (the audience rule of the pack download), else 404.

- **Resolution.** `resolveSource` turns a layer's source into a URL template, an archive URL or a WMS request and a cache key (the first 32 hex characters of the SHA-256 of the canonical source, so a changed source never reads the old source's tiles). The service looks in the disk cache, else fetches upstream, checks by the first bytes that the answer is an image, stores it and returns it. Callers for one tile share one fetch (single flight); a 404, an HTML page, a failure or a `no-store` answer is never cached. A failure is 502 `upstream_failed`.
- **Cache** (`tiles/cache.ts`): `<dataDir>/tiles-cache/<project>/<source key>/<z>/<x>/<y>.<ext>`, atomic writes (temp file, rename), a size cap with least-recently-used eviction from an in-memory index built once, and an age limit kept in the file's mtime (no sidecar). Limits are the registry `TILE_PROXY_LIMITS`.
- **Politeness** (`tiles/limiter.ts`, `tiles/upstream.ts`): one limiter per upstream host with a concurrency and a rate, shared by the proxy and the pack builder; the User-Agent `Überblick/4 (+<PUBLIC_URL>)`; retries with backoff; `Retry-After` and `Cache-Control` honoured. The registry `TILE_HOST_POLICIES` caps the tiles of one pack layer per host (OSM: 10,000).
- **SSRF guard** (`tiles/guard.ts`, `address.ts`, `pinned-fetch.ts`): one guard for every request to a layer host (proxy upstream, pack tile and range fetches, pack readers). It resolves the host once, refuses unless every address is public (loopback, private, link-local and cloud metadata, unique-local, mapped and NAT64 included) or the host is the instance itself (`PUBLIC_URL`), connects to the validated address (Host and TLS name kept), checks every redirect hop, and refuses with a typed `UpstreamRefused` before any request. A layer URL that is a path on this instance (`/…`) is self-hosted: the routes answer 404 `not_proxied` and the pack builder reads it from the origin without the guard (`//host`, `/\host` and paths with control characters stay absolute and guarded; a 404 tile is absent). A-033 item 9.
- **Packs** read `xyz` and `preset` layers through `TileService.tile` (`PackTiles`), so building a pack fills the cache.
- WMS passes on only `bbox`, `width`, `height` and `crs`; the rest comes from the layer's config.
- `X-Tile-Cache: HIT|MISS` tells which it was. Budgets in docs/12.

**Canvas layout (WP-366, E-21).** Where the admin dragged the nodes of a feature type's workflow canvas is stored in the project database table `canvas_layout(type, node_id, x, y, updated_by, updated_at)`, primary key (type, node_id), project migration 23. It is an admin aid next to the draft and belongs to no config: it is not in the overlay, the draft or any `config_versions` row, and publish, rollback and template upgrade never touch it (`builder-draft/layout.spec.ts`). `LayoutStore` (`packages/server/src/builder-draft/layout.ts`: `get(type)`, `replace(type, nodes, by, at)`) is the port; `replace` makes the given nodes the stored set of the type in one transaction, so a node that no longer exists is pruned by the next save. `GET /builder-api/<project>/layout?type=<t>` returns `{ type, nodes: [{ id, x, y }] }`; `PUT` takes `{ type, nodes }` (at most 500 nodes, ids up to 200 characters, finite numbers, body up to 100 KB: 400 or 413 otherwise). Both use `authorizeAdmin` like the draft routes (401 anonymous, 403 otherwise) and the project of the URL. Another canvas (H1, H5) stores its positions with the same key, adding a `scope` column if needed: a column, not a table.

## Offline packs: build and store (WP-350, A-032)
A pack is declared in `map.packs` (WP-349). The server builds one PMTiles v3 file per (pack, layer) in `packages/server/src/packs`. `pack_hash = sha256(canonical(bounds, zooms, layers sorted, each layer's source and maxzoom))` (`hash.ts`; label and `roles` are left out, so they never rebuild). Project migration 19 adds `pack_builds(pack_hash, pack_key, layer, state, tiles_done, tiles_total, bytes, sha256, max_zoom, tiles, error, updated_at)`, states from `PACK_BUILD_STATES` (queued, building, ready, failed). Files live at `<blobs>/packs/<project>/<pack_hash>/<layer>.pmtiles`.

**Deploy writes the first pins (WP-317, A-029 item 5).** `deploy(db, file, by, deps, mappings, choices)` and `plan(db, file, deps, choices)` take `choices: { [type]: 'keep' | 'move' }` (registry `VERSION_DEPLOY_CHOICES`, default `VERSION_DEPLOY_DEFAULT = 'move'`, owner question P2 (a)). A type is *changed* when any diff entry sits under `types.<type>` or under a task or rule that is offered on, creates or watches it. For each changed type with running (`aktiv`, `RUNNING_LIFECYCLE`) features the plan returns `versions: [{ type, running_floating, already_pinned, settled_floating }]`, one SQL per type (`deploy/pins.ts`). `keep` writes one `$pin` system run per `running_floating` feature (core `plan/pin.ts`, registry `SYSTEM_TASKS`: input `{ version }`, an integer pins and `null` unpins, idempotent, system actor only) through `deps.pins` (the project's store and run ids, `ProjectServices.pins`), in batches of `PIN_BATCH_SIZE` (500) inside the deploy transaction while the previous version is still the deployed one, so no feature ever floats on the new version; a refusal throws and rolls the deploy back. A choice for a type that is unknown, unchanged or has no running features is a typed problem (`unknown_path` at `versions.<type>`, an unknown value `schema_invalid`). The first deploy and `move` write nothing. Completed and archived floating features are never pinned (P1 (a)): they move with the values. `move-select.ts`'s `liveAnd` carries `pinned_version IS NULL`, so the plan's `affected` counts and the executor's selection skip pinned features from the one definition. The admin endpoints `POST /api/admin/p/<project>/{plan,deploy}` take the choice as `?versions={"baum":"keep"}`. Bench `bench/deploy/pin-keep`: 10k pins inside one deploy.

**Manual move of pins (WP-368, owner P3).** `deploy/pin-move.ts`: `planPinMove(db, from)` is the diff of version `from` against the deployed one with `affected` counted over the features pinned to `from` (`move-select.ts` takes `pinnedTo`, so the predicate `pinned_version = N` replaces `IS NULL` in the one definition), and `movePins(db, pins, from, mappings)` writes one `$pin` run with `{version: null}` per pinned feature (every lifecycle state) plus the `$move` runs of the `{ to }` mappings through the same `pins.store.submitBatch`, batched like a deploy, in one transaction (a refusal rolls back and answers a typed problem). It reads the pinned ids of each move before the unpin (the unpin empties the pin). `pinCounts(db)` is the per-version count for the Versionen page (a group over the partial index `features_pinned`). Endpoints: `GET|POST /admin/projects/<project>/versions/move`. Bench `bench/deploy/pin-move`.

**Blob access per version and one cache (WP-317).** `http/blobs/access.ts` judges a blob under the permissions of its feature's effective version (`coalesce(pinned_version, deployed)`) through `createLiveScopes` over the sync service's resolver (`services.sync(key).versions`); the deployed-only `createScopes` is gone. `versionCacheFor(db)` (`http/shared/config-cache.ts`, memoised on the `Db`) is the one `VersionCache` per project database: `composeProjectStore` passes it as `StoreDeps.versions` and `createProjectServices` as `SyncServiceDeps.versions`, so a version's config and permissions are compiled once for runs, sync pages and blob access (timers and derive take it in WP-318). `versions` is required on `StoreDeps` and `SyncServiceDeps` (WP-355): neither builds a cache of its own; a tool that injects its own configs passes `versionCacheFor(db, load)` (a cache over that loader), tests pass `createVersionCache(...)`.

`deployProject` queues every (pack, layer) of the new config whose hash has no row (`enqueuePacks`; a failed row is queued again; ready, queued and building rows are left alone, so a redeploy with the same hash enqueues nothing). `createPackBuilder(...).drain()` is the worker: one layer at a time, in the background, never inside a run transaction. For a `pmtiles` source it reads the archive by range through the `fetchRange(url, offset, length)` port (the only network access; `httpFetchRange` adds a concurrency limit and an identifying User-Agent, `withRetries` retries with backoff), lists the tiles of bounds x zooms in tile-id order, capped at the archive header's max zoom, merges near byte ranges into one request, and appends the stored tile bytes to a spool next to the target (`.part` plus one 24-byte record per tile in `.idx`). After each batch of 512 tiles the row stores how far the list is done and the spool size, so a restart cuts the spool back to the committed point and continues (no tile twice or missing). The writer (`archive-write.ts`) then emits header, root directory, metadata, leaf directories (only when the root would not fit 16 KiB) and the data, clustered, directories gzipped, to a temp name that is renamed once complete; `bytes`, `sha256`, the layer's built `max_zoom` and `tiles` go into the row (the manifest fields of WP-351). A fetch that fails after its retries ends in `failed(reason)`; the admin endpoint re-queues it. Only sources whose `MAP_SOURCE_TYPES` entry has `packable` are built (`pmtiles`, `xyz`, `preset`). Where the tiles of a layer come from is a `LayerReader` (`packs/readers.ts`): a `pmtiles` source is read by range as above; an `xyz` or `preset` source is read tile by tile through the tile service (next section), so the build warms the proxy cache. WMS and geojson are not packable.

`builder.sweep()` is the garbage collection, O(hashes). It runs at the start of every `drain` rather than in the blob sweeper (a deviation from A-032 that lead-a accepted: the blob sweeper is the per-blob tombstone sweeper, outside this work package): it deletes the directory and rows of every hash that no deployed config (or `pinned()` hash, the seam for version pinning, A-029) references. Admin endpoint: `GET /api/admin/p/<project>/packs` and `POST …/packs/<key>/rebuild` (`packages/server/src/http/admin-packs`; reference `docs/user/admin/reference/packs-api.md`). Bench `bench/packs`: the build runs at well above 2,000 tiles/s from a local fixture (docs/12).

**Runtime wiring and serving (WP-351).** `createPackRuntime` (`packages/server/src/packs/runtime.ts`) holds one `PackBuilder` per project (`pinned = pinnedPackHashes(db)`: the pack hashes of every version a feature still pins through `features.pinned_version`, so GC keeps them until nothing pins that version) and the rule that drains never overlap: `kick(project)` queues the deployed config's packs and drains in the background; a kick during a drain only marks "run again" and the running drain loops once more. `apps/web/src/lib/server/runtime.ts` creates it (`runtime.packs`), wraps `services.afterDeploy` so every deploy path kicks it (never for a preview key), kicks every project at start (an interrupted build resumes) and after the admin `rebuild`, and aborts the drain signal in `stop()` (`sveltekit:shutdown`). Files are written and served from `<dataDir>/blobs/packs/<project>` (`packsDir`). The tile and range fetches send `User-Agent: Überblick/4 (+<PUBLIC_URL>)` (`tileUserAgent`, shared with the tile proxy), two ranges at a time, with retries. **`PACK_BUILD=0`** (environment, default on; `config/`, internal like `UEBERBLICK_INSECURE_COOKIES`) builds and queues nothing from the runtime. Unit tests that do not test packs set it off; the e2e server leaves it on (its fixtures declare no `map.packs`, so a drain finds nothing to build). A failed build or a throwing drain logs `packs.failed` (project key and a code, never a message). Serving: `GET /api/p/<project>/packs` and `GET /api/p/<project>/packs/<hash>/<layer>.pmtiles` (`packages/server/src/http/packs`, protocol in docs/07). Both decide the audience with one core function, `packsForRoles(map, roles)` (`core/registry/map-layers.ts`, next to `layersForRoles`). `parseByteRange` (`http/shared/range.ts`) is the one `Range` parser.

## Admin-Korrektur: the system task `$correct` (WP-370, E-11)
v3's "Bearbeitungsmodus" on the data page saved cells through a faked `admin_edit` submission with no checks. v4 has one system task for it (registry `SYSTEM_TASKS`, `plan/correct-task.ts`, owner answer A1): `$correct`, label "Admin-Korrektur" / "Admin correction". Actor kind `admin` only (so no role check); input `{ values: { <property>: value } }` on `run.featureId`.
- **Checks.** Every value goes through `valueRefusal` (`plan/values.ts`, shared with `$seed` and `$import`, R1): an unknown property, a `$` system key or a value that does not fit is `invalid_input`; the process (stage) property is `not_permitted` (a stage moves through tasks, so its rules and steps run). Each refusal carries the path `input.values.<property>`. A value equal to the current one writes nothing; an empty one clears the property with an explicit null.
- **Planned as any run.** The changes go through the overlay, computed values follow in the same run (`recomputeAfter`) and the rules of the changed properties fire (`<type>.<property>`, `<type>.*`, `fireRules`), so the effects are in the history like any other. One call is one run, so a row's edits are one entry in Aktivität (`runs.feature_id`, WP-362).
- **Endpoint** `POST /api/admin/p/<project>/features/<id>/correct`, body `{ values, expected_seq? }` (`packages/server/src/http/admin-features/correct.ts`; reference `docs/user/admin/reference/features-api.md`). Admin and project scoped as the other admin endpoints; the run is submitted through the project's store (R3) with the admin's account id as actor. `expected_seq` is the row's `$seq` (`features.updated_seq`, delivered with every list row); it goes into the run's input and core checks it in the plan, inside the run's transaction (`not_available` at `input.expected_seq`), so a second writer cannot interleave; another value is `409 conflict`, so a stale edit never overwrites a newer value. A refusal is `422 run_refused` with `issues: [{ path, message }]`.
- **History names.** `features/<id>/history` gives an admin run `actor.name` from the account's e-mail (`AdminFeaturesDeps.adminName`; accounts live in the control database, not in `participants`).
- **Seams (H4, H6).** An assistant's data fix is a `$correct` run, with the same checks and audit; QGIS edits stay task runs and never use it.

## Admin creation and deletion: `$create` and `$lifecycle` by an admin (WP-382, E-12, E-13)
The Tabellen page (v3 `custom-tables/[tableId]`) adds and deletes rows. Rows are features, so both are runs (R3). `$create` (registry `SYSTEM_TASKS`, `plan/create-task.ts`) is the admin's counterpart to `$correct`: actor kind `admin` only, input `{ type, values }`, feature id `run.featureId` or a fresh one. Every value goes through `valueRefusal` (the check `$seed`, `$import` and `$correct` share, R1); the process property is refused (a new feature starts at the process `start`); defaults fill the rest, `requiredMissing` (the creating task's own check, `plan/run.ts`) refuses a missing required value, computed values follow in the same run. It writes `$type` and `$created_by` (the admin's account id), so the audit columns show the admin. Rules do not fire. `$lifecycle` (see below) now also accepts the `admin` actor; the admin's delete is `{ state: 'deleted' }`.

- **Endpoints** `POST /api/admin/p/<project>/features` (`{ type, values }`, `201 { runId, id }`) and `POST …/features/<id>/lifecycle` (`{ state }`, `200 { runId }`), `packages/server/src/http/admin-features/create.ts`; refusals as for `correct` (`admin-run.ts`: `422 run_refused`, `409 conflict`).
- **Columns and the table itself are config, not runs:** a Tabelle is a type without geometry and process; adding, renaming, removing and reordering its properties, and renaming, describing, restricting (`permissions.see`) or deleting it, are builder Doc ops on the draft (Q16) through `routes/(admin)/admin/projects/<p>/tables` (`table-ops.ts`; the property ops are the field pane's, one set, R1). The first property is the "Hauptspalte" (Q15).
- **Seams (H4, H6).** An assistant fills a table through the same runs; QGIS edits stay task runs.

## Import over HTTP and the system tasks `$import`, `$lifecycle` (WP-363, E-10)
`POST /api/admin/p/<project>/import/plan` (dry run), `POST …/import` (start) and `GET …/import/<job>` (progress) are in `packages/server/src/http/admin-import` (behind `authorizeAdmin`, a project that was never deployed answers `not_published`). The body is multipart: `file`, `mapping` (JSON: `ImportMapping` of `io/contract.ts`, with `constants`), `format` (else the file extension) and for the start `mode` (`atomic` default, `skip`) and `replace`. Registries (core `registry/import.ts`): `IMPORT_JOB_STATES` (queued, running, done, failed), `IMPORT_ERRORS` (`not_published` 409, `replace_needs_atomic` 422, `file_too_large` 413, `invalid_import` 400, `unknown_job` 404, answered as `{ error: { code, message } }`), `IMPORT_LIMITS` (100 MiB file, 200 problems kept, 10 preview rows). There is one reader and one planner: the endpoint calls `planImport` and `submitPlan` (`io/import.ts`; `importFile` is the same two calls drained at once).
- **Dry run** plans in `skip` mode (so counts and problems are complete) and writes nothing: `{ counts: { valid, problem_rows, problems }, problems, preview }`. Problems of rules and permissions arise only when runs are submitted; the job reports them.
- **Job.** `start` inserts a row of `import_jobs` (project migration 22: state, mode, replace, `rows_total`, `rows_done`, `imported`, capped `problems` with the exact `problem_count`, `outcome` accepted or refused, `error`) and answers `202 { job }` at once; the work runs after the response, one job at a time per process. `atomic` is one `submitBatch` (all or none, rules included, doorbell once after the commit), so `rows_done` jumps from 0 to the total at the commit; `skip` submits runs one by one, `IMPORT_BATCH` (100) per step, and the job yields to the event loop between steps (a step holds it about 70 ms, `bench/server-import`). A refused atomic import ends `done` with `outcome: refused` and the problems. A `queued` or `running` row that no live job in this process owns reads as `failed` (a restart), so no job runs forever. The file itself is not kept.
- **Constants** (`mapping.constants`, v3's "In Stufe importieren"): with constants a row is a run of `$import` (input `{ task, values, constants }`, actor kind `import` only). Core plans the creating task exactly as a normal run (form, then steps, defaults, process start, rules) and then writes each constant as a further observation of the new feature, so a constant wins over the task's own value, the stage included. Every constant goes through `valueRefusal` (`plan/values.ts`, shared with `$seed`): an unknown property, a system key (`$…`) or a value that does not fit is `invalid_input`. Without constants the rows stay plain runs of the creating task.
- **Replace** (`replace: true`, owner Q19, needs `mode: atomic`): the same `submitBatch` holds, first, one `$lifecycle` run per existing feature of the type that is not yet `deleted`, then the imported rows. `$lifecycle` (actor kind `system` or `import`, input `{ state }` from `LIFECYCLE_STATES`) writes the reserved key `$lifecycle` as the `lifecycle` then step does and is idempotent. Any refusal rolls the whole batch back and the old features stay as they were.
- The import actor holds every role of the config, so a task's role `when` lets an admin's file through. Admin and project scoping are as for the other `/api/admin/p/<project>/…` endpoints. A QGIS plug-in or an assistant can call the same endpoints (H6, H4): the dry run is the safe preview.

## Project ZIP: export and import (WP-384, S3-8)
The Projekte page's ⋮ menu exports a project and its import creates one. Code: `packages/server/src/io/archive` (format, `zip.ts`) and `packages/server/src/http/admin-export` (endpoints); wiring in `apps/web/src/lib/server/handlers/admin-export.ts`.
- **Endpoints** (behind `authorizeAdmin`): `GET /api/admin/p/<project>/export/zip` (the project ZIP), `…/export/csv` (`?type=<t>` one CSV of that Objektart; without it a ZIP with one CSV per Objektart, as v3's "Daten exportieren (CSV)"; `lifecycle=` as on the data page), `…/export/gpkg` (the GeoPackage of WP-111, one layer per Objektart or `?type=`). CSV and GeoPackage need a deployed config (`conflict` 409 otherwise); the ZIP of a never-deployed project holds the draft file and no data. `POST /api/admin/projects/import-zip[?name=]` takes the ZIP as the raw body (streamed to a temporary file, `ARCHIVE_LIMITS.maxBytes` 2 GiB, 413 above; the instance `UPLOAD_LIMIT` (default 50M) refuses a larger declared body first, so a big archive needs it raised) and answers `202 { job }`; `GET …/import-zip/<job>` answers `{ job: { state, done, total, key?, problems? } }` with the states of `IMPORT_JOB_STATES`. The job table is in this process: after a restart the job is unknown (404) and the page reads it as failed.
- **Format** (`archive/manifest.ts`, version 2; an importer refuses a newer one, a version 1 archive has no roster and imports as before): `manifest.json` (format `ueberblick-project-zip`, version, project key and name, `deployed`, features per Objektart, blob count and bytes), `project.yaml` (the effective file: deployed version, else the draft), `data/<type>.ndjson` (one line per feature: `{ id, lifecycle, properties }`, every lifecycle state), `blobs.ndjson` and `blobs/<sha256>` (stored, not compressed), and, since version 2, the roster: `roster/columns.json` and `roster/participants.ndjson` (see the next item). The ZIP codec is `archive/zip.ts` on `node:zlib` (streamed writer with data descriptors, central-directory reader with CRC check; no Zip64, so 4 GiB at most, `ZipTooLarge`).
- **Roster with login tokens (WP-432, A-046, owner A7).** The manifest's optional `roster` counts the participants and columns; `roster/participants.ndjson` has one line per participant (`id`, name, E-Mail, Telefon, roles, custom columns, `selfJoined`, `createdAt`, `disabledAt`, `hidden`, `login: { token, expiresAt } | null`). The token is the one the server stores (readable, C-002), so **the file is sensitive**: the menu item and the export toast say so. Admin accounts are not in it. Import (`archive/import-roster.ts`, `roster.ts`) reads and checks the roster before the project is created: a token twice in the file refuses everything with the typed problem `token_duplicate`; a token that exists on the instance (`Auth.tokensInUse`; the scope is the whole instance, not the project, so a copy of a project on the same instance collides on all) is not taken: that participant gets a fresh token (`Auth.replaceCredential` without a chosen token, expiry kept) and the job result carries `renewedTokens`. Then it writes through the roster's own functions (`importParticipant`, `setColumns`, `Auth.replaceCredential`), keeping the ids, so the old token signs in on the new instance. An archive without a roster creates no participants.
- **Why folded features, not the observation log.** A log can only enter through the runs that wrote it (R3), and replaying runs needs their tasks, rules and the config version of the time. The folded state re-imports through one `$seed` run per feature (`$lifecycle` runs for the non-active ones), keeps the feature ids and gives a project whose fold equals the original (`archive.spec.ts` compares features and edges). The history of runs and the audit metadata (created by, created at, last changed) are not carried: they belong to the source project. The actor is the `system` actor, because `$seed` allows only it.
- **Erasure (B-005).** Values an erasure blanked are empty in the fold and so absent from the export; a blob whose bytes an erasure deleted is skipped.
- **Import order.** Check the manifest and the file (compiles, every data entry names a type of it) before anything is created; create the project through `importProjectFile` (WP-383; `withOwnIdentity` publishes the file under its own template key `import_<hash>` when `key@version` exists with other content, so the same file never clashes and imports twice onto the same template); when the archive holds data, deploy the file (a run needs a config version) and put the blobs back (`BlobService.put`, hash checked); enter the features in batches of `ARCHIVE_BATCH` (200) through the project's one `Store`. A refused batch ends the job `failed` with the refusal and the feature id; the project it had begun stays and the job names its key (a project delete is step 5).
- **Zip-bomb defence.** Every number is in `ARCHIVE_LIMITS` (`archive/manifest.ts`): upload 2 GiB, all entries inflated 4 GiB, one entry 2 GiB, a text entry (`manifest.json`, `project.yaml`) 4 MiB, one NDJSON line 4 MiB. `openZip` refuses what the central directory declares over the entry or total cap; `read()` counts the inflated bytes as they come and stops at the entry's declared size (the header may lie), at the entry cap and at the total, which every read of the file adds to (blobs included); `text()` refuses an entry over the text cap before reading it; `lines()` refuses a line over its cap without a newline. A refusal is an `ArchiveLimitError` or `LineTooLong`, shown as a typed problem with a `code` of `ARCHIVE_PROBLEM_CODES`, which the dialog says in de and en.
- **Why these numbers.** CPU: inflate runs at about 300 MB/s on 1 vCPU, so the 4 GiB total cap costs about 15 s of CPU at most, and it is streamed, with no whole entry buffered. Disk: an import holds the upload's temp file (up to 2 GiB) and writes up to 4 GiB into blobs and the project database, so a bomb stopped at the cap cannot fill the disk of a small instance.
- **One ZIP writer (R1).** `io/archive/zip-writer.ts` (`createZipWriter`, `zipStream`) is the only writer in `packages/server`, with `node:zlib`'s CRC-32; the personal-data export (`export-subject/zip.ts`) is a thin layer over it that adds safe entry names and its own entry and size limits (`ZipLimitError`). `openZip` is the one reader.
- **Streaming (R14).** Export reads keyset pages of 500 rows (never an open iterator, so a run can commit between pages), deflates text entries and stores blobs as they are, and never holds more than a page; import reads one entry at a time. `bench/export`: see docs/12.

- **A file as a new type** (WP-390, S3-23, `packages/core/src/import`). The GeoJSON wizard reads the file in the browser: `surveyFeatureCollection` finds the geometry kinds and one column per property, `inferColumnType` gives each its type from the registry `IMPORT_COLUMN_TYPES` (text, long_text, number, integer, boolean, date, datetime; each names the property type it becomes), `importedType` builds the new type (geometry property `geometrie`, one property per column) and the task that creates it (`on: $none`, no `permissions`: no participant sees or creates it until the admin decides). The wizard writes both into the **draft** (`apply` of the sidebar's `TypeEditor`, two `add` ops, keys chosen against the draft's effective file), publishes it (the never-published flow of WP-364) and starts the ordinary import job with the mapping `importedType` returns, so data still arrives only as runs (R3). A GeoJSON without a `crs` member is WGS84 by RFC 7946 (`readGeoJson` reports `EPSG:4326`); a declared system the platform cannot reproject is still refused. Text columns get the file rewritten so that non-text values (numbers, booleans, nested objects) arrive as text (`stringifyForText`). H6: any other reader of features (GeoPackage, WFS) feeds the same functions.

**Failed ZIP import (WP-424).** `importArchive` removes the project it created when any later step fails (deploy, blob, row, zip limit, corrupt entry) through the admin's one delete path (`deleteProject`, dep `removeProject`); the failure result carries no `key`. A removal that throws is logged (`onCleanupError`) and the startup sweep finishes the files.

**Reserved project keys (WP-424).** `RESERVED_PROJECT_KEYS` (`tiles`, `packs`; core registry) are the names of directories shared by all projects under `blobs/`. `freeKey` never generates them (a project named "Tiles" gets `tiles_2`), `assertProjectKey` refuses them with `ReservedProjectKey`, and `removeProjectFiles` throws before it deletes anything for one. The key of a failed import is retired like any deleted project's and never reused.

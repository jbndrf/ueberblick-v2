# 07 · Sync and offline

The v3 dbperf work (`reference/`, branch `stage/dbperf`, `docs/dev/read-model.md` there) proved the model at 60k features. **Port the design, not the code.**

## Principles
- **The server is authoritative.** The device predicts with the same `core.plan`. No CRDTs.
- **Sessions slide.** A participant token is reusable on any device until revoked or expired. A participant session lasts 90 days and `authenticate` extends it on use, at most once per day, so a field worker who comes online once a quarter stays signed in. A disabled participant is refused on the next request.
- **Order = server `seq`.** Device clocks are metadata only (`client_time`).
- **The realtime channel is only a doorbell** (SSE: "something changed"). Data always comes from a pull.
- **Never lose field data.** A refused run stays visible, with its reason, and its input can be recovered.

## Pull protocol (versioned in `core/sync`)
- `GET /sync?since=<seq>&scope=<fingerprint>&v=<protocol>` (a snapshot continues with `&after=<cursor>&pin=<head>`).
- `since=0` means a snapshot, paged by feature. Otherwise it is a delta: features, edges and tombstones with `updated_seq > since`.
- Each snapshot page carries the **last 10 observations per (feature, property)**.
- The **scope** is the permission result for this participant, as a fingerprint. If it changes, the device re-snapshots. A later improvement is per-scope checkpoints, so only newly visible data loads. The access change also changes who the device is (WP-784): a pull that ends in `scope_changed`, or whose `header.access` differs from the last pull's (WP-793), rings `Device.onAccessCheck`; the map route then reads the bootstrap again (`startSession`, online) and `switchDevice` (`device-switch.ts`) applies a changed role set **in place** (WP-796; v3 followed its live `roles` collection the same way, `reference/src/routes/(participant)/map/+page.svelte:405`): the device keeps its database, queue, drafts and store, the roles are one reactive value (`roles-live.svelte.ts`) that `Device.actor`, `roleKey` and `participant` read, `Device.onRolesChange` rings, the change feed rings `ALL`, and the screen re-derives the role's tasks, tools, views and layers (`shell/role-controllers.svelte.ts`) without a remount, so open sheets stay open. A start for another participant or project still closes the device and opens the other's (WP-768). Runs already queued keep the roles of their time. A failing bootstrap is ignored and the old roles stand until the next sync.
- Rows are sent as **tuples** (column list once per page) in a **streamed gzip** response, with no ORM reflection. These are the dbperf lessons that took the snapshot from about 8 h down to about 18 s.

### Protocol fields (`packages/core/src/sync`, `SYNC_PROTOCOL_VERSION = 3`, a major number bumped only when a column, field or meaning is removed or changed)
- **Request** `SyncRequest {since, scope, v, after?, pin?, limit?, choosable?}`. `after` and `pin` are for snapshots only: `after` is the `cursor` of the last page received, `pin` the head the snapshot began at. The server answers as of the pin — a **filter on `seq ≤ pin`**, not a reconstruction of past state: rows changed after the pin are skipped here and arrive in the following delta — and every snapshot page carries it as `header.head`. When the last snapshot page is applied the device continues with a delta from `head`, so writes made during the snapshot arrive there (a replay is harmless). The protocol version is 3 since WP-316 (feature rows carry `version`, the header carries `versions`; 2 since WP-305: the `deleted` column became `lifecycle`; pre-release, no compatibility). A `v` other than the server's is a typed `version_mismatch` error, never a fallback (R11).
- **Page cap:** `SyncRequest.limit` (optional, positive integer) is the most feature rows the device wants per page. The server must honour it (WP-106); the device treats a page with more feature rows as `malformed`.
- **Page** `{v, header, features, edges, observations, tombstones, runs, people}`. `header = {kind, cursor, head, more, scopeFingerprint, versions}` (`access` is optional (WP-793): a hash of the actor's sorted role keys (plus any per-role setting that decides task availability), separate from `scopeFingerprint` so a role change never re-snapshots; the device's baseline is the `access` of the bootstrap answer (WP-798, same `accessOf`; `startSync` compares it with the first pull's `PullResult.access` and rings on a difference, so a role change between bootstrap and first pull is not missed); without a seed (offline start, older server) the first pull's value is the baseline, and it rings on a later different one; an older server omits it; `head` is the server head seq; a delta whose `head` is behind the device cursor means the server was reset and the device re-snapshots); `kind` is `snapshot` or `delta` (registry `SYNC_PAGE_KINDS`).
- **OGC writes use the same permission check (A-043, WP-402).** A participant (cookie or API token) writing through OGC Part 4 is planned as actor kind `participant` by core `plan`, so role, `when`, create and field-write permissions and rules are the app's own; the OGC handler holds no second check. A permission refusal is `403` with core's refusal path; see `docs/user/admin/how-to/connect-qgis.md`.
- **Sync per version (A-029, WP-316, protocol 3).** The server serves a **live set** of config versions: `{deployed} ∪ distinct features.pinned_version`, read per page by a loose scan of the partial index `features_pinned` (O(live versions) probes, never O(features)). `header.versions = {deployed, live}` (`SyncVersions`; `live` ascending, each once, always containing `deployed`) tells the device which versions to hold. Every feature row carries `version = coalesce(pinned_version, deployed)` (`SyncFeature`, wire column `version` after `type`). **Visibility** is the union over the live set of each version's own predicate, each guarded by `coalesce(sf.pinned_version, deployed) = v`: a feature is visible under the `visible_when` and permissions of **its own** version (`server/src/sync/live.ts`; the one `ConfigResolver` of `store/run/config-for.ts` resolves versions, `SyncService.versions` shares it with the OGC write check). **Readable properties** are cut per row version in rows, observations, relation edges and redaction tombstones, so a property readable in v1 and not in v2 is sent for a v1 row and redacted for a v2 row. **The fingerprint covers the live set:** with one live version it is that version's fingerprint (so with no pins nothing but the new fields differs), with several it hashes `version|fingerprint` per live version, so a change of the live set (first pin, last pin gone, a deploy that moves the deployed version) makes the device re-snapshot. The device side (WP-669): every page header goes to a `VersionsSink` (`config/sink.ts`): `follow(header.versions)` sets `deployed` and wants each live version (single-flight background fetch; one already stored and readable is not fetched again). After a **completed** pull the sink calls `ConfigVersions.retain(keepSet(live, queued runs))`, which drops every other version from memory and the store. `follow`, a fetch's commit and `retain` run one at a time inside `ConfigVersions` (one critical section); `retain` reads the queued runs' versions inside it, after the last `follow`, never drops a version the latest header names, and does nothing before the first header; a queued run keeps its version until it has left the queue, and a failed or offline pull prunes nothing. `ConfigVersions` and the run queue live on the main thread, so the worker host forwards the headers and the completed pull as the host message `versions` (host protocol 2) and the in-thread host calls the same sink directly: one decision function (`keepSet`, `config/keep.ts`), both hosts alike. Only the versions are touched, never the features. The planner (WP-319) and the participant reader (WP-675) resolve a feature through the one `createFeatureConfigs` (`config/resolver.ts`): `versions.get(feature.version ?? deployed)`, the deployed version standing for a create and, before the first header, the run's own or the bootstrap version. The stored feature's `version` is `FeatureState.version` (core `model.ts`), one type for the sync row, the store and the predictor. A feature whose version is not on the device yet (`'refetching'`) is shown read-only with no tasks (`Reader.awaitingVersion`), as the run queue holds a run as `awaiting_config`; the sheet re-reads when the version arrives. Resolving is one map lookup per open. Bench `bench/sync/sync-versions.bench.ts`: snapshot, empty delta and a 100-row delta at 60k features with 1 and 3 live versions.
- **Tables** are `{columns, rows}`: the column list once, then tuples. `SYNC_COLUMNS` lists the known columns. **Compatibility rule:** `decodePage` maps by column name and ignores unknown extra columns, so additive server changes never break an offline device within a protocol major. A missing known column is a typed `missing_column` error.
- **Rows:** features `id,type,version,properties,lifecycle,createdBy,createdAt,changedAt,updatedSeq` (the three audit fields are strings or null, docs/04; a stale peer without them fails with `missing_column`; `lifecycle` is `active` or `completed`; an archived or deleted feature is never a row: it leaves the device as a `feature` tombstone); edges `from,relation,to,derived,updatedSeq`; observations `featureId,property,result,phenomenonTime,seq,runId` plus the additive column `resultTime` (null when absent; an older peer without it reads as null, WP-794) (at most `SYNC_OBSERVATION_HISTORY` = 10 per feature and property per page; `encodePage` and `decodePage` throw `history_exceeded` otherwise); tombstones `seq,kind,id` (`SYNC_TOMBSTONE_KINDS`: `feature`, `edge`, `redaction`, `blob`).
- **Audit times are always set (WP-724).** The server's run intake (`Store.submit` / `submitBatch`, `server/src/store/run/transaction.ts`) fills a missing `clientTime` with the server clock's time before planning, so `createdAt` and `changedAt` exist for runs from every source (device, admin, OGC, import, rule runs caused by such a run). A client-supplied `clientTime` is kept as the work time (`phenomenonTime`), except that a participant run's is clamped to `[receivedAt - 366 days, receivedAt + 5 min]` (WP-762); imports, migration, admin and system runs keep their times. The `runs.clientTime` column therefore holds the (clamped) client time, or the server's receive time when the client sent none. **The audit times are not these** (WP-794, owner M8 = b): the intake stamps every observation with `resultTime` (the receive time; an import run keeps its historical time) and `createdAt` / `changedAt` read it, as v3's server created / updated.
- **Creation on the device (WP-721):** the device never gets `$type` or other `$`-observations; the creation of a feature is known from `createdAt` / `createdBy` of its row. `createdAt` is the `resultTime` of the creating run (the server receive time); a not yet synced create shows its device time (`phenomenonTime`) until the sync replaces it, as v3 did. Aktivität shows v3's "Erstellt" entry from these two fields.
- **Runs and people (WP-601).** `runs` `id,task,actor,clientTime,receivedAt,seq,causedBy` (`SyncRun`; times are epoch ms, `clientTime` and `causedBy` may be null): one row per run that has an observation on the page, so a delta resends a run only with the observations it resends and a run whose observations are all clipped is never shipped. `people` `id,name[,choosable]` (`SyncPerson`) names the actor ids that appear in `runs`; the optional column `choosable` (additive, WP-725; a table without it means "no choosable information", never an error) marks a participant the receiver may choose for a participant property (`select.all`, `docs/05`): all enabled participants, name only (empty when unnamed), sent only to a caller whose role is in some `select.all`. **Sent only when changed:** the device sends `choosable=<hash>` with every pull, the `choosableHash` of the set it holds (`''` for none; order-free, over id and name). The server computes the hash of the current set (one scan of `participants`, hundreds of rows, only for such callers) and, when it differs, adds `header.choosable=<hash>` and the whole list as `people` rows with `choosable` on that page (any page type, an empty delta included). The list REPLACES the device's set, so a removed participant leaves it (an empty list with `header.choosable=''` clears it); a page without `header.choosable` leaves the set alone. The device keeps the set in its meta store and offers it through `store.choosableParticipants()`. The scope fingerprint covers only whether the caller may choose anyone, so participants joining or leaving cause no re-snapshot. **Clipping:** `actor` is the participant id when one of the receiver's roles has `roles.<r>.app.activity_names` (default true) or the run is the receiver's own, else null; no `people` row is sent for a null actor. The feature row's `createdBy` is clipped by the same rule (WP-762: kept for the receiver's own features, null for others when names are off). The scope fingerprint includes the setting (`server/src/sync/runs.ts`), so a change re-snapshots. `SyncPage.runs`/`people` are required in the object form (empty when the page has none). Additive: no protocol bump.
- **Tombstone `edge`:** `id` is the edge key (`from`, `relation`, `to` joined by NUL; core `edgeKey`). The server writes it in the run transaction when an edge is removed. A page applies its tombstones **before** its edge rows: an edge that was removed and put again keeps its old tombstone, and the put carries the higher `updatedSeq`.
- **Tombstone `redaction`:** one personal property of a feature was blanked; `id` is `<featureId>#<property>` (one tombstone per property) and the same page carries the feature row, which the device applies (the feature stays). The device also drops the cached history of that property, before it applies the page.
- **Tombstone `blob`:** a blob was purged; `id` is its sha256 and the device drops its cached bytes.
- **Codec** `encodePage` / `decodePage` is pure. Compression and HTTP belong to the adapters. Geometry is a normal property value and keeps its Z. Telemetry is not part of this protocol.
- **Scope** `scopeFingerprint(inputs)` is a 128-bit non-cryptographic hash over the sorted inputs; it detects change only.
- **Page cap and decode:** the device asks for at most `SYNC_PAGE_MAX_ROWS` (1,000) feature rows per page, and decodes each page in a worker (`packages/client/src/sync/decode.ts`), so no main-thread task in a sync exceeds 100 ms.
- Benchmark `bench/sync-codec`: a 1,000-feature page (3 observations each, with its `runs` and `people` tables) parses and decodes in about 11 ms.

## Server endpoint (`packages/server/src/sync`, `http/sync`, WP-106)
- **Routes** (mounted in `apps/web/src/routes/api/p/[project]/sync`, route files only): `GET /api/p/<project>/sync?since&scope&v[&after&pin&limit]` answers **one page** per request as tuples in a streamed gzip body (plain JSON without `Accept-Encoding: gzip`); `GET /api/p/<project>/sync/events` is the SSE doorbell. Callers: a participant of that project, or an admin with a role in it (401 / 403 / 404 otherwise). A wrong `v` is `409 {code: version_mismatch}`, a malformed query `400 {code: malformed}`, no deployed config `409 {code: no_config}`.
- **Session participant (WP-768).** The device database is per participant, but the session cookie is shared by every tab of the browser, so a second sign-in turns an open tab's session to another person. The device sends `X-Ub-Participant: <id>` (core `SESSION_PARTICIPANT_HEADER`) on every participant API request (`/api/p/<project>/…`: runs, sync, files (`/blobs`, PUT, GET and HEAD), packs, preferences and tool data; the device has one guarded `fetch`, `Device.fetch`, and no allow-list of paths), as the participant it works as. Every handler that authorises through `authorizeProject` (`http/shared/access.ts`) compares it with the session's participant before it reads a body, a page or a file: on a difference it stores and sends nothing and answers `409 {v, code: "session_changed"}` (core `SESSION_CHANGED_CODE`). The replies of runs, sync, file uploads and preferences name the session's participant in the same header (cacheable replies, files and packs, do not: a cached reply would name an earlier session; the request check covers them). A request without the header (an API token, QGIS) is not checked, and neither is a browser-made `<img>` or map-tile request, which cannot send it (it reads with the cookie's person only); the SSE doorbell carries no header and no data. The device (`apps/web/src/lib/participant/session-guard.ts`, in the page and in the sync worker) judges each reply by it: a reply naming another participant is not used, the guard sends nothing more, and it posts `session-changed` on a BroadcastChannel (`session-channel.ts`; the login exchange posts it too). Every `/map` tab hears it and bootstraps again: the same participant keeps the open device, another one replaces it (`switchDevice`), no session goes to `/login`. Queued runs of the previous participant stay in that participant's own database and go out when that person signs in again.
- **Run replies (WP-144).** `POST /api/p/<project>/runs` and `.../runs/batch` share the one `SYNC_PROTOCOL_VERSION`: every reply, accepted, refused, review and every error envelope, carries a top-level `v` (built in one wrapper, `packages/server/src/http/runs/handlers.ts`). The device queue refuses a reply whose `v` is missing or different (R11).
- **Blobs over HTTP (WP-604).** A file value is a list of `{sha256, name, mime}` entries; the bytes of each go first: `PUT /api/p/<project>/blobs/<sha256>` (body = bytes, `Content-Type` = mime; 201 whether new or already stored (the body is always hashed; the caller becomes an uploader, `blob_uploads`, WP-757), 409 the bytes do not hash to the path, 413 over `DEFAULT_BLOB_LIMITS.maxUploadBytes` (50 MiB, `http/shared/contract.ts`; the runtime may override it), 401/403), `HEAD` (200 only for a file the caller uploaded or may download, else 404, for resuming), then the run references the shas. The server stores the bytes under `<dataDir>/blobs/<project>`, streaming, and refuses a run whose file value names a sha it does not hold (`blob_missing`, raised by the run store), and a participant run naming a sha the actor did not upload, never named in an earlier accepted run, not already on the run's feature and that the actor may not already read (`not_permitted`, WP-774). `GET` (`Cache-Control: private, no-cache` so the browser revalidates each time and an erased or out-of-scope photo is not kept (WP-770; the 304 is answered after authorisation), `ETag` = sha, `nosniff`) answers 404 when the bytes are absent or the caller may not see them. `GET ?thumb=<size>` (a size of the core registry `THUMB_SIZES`) answers the WebP the server made once for that size and caches next to the blob (`ETag` = `"<sha>-<size>"`, 304 on an exact `If-None-Match` match, checked after authorisation; 404 for an unknown size or a non-image; an image that cannot be made into a thumbnail is a 500, and the app shows the original blob); authorisation is the original's. Allowed: an admin of the project; the actor of a run that named the sha (own submissions stay viewable); a participant whose sync scope sees a feature whose readable property still holds the sha; every participant of the project for a blob the deployed config names (`branding.icon`, A-036, `configBlobs` in `http/blobs/access.ts`). Authorisation reads `blob_refs(sha256, feature_id, property, run_id)` (project migration 13), written in the run transaction; erasure deletes the rows with the values.
- **Scope.** One SQL predicate (`SyncService.visible(actor, alias)`, the OR over types of `perms.seeSql`) clips features, edges and tombstones; properties are cut to `readable(subjects)` in feature rows **and** observations (per-property `see`). Reserved observations (`$type`, `$lifecycle`, `$created_by`) are never sent. The **fingerprint** hashes each type's row filter (at a fixed instant) and readable properties for this actor, so it changes when access changes and not on an unrelated deploy. A request whose `scope` differs gets an empty page of the same kind carrying the new fingerprint: the device re-snapshots.
- **Snapshot** (`since=0`): live features by `updated_seq` (index `features_by_seq`), `limit` per page (default and cap 1,000), last 10 observations per (feature, property) up to the pin, and the edges of the page's features whose other end is visible.
- **Delta**: a window of whole features (`updated_seq > since`, up to `limit`); `cursor` is the last one, or the head when the window is complete. A visible feature is a row (served states only; one that became archived or deleted is a tombstone) with the last 10 observations per property and **all** its visible edges, so a feature that joins the scope arrives complete. Edge tombstones pass when the participant sees both ends, redaction tombstones when they see the feature and may read the property, blob tombstones always.
- **Leaving the scope, with no per-participant work per run.** A run only advances `features.updated_seq`. At pull time a changed feature that is not visible now gets a `feature` tombstone if it was visible in **any committed state** of its history (`sync/ever-visible.ts`): a delta is paged by feature, so `since` cannot say what the device still holds of a feature waiting for its page. A feature that was never visible produces nothing. The cost is the history of the changed, currently invisible feature, paid by the puller. Limits: a relation-based `visible_when` takes the feature's own properties and references from its history but reads the related features (and inverse relations) as they are now, so the replay can say "was visible" once for a feature the device never held: the delta then carries an id-only tombstone, which the device applies as a no-op (A-015, pinned by `sync/ever-visible.spec.ts`). A `visible_when` on `now` cannot flip without a run, so nothing is sent for it.
- **A run waiting for its pull (WP-865).** An accepted run stays in the queue (`accepted`, `QueueStatus.awaitingPull`) until a pull covers its seq. `startSync` pulls once whenever `awaitingPull` grows, so the entry stops waiting even when the device started offline and has no doorbell stream yet.
- **Doorbell.** A message is `event: seq` with `{from, to, head}` (a seq range and the head; no data, no telemetry: H5), `event: hello` with the head on connect, and a `: heartbeat` comment every 25 s. `withDoorbell(store, bell)` rings after a run committed; while someone listens, a head check every 2 s covers writers in another process. The runtime wires it once: `projectStoresFor(runtime())` wraps each project's store with `withDoorbell(store, runtime.doorbell(key))`, so the run endpoints and the timers loop ring the same bell that `sync/events` listens on (`runtime.services.doorbell(key)`). A deploy rings it once after its commit (`ProjectServices.afterDeploy`), a `move` deploy included, because the config devices see changed; the pin runs written inside the deploy transaction never ring. A stream whose request is already aborted subscribes to nothing, and a cancelled page download destroys its source (`stream.pipeline`).
- **Tool streams (B-020, WP-682).** A tool with its own data keeps a message stream on the server, outside the run sync: `GET /api/p/<project>/tools/<tool>?after=<seq>&limit=<n>` pages it by server `seq` (default 200, at most 500; the answer is `{ messages, head, read, members }`; `members` is `[{ id, name }]`, names only: every participant, not hidden or disabled, whose role has the tool (the rule above), in name order, a person without a name by id: the chat's person picker as v3's `mentionable-participants` listed it), `POST /api/p/<project>/tools/<tool>` `{ id, body }` appends one message (idempotent by the client `id`: 201 when new, 200 for a replay, 409 when another person used the id; body 1 to 4000 characters), and `POST …/tools/<tool>/read` `{ last_read_seq, last_mention_seq? }` advances the person's read marks (they only grow and never pass the head). Only a participant whose role has the tool `offered` or `active` in the deployed config may call them (the project declares `tools.<key>`; a role without `app.tools` has the project's tools, active: core's `toolAvailabilityFor`, the rule the device shell uses too); a live preview works like a project; everyone else, an unknown tool and a project without a deployed config get 404, like a pack file. A malformed query or body is 400 (`invalid_query`, `invalid_body`). **Erasure re-delivers:** a message that erasure changes gets a new `seq` above the head, and one whose author was erased arrives once as `{ removed: true, body: null, author: null }`; devices upsert by `id`. **Tool bell:** the runtime owns one (`services.toolBell`); after an accepted new message `ring(project, tool)` is called; the SSE doorbell writes it as `event: tool` with `{"tool":"<key>"}` and no other data (H5), and the device answers with a pull of `tools/<tool>?after=`. Server-side, `chat` is the first stream tool (`STREAM_TOOLS`).
- **Indexes.** `features_by_seq` and `edges_by_seq` come from project migration 4 (`sync_indexes`); the service creates nothing.
- Benchmark `bench/server-sync` (60k features): snapshot in about 14 s over 60 pages with flat heap after gc, empty delta p95 about 3 ms, viewport query with the predicate p95 under 1 ms, a reassignment reaches both devices in under 20 ms.

## Run queue (device)
- A run gets a UUIDv7 and records `config_version`. It is stored in IndexedDB before anything else happens.
- Runs are sent **sequentially per device**. The server **ledger** returns the stored result for a repeated ID.
- **Only a typed refusal refuses** (the run endpoint envelope on its own status); timeouts, 5xx (a transaction hook that throws, e.g. timers, is a rolled-back 500 logged `hook_timers`, B-029; a busy database is a 503), offline and unknown 404 are transient (capped backoff), a 401 pauses the queue, and a reply that names another protocol version holds it (`incompatible_protocol`: no retry, no run lost, update the app). The submit answer carries `created` (per run id, the ids of the features the run's local plan created; they are `seededIds(run.id)`, so a rebase, a re-plan and the server's own plan give the same ones, WP-748) and `RunQueue.createdBy(runId)` answers the same later: a form opens the new feature after a create without a map position (`on: $none`) from it (WP-681). Implementation and API: `packages/client/README.md` "Run queue".
- **Files go first (WP-605).** A run's file values are bytes held in IndexedDB with the run, together with their MIME type, so they survive a reload and offline. Before the queue sends a run (or an atomic batch) it uploads each file whose bytes are on the device with `PUT /api/p/<project>/blobs/<sha256>` (idempotent, so no `HEAD` probe first: its 404 would be a browser console error on every new photo; WP-785; the body is the bytes, `Content-Type` the MIME type), one file at a time, then sends the run: a run never references bytes the server lacks. Each file that was PUT is remembered on its stored run row (`uploaded`, optional and additive, WP-803), so a retry after a later failure (the next file, or the send itself) does not send those bytes again; a file the server later lost is covered by the run's refusal (`blob_missing`) and a resubmit, which is a new row. A network error or 5xx is transient (the run is not sent, capped backoff). 409 (hash mismatch, `blob_mismatch`) and 413 (over the limit, `blob_too_large`) refuse the run locally like a server refusal, and the bytes stay for editing and resubmitting. A file whose bytes (or mime) are no longer on the device is looked up with `HEAD`; if the server holds it the run proceeds, otherwise the run is refused the same way (`blob_lost`).
- **Discard (WP-627).** A participant can discard a run that was never sent (v3 `discardTaskRun`, no confirmation): `queue.discard(runId)` takes `refused`, `review` and `queued` runs. A run being sent (`QueueStatus.sending`, or any run of its batch) is refused with `not_discardable`; the UI disables the button until the send settles. Discarding drops the run and its batch, their predictions and their parked bytes (a file another run still references stays), then re-plans the later waiting runs, which may be refused locally if they built on the dropped one. Nothing reaches the server.
- **On refusal:** drop that prediction, **rebase** the remaining runs by re-planning each against the new state, and refuse only those that now fail. Keep refused input as a recoverable draft.
- **Config versions on the device** arrive as `CompiledConfigData` (A-005 item 2) and are hydrated without the compiler. If the device holds queued runs against a version whose `format` its core cannot read (after an app update), it refetches that version from the server, which recompiles it on demand; until then those runs stay queued and visible (`ConfigVersions.get` answers `'refetching'`, see `packages/client/README.md`).
- An **app update never clears the queue.** A run is validated under the **feature's** version (A-029 L1): a run planned on a device under another version than the feature's is replanned under the feature's version (`planFor` with `configFor`, stamped with that version); a refusal of that replan goes to review like any server refusal. `Run.configVersion` stays "what the device planned with". Only a feature without a pin (floating) is judged under the deployed version. The device plans the same way: its planner resolves each feature to the version the sync sent with it (a create to the deployed one), and a run whose version is not on the device yet is not previewed until it arrives. If the version a run needs is gone, the run goes to a review state and is never dropped silently.

## Rules offline
- Automatic actions triggered by events (`after`, `change`, or an edge on `when`, docs/05) are **predicted on the device** by core, just like runs.
- Rules triggered by time (`elapsed`, `schedule`) are **server-only**, driven by `timers` and the timers loop (docs/03 "Server runtime wiring"). A due row fires at the first tick at or after its time (default beat 30 s), and the run it makes reaches devices through the doorbell and a pull like any other. **Limit:** a row is rescheduled when its feature is created or restored, or a property its expressions read changes on that feature. A change to a *related* feature, or to `inputs.*`, does not reschedule until the feature is touched or the next deploy (`rebuild`).

## Device storage
- IndexedDB stores: features, edges, history (capped), runMeta, people, runs, blobs, predictions, meta, configVersions. Packs go in OPFS. `runMeta` (the run rows of WP-601) and `people` (names) are cache stores written in the same transaction as the page and dropped by `clearCache`. A run row lives only while a history row names its run (index `history.runId`, schema step 3): trims, feature tombstones and `dropHistory` release the rows they leave unreferenced, so nothing leaks over time.
- **Last sync (WP-678):** the `meta` store key `lastSynced` holds the instant the last pull completed (`SyncMeta.writeLastSynced`, clock port). `SyncEngine.restore()` loads it into `SyncStatus.lastSyncedAt` at host start, so a cold start does not say "never synced". Only a completed pull sets it; a snapshot restart (cache cleared) forgets it.
- **Several tabs:** one tab per device database pulls. It holds the Web Lock `ueberblick-sync:<db>` and runs the sync worker; the other tabs keep only a read replica, fed by the holder's change notices over a `BroadcastChannel`, and forward their doorbell to it. When the holder closes, the next tab takes the lock and resumes from the stored cursor (`packages/client/README.md`). The takeover runs in order: lock granted, replica checked against the stored cursor (re-read if the database moved), worker started, `holder` announced. A pull made in that window (the tab's own, or a follower's doorbell) waits for the worker start and then runs once; pulls in the window share that one worker pull, and none is refused or dropped. While the replica re-reads the database, `pageInFlight()` stays true until the cursor is restored, so no reader sees features without their cursor.
- Features, edges and blob keys are held in memory (hydrated at open) behind the synchronous `Facts`/`Blobs` ports; history loads on demand (`warmHistory`); `warmActivity(feature)` also loads its run rows (a bounded memory cache of 20,000; names are all in memory) and the queued runs of the device are mirrored in memory, so the reader's `activityOf(feature)` stays synchronous: one `ActivityEntry` per run (task label, actor name or the neutral label when the actor is null, time, changed values, status `accepted`, `pending` or `refused`), newest first, the device's own queued and refused runs on top and no duplicate once the sync delivers the run. A pending run's values are its input entries that are properties of the feature's type; values a rule writes appear once the server accepted the run. Details: `packages/client/README.md`. Predicted states come from `core.fold`. Clustering runs in a worker (Supercluster).
- **iOS:** browser tabs lose storage after 7 days of Safari use without visiting the site, while installed PWAs are exempt. Detect `display-mode: standalone`, and push installation during onboarding. Show "N runs not sent, data at risk" and offer a queue export. There is **no Background Sync on iOS**, so sync on open, `online` and `visibilitychange`.

## Offline packs on the device (WP-662, contract A-032)
- `packages/client/src/packs`: `createPackManager({ storage, transport })`. `refresh()` fetches `GET /api/p/<project>/packs`, deletes packs that left the manifest and marks the rest `ready` or `absent`; `download(keys)` fetches only changed layers (a layer with an equal `sha256` stays where it is, even when the pack `hash` changed); `sync()` does both. Files are `<hash>/<layer>.pmtiles` in OPFS plus `index.json`, all inside `packs/p-<project>/u-<participant>/` (WP-773: `deviceOpfsStorage(navigator, { project, participant }, writer?)`), so the index, the cleanup of files the manifest does not list and every read stay inside one project and person; `clearPackScope(navigator, scope)` deletes that directory (Abmelden calls it from `wipeParticipantDevice` via its `clearPacks` port, WP-782; a failure is logged and swallowed) (pack key to hash, layers, pending downloads). Old files are removed only after the new version is ready.
- Downloads resume by HTTP Range from the size of the partial file (a server that answers 200 restarts from 0), stream into the store in chunks, and are verified with an incremental SHA-256 (`sha256.ts`) read back in 1 MB chunks. A mismatch fails the pack with the reason `sha256 mismatch: <layer>` and keeps the old version.
- The progress signal is `manager.progress`, a Svelte-store-compatible `{ get, subscribe }` over `Record<packKey, { state: absent|queued|downloading|ready|failed, bytes_done, bytes_total, reason? }>`. `manager.counts()` returns bytes, tiles, layers and `built_at` per pack plus totals (the tile count is the manifest's `tiles`). `manager.remove(keys)` deletes packs and their files (a pack the server still lists becomes `absent`); `manager.hasLayer(layer)` answers synchronously from the ready packs after `load()`.
- The manifest types and `decodePackManifest` live in `@ueberblick/core` (`sync/packs.ts`), so the server's builder and the device share them; `fetchPackTransport` decodes with it and a bad manifest fails `refresh()` with the field path.
- Safari has no OPFS `createWritable` on the main thread: `deviceOpfsStorage(navigator, scope, writer)` takes a `PackFileWriter` (`workerPackWriter`) that posts writes to a small dedicated worker (`serveWriter(self, scopedPackRoot(root, scope))`, sync access handle; the app passes the scope in the worker name, a query string, because a worker URL that is not a plain literal is not bundled and so not precached). `PackStorage` is unchanged; the manager and the map protocol stay on the main thread.
- No OPFS (`deviceOpfsStorage` returns `supported: false`): `refresh()` answers `{ ok: false, reason: 'not supported' }`, no pack files are listed and the map reads the network.
- **Pack file (WP-668, B-017, v3's `.ubpack`).** One module, `packages/client/src/packs/bundle.ts`: `"UBPK" | u32le manifestLength | manifest JSON | layer 0 | layer 1 | ...`. The manifest is `{ version: 1, pack: <A-032 PackManifestEntry>, layers: [{ layer, offset, length }] }`, offsets from the end of the manifest. `manager.packFile(key)` answers `{ filename, blob }`: a header plus the stored layer files as a lazy Blob (OPFS `getFile().slice()`), never read into memory, so the app can hand it to the browser as a download. `manager.importPack(chunks, onProgress)` reads a byte stream (a `File` stream), writes each layer to `<hash>/<layer>.pmtiles` through `PackStorage.open` (the Safari writer worker included) and checks its sha256 incrementally; then the index and `progress` say `ready`, so the map uses it at once (`onReadyPacksChange`) and the next `refresh()` sees the same hash and downloads nothing. It refuses, with a `kind` from the registry `PACK_REFUSALS` (`packs/refusals.ts`: not_a_pack, truncated, trailing_bytes, sha256_mismatch, wrong_project, unsupported_version, bad_manifest, unsafe_name, not_supported, write_failed; `ImportResult` and `PackFileError` carry it, the detail string is for logs only and the Offline tab shows one translated sentence per kind, `participant_offline_packages_refusal_<kind>`) and no files left, a file that is not a pack, is truncated, has bytes after the last layer, fails a layer's sha256, carries a name that could leave the pack directory, or (once the device has seen a manifest) names a pack the project does not list; the previous pack stays. A pack the device already holds is not read again. The same file can be served by the server later or opened by external GIS tools (each layer is a plain PMTiles archive at a known offset), so the format is not device-private (H6).
- Map side: `packages/ui/src/map/maplibre/packs.ts`, protocol `ubtile://<layer>/{z}/{x}/{y}`: the pack (PMTiles over range reads, `pmtiles` library), then the network (template from `registerTemplate`, which is the layer's tile-proxy URL, A-033, never the provider), then overzoom from the layer's own `max_zoom` (raster only; vector sources use MapLibre's `maxzoom`); a tile none of them has (offline, outside every pack) is an empty tile (transparent png, or empty bytes for a vector pack), never a throw, so panning past the pack logs no console error (WP-863). It registers through the `addProtocol` seam of `renderer-basemaps.ts`; the renderer's `packProtocol` option turns it on, and `basemaps.ts` then draws `xyz`, `preset` and (with a proxy) `pmtiles` layers that have a pack through `ubtile://<layer>/{z}/{x}/{y}`. **Tiles through the proxy (WP-689, A-033):** the one rewrite is in `basemapSpecs(config, selection, packs?, proxy?)` with `proxy = { project, origin }` (the participant map takes `device.project` and `location.origin`; the admin previews pass the project with an empty origin). Every layer whose source type is `proxied` draws from `<origin>/api/p/<project>/tiles/<layer>/{z}/{x}/{y}` (xyz, preset, and a remote pmtiles archive, as `raster` or, with `tile_type: vector`, `vector`) or `<origin>/api/p/<project>/wms/<layer>?bbox={bbox-epsg-3857}&width=256&height=256&crs=EPSG:3857` (wms), so no tile request leaves the origin. `geojson`, a self-hosted path (`isSameOriginPath`) and a same-origin `.pmtiles` file stay direct. `PACK_STATES` and `PACK_TILE_TYPES` are in `core/registry/packs.ts`.
- **Offline-Bilder (WP-667, `packages/client/src/blobs`, `apps/web/src/lib/participant/offline/images.ts`).** The run queue's IndexedDB `blobs` store is irreplaceable queue data (the device's own uploads, keyed by the original's sha256, written with a run, purged with it), so thumbnails do not go there. They live in a database of their own per project and person (`idbThumbCache`, rows `{ sha256, bytes, mime }`; a `ThumbCache` port with a memory fake for specs), rebuildable from the server and dropped as a whole when the switch goes off (v3 `deleteDownloadedFiles`). One size is kept, the registry's `preview` (800 px wide, v3 `?thumb=800x0f`); the list size draws from it. `downloadThumbs` fetches `GET /api/p/<project>/blobs/<sha>?thumb=preview` (3 at a time, skips what is stored, one failure costs that photo only, stops at 256 MiB or on abort). The photos in scope are the images in file values of the features on the device (`scanPhotos`, in slices of 500 features with a macrotask between, so no long task). The switch is the personal preference `ui.offline_images` (docs/04), so it follows the person: a new device starts with it on and fills the cache at start, and a change from another device is followed. It fills at the start, when a sync ends with other features and when the connection returns; offline nothing is fetched. `photo-url.ts` reads, in this order: bytes the photo tool holds, bytes queued with a run, the kept thumbnail, the server URL (`original(sha)` is the full blob, which `GalleryImage` shows when a thumbnail does not load; if that fails too, a placeholder); a photo the device still holds unsent is always shown from those bytes (a `blob:` URL) and never asked from the server: the resolver builds a server URL only when the device holds nothing (WP-720; the only request for an unsent file is the queue's own `PUT`; `HEAD` only when the device lost the bytes); the device shows only what it holds, so offline with the switch off an image is empty. The Offline tab's Dateien cell is `ThumbCache.count()`.
- App wiring (WP-650): `MapScreen` builds the manager, waits for `load()` before the map mounts and passes `createPackProtocol` as the renderer's `packProtocol` (`createRendererMap(extra, { packProtocol })`). A pack is used at once when it turns ready or is deleted: `onReadyPacksChange` rings and `MapCanvas` (`onPacksChange`) applies the basemaps again.

## Offline packs on the server (WP-351, contract A-032 items 3 and 4)
The manifest and the files are **not** part of the run or feature sync: no seq, no tombstones, no doorbell. A device asks for them when the settings tab opens or on its own schedule.
- **Manifest:** `GET /api/p/<project>/packs` (participant auth) returns `{ "packs": [ { key, label, hash, bounds, min_zoom, max_zoom, layers: [ { layer, tile_type, url, bytes, sha256, max_zoom, tiles } ], bytes, built_at } ] }`. A pack is listed when the deployed config has it, every one of its layers is `ready`, its `roles` is absent or matches the caller's, and at least one layer is visible to them (`packsForRoles`); it lists only the layers they see. `label` is resolved for `Accept-Language`, `bytes` is the sum of the listed layers, `built_at` the newest layer build, `tile_type` comes from the layer's source (`PACK_TILE_TYPES`). `Cache-Control: private, no-cache` and an `ETag` over the body: send `If-None-Match` and get `304`.
- **One contract:** `buildManifest` returns core's `PackManifest` (`packages/core/src/sync/packs.ts`); `decodePackManifest` is the shared check, and `manifest-contract.spec.ts` runs the real handler response through it.
- **How the device diffs:** a pack whose `hash` equals the stored one needs nothing. Otherwise it compares each layer's `sha256` with the stored file and downloads only the layers that changed (`packages/client/src/packs`). New fields in the manifest need no protocol bump: the `hash` versions the content, and the device ignores fields it does not know.
- **Download:** `GET /api/p/<project>/packs/<hash>/<layer>.pmtiles`: the same audience; a hash or layer the caller may not see, an unknown one and one that is not `ready` answer `404` (never `403`). Only hashes of the deployed config or of a version a feature still pins are served. `Range: bytes=a-b`, `a-` and `-n` answer `206` with `Content-Range`, a range past the end `416`, several ranges the whole file (`200`). `ETag` is the layer's `sha256` (`If-None-Match` gives `304`, `If-Range` is honoured), `Cache-Control: private, immutable`, `Accept-Ranges: bytes`. The file streams from disk. It is a plain static-file contract, so a CDN or another host can serve it later.

## Service worker and install (WP-631)
`apps/web/src/service-worker.ts` (SvelteKit's native worker, no dependency; routing in `src/service-worker/`) gives the participant app its offline cold start.
- **Install** caches the build and static files (`$service-worker` `build` + `files`), the **worker bundles** and the two page shells `/map` and `/login` (the app is `ssr = false`, so each page is a shell that starts the client; the nonce CSP header is cached with its page, so the pair stays valid offline). The cache is named `ub-shell-<build version>`; `activate` deletes every other `ub-shell-*` cache.
- **Worker bundles (WP-717).** SvelteKit's `build` list leaves out the Vite worker bundles (`_app/immutable/workers/`: sync, photo/pack writer, cluster) and MapLibre's worker (`_app/immutable/maplibre-gl-<version>/`). Without the sync worker an offline start never finished. `workerAssetsPlugin` (`service-worker/worker-assets.ts`) lists those folders from the client build output into `_app/worker-assets.json`; the install fetches it and caches every file (`precacheList` merges it with `build` and `files`: one list, no hand-typed hashed names). Everything under `/_app/immutable/` is answered cache-first. Proven by `e2e/participant/offline-start.spec.ts` (reload and a new page offline show the map).
- **A start never hangs.** Opening the sync host has a 15 s limit (`HOST_OPEN_TIMEOUT_MS`, `start-sync.ts`): a worker that does not answer ends the start with the load error and a retry button (`map/+page.svelte`), and the worker is terminated.
- **Fetch.** Shells and precached files are **cache-first**: a start never waits for the network (v3 waited up to 10 s, B6). A served shell is refetched in the background and replaces the cached one (stale-while-revalidate, WP-957), because its CSP header carries the map origins of the deployed configs: a layer host deployed after the install is allowed from the next start online (offline keeps the cached shell). Then the app syncs from IndexedDB and the server. `/api/**` and `/participant-api/**` (sync, auth, bootstrap, blobs), other origins (tile hosts), non-GET requests and every other page are not answered by the worker, so nothing from them is ever cached. A navigation to `/` falls back to a redirect to `/map` when the network fails.
- **Redirected shells (WP-853).** A shell is stored only when the answer is direct and `ok` (`storableShell`): signed out, the server redirects `/map` to `/login`, and a redirected response cannot answer a navigation (`net::ERR_FAILED`). A cached shell that is `redirected` (also one an older build stored) is ignored: the network answers and the background refresh replaces it once a sign-in makes `/map` answer directly, so the offline start works again after a new sign-in. Proven by `service-worker/handler.spec.ts` and `e2e/participant/signout-cache.spec.ts`. Sign-out data clearing is unchanged.
- **Update.** A new build is a new worker: it installs its own cache, `skipWaiting`s and claims the page. The inline script in `app.html` reloads the page on `controllerchange` unless this was the first install (nothing outdated) or a `<form>` is open (it asks again every 5 s; drafts are kept anyway). Proven by `service-worker/update.spec.ts`, which runs that script against fakes.
- **Manifest** `static/manifest.webmanifest`: name and short name "Überblick", `start_url` `/map`, scope `/`, standalone, portrait-primary, the four icons of v3 (192 and 512, any and maskable).
- **Cold start (offline, local, headless Chromium, 60k not loaded), indicative:** about 0.8 s from reload to the settled map (measured by nothing yet; `apps/web/e2e/participant/offline-start.spec.ts` proves the start and the cached data, not the time; the 60k-feature budget row stays with `bench:browser`).

## Tool streams on the device (`ctx.data`, WP-683, B-020)

A tool that keeps server data (the Projekt-Chat first) gets one stream per tool key. It rides on the existing sync and is not part of the run or feature pull: no run, no fold, no feature seq. Code: `packages/client/src/tooldata`.

- **Wire** (WP-682, `packages/server/src/modules/chat/handlers.ts`; the device maps it to its own shapes in `tooldata/http.ts`): `GET /api/p/<project>/tools/<tool>?after=<seq>&limit=<n>` (default 200, at most 500) answers `{messages, head, read: {last_read_seq, last_mention_seq}, members: [{id, name}]}`, oldest first; a message is `{id, seq, author, at, body, removed, mentions}`. `POST …/tools/<tool>` takes `{id, body}` (the client UUID is the idempotency key, at most 4000 characters) and answers `{message}`: 201 new, 200 replay, 400 a refusal `{error: {code, message}}`, 409 when another person used the id. `POST …/tools/<tool>/read` takes `{last_read_seq, last_mention_seq}` (both only grow, never past the head) and answers `{read}`. 404 means the tool is not available to the person, 401 that the session ended; anything else is transient.
- **Erasure** (B-005): a message the erasure changed gets a **new seq above the head**, so the next pull re-delivers it, redacted or as `removed: true` (author and body null). The mirror therefore upserts by `id`: the older row of the id goes, and a removed id is dropped (the cursor still moves past it). A re-delivered message shows at its new place at the end.
- **Doorbell.** `event: tool` with `data: {"tool":"<key>"}`: the key and nothing else (H5; the server's `toolEvent`). Auto sync (`createAutoSync({ tools })`) pulls that tool after the 500 ms debounce (one timer per key); on open, `online` and `visible` it sends the outbox and the read marks and pulls every available tool.
- **Mirror.** Its own IndexedDB database `<name>-tooldata` (stores `records`, `outbox`, `meta`), separate from the device store, so `clearCache` never touches the outbox. Memory is hydrated at open. A pull pages from the stored cursor (100 per page, one page held at a time) and applies records and cursor in one transaction. Only tools in the person's `available()` list (the role offers or activates them and the person did not switch them off) are pulled or sent.
- **Outbox.** `append(body)` writes a pending entry (device counter `order`, never a clock) before anything else and returns it; it survives a reload. A drain (single-flight across tabs through the same Web Lock port as the run queue) sends in creation order. Accepted: the entry leaves the outbox and its record joins the mirror in one write, so it is never listed twice. Refused: the entry stays with `refusal {code, reason}` until `retry` (a new id, a new place at the end) or `discard`. A network failure or timeout stops the drain and loses nothing; 401 pauses it. There is no timer of its own: a drain starts after an append (`kick`), on `online`, `visible` and the doorbell.
- **Read state.** By server seq, never clocks. `markRead(seq)` keeps only the highest seq (monotonic, persisted) and one request goes out after 1 s or with the next sync, however many calls came; it carries `last_mention_seq` too, the newest mirrored message at or below `seq` that mentions the person; the reply and every page carry the cursor, so a second device sees the first one's reads.
- **Members.** Each page brings the people who have the tool, names only (`ToolPage.members`); the store keeps the latest list per tool in `meta` (`members:<tool>`), replaced by each page and kept across a reload, so `handle.members()` (the chat's person picker) works offline after the first pull. A new participant appears with the next pull.
- **Cursor.** `handle.cursor` is what the person has read: the server's answer, or the newest mark not yet sent when that is higher (`max(acknowledged, pending)`, the mention mark from the mirrored messages). Reading offline therefore clears the badge at once; the one source of the badge and the unread line, no second copy in the shell.
- **Device boot** (WP-684, `apps/web/src/lib/participant/tools/device-data.ts`, wired in `device.ts`). One `createToolData` per device over its own IndexedDB, `httpToolDataTransport`, the keyed doorbell on the shared SSE connection (`kick` drains at once), and `available` through core's `toolAvailabilityFor` over the manifest's `data` tools (the server's rule, R1). `startSync` passes the service to `createAutoSync({ tools })`.
- **Budget.** Mirroring 10,000 records is paged, and an append costs the same at 10,000 as at 10 (`bench/client-tooldata`, docs/12 line `tooldata-mirror-page-apply` and `tooldata-append-p95`).

## Personal preferences (WP-612)
The record that follows the person (tools on/off, per-tool preferences, saved filters, theme, font size, language) is **not** part of the pull protocol: it has its own endpoint, `GET | PATCH /api/p/<project>/prefs` (`DELETE ?participant=<id>` resets one person, admin only), and never appears in sync pages, the doorbell or exports.
- **Device:** `createPrefsClient` (`packages/client/src/prefs`) caches the stamped record per project and person (a `KeyValueStorage`, localStorage in the app, so no schema step in the device database). `set(path, value)` stamps the key with the device clock and applies it at once, also offline. `sync()` sends the pending keys (or just reads) and merges the answer; the app calls it before the map opens (a new device gets the record first) and the sync worker calls it on every sync.
- **Per person, not per device (WP-695, owner answer 3):** tool switches, the Kartenlayer choice, saved filter views, Offline-Bilder and the look (`ui.theme`, `ui.font_size`, `ui.locale`) live in this record. Only the tile pack, the app install and the remembered tab stay on the device. The device keeps the look as a cache: the theme key `app.html` reads before first paint and the `ub:locale` key plus the `PARAGLIDE_LOCALE` cookie for the sign-in page. Before the record arrives the device value shows; after, the record wins and the cache follows.
- **Merge:** last write wins **per key**, by the client time (`mergePrefs`): two devices that changed different keys keep both; for the same key the later time wins. The server cuts a time more than 5 minutes ahead of its own clock back, so a wrong device clock cannot pin a key.
- **Not in this record:** device-only settings (tile pack, install, the settings sheet's remembered tab) stay in device storage. Offline-Bilder (`ui.offline_images`, WP-667) and the filter sheet's remembered tab (`ui.filter_tab`, WP-648) are in the record.

## Bootstrap (`GET /participant-api/bootstrap`, WP-550, WP-611, WP-660)
- **Device data (WP-660).** `participant` also carries `email` and `phone` (the roster's, `null` when none; a guest has none). `infoPages: [{ key, title, content }]` are the project's info pages in `sort_order` (equal or absent orders keep the authored order), with every locale (the device picks one), content as authored HTML. `legalPages: [{ slug, title, body }]` are the instance's legal pages (WP-638) in the operator's order. All three are part of the identity record, so they are cached and an offline cold start shows them (fixes v3 B8). The device never fetches them on demand; the cache `format` is 2.
- One JSON record, `no-store`: `project { key, displayName, icon, preview }` (`icon` is a blob sha or `null`; `preview` is `true` on a preview login, computed on the server, WP-373), `participant { id, name, roles, email, phone }` (the id stands in for a missing name), `session { expiresAt }`, `login { token, link } | null` (the participant's own active token and its login link, the info-page variables `$token`, `$loginlink`, `$qrtoken`, `$qrloginlink`; `null` when no token can be exchanged any more), `version`, `infoPages`, `legalPages` and `compiled` (the deployed config). About 400 bytes without `compiled`, the info pages and the legal pages; the golden's two info pages add about 350 bytes, and the legal pages add their text (the size test allows 1500 bytes for the golden project).
- **Cache.** The identity part (all but `compiled` and the `login` token and link, which stay in memory and are `null` in the cache: WP-772) is kept in `localStorage` (`ub:bootstrap`) as `{ format, identity }`. With no answer from the server, the cached identity opens the app, so an offline cold start shows the same header and profile card; the compiled config is read from the store (put there by the last online start). Format 4. A record of another `format` or shape is refused (no fallback). A 401 clears it; a refusal or a bad answer is never replaced by the cache.
- **Takeover.** The device database is `ub-<project>-<participant>`. A bootstrap for another participant than the open device (`switchDevice`) closes that device and opens the newcomer's database; the old one stays on disk.
- H3: role-app data arrives here as new fields behind a `format` bump.

## Testing
A **simulation harness** (WP-050) runs N simulated devices against a simulated server, (`packages/core/src/testing/README.md`) with a seeded PRNG controlling network loss, duplication and reordering, offline periods and app restarts. The invariants:
- all devices converge to the server state
- no accepted run is lost
- refused runs leave no trace in the state

The same invariants are also checked against the **real adapters** (WP-513, `packages/client/src/simulation`, `fixtures/golden/simulation`): each simulated device is the real IndexedDB store (fake-indexeddb), run queue and sync worker, the server is the real SQLite run store behind the real run and sync HTTP handlers, and the seeded faults sit on the wire (lost requests, lost replies, duplicates, late duplicates, offline periods, restarts, atomic batches from a device and from the admin). "Converge" means every device's confirmed features and edges equal a fresh device's snapshot of the same actor, the cursor equals the server head, and no device holds an unsent or unconfirmed run. The **check** profile runs in `npm run check` (one test per seed, each about 0.2 to 0.5 s; the **short** profile is the 30 s benchmark); `npm run sim` runs the **long** one (50 seeds of 20 devices x 500 runs). A failing seed prints a minimal reproduction: the same seed shrunk to the fewest devices, runs and fault kinds that still break the same invariant, as a `SIM_SEED=... npm run sim` command line. Add a seed that once failed to `regressions` in `fixtures/golden/simulation/profiles.yaml`.

The id a device plans for a feature that a task or a rule creates is the id the server stores (`seededIds(run.id)`, WP-748), so a follow-up run on a predicted feature is accepted. A create onto an id that already exists is refused (`id_taken`, on device and server alike); no run overwrites a feature. Accepted limits, encoded as expected behaviour in `fixtures/golden/simulation/limits.spec.ts` and not as failures: a prediction covers reference edges only, so derived edges (geometry relations) appear with the pull.

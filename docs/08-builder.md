# 08 · Builder

> **The builder UI is v3's** (canvas, task tabs, form editor, rules, permission matrix, Code view) editing the v4 project file (`docs/process/rebuild.md`, register `a3-builder.md`). The first build's lens UI (data model, process, task, roles, rules, views, YAML, simulate lenses and their shell) was deleted in WP-423; the headless parts (`src/doc`, `src/simulate`, the pure models and ops under `src/lenses`) stay.

The builder is an **IDE for the project file**. It edits exactly one document, the overlay, or the template when the owner authors one. It writes no data rows; its only stored state is the working draft (one row per project, WP-213).

## Navigation
The builder opens on one feature type (`Project › feature type`, e.g. `Baumkataster › Baum`); its tasks, fields and stages are selected inside the page.

## Views (all edit the same document)
The page of one Objektart (`/admin/projects/<project>/types/<type>/builder`) has the toolbar, the catalogue on the left, one centre view and an inspector on the right. Every view edits the one `Doc` through ops.

| View | Shows | Editing |
|---|---|---|
| **Workflow** | The Objektart canvas: stages, task buttons, rules, entries, arrows (`v3/canvas`) | Rename, draw, move and delete arrows, add stages and buttons, reorder, move or copy tools, right-click menu, move boxes |
| **Modell** | The Objektart's fields and tasks, with the permission matrix (`v3/model`) | Add or change fields, tasks, permissions |
| **Code** | The effective YAML of the selected entity (`doc.entityYaml`) | Edit and apply as ops |
| **Probleme** | The problems list (`problemItems`) | Jump to the entity |

Task, rule, stage and field panes sit in the inspector (`registerTaskPane`, `registerRulePane`, `registerStagePane`, `registerFieldPane`). Roles and Beziehungen have their own admin pages.

## What it does with the result
1. **Validates continuously.** `core.schema.compile()` feeds a problems panel: dangling references, unreachable options, tasks that can never be available, rule cycles, type errors, lock violations.
2. **Simulates.** Core runs in the browser. Pick a feature (real data seeded into a sandbox, or a generated one) and an actor: which tasks are available? Submit, then see the observations, the fired rules and the new state. LLM edits follow the same cycle: propose, simulate, accept.
3. **Diffs and deploys.** It shows a plan against the running config version: entities changed, features affected, breaking changes, and required mappings (e.g. a removed option → which option replaces it). Deploy writes a new `config_versions` row. The **deploy overview** (WP-360, `apps/web/src/lib/admin/deploy/`) shows that plan as one dialog opened by "Veröffentlichen" in the publish bar and in the builder toolbar (`deployOverview.show()`): a card per Objektart with its diff lines, the radio "belassen / verschieben" for types with running objects, "verschieben nach / Werte verwerfen" rows for breaking entries that still hold values, the blockers (`Doc.problems()`) with "Gehe zu" (the builder opens with `?select=<key path>`), and the confirm. It computes no counts (R1); it re-plans when a choice changes.
4. **Upgrades templates.** It uses the same diff UI and resolves three-way conflicts per key (`05-config-format.md`).
5. **Keeps history.** Compare any two versions and roll back (a rollback is a new deploy).

## Accessibility
The canvas needs a non-drag alternative for every drag action (WCAG 2.5.7). Every view has a keyboard path.

## Document model (WP-200)
Code: `packages/builder/src/doc`, headless (no DOM, no I/O), so the UI, the MCP server and assistants share it. `openProject(templateSrc, overlaySrc)` returns an immutable `Doc`. Edits are `Op`s (`set`, `add`, `hide`, `unhide`, `reset`, `order`; `reset` and `hide` also drop the `order` of a map at or below the path, so removing a form leaves no dangling order (WP-477); `order` writes the overlay's `order.<path>`, which core's `merge` validates, so an unknown map or key refuses the op) and every one lands in the overlay (`override`, `add`, `hide`, `inputs`); the template is never modified. `apply` returns the new `Doc` plus the problems of the effective file (`template.merge` issues, then `compile`), or `refused` with a reason when the path is not a key path, the op would turn a valid file into one that breaks the file schema (`schema_invalid` problems), or the effective file would not take the op (a hidden, locked or missing path, or an edit below a parent an earlier `set` made a single value). Every `Refusal` carries a `code` from `REFUSAL_CODES` (`doc/refusal-codes.ts`, R6) and, for `schema` and `dead_entry`, the checker `problems` it would add; `message` is English for logs and assistants. The frame words a refusal with `refusalText` (`v3/shell/refusal.ts`, WP-518): a locked path says so, a refusal with problems shows `problemText` of the first one (R1, "Nicht übernommen: …"), any other code its `builder_refusal_<code>` text (de and en), an unknown code the generic `frame_refused` line. An op never silently does nothing (R11); a `set` on a path the template lacks is written as an `add` by `apply`, so lenses do not choose. `applyBatch(ops)` applies several ops as one edit: each op is checked on its own (key path, lock, hidden or missing path, effect) but the file schema only on the end state, so ops that are invalid one by one (a `form` and its form step) can go together; all or none, the Doc stays immutable, and the frame gets one change (`ctx.applyBatch`; `planEdit` and `commitOps` use it). `replaceOverlay(text)` (the YAML lens) validates typed text like `openProject` and keeps it byte for byte until the next op. `provenance(path)` gives `template`, `changed` or `added`. `save()` returns the overlay text (byte-identical when unedited, comments and key order kept) and a revision; `saveIf(expected)` refuses a stale revision. Budget: one edit to new problems ≤ 50 ms (measured about 3 ms). See `packages/builder/README.md`.

**Code view (WP-332).** `doc.entityYaml(path)` renders the effective YAML of one `types.<t>`, `tasks.<k>`, `tasks.<k>.auto.<n>` or `types.<t>.properties.<p>`, with `{ line, path, provenance }` per line (`template`, `changed`, `added`; the UI adds the lock mark from the template's `lock`). `doc.applyEntityYaml(path, text)` parses an edited text, diffs it against the effective entity and returns the minimal overlay ops: a changed scalar or list is a `set`, a new key an `add`, a deleted template key a `hide`, a deleted added key a `reset`, and a value set back to the template's a `reset`. It applies nothing: it returns the ops after a trial fold, and the caller applies them with `applyOps(doc, ops)` (the all-or-none fold in `src/doc/apply-ops.ts`), which folds the ops over `apply` and adopts only the last Doc — a Doc is immutable, so a refusal at any step drops the whole fold and leaves the original Doc untouched, and a refusal is not expected because the trial fold already tried the ops in order. Problems (`ok: false`): YAML errors with `line` and `column`, a locked path (`lock_violation`), an op `apply` refuses, new compile problems. Whole-file text stays `replaceOverlay`. Typing budget: one frame (measured 4 ms view, 2 ms edit, `bench/builder-doc`). MCP tools can call the same two methods (H4).

**Code view of one Objektart (WP-379).** `registerCodeView(registry)` (`packages/builder/src/v3/code`) fills the toolbar's `code` view, v3's `WorkflowCodeView`. `typeYaml(doc, scope)` renders `types.<type>` plus the tasks offered on it and the rules that run them (`scopeOf`, the catalog's own lists) in the template file's shape, `applyTypeYaml(doc, scope, text)` is the inverse and `provenanceLines(doc, text, base?)` tags the lines of any (edited) text. They sit in `src/doc/type-yaml.ts` and reuse WP-332's entity diff and `checkOps` (lock check, trial fold, new compile problems), so there is one YAML-to-ops path; the entity level is added: a new key below `tasks` or `rules` is an `add`, a deleted one a `hide` (template entity) or a `reset`, a hidden entity typed back unchanged an `unhide`; another type, another section or removing the type is a problem. Problems carry a `line` (parse errors from the parser, the rest by the deepest key of the path that the text has). The UI is one panel (`YamlPanel.svelte`: hint, Kopieren, Neu laden, Übernehmen, problem list, legend) around one editor (`CodeEditor.svelte`; CodeMirror 6 only in `editor.ts`, a lazy chunk and the one base the old YAML lens also uses: line numbers, folding, lint marks, a provenance gutter, reference completion). Übernehmen hands the ops to the frame (`ctx.apply`); it does not save, the toolbar's Speichern does (v3). The checks run 150 ms after the last keystroke. `registerEntityYaml(registry)` wraps the inspectors of `type`, `rule` and `field` (`registry.registerInspectorWrap`: the registry wraps at lookup, so the order of registrations does not matter; a kind without a pane shows the YAML alone) with v3's `InspectorHost` toggle Formular | YAML; the YAML side is `EntityYamlView` (`doc.entityYaml(path)` and `doc.applyEntityYaml`). Completion (`refs.ts`, headless): reference keys only (property, stage, role, task, type), v3's vocabulary completion has no counterpart here. Extensibility (H3): a new pane is one more registered view or inspector; the toggle needs no frame edit.

**Anpassungen and Formular kopieren (WP-440).** The Code view has two tabs when the template has content (`hasTemplateContent`: types or tasks; the empty project `leer` has none): "Code" (the panel, kept mounted behind the other tab so typed text survives) and "Anpassungen" (`OverlayTab.svelte`, read-only text and Kopieren). The text is `overlayYaml(doc, type, locale)` (`code/overlay.ts`): the entries of `Doc.overlay()` (`override`, `add`, `order`, `hide`) whose key path sits at or below the type, a task or a rule of the Objektart; the scope is the union of the effective file's (`scopeOf`) and the template alone's, so a task the overlay hid still counts. `''` means nothing changed there. `formYaml(doc, task)` (`code/form-yaml.ts`) is the `form` map plus `steps`; `CopyFormButton.svelte` (v3's "Formular kopieren", `EntityYamlView.svelte:86`) sits above the task pane's YAML tab, writes it through `copyText` (`code/clipboard.ts`) and toasts "Formular kopiert". The Code view's own button stays "Kopieren" (v3 bug 14: it copied the whole workflow under the label "Formular kopieren"). Project-wide entries (`inputs`, `views`, `map`, `tools`) are not shown: they belong to no Objektart.

**Provenance marks (WP-445).** `packages/builder/src/v3/shared/provenance.ts` is the one reading of `Doc.provenance` for the places where an element is edited: `provenanceOf(doc, paths)` (the strongest of the paths: added over changed over template; `undefined` for a project whose template is empty, which shows no marks), `lockOf` (the template `lock` entry that covers a path), `resetOps` (a `reset` for every overlay `override` / `add` entry at or below the paths and an `unhide` for each `hide` below them; an entry above the element is never touched) and `hideOps` (`removeOp`: a template element is hidden, an added one dropped). `ProvenanceMark.svelte` draws the mark (labels `dm_provenance_*`, the lock with `prov_locked`). A form field card is its property (`types.<t>.properties.<k>`) and its form entry (`tasks.<k>.form.<f>`): `fieldProvenance` (`provenance-field.svelte.ts`) reads both, writes a reset through `commitForm` and hands the "⋯" menu (`CardMenu`) the same through a Svelte context (`provenance-context.ts`), so no layer between passes it on. The task pane reads `tasks.<k>`. A changed element offers `prov_reset`; a non-added element reads "Ausblenden" (`prov_hide`) where v3 said delete. **On the rule pane and the canvas (WP-454):** `shared/provenance-elements.ts` names the paths of an element (`elementPaths`: a task `tasks.<k>`, a stage `types.<t>.properties.<p>.options.<k>`, an automatic action `tasks.<t>.auto.<n>` plus the task only it runs), so the rule pane (`RulePane.svelte`: mark, `prov_reset` beside it, `prov_hide` in place of `rp_delete`, the confirm text `rp_hide_*`) and the canvas read the same. `ProvenanceMark` takes `compact` (a dot, the name as its title) for the stage node, task row, rule node and entry marker. `canvas/provenance.ts` adds the right-click entries to `CanvasMenu` (`resetItems`, `deleteItem`; a locked element's entries are `disabled`); the canvas state's confirm request carries `hide` so `ConfirmDelete` says "ausblenden" (`tp_`/`rp_`/`stage_hide_*`). A reset applies through the frame's `applyBatch`. **Hidden template elements (WP-452, A-050):** `buildInventory` also returns `hiddenTasks`, `hiddenRules` and `hiddenFields` (template elements of this Objektart whose path is in the overlay's `hide`, read from `Doc.overlay().hide` and `Doc.template`); the catalog lists them at the end of Aufgaben, Regeln and Feldbibliothek, greyed (`catalog/HiddenRow.svelte`), with "Einblenden" = the `unhide` op through the builder context. They are not counted and not selectable. 

**Stage pane (WP-335).** Code: `packages/builder/src/v3/stage`, registered with `registerStagePane(registry)` for the selection kinds `stage` and `none` (v3's `StageInspector`). `ops.ts` holds the writes as pure functions: `stageOps.rename` (a `set` of the option label, `types.<t>.properties.<stage>.options.<key>`, the same entry the canvas edits), `stageOps.setType` (start, intermediate, end: one `set` of `types.<t>.process`; refused with `start_needed` when the stage is the start, `end_needed` when the process would have no end), `stageOps.addButton` (a task with `when: self.<stage> == '<key>'`), `stageDeleteImpact` (the removal on a copy, with the problems it adds) and `stageLock` (why the template refuses). `preview.ts` computes the participant preview from the file: `stagePreview(file, type, stage, role, locale)` opens the simulator, generates an Objekt in the stage, lists the tasks pinned to the stage or unpinned, dims those `Simulation.availability` refuses for the role (with core's refusal text) and marks each property visible and editable from `compilePerms(config).forType(type).readable/writable`. Not fetched: everything comes from the file. Limit: the Objekt is generated, so a task whose condition depends on other generated values may differ from a real Objekt. **Daten tabs (WP-444, v3 `DataTabsSection`).** `DataSection.svelte` (with `DataTabBar`, `DataRow`, `DataLibrary`) shows the active Daten tab from `buildFieldHub` (the Felder hub's model, core's `layoutTabs`) and writes only `model/fields/layout-ops.ts` ops, the ones FieldHub uses (R1): `addToTabOps` (end of a tab; a tab no property has yet gets the next `display.tab_order`), `removeFromTabOps`, `renameTabOps` (every property of the tab, hidden ones too; empty or taken names change nothing), `deleteTabOps` (the properties lose `tab` and `tab_order`, the visible ones become new last rows of the default tab, hidden ones stay hidden), `moveLineOps`/`setColumnOps` (up, down, left, right, full), and `setHiddenOp` (the field pane's "In Daten-Tabs ausgeblendet", `display.hidden`). A tab made with "+" that holds no property is local state of the pane (v3 `transientTabs`) until a property lands in it.


## Shell, navigation and problems (WP-212)
Code: `packages/builder/src/shell` (pure helpers) and `src/problems`; the v3 frame is `src/v3/shell`. `locate(file, path)` maps a key path to a `Location` (`{ type?, task? }`: types.* to the type, tasks.* to the task under its first `on` type, `creates`, or offer `$map`/`$none`; everything else to the project), `focusPath` focuses the deepest `data-path` element of a problem's path. The problems list is data: `problemItems(doc, locale)` and `problemsReport(doc, locale)` (H4) are what the Probleme view and `GET /builder-api/<project>/problems` show. Builder code is only imported by the `(builder)`, `(admin)` and `api/mcp` routes (depcruise rule `participant-no-builder`, planted-file spec `shell/isolation.spec.ts`) and lands in those routes' chunks: `apps/web/e2e/builder-bundle.spec.ts` builds nothing itself but fails without a build, and checks by `BUILDER_BUNDLE_MARKER` (rendered by the v3 shell) that the entry and root layout do not link it. UI text is Paraglide (`packages/builder/messages`), as in `packages/ui`; it is the only place builder UI strings live, and every builder work package may add keys there. **Draft lifecycle (A-011, WP-213).** A project has one working draft in `builder_draft` (docs/04), not a `config_versions` row, because a draft in progress often does not compile. The `DraftStore` port (`packages/server/src/builder-draft`: `get`, `seed`, `putIf(revision)`) has a SQLite adapter. `GET /builder-api/<project>/draft` returns `{ template, templateVersion, overlay, revision, updatedBy, updatedAt }` and, on the first read, creates the draft from the deployed version (its template version and overlay; a plain deployed template starts as an empty overlay on its major); with nothing deployed it answers 404 `no_version`. `PUT` takes `{ overlay, revision }`: 200 `{ revision }` when `revision` is the current one (the write is one compare-and-swap statement), 409 `{ code: 'stale_revision', draft }` when it is not (nothing changes), 400 for a malformed body, 413 above 1 MB, 404 `no_draft` before the first read. Both need an admin with a membership in the project (`authorizeAdmin`, A-008): 401 anonymous, 403 otherwise. Assistants and the MCP server (H4) use the same two calls and see the same 409. The page saves every edit (`draft-saver.ts`: one write in flight, the latest overlay wins, each write names the revision it started from); on a 409 it stops saving and shows a "changed elsewhere, reload" message without touching the editor. `GET /builder-api/<project>/problems` reads the draft without creating it. Deploying the draft is the Versions page (WP-210, below). Seam: `apps/web/src/lib/admin/draft/draft-source.server.ts` is the only place the routes reach the store; the browser clients `draft-saver.ts` and `versions-client.ts` sit beside it (WP-326, moved out of `(builder)` so every admin page uses one draft client). `GET /api/admin/p/<project>/draft/status` answers `{ dirty, neverPublished, problems, revision, type }` (`draftStatus` in `packages/server/src/builder-draft/status.ts`: the draft is dirty when its compiled hash is not the deployed version's; with nothing deployed it is `neverPublished`; `problems` counts what keeps it from deploying; `type` is the Objektart to open). The admin shell mounts `PublishBar` (`lib/admin/draft/PublishBar.svelte`) when `dirty || neverPublished`; it deploys with `POST /builder-api/<project>/deploy` (`revision` of the status, no mappings), so a breaking diff that needs a mapping answers `mapping_required` and links to the builder. A page that saves the draft calls `notifyDraftChanged()` so the bar follows.

### The language of problems (WP-416)
A compile problem is `{ path, code, message, hint?, params?, span? }`. `message` and `hint` are English and stay for logs, the MCP route and assistants; core translates nothing (R2). `params` is a flat record of the values the message is made of (`value`, `existing`, `type`, `property` …); a `params.variant` (registry `PROBLEM_VARIANTS`, key `<code>.<variant>`) picks one of several wordings of a code, and a dangling reference names `params.what` (registry `DANGLING_KINDS`). The builder words the problem in the admin's language: `problemText(problem, locale)` (`packages/builder/src/problems/text.ts`) fills the catalogue entry `builder_problem_<code>[_<variant>]` and its `_hint` from the params, in `de` and `en`; `problemItems` (panel and `GET /builder-api/<Projekt>/problems`) is the only caller. An expression problem (`expression_parse`, `expression_type`) carries `params.expr_code`, the parser's or checker's code (registry `EXPR_ERRORS`, docs/06), followed by that error's own params (`expected`, `actual`, `name`, `near` …) and `source`; `params.hint_variant` names the wording of the checker's hint. `problemText` words the detail from `builder_expr_<code>` and the hint from `builder_expr_<code>_hint[_<variant>]`, and what the parser found (`found_kind`, registry `EXPR_FOUND_KINDS`) from `builder_expr_found_<kind>`; `expr-text.spec.ts` walks the registry in both locales. Type names stay as docs/06 names them (`bool`, `list<string>`, `feature baum`). A code, variant or noun without a catalogue entry fails the typecheck and `text.spec.ts`; there is no fallback to the English text. Only a problem without `params` (a deploy check, not compile) shows its English text. A new problem code needs its params in core, a registry entry, and a message and hint in both locale files (`npm run messages:sort`).

## Simulator (WP-202)
Code: `packages/builder/src/simulate` (headless; the first build's simulate view is gone). `openSimulation(effectiveFile)` compiles with core and returns a `Simulation`: `generate`/`seed` put features into core's in-memory store (`MemoryStore` from `@ueberblick/core/memory`, the same store diffcheck uses; state is `core.fold`), `availability(feature, actor)` lists every task of the feature's type as available or refused with the `core.expr.explain` text, `facts` (the store as the read-only `Facts` port), `factsAfter(observations)` (a `clone()` with observations applied), `config` and `geo` are exposed for `explain` (`explain` needs them); `submit`/`submitBatch` call `core.plan` and return the runs (depth, `causedBy`, the rule `core.plan` names for a rule run, observations), the before/after state of every touched feature and the refusal when there is one. `commit: false` is a dry run on a `clone()` of the store. No planner and no store of its own (R1, R2, WP-130). The assistant's `simulate` tool (WP-211, H4) is this session. Budget: one run <= 50 ms (measured about 0.2 ms).

## Process helpers (WP-204)
`deriveProcesses(file, type)` (`packages/builder/src/lenses/process/graph.ts`) is a pure function of the effective file: options are nodes, a task step that sets the property to a quoted option is an arrow, a rule that runs such a task is a dashed arrow, and a task available in a state without changing the property sits on that node. An arrow starts at the state that `self.<property> == '<option>'` (or `in [...]`) pins in the step's or the task's `when`; an arrow whose `when` cannot be read or names no state is marked "start not fixed", one without a `when` starts "in any state". `connectOps` / `retargetOps` / `removeOps` (`edit.ts`) turn drawing an arrow into one op. The canvas (WP-334) and the stage pane use them (R1). The first build's Process lens UI is gone.

## Objektart canvas (WP-334)
The centre view `workflow` of the v3 builder frame (`packages/builder/src/v3/canvas`, `registerCanvas(registry)`). `buildCanvas(doc, type, locale)` is a pure function of the Doc and reuses `deriveProcesses` (R1): stage cards (kind start/end/step from `processesOf`), task buttons placed in the stages their `when` pins or their arrows start from (else the global container), entry markers (`on: $map`, `creates: <type>`), rule chips and the arrows (task, rule and entry). `arrange(model)` places the nodes automatically from the process layout's columns. Every node is draggable (stage, Global container, rule, entry marker; v3 stored only the stages and lost the others on reload, `posCache`) and the position is stored per project next to the draft (WP-366, E-21; `docs/03` "Canvas layout"), never in the config. `layout-api.ts` is the port the host provides with `setCanvasLayoutApi` (`apps/web/src/lib/admin/draft/layout-client.ts` over `/builder-api/<project>/layout`); the canvas loads the positions before it mounts the flow (so `fitView` frames them), `withStored` lays them over the arrangement (stored wins, nodes without one keep the automatic place, positions of nodes that no longer exist are ignored), and `onnodedragstop` hands the positions to a debounced saver (`createLayoutSaver`, one `PUT` per burst of drags, only the nodes that still exist, which prunes the rest). A failed load or save changes nothing else: the arrangement shows and the next drag saves again. There is no reset button (v3 had none). The view uses `@xyflow/svelte` (as v3). Selecting writes `ctx.select`, renaming writes one `set` op (`stageOps.rename` of WP-335: `types.<t>.properties.<p>.options.<stage>`, `renameTaskOp`: `tasks.<k>.label`; only the builder language's text, other languages kept). A template `lock` on the options makes `Doc.apply` refuse the stage rename; the frame shows the refusal. **Editing on the canvas (WP-435, S4-4).** Every gesture is a pure op, so the pointer, the keyboard path and an assistant (H4) write the same thing (R1). `canvas/edit.ts`: `drawArrow` / `retargetArrow` / `removeArrow` wrap the process lens' `connectOps` / `retargetOps` / `removeOps` (an emptied `then` is cleared, never kept as `[]`); `reorderOps` / `nudgeOps` write the overlay `order` of `tasks` (WP-333) so the buttons of one scope swap among the slots they hold and other scopes keep theirs; `addTaskOps` is the stage pane's `addButton` (a task pinned to the stage by its `when`) or the catalog's task chip (global); the task and rule `deleteOps` cut a task out of `order.tasks` first (`cutTaskOrder` in `task/ops.ts`: the file refuses to hide a key an `order` still lists, and a reorder lists every task). `v3/model/step-copy.ts` (`copyStepOps`) moves or copies a task step, which is a tool icon, to another task: a form step takes its `form` along, refused with `has_form` (one form per task) or `property` (one writer each, or the target's feature type lacks it); v3's Ctrl "copy by reference" does not exist because a form or quick edit belongs to one task. The tool icons are one per step of the task (`stepsOf`), so icon i is step i. `canvas/state.svelte.ts` holds what the nodes call (`createCanvasState`, shared by `setCanvasState`): every write goes through `commitOps` (a template lock, a refusal or a new problem comes back as a note, nothing half applied), a delete asks first with the impact list (`ConfirmDelete`: rules that run the task; the problems `stageDeleteImpact` adds; the task a rule owns). xyflow never keeps an edge of its own: `onbeforeconnect`, `onbeforereconnect` and `onbeforedelete` run the op and return `false`, and the model draws the edges again. A task's arrow is selectable and focusable (Enter selects, Delete removes it); a selected arrow shows a handle at its end (`EdgeReconnectAnchor`) to drag it to another phase. Reorder and tool drags are pointer events (`canvas/drag.ts`, so touch works; v3's HTML5 drag did not): the grip of a button reorders within its scope (before the button under the pointer, last on "Button hinzufügen"), a tool icon moves to the button under the pointer, Alt, Ctrl or Meta copies. Keyboard: Alt+ArrowUp/Down on a button (or ArrowUp/Down on its grip) moves it; Space on a tool icon picks it up, Enter on a button drops it there (Alt copies), Escape lets go; the context key opens the right-click menu; the arrow itself is also written by the task pane's "Übergang zu" (same ops). The right-click menu (`CanvasMenu.svelte`; the kit has no context menu, and its dropdown menu closed itself when opened by the pressed pointer, so it is a small own menu at the pointer) is v3's `Deletable`: task button and rule "Schlüssel kopieren" + delete, phase the same, entry marker only delete, tool icon "Aus Aufgabe entfernen". A catalog chip dropped on the canvas creates the node where it fell (the position is stored like a drag) or, for the task chips, a button in the phase or Global container under the pointer, or a form step on a button without one. Entry markers and rules have no exit to draw from (the engine puts an entry at the start phase; a rule's arrow follows the task it runs). **Fit and overlays (WP-472).** The canvas is the space between the catalog and the open pane, so `FlowProjector` fits the graph again whenever that area resizes (a pane opens or closes), until the person pans or zooms (`minZoom` 0.05 so a wide graph fits a narrow area). "Phase hinzufügen" on a type without a process creates it (WP-508, `createOp` in `v3/catalog/ops.ts`): a `select` property `stage` (label "Phase"), the new stage as `process.start` and one end stage ("Ende"), as the op plus `after`; the shell and the canvas apply them with `applyBatch`, so it is one undo step. v3 started a workflow with one start stage; v4 needs an end stage too. - **Anbindung** = the child's creating task `rel_<parent length>_<parent>_<key>_create` (the length keeps two relations from sharing a key; an author task under that key that is not shaped like it is refused `key_clash`) (`on: <parent>`, `creates: <child>`, `then: [{ set: { <reference>: self } }]`, label "<name> anlegen" / "Create <name>") for both values, and `required` on the child's reference for Verbindlich (a create without a parent is refused `required_missing`); Optional leaves it off. Reading takes the options back from these entries (block over cascade over the default trennen), a relation of the template without them reads as Optional and trennen.
- `createRelation` defaults to v3's Verbindlich and trennen, `updateRelation` writes only the options that differ from what the file says, and moves the entries with a moved relation; `deleteRelation` removes the generated entries first, so `uses` lists only what the admin made. A value that is the template's own again drops its override (the draft returns to the published file).
- The process helpers skip a `set` step with `of` (it writes the children, not the subject's stage).
- **Geometrie beim Erstellen (WP-396, lead-a decision).** v3's `inherit` / `draw` / `none` (`SPAWN_GEOMETRY_MODES`) is not stored as a mode; `v3/relations/geometry.ts` reads and writes it from two facts (registry `RELATION_GEOMETRIES`): `inherit_position: true` on the parent's relation is `inherit`; without it, a child type with a primary `geometry` is `draw` and one without is `none`. A child with its own geometry can only be `draw` (`inherit_position` would be `inherit_with_own_geometry`), so `createRelation`/`updateRelation` never write it there and a move to such a child drops it; a new relation to a child without geometry defaults to `inherit` (v3's default). Nothing adds or removes a geometry property on the child (that stays in Felder). `RelationEntry` carries `geometry`, `childHasGeometry` and, while the engine reports `inherit_with_own_geometry` for the relation (the child gained a geometry later), `geometryProblem`; `RelationSource.problems` supplies it, `TypeOption.hasGeometry` lets the dialog offer only the valid modes.

## Versions (WP-210, page since WP-325)
Code: the lens UI is gone (WP-325): the page is `apps/web/src/routes/(admin)/admin/projects/[projectId]/versions` with `apps/web/src/lib/admin/versions` (the server side) and the components next to the page (list, rollback, compare, upgrade offer, "Entwurf verwerfen"; the builder routes serve the calls); `packages/builder/src/lenses/versions` keeps the pure modules (`plan`, `upgrade`, `sources`, `api`; the publish check is core's `checkPublish`). Routes `apps/web/src/routes/(builder)/builder-api/<project>/{versions,versions/<n>,deploy,rollback,upgrade,publish}`, handlers `(builder)/versions-handlers.ts`, service `(builder)/builder-versions.ts`, source seam `(builder)/versions-source.ts`, browser client `apps/web/src/lib/admin/draft/versions-client.ts`. The lens knows no URL: the host gives it a `VersionsApi` with `setVersionsApi` (Svelte context; a test passes `VERSIONS_API_CONTEXT`).

- **Plan.** `buildPlan({ deployed, effective, featureCounts })` is `core.diff(deployed, effective)` grouped by section and entity (`entries` is exactly the diff, R1), plus the features of each changed feature type and `mappings`: one request per breaking entry, whose `choices` are the remaining options (removed option) or the sibling keys (removed entity) and empty for a changed type. A mapping is `{ to: <key> }` or `{ discard: true }`. `missingMappings` / `mappingsComplete` say what still blocks the deploy. A reordered map (properties, form fields, options, tasks, layers) is one `order_changed` entry, never breaking (A-042), shown in the deploy overview as "Objektart „Baum“: Reihenfolge der Eigenschaften geändert" (the owner of the map by `ORDERED_MAPS` pattern, WP-414; top-level maps have none). A type whose changes are all `order_changed` stays in `entities` but is not in `affected` (no feature is touched), so the versions plan, the upgrade offer and the deploy overview show no feature count for it, and the server's `versionPlans` offers no keep / move for it. One rule: `isOrderOnly(changes)` in core, used by `buildPlan` and `changedTypes`. The plan is computed in the browser from the draft and the running file; the server computes the same with the same functions before it deploys.
- **Deploy.** `POST deploy { revision, mappings }` deploys the saved draft of that revision through `deployProject()` (WP-169: `deploy()` (WP-112) plus the `afterDeploy` dep, which rings the doorbell once, rebuilds the timers and adds the missing cron rows when the running config changed): 200 `{ ok, version, created }`; 409 `stale` when the saved draft is not that revision (the client first waits for the draft saver, `settled()`), 409 `mapping_required { paths }`, 422 `problems`. Mappings are validated against the plan: a path that is no breaking entry is `unknown_path`, a `{ to }` that is not another option or property of the new version is `dangling_reference`, and `{ to }` on anything but a removed option or property is `schema_invalid`. In the deploy transaction every `{ to }` becomes one `deploy_moves` row (project migration 12: version, path, payload, `next_id`, done); `{ discard }` records nothing. The move executor (`createMoveExecutor`, `deploy/move-executor.ts`) then moves the values as `$move` system runs (registry `SYSTEM_TASKS`; actor `system`, no `causedBy`, one run per feature, visible in the history): batches of at most 500 features per transaction, `next_id` saved with each batch, a yield between batches, resumed at server start (`ProjectServices.resumeMoves`) and started by `afterDeploy`. `$move` input is `{ property, from, to }` (an option, also inside a multiselect list) or `{ property, to_property }` (a property's value; a value the new property already holds is kept); a feature without the value is a no-op, so a move is idempotent. Feature selection is the one function `featuresToMove` (version pinning, A-029, adds its predicate there). The plan and the deploy result carry `affected` on each breaking entry (live features holding the removed option or property, one SQL count each, never a fold). Measured: 20k of 60k features move in about 1.7 s, the longest batch about 90 ms (`bench/deploy-moves`); counting 3 entries over 10k features takes a few ms. Deploying is always an explicit POST (H4): assistants and the MCP server prepare a plan and a human sends it.
- **Deploy choice per type (WP-317, for the deploy overview S4-18).** The dry run (`plan`) also returns `versions: [{ type, running_floating, already_pinned, settled_floating }]` for every changed type with running features, and `deploy` takes `choices: { [type]: 'keep' | 'move' }` (default `move`; labels "Laufende Objekte auf alter Version belassen" / "auf neue Version verschieben" from `VERSION_DEPLOY_CHOICES`). The overview shows the choice only for the types listed in `versions`; the counts say how many objects a "belassen" pins, which stay pinned and which always move. `deployProject(…, mappings, choices)` returns `pinned`, the number of features pinned. The HTTP form is `?versions={"baum":"keep"}` on the admin `plan` and `deploy` endpoints; the builder routes carry it too (WP-360): `GET /builder-api/<project>/plan?versions=&locale=` is the dry run of the saved draft for the deploy overview (`DeployPlan`: `revision`, `first`, `warnings`, `groups` per type with the diff in plain lines, `versions`, `mappings` with their targets and `affected`, `blockers` from `Doc.problems()`), and `POST /builder-api/<project>/deploy` takes `{ revision, mappings, versions }`. A preview refresh keeps the default. `affected` on a breaking entry does not depend on the choice.
- **History.** `GET versions` returns the stored versions, the running effective file, feature counts per type and the upgrade offer; `GET versions/<n>` the effective file of one version (compare = the same plan view between two). `POST rollback { version }` deploys the stored file of that version through the same `deployProject()`, so an older version becomes the running one again (`created: false`, the row is reactivated as for any known hash) and the same checks apply.
- **Manual move of pinned Objekte (WP-368, owner P3).** The Versionen page's "Auf aktuelle Version verschieben" per old version. `GET /admin/projects/<project>/versions/move?version=N&locale=` is the dry run and `POST …/versions/move { version, mappings }` the move (admin handlers `pinMovePlanHandler` / `pinMoveHandler`; engine `deploy/pin-move.ts`: `planPinMove`, `movePins`, `pinCounts`). The dry run is the existing diff between version N and the deployed one with `affected` counted over exactly the features pinned to N (`featuresToMove` / `affectedCount` take `pinnedTo`), arranged as the overview's own shapes (`PinMoveView`, `lib/admin/deploy/pin-move-view.ts`; the dialog reuses `DeployGroup`). The move writes one `$pin` run `{version: null}` per feature pinned to N in every lifecycle state (P1) and one `$move` run per feature of every `{ to }` mapping, through `deps.pins.store.submitBatch` in batches of 500, in one transaction: a missing answer for a breaking entry with `affected > 0`, an invalid target, a pinned Objekt of a type the deployed version dropped, or a refused run changes nothing (422 `problems`). Afterwards `afterDeploy` rings the doorbell once and rebuilds the timers; N has no pins, so sync's live set drops it. Bench `bench/deploy/pin-move`: 10k unpin plus 10k move runs. No automatic move when an Objekt is completed (P4).
- **Upgrade.** `startUpgrade`/`resolveUpgrade` (`upgrade.ts`) wrap `template.upgrade`: per conflict `overlay` (keep) or `template` (drop the overlay entry), per unresolved removal `drop` or `keep`; `resolveUpgrade` answers `pending` until every key has a choice, else the overlay (and its YAML text) with the merge issues of the result. `POST upgrade { overlay, mappings }` deploys that overlay through the same checks and, on success, restarts the draft from the deployed version (the draft is pinned to the old template; the route drops the row and seeds it again, a TODO to use `DraftStore.reset` in `builder-versions.ts`).
- **Publish.** `checkPublish(previous, next)` (`packages/core/src/template/publish.ts`, with `compareVersions`; the refusal codes are the registry `PUBLISH_REFUSALS`) refuses a changed key, a version that is not higher, and, inside a major, any `template.breakingChanges`; a new major may break. `POST publish { template }` (YAML text) parses, checks against the highest published version below it, and calls `publishTemplate`: 200, 409 `refused`, 422 `invalid`. The same function (`publishTemplateVersion`, `packages/server/src/templates/publish-version.ts`, WP-395) is also behind `POST /api/admin/templates` since WP-383, the Projekte page's "Als Vorlage veröffentlichen" (`docs/03-architecture.md`, "Project files").
- All routes need an admin of the project (A-008). Budget: the plan for the largest golden project <= 1 s (measured about 1 ms, `bench/builder-versions`).

## MCP server (WP-211)
Code: `packages/builder/src/mcp` (headless), routes `apps/web/src/routes/api/mcp` (`handler.ts` thin, `source.ts` the one place that reaches the runtime). `createMcpServer(ctx)` is a function from one JSON-RPC 2.0 message to its response (MCP over HTTP with JSON responses: `initialize`, `ping`, `tools/list`, `tools/call`; a batch is answered with a JSON-RPC error, a notification with 202 and no body). A tool is `defineTool({ name, description, input (zod), writes, run })` in a registry (`defaultTools`), so the server knows none by name; a tool's input is validated before it runs and an invalid input or a refusal is a tool result with `isError`, which the assistant corrects. `tools/list` publishes each input as JSON Schema and marks `readOnlyHint`. Tools: `read_config` (effective file or one top-level section, with the draft revision), `read_problems` (`problemsReport`), `read_schema` (`projectFileJsonSchema`), `propose` (`{ ops }` on the draft in memory: `core.diff` of the effective files, both overlay texts, the problem list; nothing stored), `simulate` (`openSimulation` on the file with optional ops: `availability` of a generated feature and a dry-run `submit`), `apply`. Every edit is `Doc.apply` (R3); the first refused op stops a list and is named by index.

- **Authority (O15).** Assistants read and propose; `apply` is the only tool that writes and it needs `confirmation`, a token bound to (project, draft revision, resulting overlay text, expiry) by a keyed signature (`ConfirmationPort.sign`, HMAC in the app, `UEBERBLICK_MCP_SECRET`, TTL 10 min). The token is issued by the human step `issueConfirmation` = `POST /api/mcp/<project>/confirm { ops, baseRevision }` (200 `{ token, expires }`, 400, 409 `stale_revision`, 422 refused op), which is only accepted from a same-origin browser request (`Sec-Fetch-Site`). That check is a speed bump, not a boundary: an assistant holding the same admin session could forge it. A separate MCP credential is the follow-up (later topic A-018); "execute under limits" would be another `ConfirmationPort`, not another write path.
- **Draft (A-011).** The app's `DraftPort` calls the draft handlers of `GET`/`PUT /builder-api/<project>/draft` in process, so the 1 MB cap, the revision compare-and-swap and the 409 are the builder's own. `apply` refuses (`stale_revision`, with `currentRevision`) when the draft moved after the proposal, before and again at the write. It never deploys.
- **Untrusted input (H4).** At most 50 ops, 200,000 characters, value depth 32, strings at most `PARSE_LIMITS.untrusted.maxLength`; after the ops are applied, every compiled expression at or below an op's path must parse under `PARSE_LIMITS.untrusted` (16,384 characters, depth 16), else `expression_limits`. When the file does not compile there is no expression list to check; the config limits still bound each expression.
- **Route.** `POST /api/mcp/<project>` needs `authorizeAdmin` (A-008); a body over 1 MB is 413, non-JSON 400. `apps/web/src/routes/api/mcp` is the one non-`(builder)` place that may import `@ueberblick/builder` (depcruise `participant-no-builder`). Budget: `propose` on the largest golden project <= 200 ms (`bench/builder-mcp`).

Every other `then` step is a row (`outcomeRows`): `set` (a literal or an expression, as typed: `textValue`), clear (`set: null`), status (a `set` of a select option), `lifecycle` (registry `LIFECYCLE_STATES`) and `redact` (read-only here); `creates` is the "Objekt anlegen" row (at most one, `ADD_REFUSALS.secondCreate`; an entry task keeps its type). A row's `when` / `otherwise` are "nur wenn …" (the Bedingungen rows over core's chips, with `form.<field>` paths from `stepPathOptions`) and "sonst". Values and conditions are checked by core through `planEdit`; v3's snapshot has no engine home (E10). *Definition*: `buttonOps` writes `button.color` (a `TASK_BUTTON_COLORS` key or `#rrggbb`) and `button.icon`; `confirmOps` writes `confirm` with a standard text so the file holds the state, `confirmTextOps` edits it.

## One action (WP-1045, C-004 step 1)
An action is one condition plus one outcome, carried out by people (a task with roles) or automatically (a task without `who`, carrying an `auto` entry, C-004 steps 2 and 3; the task pane's role chips write `tasks.<t>.who`, with an Admin option and an "Automatisch" mark when it is empty). The file has one place for it: `tasks.<t>.auto.<name>` (undo, provenance, hide and locks work on those paths; a lock on `tasks.<t>` covers its entries). `rule/auto-task.ts` says which tasks an automatic action owns (`ownedTasks`: system-only and carrying that one entry) and which are automatic-only (`isAutomaticOnly`: system-only, owned by none). An owned task is never a canvas button, a catalog row or a task-pane entry; `rule/summary.ts` (`outcomeParts`) reads its `then` steps as the one line the action node shows (for example "Priorität → Hoch"). The catalog lists one list "Aktionen" (`catalog/actions.ts`, `ActionList.svelte`) with the filter Alle, Personen, Automatisch. The task pane and the action pane share the sections Bedingung (for an action: trigger, then condition) and Ergebnis (a "Wer" tab was removed by owner order, WP-615: who may act is in the Bedingung, "Automatisch" is the catalog mark). The selection kind stays `rule` and its id is the action's id `<task>.<name>` (`AutoId`). `who` and the one shared condition (step 3, WP-1047) are not part of this.

## Permission matrix of the Modell view (WP-331)
Code: `packages/builder/src/v3/model/permissions`. `registerModelView(registry)` registers the `model` view (v3's `ModelOverviewView` sub-tab strip; `TABS` in `ModelView.svelte` holds Felder, Berechtigungen, Aufgaben in v3's order, Felder first). `model.ts` (`buildPermissionModel(doc, type, locale, t)`) is the pure model: Section -> Band -> Row, columns are the roles. A cell's `allowed` is the matrix lens' `buildMatrix` (so `core.perms`, R1); a row's `audience` (`all` / `roles` / `none`) and its `locked` reason (`row`: the type's `see` is a role list, so a property read cannot differ; `all_rows_visible`: `see` is a map) come from the file through `field/perms.ts` (`propertyAudience`) and `typeAudience`, so the matrix and the field pane's pickers are one model. `ops.ts` builds the `Doc.apply` ops: `toggleOp` (v3 `toggleRoleInList`, with an empty result meaning nobody, written as `[]` through `setPropertyAudienceOp`, not v3's "empty = all"; every role in means `$all`), `resetOp`, `privateOp` / `privateState` (`visible_when: self.$created_by == actor.id`, WP-306's system field; another condition is `custom` and is never overwritten) and `cellOp` for the whole-type rows (`see`, `create`, `delete`). Provenance per cell: a cell is `modified` when its role's access differs from `doc.template`'s; reset toggles it back (a cell edit rewrites the whole `permissions.<action>` value, so one overlay entry covers a row; the per-cell reset restores one role's access, not the entry). The whole-type `write` row does not exist (as in v3); `create` and `delete` rows are advanced rows. Not in v3, not added: whole-row and whole-column toggles. A draft that does not compile shows a notice instead of cells (`available: false`).

## Felder and Aufgaben of the Modell view (WP-378)
Code: `packages/builder/src/v3/model/fields` and `.../tasks`; both are entries of `TABS` in `ModelView.svelte` (the Felder and Aufgaben tabs sit in v3's centred card, the matrix is full-bleed). **Felder** is v3's `FieldHub`, the Daten layout editor over `properties.<p>.display` (WP-659): `hub.ts` `buildFieldHub(file, type, locale)` is the pure model (tabs = distinct `display.tab` names, default tab first then `tab_order`; lines = same `display.row`, `left < right < full`; the library = `display.hidden`, all from `layoutTabs`; the geometry property is not listed, as v3 left out its system defs), `searchFields` is the search (label, key, type label), `used-in.ts` `usedIn(file, type, property)` lists the tasks whose form, quick-edit/location step or `then` writes the property and the rules that read it (change trigger, or `self.<property>` in the condition, via core's parser). `ops.ts` builds the edits as Doc ops (`hideOp`, `showOp`, `moveOp`, `dropOnCardOps`, `dropOnTabOp`, `addFieldOp`), always writing the whole `display` object. The button versions of the drops for a phone (up/down, Links/Rechts/Volle Breite, "In Tab verschieben") are `layout-ops.ts` (`moveLineOps`, `setColumnOps`, `moveToTabOps`, `reach`): they renumber the lines of the tab and emit the same `display` sets. The tab and line ordering is core's `layoutTabs` (`packages/core/src/display/layout.ts`), shared with the participant Daten view (`buildDataLayout` keeps only its role, condition and empty-tab filters). A card opens the existing Felddefinition (`select({kind: 'field'})`, no second editor); delete reuses `deletePropertyOps` and the pane's confirm dialog. **Aufgaben** is v3's task table: `tasks/model.ts` `buildTaskRows` (the catalog's task inventory plus roles via `rolesOf`, the pinned Phasen, the start, the form field count and the target Phase from `deriveProcesses`); a row selects the task (WP-336's pane).

## The preview follows the draft (WP-341)
Every accepted draft save updates the project's preview store about a second later (debounced, one deploy per burst of saves), so a phone that syncs the preview sees the change within seconds. It is v3's "fork" without a second project: the preview is the draft deployed into its own database (docs/03 "Preview store and isolation"). A breaking change needs no mapping from the admin: a removed option moves the preview features to the first remaining option (the process start for the stage), a removed property is discarded. A draft with problems leaves the last good preview in place; `GET /builder-api/<project>/preview` reports `stale` and the problem count until the next good save. The admin sees its logins in the deploy overview (WP-373, below).

## Preview logins and carry-over (WP-373, A-034)
v3's release page listed "Vorschau-Logins": one throwaway participant per role plus "Keine Rolle" with a copyable link, so the admin could try the draft on a phone. In v4 the deploy overview (WP-360, the successor of that card) has the same card under the changes: a row per role of the draft, "Keine Rolle" last, the link `<origin>/login?token=…` in a `code` box and "Link kopieren" that turns into "Kopiert!" (`apps/web/src/lib/admin/preview/PreviewLogins.svelte`, data from `GET /builder-api/<project>/preview`). The tokens do not change on a save or a publish: the preview is **not discarded on a publish**, its Objekte (demo data and what testers entered) move to the new config with the same value moves as live (docs/03). A new role gets a login with the next save, a removed role's link stops working.

## Demo data in the preview (WP-342)
The first deploy into an empty preview seeds it: about 5 generated Objekte per Objektart, the first at the process start and the others spread over the further stages, centred on `map.start.center` (else 7.1 / 50.73), within about 1 km. Each is one run of the reserved system task `$seed` (`{ type, values }`, only the `system` actor, `packages/core/src/plan/seed.ts`): a creating task cannot set the stage, so `$seed` writes any declared property, validated per property type (`typeFits`), and refuses a stage that is no option. Only `seedPreview` (`packages/server/src/preview/seed.ts`) submits it, and only into a preview database. The generator is core's (`packages/core/src/generate`, a seeded `rng`, no `Math.random`); references point to generated Objekte (types are seeded referenced-first) and `participant` values to a preview login's participant (WP-373). A later refresh never re-seeds (it seeds only while the preview has no run). `POST /builder-api/<project>/preview/reset` drops the preview and deploys and seeds it again (new ids, generation bumped); the real project is untouched, and the preview logins stay (WP-373). The button "Demo-Daten zurücksetzen" sits in the "Vorschau-Logins" card of the deploy overview, behind a question. A template `demo:` section (owner question V1 b) would replace the generator per type inside `seedPreview`.

**Frame at phone width (WP-345).** `packages/builder/src/v3/shell/BuilderShell.svelte` asks the kit `IsMobile` (the one breakpoint of 768 px, the shared helper `packages/ui/src/breakpoint`) whether it is a phone; the toolbar's `@media` CSS (`packages/builder/src/v3/shell/BuilderToolbar.svelte`) uses the same edge (`max-width: 767px`). If so, the catalog and the inspector are rendered in `packages/builder/src/v3/shell/PhoneSheets.svelte` (the kit Sheet: catalog from the left, inspector from the bottom) instead of beside the canvas, opened by the toolbar buttons `open-catalog` and `open-inspector`. All selection goes through the frame `choose()` (also behind `ctx.select`): it closes the catalog and opens the inspector for a real selection; closing a sheet leaves the selection. The registered panes are the same components in both places (H3). The sheets use `preventScroll={false}` (the scroll lock makes the body inert, so the body-level MultiSelect dialog of the role pickers would be unclickable) and only a tap on the sheet overlay counts as an outside tap.

## Objektart settings pane (WP-437)
The toolbar's gear (`BuilderToolbar.svelte`, `data-testid="type-settings"`, after the view switch) selects `{ kind: 'type' }`; `registerTypeSettingsPane(registry)` (`packages/builder/src/v3/type-settings`) registers `TypeSettingsPane.svelte` for that kind (v3's `workflow` pane, `SharedSidebar.svelte:99-142`). Every control writes the op of its other place (R1, `type-settings/ops.ts`): the name is `setLabelOp` (the toolbar's), "Sichtbar für Rollen" is the matrix's `cellOp` on the whole-type row `see` through the shared `RoleSelect` (a per-property audience is not edited here, the pane points to the Modell), a role made in the picker is the task pane's `createRoleOps`, "Private Einträge" is the matrix's `privateOp`. "Standardfilter & Marker-Symbole" is a link, not a second editor: the host passes `links={{ icons }}` to the frame (`BuilderContext.links`), the route points it at the Objektart's data page, where the icon designer is; without the link the entry is not shown. The "?" Hilfe button is not built (no route serves the user docs).

## Change view (WP-506)
The deploy overview's change list says which parts of a changed element changed (`PlanEntry.parts`: first key below the element, a task's form entries as `form.<key>`), plus the Objekte per Objektart (`PlanGroup.objects`). "Projektdatei vergleichen" (`ProjectCompare.svelte`, in the overview and in Projektstatus) loads `GET /builder-api/<project>/compare` (`{ live, draft }`: the compiled effective file as YAML with sorted keys, so both sides read alike; `live` is `null` before the first deploy) and shows `lineDiff` (Myers after trimming the common head and tail; beyond 3000 edits the middle falls back to all removed, all added) with `collapse` folding unchanged runs beyond 3 context lines. 5000 lines with a few edits: about 10 ms.

# 12 · Performance budgets (binding)

Überblick runs on **cheap phones** and on **small servers**. Performance is a feature, and a regression is a bug that blocks the merge (CLAUDE.md R14).

## Reference hardware
- **Device:** a low-end Android phone with about 4 GB RAM, a mid-range 2021 SoC, Chrome, 4G. Emulate it in CI with Playwright CPU throttling ×4 and "Fast 4G".
- **Server:** 1 vCPU, 1 GB RAM, SSD, several projects on one instance.

## Rules of thumb that keep us inside the budgets
- **Never O(N over all features) per interaction.** Use indexes (R*Tree, per-type maps), incremental updates and workers. v3's known stall was an O(N) map rebuild per sync page.
- **Heavy work runs off the main thread.** That covers clustering, sync decoding, fold of snapshot pages and geometry maths on large sets.
- **Stream, don't buffer.** Sync uses tuples and streamed gzip, and does no ORM reflection on hot paths.
- **Compile once.** Expressions, permissions and styles compile at deploy time or config load, never per evaluation.
- **Lazy by default.** Load tools, 3D renderers (H1), the builder and rarely used views on demand.
- **Measure, don't guess.** Every work package that touches a hot path (sync, fold, plan, map, expr evaluate/toSql, server transaction) ships a benchmark in `bench/` and records the numbers in its Log.

## Where a time is asserted (WP-147)
A budget is measured in `bench/` through `defineBudget`, never asserted in a unit spec. A `*.spec.ts` under `packages/**` or `apps/**` asserts behaviour only: under CI load a `expect(ms).toBeLessThan(200)` flakes and reverts lands (WP-205, WP-207, WP-208 on 2026-09-30). A spec may read a clock to log a duration. `scripts/guardrails.spec.ts` fails when a spec reads a clock (`performance.now`, `Date.now`, `process.hrtime`, `hrtime.bigint`) and asserts on the elapsed value with `toBeLessThan`, `toBeLessThanOrEqual`, `toBeGreaterThan`, `toBeGreaterThanOrEqual` or `toBeCloseTo`. The check follows a difference of two clock reads (`performance.now() - t`) through variables, `push` and `Math.min`. It has no allowlist; the heuristic is in `scripts/guardrails/wallclock.ts`.

## Enforcement
- **How a row is measured.** Every bench line names the row it is (`row`) or says how its limit derives from one (`derivedFrom`), and how it was measured (`device`). Device rows measured in node are multiplied by 4 (the CPU throttle of the reference phone) before they meet the limit, and the report shows the raw and the adjusted value. Rows that need a real browser (cold start, warm start, INP, heap, delta) are proven by `npm run bench:browser`. `npm run bench` ends with the 14 rows and their current adjusted value, or "unmeasured". Details: `bench/README.md`.
- `bench/` holds reproducible benchmarks, seeded, with 60k-feature fixtures generated rather than committed. `npm run bench` (WP-101, see `bench/README.md`) runs them against the budgets above. A line is `PASS`, `FAIL` or `UNRELIABLE`: a time line over the limit on a busy machine (load per core above 0.5) is `UNRELIABLE` and does not fail the run, but a size line (KB, MB) is judged at any load (WP-858), and a value above 2x the limit is `FAIL` at any load, and `npm run bench -- --strict` (or `BENCH_STRICT=1`) counts `UNRELIABLE` as `FAIL`. The run exits non-zero on any `FAIL`. The phase-end report runs in strict mode on a quiet machine. Details: `bench/README.md`.
- The lead records the budget table's current values at every phase end in `docs/process/roadmap.md`.
- If a work package can't meet its budget, the reviewer fails it. If it can't be met by design, the lead decides provisionally and records a later topic (`docs/decisions/later/`).

Lines `list-time-to-rows-60k` and `filter-change-60k` in the browser (WP-859, `bench/browser/scenarios/list`, x4, median of 3, load 20 to 39 on 64 cores).

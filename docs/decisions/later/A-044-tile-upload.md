# A-044 Tile upload: an admin brings their own tiles, stored as one PMTiles archive per upload
priority: medium        status: provisional (lead-a, WP-405)
date: 2026-10-03   lead: a   work packages: WP-405 (engine), WP-406 (the admin tab)   touches: H6 / R13 / R14 / A-032, A-033

## Context
v3's Kartenebenen dialog had a tab "Hochladen": name, tile format, a ZIP / MBTiles / PMTiles file, chunked upload with progress, server processing, polling (`LayersSection.svelte`, `tile-processor.ts`, `tile-archive.ts`). WP-385 parked it because the engine had no upload path. The owner-side lead decided to build it (WP-385 option 2).

## Chosen (provisional)
1. **Storage.** `<dataDir>/blobs/tiles/<project>/<id>.pmtiles`, one file per upload, `<id>` = 16 random hex characters (a capability-style name, so the URL cannot be guessed). Open uploads live in `.uploads/<id>/` beside it: `data` (bytes so far), `job.json` (the job, kept after the end so the status stays pollable). The only place that knows this layout is `packages/server/src/tiles/upload/store.ts` (`TileUploadStore`); an object store or an external tile server (H6) is another implementation of that port, or simply a `map.layers` entry with an `https` URL, which needs nothing from this WP.
2. **Limits** (`TILE_UPLOAD_MAX`, `packages/core/src/registry/map-tile-upload.ts`): 2 GB per upload, 16 MiB per chunk, 1,000,000 tiles, 4 MiB per tile, 3 open uploads per project, 256 tiles between two yields. The chunk limit is below the default `UPLOAD_LIMIT` (50M), so the server-wide request limit never cuts a chunk.
3. **Upload protocol** (admin only, under `/api/admin/projects/<key>/tiles`, next to the project routes):
   - `POST /api/admin/projects/<key>/tiles/uploads` with `{kind: zip|mbtiles|pmtiles, name, size, format?: png|jpg|webp}` gives `201` and the job (`id`, `received: 0`, `state: receiving`). `format` is the admin's choice (v3); when the file says otherwise the upload fails with `wrong_format`. Absent: taken from the file.
   - `PUT …/uploads/<id>?offset=<n>` with the chunk bytes as body. `offset` must equal `received`; anything else is `409 bad_chunk` with `received` in the error, so a client resumes from there. A chunk that fails halfway is cut back to its start. Never the whole file in memory: the body streams to the file.
   - `POST …/uploads/<id>/finish` gives `202` and the job as `queued`; `409 incomplete` while bytes are missing.
   - `GET …/uploads/<id>` is the job: `state` (`receiving|queued|processing|done|failed`), `received`, `progress {done,total}` (tiles), `result` or `error {reason,message}`.
   - `DELETE …/uploads/<id>` aborts an open, queued or failed upload and removes its temp files (a done upload is not aborted; delete the archive).
   - `DELETE /api/admin/projects/<key>/tiles/<archive>` removes a finished archive. It is `409 conflict` with `references: ["map.layers.<key>", "map.packs.<key>", …]` while the deployed config or the current draft has a pmtiles layer with that archive's URL, or a pack that holds such a layer. A key found only in the draft is listed as `map.layers.<key> (Entwurf)`. The draft file is the draft's template merged with its overlay (`draftTemplateFile`, read-only).
   - Errors: `{error: {code: 'upload_refused', reason, message, received?}}`, `reason` from `TILE_UPLOAD_REFUSALS`.
   - The routes use the existing `projects/[key]` directory (same parameter name, no sibling conflict with `[project]`).
4. **Processing** (`tiles/upload/service.ts`): a job runs in the server process, one at a time across projects, started after `finish`. The converters hand a `TileSource` (sorted tile ids and a reader) to one emitter (`emit.ts`) that copies tiles into a spool file in batches of 256, yielding to other requests (`setImmediate`) between batches, then uses the existing PMTiles writer (`packs/archive-write.ts`). MBTiles: two passes over SQLite (keys, then blobs by key in tile-id order; TMS y flipped); vector tiles (gzip) keep their compression. PMTiles: header, directories and section bounds are validated with the existing reader (`packs/archive-read.ts`) and the file is kept as is. ZIP: `z/x/y.<ext>` entries through `io/archive/zip.ts` (`openZip` with its zip-bomb limits). A job that was running when the process stopped is reported `failed` (`incomplete`) the next time it is polled; the admin uploads again. Uploads that stay `receiving` longer than `TILE_UPLOAD_MAX.stale_hours` (24) are removed by `sweepStaleUploads` at startup (idempotent; a failure is logged as `tiles.sweep_failed`, never thrown).
5. **Serving.** `GET /api/p/<project>/tiles/archives/<archive>.pmtiles` with `Range` (200, 206, 416), `Accept-Ranges`, an ETag (the id: the file never changes) and `Cache-Control: private, max-age=86400, immutable`. A session of the project (participant or admin) is needed: 401 without, 403 for another project, 404 for an unknown archive. The archive is not filtered by role (the layer entry decides who sees the layer; the id is unguessable); a stricter rule would need a layer lookup per range request.
6. **Layer.** The job's `result` is `{url, archive, format, bounds, minZoom, maxZoom, tiles, bytes}`; `url` is the instance-local path above. WP-406's tab writes the `map.layers` entry (source type `pmtiles`, `tile_type` raster for png/jpg/webp, vector for pbf) as a draft op. This WP writes no layer.

## Seams (R13, H6)
`TileUploadStore` (where the bytes live), `TileSource` (one more input kind is one more converter), `TILE_UPLOAD_*` registries (limits, kinds, formats, states, reasons). External tile servers stay `xyz`/`wms`/`pmtiles` layers with a remote URL (A-033).

## Cost to change later
now: one folder under `tiles/upload` and two small handler folders. After the build: moving to an object store is a new `TileUploadStore` plus a redirect or proxy in the archive route; the URL a layer stores does not change.

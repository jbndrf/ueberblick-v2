# B-018 The classifying property per type: v3's per-value icons and colours (gap G1)
priority: high        status: provisional (lead-b accepted option B, 2026-10-02)
date: 2026-10-02   lead: b   work packages: WP-674   touches: H1, H3, H6, R4, R6, R13, R14

## Context
v3 lets each workflow name one classifying property, the stage or one dropdown field, and one flat map of per-value icons. Four places read it: the marker icon (register #2), the cluster colours (#3), the Einfach switches (#17) and the cluster-detail rows (#25). v4 has none of it: a default dot and grouping by stage only (`apps/web/src/lib/participant/sheets/filter/filter-model.ts:70-87`, `packages/ui/src/map/maplibre/layers.ts:54-66`). The decision needs a shape in `packages/core/src/schema` (R13) and has to survive `property.options` being read in many places.

## What v3 does (each element, with its source)
- **Where it is named.** On the type (v3 "workflow"), as a tag mapping on one form field: `filterable` with `filterBy: 'stage' | 'field'`, offered only for dropdown and multiple-choice fields (`reference/src/lib/workflow-builder/tools/tag-types.ts:38-50`). The participant app reads it into one mode per type (`routes/(participant)/map/+page.svelte:844-858` `filterModeByWorkflow`, `:1318-1344` `filterableValueOf`; `FilterSheet.svelte:298-301`). It is never named on a view or a layer: v3 has one map, so "per type" and "per map view" were the same thing.
- **Where the per-value icons live.** One flat map on the type, `workflow.filter_value_icons: Record<value, IconConfig>` (`map-icons.ts:35-39`), keyed by the stage key in stage mode and by the dropdown value in field mode (`workflow-icon-designer.svelte:81-83,324-327`). The two kinds of key share one map, so a stage key and a field value that are equal would collide. The icon designer fills it (`workflow-icon-designer.svelte:309,385-455`, "only when filterMode='field'" for the value list, per stage for the stage list), and the old per-stage `visual_config` is retired (`:82-83`).
- **What an icon is.** `IconConfig = { type: 'svg', svgContent, style: { size, color, borderWidth, borderColor, backgroundColor, shadow, shape: 'none'|'pin' } }` (`map-icons.ts:14-31`). The designer takes the SVG from a template, a file upload or pasted code, validated by `validateSvg` (`svg-icon-designer.svelte:150-170`, `lib/utils/svg-validator.ts:22`), and always saves the style `border 0, transparent, no shadow, shape none` with `size` and `color` (`svg-icon-designer.svelte:173-195`). The SVG is stored inline in the database row, not as a file. `style.color` doubles as the value's colour.
- **Fallback chain for the marker icon.** value icon, then the type's own `icon_config`, then a dot in the type's `marker_color` (default `#6366f1`) (`map-icons.ts:175-200`; participant list icons `+page.svelte:555-567`). Lines and polygons take the same chain's colour: value icon `style.color`, else type icon, else `marker_color`, else `#3b82f6` (`+page.svelte:570-590`).
- **How it reaches the cluster.** Every point carries one `filterValue` (`supercluster-manager.ts:10,32,107`); the worker reduces the cluster to frequency counts under the key `fv:<value>`, else `wf:<type>` (`workers/cluster-worker.ts:11-14`, merge `:17-23`). In stage mode `filterValue` is the stage key (`+page.svelte:1339-1344`), so the one key is the classifying value in both modes.
- **What the cluster icon draws.** The donut is **grey**: slices cycle three greys, and the colour registry argument is `_registry`, unused (`donut-cluster-icon.ts:13-17,43-48,70-78`). So in v3 the cluster icon shows the mix by slice size, not by colour. Colours come back only in the cluster-detail rows. Register #3 ("donuts coloured by type or value mix") and gap G1 ("donut colours") say more than v3's code does; see Open 1.
- **Cluster-detail rows.** Group by type, then one row per key: stage key in stage mode (`'_unknown'` if absent), the value in field mode (`'_unset'` if absent). Colour and label come from `visualKeyRegistry` under `stage:<key>` or `fv:<value>`, else grey `#9ca3af`. The registry only ever sets `fv:` keys (`:826-838`), so in stage mode the `stage:` lookup misses and v3 shows grey rows with `shortLabel(key)`: a v3 slip, not an intent (the registry comment says stage colours live under `fv:`). v4 does not port it; rows sort by count (`+page.svelte:1808-1870`). The registry is built from every `filter_value_icons[v].style.color` as `fv:<v>`, plus `wf:<type>` from `marker_color` (`+page.svelte:812-844`).
- **Einfach switches.** One switch per value that occurs in the data (not per declared option), with icon and count, from `filterableData`: stage mode counts `current_stage_key` and takes stage names from the document, field mode counts the field's current values and splits multi-select values so each option counts once; both sort by label and take the icon from `filter_value_icons` (`FilterSheet.svelte:288-351`). A project may preset which values start on: `visible_tag_values: workflowId -> values` (`lib/schemas/map-settings.ts:66-72`).

## What v4 already gives us
- The stage **is** a `select` property: `types.<t>.process.property` (`packages/core/src/schema/feature-type.ts:35-46`, `docs/research/v3-parity/stages-intent.md`). So v3's `stage | field` mode collapses into one thing: **one select property of the type**. There is no second mode to port, and no key collision, because the values are the keys of that one property's `options`.
- The cluster worker already carries per-feature property values for the keys the style names (`KeysMessage`, `packages/ui/src/map/cluster/protocol.ts:34-39`, `index-core.ts:75-77`), and Supercluster accepts `map` and `reduce` functions. The reduce by value is therefore a worker change, not a main-thread pass (R14).
- B-013 makes the stored config self-contained: a `{ $ref }` asset is embedded once at ingestion (`docs/05-config-format.md`, "Layer styles"). It is the existing port for icon files.

## Options
- **A) Richer options.** `options: { <key>: LocalizedString | { label, color?, icon? } }`. One place holds everything about a value. Costs: all label readers above change, the builder's writes must preserve the extra fields, `breaking.ts` and the `lock` paths need rules for the new fields, and an option now carries presentation for a project that never draws a map. Appearance is on every select, not on the classifying one, so a per-value icon exists with no type-level reason to use it. R11 forbids keeping both shapes, so the bare string form must be removed, and every fixture rewritten.
- **B) A `classify` section on the type next to `process`, options untouched.**
  ```yaml
  types.baum:
    classify:                       # one select property of the type: the stage or any other select
      property: vitalitaet          # key of a select or multiselect property of this type
      values:                       # option key -> how it looks; every key must be an option
        gut:     { color: '#16a34a', icon: { key: leaf } }
        mangel:  { color: '#dc2626', icon: { svg: '<svg …/>' } }   # or { $ref: assets/icons/mangel.svg }
  ```
  `compile()` checks that `property` is a select or multiselect of the type (`dangling_reference`/a new problem code from the registry), that every `values` key is one of its options, and that colours are hex. An overlay addresses it by key path (`types.baum.classify.values.mangel.color`), so the ID-keyed-map rule holds. No reader of `options` changes. The type's `process.property` can be the same key; nothing forces it. Costs: option removal or rename must also touch `classify.values` (a compile problem, not silent, and `breaking.ts` learns one more path); two places describe an option (its label in `options`, its look in `classify`).
- **C) Appearance on the property, the classifying choice on the type.** `properties.<p>.options_style: { <key>: { color, icon } }` and `types.<t>.classify: <propertyKey>`. Same reader cost as B (none), and the look follows the property when the classifying choice moves. It splits what the designer edits in one sitting (v3: one icon list, `workflow-icon-designer.svelte:385-455`) across two keys, and lets any select carry icons nothing reads.

## Where to name it: type, view or layer
- **Type (recommended).** It matches v3 (one per workflow), matches `process` (also one per type), and four of the five readers are not the map: the Einfach cards are built per type (`filter-model.ts:61-87` loops over `types`), the cluster rows are per type, and the participant's list icons need it too. A layer is the renderer's presentation (H1: `renderer` is a registry and a 3D layer needs the same colours), and a view may span layers of several types, so naming it there would repeat the key once per layer and per view.
- **View or layer (the register's G1 sketch).** Needed only if two maps of one type should classify by different properties, which v3 cannot do. Keep the seam: a layer may later carry `classify: { property }` that overrides the type's; the compile step already resolves a layer's source type, so adding it changes no shape.

## How it compiles
- **Markers (maplibre-2d).** The renderer draws `icon-image` as `['match', ['get', <property>], <value>, <image id>, …, <fallback image id>]` and `circle-color`/`fill-color`/`line-color` as `['match', ['get', <property>], <value>, <colour>, …, <fallback colour>]`. The property is one of the keys the cluster worker already carries for the style, so there is no extra pass. Images are registered once per value with `map.addImage` (v3 rasterises each SVG once and interns it, `map-icons.ts:1-14`). A `symbol` layer replaces `ub-single`, which is today a `circle` layer (`layers.ts:54-66`); the default-layer replacement rule (`docs/05-config-format.md`, "maplibre-2d view styles") stays.
- **Clusters.** The worker uses Supercluster `map`/`reduce` with `{ <value>: count }`, a frequency map like v3's `_counts` (`cluster-worker.ts:17-23`), keyed by the classifying value. The cost is O(1) per point at build and per merge; no pass over all points per interaction. A feature without a value counts under a reserved `_unset` key, as v3 does. The cluster item carries `counts`; the cluster icon and the detail rows read it. WP-674 phase 2 must measure the 60k build against `map-cluster-build-60k` (`docs/12-performance-budgets.md`).
- **Sheets.** The Einfach cards (`filter-model.ts`) and the cluster-detail rows read `classify.values` for the colour and icon and `options` for the label; the data-present rule (values from data, not from options) is kept as v3 has it.

## Icon assets
- **(i) A registry of icon keys**, like `TASK_BUTTON_ICONS` (`packages/core/src/registry/task-steps.ts:28`, nine lucide names). Cheap, offline, R6-clean. But it cannot express what v3's designer lets the admin do: upload or paste any SVG (`svg-icon-designer.svelte:150-170`).
- **(ii) Inline SVG** `{ svg: '<svg…>' }` in the config, v3's own model (`svgContent` stored in the row). Faithful and trivial to migrate. The config grows with the icons, and core cannot parse SVG (R2: no DOM), so it can only check size and a conservative text rule, while the full `validateSvg` stays in the builder (the same split as view styles and basemaps).
- **(iii) `{ $ref: assets/icons/<name>.svg }`**, resolved at ingestion by the existing assets port (B-013), embedded in the compiled config like a layer style. The project bundle keeps real files, and the runtime is the same as (ii).
- **Recommended: (ii) plus (iii) as one shape, with (i) as a registry fallback.** `icon` is `{ key }` (registry `MARKER_ICONS`, a superset of the lucide names the design system already draws), or `{ svg }`, or `{ $ref }` (the last two after compile are `{ svg }`). v3's `style` fields (`borderWidth`, `borderColor`, `backgroundColor`, `shadow`) are not carried: the designer always saves them as `0, transparent, transparent, false` (`svg-icon-designer.svelte:179-186`), so they are dead values; `size` and `color` are carried, as `color` and the one icon size of the renderer (Open 2).

## Extensibility check (R13)
- **H1 (3D).** The classifying property and `values` are on the type, not on a layer or a style, so a `3d` renderer reads the same `color` for a tile or a model highlight. `icon` is a point-marker concept; a 3D renderer ignores it and uses `color`. Nothing here is MapLibre-specific in core: the `match` expressions are built in `packages/ui/src/map`, the seam `renderer`.
- **H3 (role apps).** Nothing assumes one look for everyone. The shape is type-wide; a per-role app profile may later carry `classify.values` overrides (`roles.<r>.app`) or hide values, and the participant code reads the effective one through the compiled config, not through `types` directly. No per-role field is added now (the lead decides whether to reserve one).
- **H6 (external GIS).** The classifying values are config, not data, so OGC API Features output is unaffected. An external editor writes the same property through a run like any other, and a style export (SLD/QML) can be generated from `classify` later without a schema change. A colour is hex, never a MapLibre-only token.
- **R4.** The classifying property is a config-declared property and no built-in domain concept; the stage is not special-cased beyond being one select property.
- **R6.** Allowed `icon.key` values live in a registry; hex colours are a pattern in the schema. No inline union.

## Open (v3 does not decide it; for the lead or the owner)
1. **Cluster colours.** v3's donut is grey (`donut-cluster-icon.ts:13-17,70-78`, the registry argument is unused); register #3 and gap G1 expect colours. Options: port v3 (grey donut, colours only in the detail rows) or colour the donut slices from `classify.values`. The latter is a deviation from v3 without an owner decision. Needs an owner decision (`QUESTIONS.md`); until then phase 2 draws the grey donut and carries `counts` so either is a renderer change only.
2. **Type-level icon and colour.** v3's fallback chain ends in the type's `icon_config` and `marker_color` (`map-icons.ts:175-200`). v4's feature type has neither, and no register row or owner decision adds them. Without them the fallback is the default dot (what v4 draws today). Needs a lead or owner decision; it would be `types.<t>.icon`/`color` outside this record.
3. **Value `color` without an `icon`, and an icon without a colour.** v3 has the colour only inside an icon's `style`. v4 as proposed allows either alone. The fallback colour for a value with an icon but no colour is open.
4. **Multi-select classifying property.** v3's cluster key is one `filterValue` string per point; the Einfach counts split multi-select values (`FilterSheet.svelte:305-340`). A multi-select point has several values and one marker. Proposed: only `select` is allowed as the classifying property in the first build; the lead decides.
5. **`visible_tag_values`** (startup defaults for which values are on, `map-settings.ts:66-72`) belongs to the preference and startup defaults work (G4 and register #18), not to this record.
6. **Icon size.** v3 saves `size` per icon. One renderer-wide size, or `size` per value, is open.

## Recommendation
**Option B on the type** (`types.<t>.classify`, options untouched), **icons as `{ key } | { svg } | { $ref }`**, **type-level, with the layer override kept as a seam**. Reason: it ports v3's model (one classifying choice per type, one value-to-icon map) onto the engine's own shape (`process` is the sibling), touches none of the roughly 30 readers and writers of `options`, and keeps the colour and icon out of every project that does not draw them. Option A costs a breaking change across five packages for no new capability. Option C adds a second key to do what B does in one.

## Chosen (provisional, lead-b 2026-10-02)
Option B: `types.<t>.classify: { property, values: { <optionKey>: { color?, icon? } } }` on the type, with `options` unchanged. Seam: a layer may later carry `classify: { property }`. Icons are `{ key } | { svg } | { $ref }` (`key` from a registry, `$ref` through the B-013 assets port). The Open items are decided as follows:
1. **Cluster donut: grey, as v3** (`donut-cluster-icon.ts` ignores its registry). The worker still carries per-value counts, so colouring is one renderer change later. Coloured slices are an owner question (QUESTIONS.md M3); they are not built until it is answered.
2. **Type fallback:** v3's per-type `icon_config` and `marker_color` are v3 elements, so missing them is a bug. Add `types.<t>.marker: { color?, icon? }` (same icon shape) as the fallback after the value icon, before the default dot. Phase 2 builds it.
3. **Multi-select: not a classifying property; `select` and the stage property only.** v3's filterable tag allowed `multiple_choice`, but its value was the raw array (`+page.svelte:1343`). The icon lookup is keyed by one value (`:554`), so it never matched, and those features showed the type icon. v4 allows `classify.property` to be a `select` property, including the type's stage property (`process.property`). For anything else, the type's `marker` is the fallback, which is what v3 showed in practice.
4. **Icon style:** `size` is per icon, as in v3 (the designer's size input 8–128, `svg-icon-designer.svelte:75,327`). The default is 32, and the icon shape is `{ key } | { svg } | { $ref }` plus an optional `size`. v3's `shape: 'pin'` is drawn by `map-icons.ts:104,195`, but no v3 code path writes it: the designer always saves `shape: 'none'` (`svg-icon-designer.svelte:175-187`), and only the stress-test seed uses a pin. It is not carried. If the owner's real v3 export holds non-default `shape`, `borderWidth`, `backgroundColor` or `shadow` values, the migration tool (apps/migrate) reports them; they are not migrated silently. Checking that needs the real data, so it is needs-owner.
4b. **`marker.color`** keeps v3's `marker_color` (set at create, `admin/+layout.svelte:203`; shown in `FilterSheet.svelte:421` and `RecentSheet.svelte:249`). The builder's single colour picker writes the icon colour, as v3's `style.color` (lead-a).
4c. **Geometry colour:** line and polygon features use the resolved icon colour, as v3 (`instance-geometry-layer.svelte:42`, the `+page.svelte` colour chain after `iconFor`), so a shape reads the same colour as its marker.
5. **v3's stage-mode slip** (grey rows): not ported. Stage rows use their `classify.values` colour ("better, because v3's lookup key was wrong").

## Cost to change later
now: schema, registry, one compile check, the maplibre renderer and the worker reduce (phase 2) · after the build: moving to a layer-level key is one optional field and a resolve step; moving to richer `options` (A) is the breaking change in the readers table, which is why it is not chosen first.

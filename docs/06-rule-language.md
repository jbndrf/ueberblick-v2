# 06 · Rule language

**One expression language** is used for everything that decides or computes: task availability (`when`), `relevant`, `required`, `constraint`, `calculate`, `then … when`, `then.redact.of` (the participant id or feature to erase), rule conditions, derived relations, view filters, `permissions.visible_when` (the type-level row filter), `computed` (the value of a property, kept up to date by plan on the device and on the server, WP-312: only own properties of `self`, `inputs` and the stable system fields are inputs, so `actor`, `now` and `today()` are compile problems there), `display.condition` (whether the Daten view shows the property, `self` and `actor`, a bool, WP-659). It is a **CEL subset** (https://cel.dev). The syntax is familiar to LLMs, it has no loops and no I/O, and every expression terminates.

## Pipeline (all in `packages/core/src/expr`)
```
source string ─► parse ─► AST ─► check(env) ─► typed AST ─┬─► evaluate(ctx)   one feature (device, server, builder simulator)
                                                          ├─► toSql(mapping)  many features (sync scope, views, API) — SQLite dialect
                                                          ├─► explain(ctx)    "not available because self.stage == 'erledigt'"
                                                          └─► toChips()       builder chips; complex ASTs fall back to text
CQL2 (OGC API filter) ─► fromCql2 ─► same AST
```
- **Parsed and checked once, in `compile()`**. Runtime code never parses strings.
- `check` runs against an **environment** generated from the config. It knows each feature type's properties and types, declared relations, `actor`, `form`, `inputs` and `value`. Unknown names and type errors become compile problems with a path and a fix hint.
- **Evaluation is total.** Missing values are `null`, and null propagates by CEL rules. An evaluation error in `when` or `relevant` counts as `false` and is reported. It never throws into the UI.

## Scope of the subset (v1)
- Literals: bool, int, double, string, null, list, map. Operators: `! && || == != < <= > >= + - * / % in ?:`.
- Member access `self.prop`, relation traversal `self.flaeche.name`. `bind` names such as `area.name` are also allowed.
- **System fields** `self.$lifecycle`, `self.$created_by`, `self.$created_at`, `self.$changed_at`, `self.$version` (registry `SYSTEM_FIELDS`, A-028; `$version` from A-029). `$` starts a name only straight after a `.`; a bare `$foo` is a parse error, an unknown `self.$foo` a check problem (`no property '$foo'`). Types: `$lifecycle` and `$created_by` are strings, the two times timestamps, `$version` an int (`null` while the feature floats, docs/04). A feature without a creator or time reads null. Evaluate reads `FeatureState` (the planner's `featureAccess`, `readSystemField`); SQL reads the `features` columns, so "Nur eigene" is `visible_when: self.$created_by == actor.id` and uses the index `(type, created_by)`.
- A feature or a list of features (`self`, `self.kinder`) is also what a `then` step's `of` reads (docs/05, A-035); the checker needs no extra type form for it.
- Macros: `has()`, `exists`, `all`, `filter`, `map`, all over lists and relation sets.
- **Not included:** user-defined functions, backtracking regular expressions (`matches` uses a safe subset with RE2 semantics), protobuf types.

## Functions (registered via `defineFunction`, each implemented once in core and once as SQL where possible)
- **Spatial (OGC Simple Features / CQL2 names):** `intersects`, `within`, `contains`, `touches`, `disjoint`, `dwithin(a, b, meters)`, `distance(a, b)` (m, geodesic), `area(g)` (m²), `length(g)` (m).
- **Time:** `today()`, `minutes(n)`, `hours(n)`, `days(n)`, `months(n)`, `date(s)`, `days_between(a, b)`. `hours(n)` is an exact duration (n x 3,600,000 ms) like `days(n)`, and `minutes(n)` is the same in minutes (n x 60,000 ms), with the same constant folding, limits and SQL translation; it is v3's elapsed-time rule in hours ("Nach … Stunden"). The timer does not run on a clock of its own: a deadline such as `changed_at('stage') + hours(6)` is met at the first timer tick at or after it, so the resolution is the tick interval of the server, not one second.
- **History (current feature):** `last(prop, n)`, `changed(prop)`, `count(prop)`, `previous(prop)`, `changed_at(prop)` (a timestamp: the run time of the newest observation of the property, null while it has none; "last written", not "last different": writing the same value again moves it; A-038). Rule runs inherit the triggering run's time and timer runs carry the tick's time, so a stage a rule or timer writes has a time; the timer follows a property named in `changed_at(...)` (read from the AST, either quote style, at any depth). `changed_at('status') + days(3)` as `elapsed.from` / `after` is v3's "seit Eintritt in Phase": generic for any property, the stage is just one (`self.$changed_at` is the newest observation of any property). An elapsed rule re-schedules when a property it names in `changed_at` is written. On the device only the last 10 per property exist, and `check` rejects `n > 10` in device-evaluated contexts.
- **Number:** `multiple_of(value, step)` (WP-457, A-052): true when `value` is a whole multiple of `step`, exact in decimal (both are scaled by the step's decimal places, so `multiple_of(0.3, 0.1)` and `multiple_of(2.5, 0.5)` are true); it is v3's number "Step". Null in gives null. A step of 0 or below, or with more than 9 decimal places, is an evaluation error (an error result, never a crash). WP-483: it has a SQL translation, `ub_multiple_of(value, step)`, an application function the driver registers (SQL_APP_FUNCTIONS) that runs the same `isMultipleOf` as `evaluate`, so a type-level filter or `visible_when` using it runs in the database with the same decimal tolerance; in SQL a bad step gives null, which does not hold.
- **Text:** `startsWith`, `endsWith`, `contains`, `lower`, `upper`, `size`, `matches(text, pattern)` (also `text.matches(pattern)`, see "matches" below).

## matches (WP-428)
`matches(text, pattern)` is true when the pattern matches **anywhere** in the text (a search, as CEL and RE2; anchor with `^` and `$`). It is v3's field pattern check (a text property whose value must fit a pattern, register a3 E12), usable in `constraint`, `relevant`, rule conditions, filters and `visible_when`. Null text gives null like every function.
- **Linear time, no backtracking.** The pattern is compiled once to an NFA and run through a lazily built DFA (`expr/pattern`, on code points): the cost is O(text length x pattern size) whatever the pattern, so an untrusted or assistant-written pattern (H4) cannot stall a device. A 10,000-character input against `^(a*)*b$`, `^(a|a)*b$` or `(x+x+)+y` takes at most about 12 ms, and an e-mail pattern over 60k short values about 22 ms (`bench/expr-matches`, docs/12).
- **Memory is capped** (`MATCHES_LIMITS`): a program remembers at most 128 DFA states and 4,096 transitions (ASCII and non-ASCII together), and 32 compiled patterns are kept. A full cache stops remembering and computes the step (never a different result, still linear). One DFA state is at most about 5 KB, so one program stays under 1 MB and the whole cache under about 32 MB.
- **The pattern must be a string literal**, checked when the project compiles: a pattern from a property or a computation is `matches_pattern_literal`. `evaluate` validates again, so an unchecked AST gives an error result, never an exception.
- **The subset.** Characters; `.` (any character but a line break); classes `[abc]`, `[a-z]`, `[^...]` (with `\d \w \s` inside); shorthands `\d \w \s \D \W \S` (`\d` and `\w` are ASCII, `\s` is JS whitespace); escapes of `\ ^ $ . | ? * + ( ) [ ] { } /` and `\n \r \t \f \v`; groups `( )` and `(?: )` (nothing is captured); alternation `|`; `*`, `+`, `?`, `{m}`, `{m,}`, `{m,n}`; anchors `^` and `$` (text start and end, never a line). There are no flags: for a case-insensitive test write `text.lower().matches(...)`.
- **Left out on purpose**, each a typed problem `matches_pattern_unsupported` with its `feature` (registry `MATCHES_UNSUPPORTED_FEATURES`): backreferences, lookahead and lookbehind, named groups, inline flags, lazy and possessive quantifiers, `\b`, `\p{...}`, and `\D \W \S` inside a class.
- **Limits** (registry `MATCHES_LIMITS`): pattern length 200 characters (`matches_pattern_too_long`), group nesting 8, a `{m,n}` bound of at most 50, and at most 1,000 NFA states after bounded repeats are expanded (the last two are `matches_pattern_too_big`). A malformed pattern is `matches_pattern_syntax` with `detail` (registry `MATCHES_SYNTAX_PROBLEMS`) and `at`, the character index; the builder words each `detail` and each unsupported `feature` with its own text (`builder_expr_matches_syntax_<detail>`, `builder_expr_matches_unsupported_<feature>`, both walked by `expr-text.spec.ts`). Codes and params are in `EXPR_ERRORS`; the builder words them in `builder_expr_matches_*`.
- **SQL.** `matches` has no SQL translation: SQLite has no regular expressions without a user-defined function, and a second matcher would break R1. `toSql` reports it as unsupported, like the spatial predicates. A type-level `permissions.visible_when` or a server-side filter that uses `matches` therefore cannot be pushed into the query; it is evaluated in core on the rows (on the device, or after a prefilter), and the parity spec lists the corpus cases as unsupported with their reason.
- Tests: `expr/pattern/pattern.spec.ts` (accepted subset, refusal corpus, property tests against JS `RegExp` with the `u` flag on random patterns and strings, a pattern whose DFA exceeds the cache cap), corpus cases in `__fixtures__/{eval,check}-cases.ts`, codes in `check/error-codes.spec.ts`.

## Parity
There is **one implementation**, TypeScript in core, and it runs on every side. `toSql` is the only second encoding. A shared corpus (`packages/core/src/expr/__fixtures__`) runs every case through `evaluate` *and* through `toSql` against a real SQLite, and both must agree. That corpus is the spec, so add a case to it before you add a feature.

## Parser choice (provisional)
A hand-written parser for the subset (later topic A-003, from the WP-020 spike). It sits behind the AST contract (`expr/ast.ts`); any library adapter must pass `__fixtures__/parse-cases.ts`. Limits (A-005): nesting depth, not flat binary operator chains, counts towards the depth limit; config and untrusted input (assistants, CQL2) have separate limit sets.

## Parser and checker (WP-020)
Code: `packages/core/src/expr/parse` and `packages/core/src/expr/check`; the AST is `expr/ast.ts`. The spike that compared a hand-written parser with two libraries is `spikes/cel-parser/REPORT.md` (it recommends the hand-written parser, which is what is implemented).
- `parse(src, limits?) → { ok, ast } | { ok: false, errors }`. Total: never throws, no I/O. `limits` is a `ParseLimits` and defaults to `PARSE_LIMITS.config` (32768 characters, depth 64). `PARSE_LIMITS.untrusted` (16384 characters, depth 16) is for assistant-generated rules and CQL2 input; `fromCql2` uses it by default. Depth counts nesting: parentheses, brackets, call arguments, postfix chains (`.a`, `[i]`, `.f()`), unary and `?:` chains. Only flat left-associative binary chains (`a || b || …`) are exempt, so a 1,000-term `a || b || …` parses. Nesting beyond the limit is an error with a span, never a stack overflow. Any AST walker (`check`, `evaluate`, `toSql`) must walk flat binary chains iteratively. Every error has a `Span` and a plain-language message. The first error stops the parse.
- Rejected at parse time: unsigned ints (`1u`), bytes and raw strings, triple-quoted strings, struct construction (`Foo{}`), optional selection (`a.?b`), reserved words, `has()` of anything but a field selection, a macro without a variable name. `a ? b ? c : d : e` needs parentheses in the middle branch (CEL grammar). `-5` is one literal.
- `check(ast, env, { expect? }) → { ok, typed } | { ok: false, errors }`. `Env` is plain data: `vars` (`self`, `form`, `actor`, `inputs`, `value`, `other`, `now` and `bind` names, each present only where in scope), `features` (property and relation types per feature type; relations refer to feature types by name, so cycles are fine), optional `functions` (extra signatures) and `device` (history limit 10). `typed.types` holds the type of every node. All errors are collected, each with a span and, where possible, a `hint` ("did you mean 'hoehe'?"). Names checked: unknown identifiers, unknown properties, wrong operand types, wrong function signatures, non-bool predicates, `last('prop', n)` with `n > 10` on the device. In `last/changed/count/previous` the first argument must be a quoted property name of `self`'s feature type; an unknown name is an error with a hint ("did you mean …" or the list of properties), a non-literal is an error.
- **Error codes (WP-421).** Every parse error (`CodedParseError`: `message`, `span`, `code`, `params`) and every check error (`CheckError`: `message`, `span`, `hint?`, `code`, `params`) carries a `code` of the registry `EXPR_ERRORS` (`registry/expr-errors.ts`) and flat `params` (strings and numbers; type names as written here: `bool`, `list<string>`, `feature baum`). The English `message` and `hint` are unchanged, for logs, the MCP route and assistants; the builder words an error from code and params in the admin's language (docs/08). The registry lists per code the param names and the hint variants (`params.hint_variant`: `default`, `near`, `known`, `available`, `none` …). Parse codes: `hex_digits_missing`, `unsigned_unsupported`, `int_out_of_range`, `number_runs_into_name`, `number_out_of_range`, `triple_quote_unsupported`, `string_newline`, `escape_hex_invalid`, `escape_code_point_invalid`, `escape_unknown`, `string_unterminated`, `raw_bytes_unsupported`, `operator_doubled`, `assign_unsupported`, `character_unexpected`, `expected_punct`, `expected_field_name`, `reserved_word`, `keyword_as_name`, `struct_unsupported`, `unexpected_token`, `unexpected_end`, `nested_too_deep`, `too_long`, `macro_arguments`, `has_arguments`, `parser_internal`. Check codes: `minus_operand`, `branch_types_differ`, `map_key_type`, `not_operand`, `condition_type`, `list_index_type`, `map_lookup_type`, `predicate_type`, `count_type`, `unknown_name`, `unknown_feature_type`, `field_not_in_sql`, `no_role_property`, `no_property_on_type`, `no_property_on_record`, `list_field`, `cannot_read_field`, `record_index`, `cannot_index`, `has_operand`, `macro_range`, `op_needs_bool`, `op_compares_different`, `op_cannot_order`, `op_in_mismatch`, `op_unsupported`, `op_needs_int`, `op_lists_differ`, `op_not_applicable`, `unknown_function`, `no_signature`, `history_arity`, `history_needs_self`, `history_property_literal`, `unknown_property`, `count_minimum`, `device_history_limit`, `device_count_literal`, `result_type`, `matches_pattern_literal`, `matches_pattern_too_long`, `matches_pattern_syntax`, `matches_pattern_unsupported`, `matches_pattern_too_big` (see "matches"). A new error site needs a code in the registry, its params, and a text in both builder locale files (`error-codes.spec.ts` and `expr-text.spec.ts` fail otherwise). The CQL2 reader returns `ParseError`s without a code (its messages stay English).
- Numbers: `int` widens to `double`; `%` needs ints; `timestamp - timestamp` is a `duration`.
- The static type kinds are the registry `EXPR_TYPE_KINDS` in `registry/expr-kinds.ts`.
- Corpus: `expr/__fixtures__/{parse-cases,check-cases}.ts` (300+ cases). Add a case before adding a feature.

## CQL2 mapping (WP-109)
Code: `packages/core/src/expr/cql2`, imported from `@ueberblick/core/expr/compile`. To check a collection filter, `checkEnvFor(config, type)` (`@ueberblick/core/compile`) returns `{ ok: true, env }` (`self` is that feature type, server-side, the same env `compile` uses for `visible_when`) or `{ ok: false, error: { code: 'unknown_type', type } }`; then `check(ast, env, { expect: T.bool })` and `toSql`. `fromCql2(input, { limits? }) → ParseResult` (same as `parse`) reads an OGC CQL2 filter (text, JSON text starting with `{`, or a parsed JSON value; Basic + Basic Spatial) into the same AST, so `check` and `toSql` apply unchanged. Total: never throws; bounded by `ParseLimits` (default `PARSE_LIMITS.untrusted`: 16384 characters, depth 16; flat AND/OR chains and IN lists do not count as depth, so a 1,000-term OR list from QGIS reads; for a JSON object the character limit is an element budget). The first error stops the read. Text errors carry exact spans; JSON has no offsets, so JSON errors span the whole input and name a JSON pointer (`at /args/1: …`).

| CQL2 | AST / rule language |
|---|---|
| property `a`, `"a b"` | `self.a`, `self['a b']` (dotted names stay one name; no relation traversal) |
| `= <> < <= > >=` | `== != < <= > >=` |
| `AND OR NOT` (n-ary in JSON) | `&& \|\| !`, folded left |
| `IN (…)`, `NOT IN` | `x in [...]`, `!(…)` |
| `IS [NOT] NULL` / `isNull` | `x == null`, `!(x == null)` |
| `BETWEEN a AND b` | `x >= a && x <= b` |
| `LIKE 'p%'` `'%p'` `'%p%'` `'p'` | `startsWith` `endsWith` `contains` `==`; `\%` escapes; `_` and inner `%` are errors |
| `CASEI(x)` | `x.lower()` (string literals are folded) |
| `+ - * / %`, unary `-` | same; `DIV` and `^` are errors |
| `DATE('…')`, `TIMESTAMP('…')` | `date('…')` |
| `S_INTERSECTS S_WITHIN S_CONTAINS S_TOUCHES S_DISJOINT` | `intersects within contains touches disjoint`; other `S_*`, `T_*`, `A_*`, `ACCENTI`, `INTERVAL` and custom functions are errors |
| WKT (`POINT`, `LINESTRING`, `POLYGON`, `MULTI*`, `GEOMETRYCOLLECTION`, optional `Z`), GeoJSON, `BBOX`, `ENVELOPE` | a map literal shaped like GeoJSON: `{'type': 'Point', 'coordinates': [1.0, 2.0]}`; a 2D bounding box is a Polygon; a 3D box (6 numbers) is an error, "3D bbox is not supported yet"; `EMPTY` and `M` are errors |

Both encodings of one filter give equal ASTs (property-tested). Numbers: in text, a literal with `.` or an exponent is a `double`, otherwise an `int`; in JSON, integer-valued numbers are `int`. Geometry coordinates are always `double`. Corpus: `expr/__fixtures__/cql2-*.ts` (80+ cases from the CQL2 examples). Spatial functions accept these map literals wherever a `geometry` is expected (WP-021, below).

## Evaluate and the function registry (WP-021)
Code: `packages/core/src/expr/evaluate` and `expr/functions`. Contract: `expr/contract.ts`.
- `evaluate(typed, ctx) → { ok, value } | { ok: false, error: { message, span } }` and `condition(typed, ctx) → { value: boolean, error? }`. Total and deterministic; it never throws. The typed AST is compiled to closures once (cached per `TypedAst`), and the static types decide integer division, timestamp comparison and to-one versus to-many relations.
- **Null semantics.** A missing property, a member of null and a relation with no target are `null`. `==` and `!=` never give null (`null == null` is true). Arithmetic, ordering, `!`, `?:` and every function give null when an operand or argument is null. `&&` and `||` are three-valued: `false && x` is false and `true || x` is true whatever `x` is (also an error or null), otherwise an error wins over null, and null over the rest. `has(x.p)` is false for null. `exists`/`all` follow the same absorption.
- **Errors** (division by zero, integer or float overflow, list index out of range, `date('nonsense')`, a value that is not a geometry, a type mismatch on a `dyn` value) are error results with the span of the failing operation. In `condition` (`when`, `relevant`, other conditions) an error counts as `false` and is returned for reporting; `null` counts as `false` without a report; a non-bool result is `false` plus an error.
- **Values.** JSON, `{ $feature }` references and lists. A map literal key must not start with `$` (nobody can forge a feature reference). Ints are JS numbers; `int / int` truncates and `%` needs ints; results beyond the safe integer range are an overflow error. Timestamps are ISO 8601 strings and durations are milliseconds (`days(n)`; `months(n)` is a calendar duration: `date + months(n)` adds calendar months and clamps to the end of the month, Jan 31 + 1 month = Feb 28/29; months cannot be ordered). `date(s)` accepts a calendar date or a date-time with an offset, never local time.
- **Time is injected.** `now` and `today()` (UTC midnight of `now`) read only `ctx.now`; no clock or random source is touched.
- **Constants are folded.** A part made only of literals, `now`, `today()`, `date`, `days`, `hours`, `minutes`, `months` and `days_between` is computed once and reused: for good when it has no `now`, else while `ctx.now` is unchanged. Only a value is reused; an error (`date('nonsense')`) is raised again on every evaluation, with the same message and span. `now` is read only from `ctx.now`. Results never change, only the cost per feature.
- **Safe for untrusted ASTs (H4).** Comprehensions and list `+` draw on an iteration budget (`MAX_ITERATIONS`, 100,000 per call); compile depth is bounded; long flat operator chains are walked by a loop, not by recursion; a stack overflow is caught and reported.
- **History** (`last`, `changed`, `count`, `previous`) reads `FeatureAccess.history` of `self`. `changed(p)` is true when the two newest values differ or only one exists. `count` asks for at most 10,000 values.
- **One registry (R1).** `defineFunction({ name, sigs, evaluate, sql? })` in `expr/functions`; `check/functions.ts` derives its signatures from it, so there is no second table. `sql` is the SQLite encoding (WP-022, below); spatial predicates, `matches` and `last` have none (`lower`/`upper` go through application functions). Text, time, history and spatial functions each have a file there.
- **Spatial** functions call `core.geo` (`test`, `derive`, `distanceM`, `dwithin`). `distance` is the shortest distance between two geometries in metres, on the sphere of mean Earth radius (R 6,371,008.8 m): 0 when they intersect (the engine decides), haversine for point pairs and a local equirectangular frame around the probe point for point-to-segment, within 0.5 % of the ellipsoidal (Karney/Vincenty) value up to a few hundred kilometres at German latitudes. The metric lives in `core.geo` (`geo/distance.ts`, WP-031), and `dwithin(a, b, metres)` is `distanceM(a, b) <= metres`. Geometry arguments accept `geometry` values and GeoJSON-shaped map literals; `check` types a map literal with a registry geometry `type` and `coordinates` (or `geometries`) as `geometry`; bad coordinates fail at run time ("not a geometry").
- Corpus: `expr/__fixtures__/eval-cases.ts` (200+ cases: values, null, absorption, errors). Benchmark: `bench/expr-evaluate` (one `when` on 60k features: about 19 ms raw, one with a relation hop about 26 ms, on the bundled core with a real lookup per property; budgets 100 and 150 ms after the x4 device factor, derived from `delta-visible-1s` by A-012: a full re-evaluation after a config change, never per interaction). Each chain of binary operators has a fast path without fault values and the general path of this section; a fault or a non-bool operand aborts the fast path, and the chain is evaluated again on the general path, so the results are identical (`evaluate/compiled-vs-walk.spec.ts` checks it against a tree-walk).

## toSql, explain, toChips (WP-022)
Code: `packages/core/src/expr/sql`, `expr/explain`, `expr/chips`. Contract: `expr/sql/contract.ts`. Exported from core: `toSql`, `sqlApi`, `propertySql`.
- **`toSql(typed, mapping) → { ok, sql, params } | { ok: false, unsupported: { span, reason } }`.** Total. `mapping` names the aliases of `self` and `other` in the surrounding query, the plain-data variables (`actor`, `inputs`, `form`, `value`, `now`) and optionally the `inverse` relations (`sqlInverse(config)`, exported by core: `<type>.<field>` to the relation key the edges are stored under, derived from `inverse_of`; compile is the only producer). The result is an expression for a `WHERE`; the caller owns `FROM features <alias>` and must constrain `type` to use the indexes. **Every value is a bound `?`** (only `NULL`, `1`, `0` and fixed function text appear inline), so an assistant or CQL2 filter cannot inject SQL (H4). Parameters are numbers and strings, in order of appearance.
- **`propertySql(alias, key)` is the one definition of a property read** (`json_extract(f.properties, '$.key')`). Deploy builds `cfg_idx_*` with `propertySql('', key)` (the unqualified column, the only form `CREATE INDEX` accepts); `toSql` uses the same text for a single key, so `type = ? AND <expr> IS ?` and range filters search the index (test: `EXPLAIN QUERY PLAN`). Nested paths (`self.meta.x`, `self.tags[0]`) are one `json_extract` with a path. Keys must be plain identifiers.
- **Constant folding.** Every part that reads no row (`actor.kind`, `now - days(30)`, `date('2026-01-01')`, `[1, 2]`) is computed with `evaluate` and bound as one parameter, so both backends cannot disagree on it. A constant part that fails (`1 / 0`) is unsupported.
- **Supported:** literals, `== != < <= > >= + - * / %` (int division truncates, `%` follows the dividend), `&& || !`, `?:`, `in` (constant list or stored list), `has`, member paths and `[const]` on stored maps and lists, to-one relation reads (`self.flaeche.name`), `size`, `startsWith`, `endsWith`, `lower`/`upper` (Unicode, see below), `contains` (text), `days`, `hours`, `minutes`, `date`, `days_between`, timestamp plus/minus a duration in days, `ts + months(n)` and `ts - months(n)` (calendar months, clamped to the end of the month like evaluate; leap years included), `count`/`previous`/`changed` (over `observations`), `exists`/`all` and `size(x.filter(..))` over relation sets (subqueries over `edges` and `features`) and over stored lists (`json_each`).
- **Not supported (`unsupported` with a reason; evaluate in core instead):** spatial predicates and `distance`/`area`/`length` (prefilter with the R*Tree bbox, then `core.geo`), `last` (a list), `months()` anywhere but directly right of `+`/`-` on a timestamp (`months(1) + days(2)`, `months(2) + ts`), lists and maps as values, `filter`/`map` as values, bind names other than `self`/`other`, and any `==`, `!=` or `in` whose operand can fail in the rule language but be null in SQL (division by a stored value, arithmetic on untyped JSON).
- **Parity contract.** For a supported expression the rows selected by SQL are exactly the rows for which `condition` is true. Null and false are both "does not hold", which is all a `WHERE` can say. Null follows CEL: `==`/`!=` use `IS`, everything else propagates null, `?:` gives null for a null test, `all`/`exists` are three-valued. Dynamic (untyped JSON) operands are guarded by their storage type, so `3 < self.meta.name` is not true where evaluate reports an error. Stored timestamps are compared as text, so they must be in the canonical form (`YYYY-MM-DDTHH:MM:SS.sssZ`, as `date()` writes it). Relations are read as edges `(from_id, relation, to_id)` whose far end is served (`lifecycle IN ('active','completed')`, produced by `servedSql`); a relation named in `mapping.inverse` is read backwards.
- **Application functions (A-001 seam).** SQLite folds only ASCII and overflows month ends, so `lower`, `upper` and `ts +/- months(n)` are written as `ub_lower`, `ub_upper` and `ub_add_months`. They are defined once in `expr/sql/appFunctions.ts` (`SQL_APP_FUNCTIONS`), call the very code `evaluate` runs, and every SQLite connection must register them: `openSqlite` (server driver) does; a test that opens its own connection registers them with `db.function(f.name, { deterministic: true }, f.fn)`. Without them the generated SQL fails to prepare. A non-string or non-number argument gives null (the condition does not hold, as an evaluation error would).
- **OR-lists.** In a run of `||`, equalities `x == c1 || x == c2 || ...` (same stored value, string or number constants, adjacent or not) collapse to one `(x IS NOT NULL AND x IN (?, ?, ...))`, also for CQL2 `IN` lists and `a = 1 OR a = 2` chains (H6). It stays false, never null, for a missing `x`, so `!(...)` keeps parity. A 16k-term list prepares and runs together with a viewport on 60k features in about 60 ms; `toSql` itself needs about 70 to 100 ms for the 16k terms (`bench/expr-sql`).
- **Long chains.** Left-associative chains are walked with a loop. Runs of `&&`/`||` become a balanced tree (SQLite refuses expression trees deeper than 1000), so a 16k-term chain is valid SQL; an OR-list of equalities on one value is collapsed to `IN` and prepares in milliseconds; a 16k-term `||` chain of anything else takes SQLite about 4 s to prepare, so keep such filters short. Other operator chains longer than 400 terms are unsupported.
- **`explain(typed, ctx) → { value, decisive[], text }`.** Evaluates sub-expressions with `evaluate` and names the smallest ones that decided the outcome: the false conjuncts of `&&`, the first true disjunct (or every false one) of `||`, the tested value and the taken branch of `?:`. Each part carries its source text, span, value, and for a comparison the operand values (`detail`); an evaluation error is reported as `error`. At most 8 parts are listed. Example text: `not satisfied because self.stage != 'erledigt' is false (self.stage is 'erledigt')`.
- **Person-gated `when` (WP-787).** Each part also carries `actorOnly` (true when the sub-expression reads `actor` and no other state: its only free names are `actor`, `inputs`, `now`; `expr/explain/actor-only.ts`), and the result carries `more` (decisive parts beyond the listed 8). `plan` (`scope()`) refuses a false task `when` as `not_permitted` at path `when` when every decisive part is `actorOnly` and `more` is false (the condition failed only on the person: roles, kind or id; v3 "forbidden"); any other cause, or a mix with a state term such as `self.zustaendig == actor.id`, stays `not_available` at `when`. The check runs only on the refusal path.
- **`toChips(ast)` / `fromChips(chips)`.** Simple conditions (`path op literal`, or `path in [literals]`, joined by `&&`/`||` without parentheses) become a flat chip list. `toChips` succeeds only if `fromChips` gives back exactly the same tree (same precedence, left-associative), so chips never change the meaning; anything else returns `{ ok: false, text }` with the source. A `double` literal with an integer value (`10.0`) has no chip form.
- The source printer used by both is `expr/explain/print.ts` (`print(ast)` parses back to the same tree; property-tested on the parse corpus).
- Corpus and tests: `__fixtures__/sql-cases.ts`, `sql-world.ts`; `sql/parity.spec.ts` (every corpus source, two `self` rows, against real SQLite; the unsupported ones are listed with their reason), `sql/toSql.spec.ts` (index use, parameters, refusals, 16k chains, generated expressions), `explain/explain.spec.ts`, `chips/chips.spec.ts`. Follow-ups `sql/followups.spec.ts` (IN collapse, Unicode case, months, inverse from compile). Benchmark `bench/expr-sql`: viewport plus filter on 60k features about 65 ms, with a 16k-term OR-list about 60 ms (budget 100 ms). Corpus coverage: 269 of 329 sources translate; the rest are spatial predicates (R*Tree prefilter plus `core.geo`), the bind name `area` (not a row alias), lists and maps as values, `last()`, `map`/`filter` as values, dynamic operands without a SQL meaning and constant parts that fail.

## Filters (WP-640)
Role filter presets and personal saved filters are rule-language expressions over `self`, one per feature type, evaluated on the device by `core.expr` (`core/filters`: `compileFilter`, `applyFilter`). No function was added. Evaluation is clipped by permissions: a filter that reads a property the actor cannot read (member access on any feature-typed value, or a history function naming it) matches nothing, so a negated test cannot reveal a hidden value. 60k features of one type filter in about 100 ms (including the per-feature `visible_when` check). A `time` property holds an "HH:MM" string and is compared as a string (zero-padded, so order is time order); the filter builder offers `between` (either end may be open) and `is_empty` / `is_not_empty` for it, and no day-age operators.

**View builder (WP-665).** The rows of v3's FilterBuilder are `Clause` values (`core/filters/clauses.ts`; registry `FILTER_CLAUSE_KINDS`, `FILTER_EDITORS`, `FILTER_WHEN_*`): a field row (text contains, number between, day range, choice), a stage row (a choice on the process property), a "when" row (`self.$created_at` / `$changed_at`: older than N days, newer than N days, between two days) and a created-by row (`self.$created_by in [...]`, WP-306 system fields). `clausesToFilter(rows, types, stageProperty)` writes them with `filterTerm` and joins them with `&&`: field and stage rows only on their Objektart, "when" and created-by rows on every offered Objektart; an empty row writes nothing. A day range on a timestamp includes the whole last day (`< date(next day)`). Cheap terms come first and timestamp terms last (the evaluator stops at the first false term). `filterToClauses(config, filters, types)` reads a saved view back; a term that fits no row (hand-written, assistant-written) becomes a `rule` row that is written back unchanged, so no term is lost. `builderContext(config, actor, locale)` lists what the actor may filter by (readable properties with an editor, stages); `creatorIds(features)` lists the creators for the created-by row. Timestamp terms cost about 7 us per feature in core (every comparison parses its operands), so a view whose only row is a day range or "created older than N days" takes about 350-450 ms over 60k features, above the 100 ms row; see Notes of WP-665.

## Idle sweep: `schedule` with `idle` (WP-469, A10 b)
`idle` is a duration expression (`days(7)`, `months(1)`) in the scope of the task's Objektart (`self`, `actor`, `inputs`). A Objekt is  **idle enough** when `self.$changed_at + idle` is at or before the sweep's start time: one core function, `idleEnough` (`core/rules/timing/idle.ts`), used by the server sweep and meant for the simulator. An Objekt with no last change, or an `idle` that does not evaluate to a duration, is never idle enough. A run the sweep fires changes the Objekt, so it is not visited again until it has been idle for `idle` again. The sweep judges all Objekte at the instant the sweep started, also when it spans several ticks (v3 `run.at`). The server visits the Objekte in pages of 50, at most 1000 per automatic action per tick, and stops at a 40 s budget read from the clock port; the cursor row resumes it at the next tick. A throw on one Objekt counts as `failed` and does not stop the page (WP-496, v3 sweep hook lines 21-22, 112-132).

## Edge trigger: an entry without a timing (WP-427, A-045; C-004)
An automatic action (`tasks.<t>.auto.<name>`, docs/05) with no timing key is an **edge**: the task's `when` AND its own `when` are the condition that fires it, with fire-once (v3's "when" trigger). After a run, core judges the expression on each feature the run touched (a property changed, or it created the feature), with `self` that feature, twice: on the state before the run (the run's property and edge changes undone, a created feature counts as false; a feature whose edge the run added or removed counts as touched, so `self.kinder.size() > 0` fires on the first child) and after. The automatic action fires when it was false and is now true; if it was already true the trace says `already_true`. **Re-arming needs no stored flag:** once the expression turns false in a later run, the next false → true fires again. The cascade bound is the usual one (`ports.limits.ruleDepth`). The expression is a `bool` over `self` (the type the task is offered on), the actor and the inputs; reading another feature is allowed, but only features the run touched are re-judged, so a change to a related feature alone does not fire. A condition that becomes true through time alone (`now` or `today()`) is never judged by a run: compile warns `when_trigger_uses_time`, use `elapsed` (for example `elapsed: { from: self.frist }`). Cost: only touched features and only when the project has edge entries; bench `bench/plan-run/when-edge.bench.ts`.

Run the iteration below again and again until the goal is met. This file is the loop. Re-read it whenever you are unsure what comes next, and **always after your context was compacted**.

## Git rules (three leads, one repo)
- You work **only in your own worktree**, on branch `lead-a`, `lead-b` or `lead-c`. **Never edit `~/ueberblick-v4` (the main checkout) by hand.**
- Everything reaches `main` through `npm run land -- <branch>`. It takes the main lock, merges and checks in a staging worktree (`<main checkout>-land`), and fast-forwards main only when the check is green. A red land leaves main and the branch untouched. That covers your own commits (contracts, work packages, roadmap, later topics) and the implementers' `wp/*` branches alike. **Land only work packages of your own lane**: another lane's branch may have a newer round in review that your reviewer never saw.
- Lead events for the metrics: `npm run wp:event -- WP-xxx start|review <n> PASS|FAIL|blocked|unblocked|escalated`. `wp:event` is instant: it appends one line to `<git common dir>/land-pending/<WP>.log` (no lock, no commit, shared by every worktree), and the WP's successful `land` folds those lines into `work/events/<WP>.log` in its done commit, before `merged`. `merged <sha>` and `refused check|install|conflict` are written by `land` (a refusal is queued in the same pending log, because main does not move for it; logs before WP-903 say `reverted …`).
- Stage by path. Never `git add -A`, `git reset --hard`, `git stash` or `git checkout .`.
- **Land your own commits before you dispatch.** Implementer worktrees start from main, not from your HEAD, so a work-package file or contract that isn't landed yet is missing there.

## The check gate (WP-140)
`npm run check`, `npm run check:changed` and `npm test` first take one of K slots (`scripts/ops/check-gate.sh`), so at most K full checks run on the machine at once. K is 6 (raised from 4 on 2026-10-03: 5.5 waiters on average at CPU p50 54%), or `UEB_CHECK_SLOTS`. Waiters are served first come, first served (ticket files `q.<n>` in the slot dir; a dead waiter's ticket is skipped) and see their queue position. `UEB_GATE_HELD` (`<slot file>:<pid>`) is set by the gate for its own child commands so a nested `npm test` takes no second slot; it is honoured only if that pid is an ancestor of the caller and holds the slot, so setting it by hand does nothing (the command queues, with a note). A waiting command prints `waiting for a check slot (n running)`, then every 30 s its wait time and the holders (pid, minutes), so a stuck holder is visible. The check inside `land.sh` (it has `UEB_LOCKED=1`) uses a separate reserved slot and never waits behind agent checks. Slots are flock files in `<git common dir>/check-slots` and free when the holder exits by any means, `SIGKILL` included. A second, larger pool, `light` (`UEB_LIGHT_SLOTS`, default `max(4, nproc/8)`; files `lslot.<n>`, tickets `lq.<n>`, same FIFO mechanics, message `waiting for a light slot`), gates the short bursts: `npm test -- <path>` (any argument that is not an option), `npm run check:fast` (so pre-commit too) and `npm run deps:install` (`scripts/ops/deps-install.mjs`: replaces an existing install with a hardlinked copy of main's when the lockfile equals main's and main's install is current, else `npm ci` with offline-preferring flags and the reason printed; the main checkout always gets `npm ci`; implementers and review clones use it instead of bare `npm ci`). `npm test` with no path, `npm run check` and `npm run check:changed` take a full slot. A full slot covers a nested light or full command, so `check` runs its own `check:fast` without a light slot; a light slot covers only nested light commands. Land never waits for either pool. When a test run starts while the 1-min load average is above the core count, `vitest-scoped.mjs` adds `--maxWorkers=<nproc/4>` and prints one line saying so (not if the caller passed `--maxWorkers`). The 1-min load comes from `os.loadavg()`. Do not start more full checks by hand than the gate lets through. Every run that took a slot gets the time it queued in `UEB_GATE_WAIT_MS`; `steps.mjs` and `test:record` write it as `gateWaitMs` (WP-953), and `npm run -s metrics:check-cost` sums it. `check:changed` selects tests against the **merge-base** of your branch and main (`scripts/ops/changed-base.mjs`), never main's tip, so a branch a few lands behind sees only its own files (plus uncommitted and untracked ones); on main itself only uncommitted changes count. Within that diff (`scripts/ops/changed-select.mjs`), a **blanket trigger** (`RERUN_TRIGGERS` in `scripts/ops/rerun-triggers.mjs`: the lockfile, vitest/vite/tsconfig/svelte configs, `.githooks`, and the scripts `vitest.config.ts` imports) runs every test. A `package.json` is a trigger only when a key other than `scripts` and `description` changed against the merge-base (`dependencies*`, `exports`, `imports`, `type`, `workspaces`, `overrides`, ...), or when it is new, deleted or unreadable: a `scripts`/`description` edit selects the specs that read a package.json by path plus the specs that run or name a changed script (`npm run <name>` or the quoted name) (`check:changed package.json: scripts only -> N reader specs`). Every other file runs `vitest related`: its import graph, plus, for a file of a narrowed tree (`SCAN_RULES` in `scripts/ops/rerun-triggers.mjs`: `<pkg>/messages/**` and `project.inlang/**`, `docs/process/**`, `.claude/agents/**`, `CLAUDE.md`, `scripts/**`, `docs/12-performance-budgets.md`, `.dependency-cruiser.cjs` (the boundaries step checks the config itself, and the selection line says so), `eslint.config.js`, `.prettierrc*` and `.prettierignore` (the specs that run eslint or prettier; `lint:changed` lints the whole repo for them; 2026-10-04, they were blanket triggers), `fixtures/golden/**`, `schema/**`), every spec whose text reads that tree by path. Readers are found by scanning the specs at selection time (tens of milliseconds), never by a list, so a new, renamed or merged spec is picked up without anyone registering it. `<pkg>/messages/**` also selects the importers of that package's compiled Paraglide entry; `scripts/**` also every spec naming the changed file. A golden or schema file that no spec reads by path runs every test (`check:changed trigger <file> (no reader spec found for schema) -> all tests`). `check:changed` prints one line per rule with its matched spec count (`check:changed messages: 2 files -> 31 reader specs + import graph`, `check:changed trigger <file> -> all tests`), so a broad run says why. The packages that own a catalogue are found from the tree (`messageEntries` in `scripts/ops/rerun-triggers.mjs`: every `apps/*` and `packages/*` with `messages/` and `project.inlang/`). Before a messages change is planned, the package's own `vitest.global-setup.ts` compiles its Paraglide entry, or its `i18n` script when it has one and no global setup (the entries are git-ignored and missing in a fresh worktree); an entry still missing runs every test. A **deleted** file other than a spec selects the specs whose import graph **at the merge-base** contained it (`scripts/ops/fanout-graph.mjs` builds that graph from the merge-base tree, about a second; `check:changed deleted <file> -> N specs that imported it`), plus the narrowed-tree rules above if it belonged to one; a deleted trigger, a deleted package.json, or a graph that cannot be built runs every test (`deleted <file> -> all tests (no import graph at the merge-base)`). A **barrel** (every statement is a re-export; `scripts/ops/barrel-diff.mjs`, WP-992) that only gained named re-exports of **new** modules (absent at the merge-base) selects nothing, neither the barrel nor the new modules (`check:changed barrel <path>: N added exports -> no importers (their users are in the diff)`). Why this is safe: before the edit the barrel did not load those modules, so its importers' behaviour cannot change through a new name; every user of a new name, and the new module's own spec, is a changed file and selected on its own; dropping the new module from the selection is what keeps vitest from walking back through the barrel to its importers. What it does not cover: a new module that throws or has side effects at load now loads for every barrel importer (the train's full check is the backstop). A removed or re-pointed export, an `export *` added or removed, a non-re-export statement, an added line for an existing module, a new or unparsable barrel and a missing merge-base all select the barrel as before. A name added next to an `export *` is checked against that star's target (one level plus one nested star): if the target already offers the name (a local export wins over a star, so importers would be re-pointed), or the target cannot be read, the barrel is selected and the line says why. A **rename** counts as the old path deleted. A JSON or YAML under `schema/` or `fixtures/golden/` imported by code (`?raw`) is a node of that graph. The scan matches literal path text (`messages/de`, `docs/process/`, `'scripts'`, repo walkers such as `walk('docs')`): a spec that builds the path (`join('docs', 'process')`) or reads through a helper (e.g. `scripts/messages-sort.spec.ts` via `messageFiles()`) is not selected, and neither is a spec that spawns a script without naming it. The land train's full check is the backstop for all of these. `check:fast` also runs `lint:max-lines` (`scripts/ops/max-lines.mjs`, WP-974): R8's 400-line limit for `.svelte` files, which ESLint does not lint; it prints `path: N lines (R8: max 400)` per file over the limit. **The typecheck in `check:changed` is scoped too (WP-1012, `scripts/ops/typecheck-changed.mjs`):** `check:fast:scoped` runs `typecheck:changed`, which typechecks only the projects (root, ui, builder, bench, web) that contain a changed file or depend on its package, or all of them when a tsconfig/package.json/lockfile changed or a path is unknown; `check:fast` and the train's `check` keep the full typecheck. **Lint in `check:changed` is scoped (WP-997, `scripts/ops/lint-changed.mjs`, tested by `lint-changed.spec.ts`):** `check:changed` runs its steps (`check:fast:scoped`, `boundaries`, `test:changed`) **in parallel and stops at the first red** (WP-1015, `steps.mjs --parallel --fail-fast`; details in `orchestration.md`); `check:fast:scoped` is `check:fast` with `lint:changed` instead of `lint`: ESLint and Prettier `--check` on the files changed against the merge-base (the same `mergeBase` and `changedFiles` as test selection; untracked included, deleted files not passed). It prints one line, `lint: 7 changed files`, or `lint: eslint.config.js changed -> whole repo` (also `.prettierrc*`, `.prettierignore`, a changed `eslintConfig`/`prettier` key in package.json, or no merge-base). `npm run check:fast` (and the pre-commit hook's scope) and `npm run check` still lint the whole repo, so the land train is the backstop: type-aware rules on unchanged files can only show up there.

`npm run typecheck` is incremental: tsc keeps its build info in `node_modules/.cache/tsc` (WP-908) and svelte-check runs with `--incremental` (WP-912), caching svelte2tsx output in `packages/ui/.svelte-check/` and `packages/builder/.svelte-check/`. The `.svelte` files of `apps/web` are type-checked too (`typecheck:web`, WP-980; svelte-check without `--incremental`, about 40 s warm). The flag does not allow another location, so git, ESLint and Prettier ignore `.svelte-check/`.

**One slot setting for all worktrees (lead-c, 2026-10-03):** without `UEB_CHECK_SLOTS`, the gate reads K from `<git common dir>/check-slots/K` (light pool: `K.light`) before its built-in default. Every worktree shares that directory, so writing the file changes K at once, also in worktrees whose copy of `check-gate.sh` is older. Before this, a new default reached a worktree only when it merged main: an hour after K became 6, 14 of 21 worktrees still gated at 4. Only lead-c changes the file, and it journals the change with the fleet numbers.

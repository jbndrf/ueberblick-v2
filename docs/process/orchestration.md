# Orchestration: how the rewrite is run

The standing rule: **three Claude Opus 5.5 agents orchestrate, and Sonnet 5.5 agents write and review the code.** The local model (Qwen) does grunt work and never code review: **docsync** proposes doc updates (Opus reviews them), **logwatch** reads the logs and writes only alarms to `metrics/raw/ATTENTION.md`.

- **Three leads** (Opus, three sessions: lead-a, lead-b and lead-c, each in its own worktree) plan, write contracts and work packages, dispatch, and land work, in parallel lanes. lead-c, the steward, ships no product features: it owns tooling and keeps the pipeline healthy. They write no feature code. **Their loop is `lead-loop.md`**, and the build runs autonomously, without owner questions.
- The **strategist** (an Opus subagent of lead-a) runs the critical course checks and debates the lead for at most 3 rounds (`course-check.md`).
- **Sonnet** implementers write the code, and Sonnet reviewers are the merge gate.
- **docsync** (local Qwen, `docsync.md`) only writes docs, on `docsync/*` branches. It never reviews code or gives feedback. **lead-c reviews and merges or rejects** every docsync branch.
- **logwatch** (local Qwen, `logwatch.md`) reads the logs hourly; only alarms reach `metrics/raw/ATTENTION.md`, which the lead handles in loop step 0.
- **Everything is measured** (`metrics.md`), so the course checks argue from numbers.

## Roles (definitions in `.claude/agents/`)
| Agent | Model | Does | May not |
|---|---|---|---|
| **lead-a / lead-b** (two of the three main sessions; `.claude/settings.json` pins `model: opus`) | Opus 5.5 | Runs `lead-loop.md` in its lane: refines, writes contracts, dispatches, reads verdicts, lands, decides provisionally (later topics), keeps the roadmap current | implement features, edit the main checkout by hand, dispatch in the other lane |
| **lead-c** (steward; third main session) | Opus 5.5 | Runs `lead-loop.md` with the steward iteration: tooling lane, red-land triage and flakes, capacity, docsync and alarms, benches, needs-owner inbox, roadmap checkboxes, final-report draft | edit product code (except test infrastructure and quarantine skips), dispatch or land in another lane |
| `strategist` | Opus 5.5 | Course checks: on track? misconceptions? lock-in risk and reversibility? Debates the lead (max 3 rounds) | write code or docs other than its review |
| `implementer` | Sonnet 5.5 | Executes one work package in its own worktree: pre-flight checks, tests first, code, **dev and user docs**, `npm run check`, commit | leave its `owns:` globs (except the doc exception, CLAUDE.md R12), change decisions, merge |
| `reviewer` | Sonnet 5.5 | The merge gate. Checks a work-package branch against CLAUDE.md, the work package and the docs. PASS, or FAIL with a list | write code |
| `researcher` | Sonnet 5.5 | Answers "how did v3 do X?" or "what does standard Y say?" with references | write code |
| logwatch (not a Claude agent) | local Qwen 27B | Reads logs hourly, writes alarms to `metrics/raw/ATTENTION.md`, weekly server-tuning proposals | review code, apply changes |
| docsync (not a Claude agent) | local Qwen 27B via vLLM + omp | Proposes doc updates on `docsync/*` branches after merges to `main` | review code, give feedback, touch non-doc files, merge anything |

## The loop and decisions
The loop, the lanes, the git rules for three leads and the decision protocol are in **`lead-loop.md`** (the single source). Work packages are small (about 1 day of agent work, at most about 800 changed lines) with distinct `owns:` globs. Everything lands through `npm run land`.

## What `npm run land` does (tested by `scripts/orchestrate/land.spec.ts`; the script is `land.sh`, the train is `land-train.sh`)
Under the main lock: merge with `--no-ff` (forced to `LC_ALL=C`), `npm install` if `package-lock.json` changed, then `npm run check`.
- **Exit 0**: landed. For `wp/*` branches the work package is set to `done`, `merged <sha>` is logged and the branch and worktree are removed (without `--force`: a worktree git will not remove is kept, with a note, together with its branch). For `lead-*` branches the lead's worktree is fast-forwarded to main.
- **Exit 2**: merge conflict, or main moved while the check ran (cannot happen under the lock; guarded anyway). Main is unchanged. Rebase the branch onto main, then land again.
- **Exit 3**: refused, `npm install` or `npm run check` is red in the staging worktree. Main is unchanged and so is the branch; there is no revert commit and no hint to follow: fix, commit, land again.
- **Exit 5**: refused before merging. The `wp/*` worktree has uncommitted changes (tracked or untracked), or a detached-HEAD worktree is ahead of the branch tip being landed (commits the merge would miss). Nothing is merged and nothing in the worktree is touched. Commit or discard the work in the worktree, then land again.
- **Detach, verdict and status** (WP-1031, tested by `scripts/orchestrate/land-detach.spec.ts`): `land.sh <branch> [--expect <sha>] --detach` runs the same land as a detached process (`setsid nohup`, stdin `/dev/null`, output to `<git common dir>/land-logs/<branch-slug>.log`; slug = branch with `/` as `-`), prints its pid and log path and exits 0 at once. It sets `UEB_LOCK_WAIT_S` to 6 h unless set (attached lands keep 2 h). A second `--detach` of the same branch (pid in `land-logs/<slug>.pid` still alive) starts nothing and prints the first's pid. Every land, attached or detached, writes `<git common dir>/land-verdicts/<slug>.json` on exit: `{branch, expect, exit, verdict, sha, at, log}` with verdict LANDED (0), CONFLICT (2), REFUSED (3, 5, 6, 7), LOCK_TIMEOUT (75), KILLED (INT or TERM: `exit` is 128+n, the process itself still exits 130) or FAILED. A new land of the branch replaces it (`--detach` removes the old one first). `land.sh --status <branch> [--wait <s>]` (`land-status.mjs`) prints the verdict and exits with its `exit`; with a live detached land and no verdict yet it exits 75 (after the wait; "live" means the pid in `land-logs/<slug>.pid` is alive and its start time, `proc_start` as recorded at detach, still matches, so a reused pid is no land, WP-1035), with neither it exits 1 "no land for <branch>".
- **Exit 6** (WP-961, `land.sh <branch> --expect <sha-prefix>`, at least 7 hex characters, tested by `scripts/orchestrate/land-expect.spec.ts`): refused because the branch head does not start with the prefix. The land can wait up to 2 h for the lock and the branch may move meanwhile, so the check runs **after** the lock (for a train member, when the train takes it); the message names both shas, nothing is merged and the rest of the train goes on. The prefix travels as line 2 of the queue registration (`land-queue/<key>`; line 1 is the branch). Without `--expect` nothing changes. A short or non-hex prefix is a usage error (exit 64).
- **Integration branches: `--wps`** (WP-1037, `land.sh <branch> [--expect <sha>] [--detach] --wps WP-a,WP-b,…`, tested by `scripts/orchestrate/land-wps.spec.ts`): a branch that bundles several work packages (`wp/lead-a-build`) books each listed id like its own: `status: done`, its `land-pending/<WP>.log` folded into `work/events/<WP>.log`, a `merged <sha>` line, all in one done commit (`chore(wp): WP-a, WP-b done (merged <sha>)`). An id with no `work/<WP>-*.md` is reported (`note: --wps … skipped`) and skipped, never fatal. The list travels as line 4 of the queue registration and through `--detach`. A malformed list (not `WP-<n>` ids separated by single commas) exits 64 before queueing.
- **Exit 7** (WP-961): refused because the branch vanished while the land waited and the head recorded at enqueue is not on main (deleted by hand, failed cleanup). The message names the branch and the sha. A registration without a recorded sha and a vanished branch also gives 7, never 0. Restore the branch at that sha and land again.
- **Already on main** (WP-961, also under the lock): a branch whose head is an ancestor of main, or a branch an earlier train removed after landing it (the full head sha recorded at enqueue, line 3 of the registration, is an ancestor of main), is skipped with exit 0 and `already on main (<sha>)`. No done commit, no event, no worktree removal: a second queued land of the same branch cannot land it twice. WP-969: when the newer of two lands of one branch leads the train, it carries the branch once (under the older registration, whose waiter gets the result) and itself exits 0 `already on main (carried by this train as the earlier land of <branch>)`, or with the older entry's refusal; a train never holds a branch twice (a check refuses, exit 1).

### The land train (WP-915, tested by `scripts/orchestrate/land-train.spec.ts`)
A land registers its branch in `<git common dir>/land-queue/<ns>-<pid>-<start>` before it waits for the main lock, and removes it on exit. The land that gets the lock (`land-train.sh`) takes every live registration (a dead pid or a recycled pid, told apart by process start time, is skipped), oldest first, at most `UEB_TRAIN_MAX` (default 10), itself always included.
- Each branch keeps its own pre-merge refusals (exit 5). The branches are merged with `--no-ff` in queue order in staging, a conflict drops only that branch (exit 2), then **one** install (if the lockfile changed) and **one** check run for the whole train.
- Green: main fast-forwards once to the train tip, every branch gets its own `merged <sha>` (its merge commit in the train) and `done` bookkeeping.
- Red: bisect. The first half is checked and lands if green, then the second half on top of it; a red single branch is the culprit (exit 3, its own kept log, `refused check` event). Innocent branches land, main moves only on a green check. Extra cost is about log2(n)+1 checks, the common green case is 1 check for n branches.
- **The train waits to fill (WP-953, tested by `scripts/orchestrate/land-train-wait.spec.ts`).** Before it takes the lock, a land waits until `UEB_TRAIN_MIN` live registrations are queued (default 5) or the oldest one has waited `UEB_TRAIN_HOLD_S` seconds (default 300, measured in milliseconds; owner 2026-10-04, was 900), whichever comes first; then one full check covers the train (at most `UEB_TRAIN_MAX`). While it waits it prints `land: waiting for a train: n of m branches queued, t s left …`. `UEB_TRAIN_MIN=1` lands at once. `lead-*` branches skip the hold, so a lead land never stalls dispatch. Exit codes are unchanged. A train holds the main lock for its whole run (15–20 min under load), so `locked.sh` waits up to 2 h for the lock (`UEB_LOCK_WAIT_S`, default 7200) before it gives up with exit 75; a 75 means the queue is longer than two hours, not a hung check.
- **Defaults (WP-963).** `UEB_TRAIN_MIN` is 5 (owner, 2026-10-01: the full check runs about every fifth WP), `UEB_TRAIN_MAX` is 10: a train takes up to 10 waiting branches when more are queued (bisect unchanged). The hold is 300 s since 2026-10-04 (owner: at about 2 WPs an hour trains rarely filled, so the 900 s hold was most of a WP's wait from review PASS to merged).
- **Web build before the check (WP-962).** Specs gated on a current web build (`scripts/demo`, `scripts/ui`) skip without one, and a skip is invisible. When the merged diff touches `apps/web/**` or `packages/**`, the train runs `UB_MAP_PROBE=1 npm run -s build -w @ueberblick/web` in staging right before the check and marks it `probe` (`apps/web/build/.flavour`, WP-1029; the demo and ui specs accept any flavour, and the affected e2e step reuses the build instead of building a second time) (not when the check is skipped on a record). Measured 123 s at load average 37 (2026-10-02), under the 4 min limit, so there is no separate command. A failing build is a red check: same step name (`check`), same bisect, the kept log holds the build output. Tested in `land-train-build.spec.ts`.
- **A red train bisects on the failing targets only (WP-970, tested by `bisect-targets.spec.ts` and `land-bisect.spec.ts`).** After a red full check with more than one branch, `bisect-targets.mjs` reads the output: the failing spec files (vitest `FAIL` lines), the failing step (`check:fast` or `boundaries`), a failed web build, or `unknown`. With known targets the halves are split as before, but each attempt runs only `npm test -- <specs>` (plus the web build first for `scripts/demo` and `scripts/ui` specs when the diff needs it), the failing step alone, or the build alone. A branch that fails the targets alone is refused (exit 3; the message adds `targeted run: …`). The branches that pass get **one** full check (record skip and build rule as for any green path): green lands them all, red (an interaction, or a failure the targets did not cover) falls back to the full bisect of that set. A target file missing from a subset's tree (the culprit adds the failing spec) is dropped from that run, and `--passWithNoTests` covers the case that none is left. More than 200 failing files, spec paths with spaces, unknown targets and install failures bisect in full as before. Main only moves on a green full check.
- **The train's check gets a weighted share of the machine (WP-967, tested by `scripts/ops/resources.spec.ts` and `scripts/orchestrate/land-train-weight.spec.ts`).** The train's full check is the one serial step every land waits for, so `land-train.sh` runs it with `UEB_RUN_WEIGHT=3` (nothing else sets the variable; the build step does not). `scripts/ops/resources.mjs` writes each run's weight into its `running/<pid>` file (empty file = 1) and gives a run `floor(cores * weight / total weight)` workers, and the same share of the memory budget; with the train plus four agents' `check:changed` runs on 64 cores that is 27 for the train and 9 for each other run, instead of 6 each. Runs that already started keep their workers (no rebalancing); `CHECK_MAX_WORKERS` still overrides. The `tests.jsonl` row carries `weight`. **The memory share does not count other runs twice (WP-995):** `availMb` is read now, so it already excludes what older runs hold. `byMem = floor((availMb - 4096) x 0.7 x weight / (weight + youngWeight) / budgetMb)`, where `youngWeight` is the weight of the other runs started less than 60 s ago (the `running/<pid>` file holds `<weight> <start ms>`; no start time counts as old) and 4096 MB (`RESERVE_MB`) is never handed out. `byCpu` stays the fair split by weight over all runs, and the result is `max(1, min(byCpu, byMem))`. The row also carries `youngWeight`, `byCpu` and `byMem`. **The memory share uses a measured budget per worker (WP-986):** `workerBudgetMb(rows, kind)` takes the last 30 rows of the same `kind` from the last 64 KB of `tests.jsonl`, p90 of `peakRssMb / workers` times 1.25, clamped to [512, 1024] MB (1024 with fewer than 10 rows). After a row whose `peakRssMb` exceeded 80% of the memory share it was given (`memShareMb = (availMb - 4096) x 0.7 x weight / (weight + youngWeight)`, WP-998), the next 5 runs of that kind use 1024 again; rows without `memShareMb` never count. The row carries `budgetMb` and `memShareMb`. `MEMORY_SHARE` 0.7 and the 2 GB heap cap stay.
- **A recorded tree skips the check.** Before the full check, the train asks `check-recorded.mjs HEAD` (the reviewers' logic, not a copy) in staging. If the merged tree has a green full-check record (a green `kind: check` row in `tests.jsonl` **and** a green outermost `check` suite line in `check-steps.jsonl`, same git tree, clean; WP-1022, because the parallel steps let `test:record` finish green while `check:fast` or `boundaries` turn red), the train lands on it and each branch's output has a line `full check skipped, green full check recorded for HEAD (tree …): at …`.
- **Affected e2e after the check (WP-1019, tested by `scripts/orchestrate/land-e2e.spec.ts`).** When the check is green (or skipped on a record), the train runs `npm run e2e -- --affected <base>`, the e2e specs the merged changes can affect, in staging, weighted like the check; the land slot covers the e2e gate. A red e2e refuses the culprit (exit 3, step `e2e`) and bisects like a red check, **with only the failing specs (WP-1027)**: `bisect-targets.mjs <log> --e2e` reads the `e2e: failed suites:` line (already judged against the quarantine) and gives one `<suite id> <file>` target per failing spec; each half then runs `npm run e2e -- --suite <id> <file>…` (one call per suite; a file the half's tree lacks is skipped), not the check and not `--affected`. The innocents get one full attempt (check plus affected e2e), red falls back to the full bisect. No usable targets (no report, report errors, an infrastructure exit, a failing file that also holds a quarantined test, a suite named without a file) bisect in full as before. The red full check path is unchanged. Known reds in `scripts/e2e/quarantine.json` do not refuse. Over 10 minutes by recorded duration, the slowest-first subset runs and the skipped specs are printed in the land output. Selection, budget and quarantine: `docs/process/e2e.md`.
- **E2e reds that are red on the base too (WP-1033, tested by `base-reds.spec.ts` and `land-e2e.spec.ts`).** When the affected e2e is red, `affected_e2e` (`land-lib.sh`: `base_reds`, `base_run`) takes the failing specs from the log (`bisect-targets.mjs --e2e`) and checks which of them are red on the train's base too. The base is a detached worktree `<git common dir>/land-base`, moved to the base sha per train (its `node_modules` follow the lockfile like the staging tree's). It runs `npm run e2e -- --suite <id> <file>…` there, in the same land slot. The result is cached in `<git common dir>/base-reds/<base sha>.json` (`base-reds.mjs`: `red` with line, `green`), so every later train on the same base reuses it: while main is stuck on a red spec, only the first train pays. A base red is a suite, file **and line** (`{suite, file, line}`, taken from the Playwright `file:line` items of the base log and the train log): a train red at another line of a file that is red on the base is new and refuses, and the file stays a bisect target (`--exclude` leaves out only files whose every failing line is a base red). When every failing line is red on the base, the train is not refused: the land output carries `e2e: red on base main too, not refusing: <file>:<line>`, and the main checkout's `metrics/raw/ATTENTION.md` (`<git common dir>/../metrics/raw`, not the caller's worktree; entry format of `scripts/metrics/lib.mjs`) gets one `main e2e red: <suite> <file>:<line> (quarantine it, owner lane per the file)` line per newly found base red. When any failing spec is green on the base, the step stays red as before and the bisect leaves the base reds out of its targets (`--exclude`). An infrastructure failure (no usable targets), or a base run that does not check out, install, build or start, is no information: red as before (the log gets a note line). A spec the base lacks counts as green. Cache files of other bases are deleted after 2 days; the base worktree stays for reuse.
- **Gate wait.** `check-gate.sh` exports the time a run queued for its slot as `UEB_GATE_WAIT_MS`; `steps.mjs` and `test:record` write it as `gateWaitMs` to `check-steps.jsonl` and `tests.jsonl`. `npm run -s metrics:check-cost` reports checks per landed WP.
- A waiting caller that was carried by someone else's train gets its result when it gets the lock (`<git common dir>/land-result/<key>`) and prints its own `LANDED` line with the same exit code as before. Interface and exit codes are unchanged for a single land.

Every refusal says why, and keeps its full output in `metrics/raw/land/<UTC stamp>-<branch>-<step>.log` (path printed, gitignored): the output carries `<step>: <first failing line>` with step `check` or `install` (the first line of the log naming a FAIL or error, ANSI stripped, at most 200 characters) and the tail. The event `refused check|install|conflict` is queued in `<git common dir>/land-pending/<WP>.log` and written to `work/events/<WP>.log` with the next successful land of that work package, because main never moves for a refusal. `npm run metrics` counts them (and the older `reverted …` events) as "red lands" in section 2.

The merge is made in a staging worktree, `<main checkout>-land` (outside `.claude/worktrees/`, so `housekeep` never sees it), detached at main's tip. Its `node_modules` is kept between lands; `npm install` runs there only when the merged lockfile differs from the one last installed (the hash is in `<git common dir>/land-stage-lock-sha`). After a green check main is fast-forwarded to the staging merge commit (`git merge --ff-only`, guarded by main's tip), and the main checkout runs `npm install` if the lockfile changed.

The spec runs the real script against a throwaway repo with a fake `npm` on PATH.

**Table docs merge row by row (WP-960, tested by `scripts/orchestrate/merge-table-rows.spec.ts`).** `docs/ia-map.md` and `docs/process/flakes.md` (`.gitattributes`: `merge=table-rows`) are merged by `merge-table-rows.mjs`, a git merge driver that `land-train.sh` and `setup-leads.sh` register idempotently in the shared git config (`ensure_table_merge_driver` in `land-lib.sh`). Table rows are keyed by their first cell: a row changed, added or deleted on one side is taken, and a row changed on both sides is merged clause by clause (split at `; ` and `. `); other lines merge as usual. Two WPs editing different rows or different sentences of one row therefore no longer conflict. What cannot be merged (the same clause changed differently, or a row deleted on one side and changed on the other) is written with `<<<<<<< ours` / `=======` / `>>>>>>> theirs` markers around each side's row and the land stops with exit 2 as for any conflict; the driver never picks a side. The driver merges the whole file like plain git, and says so on stderr, when a file has duplicate row keys, contains CRLF line endings, or has a row that sits in different tables on the two sides and was changed on both. A missing trailing newline stays missing.

## Guardrails that make wrong work hard
- `check:changed` typechecks only the projects the change can reach (WP-1012, `scripts/ops/typecheck-changed.mjs`): the projects whose tsconfig includes a changed file plus every project that depends on the changed workspace package, one `typecheck: web (apps/web changed)` line says which; a tsconfig, package.json, lockfile or svelte.config change, an unknown code path or no merge-base typechecks all, and `check:fast`, `check` and the train keep the full `npm run typecheck`.
- `check:changed` lints only the branch's changed files (WP-997): `check:fast:scoped` swaps `lint` for `lint:changed` (`scripts/ops/lint-changed.mjs`), ESLint and Prettier on the merge-base diff, and the whole repo when a lint config changed or there is no merge-base (one `lint: …` line says which). `check:fast` and `check` lint everything, so type-aware rules on unchanged files show up in the train's full check.
- `check:changed` runs its three steps at once (WP-1015): `steps.mjs --parallel --fail-fast --before typecheck:gen changed check:fast:scoped boundaries test:changed`. The shared generation (`typecheck:gen`, Paraglide and `svelte-kit sync`, stamp-guarded) runs once first and alone, so the steps never race on it; the wall time is the slowest step instead of the sum. `--fail-fast` kills the process group of every still-running step as soon as one is red (their rows in `check-steps.jsonl` carry `exit` 143 and `killed: true`), prints the red step's output at once and exits with its code; the full `check` and `check:fast` keep their own order. All steps share the one gate slot. Inside it, `check:fast:scoped` runs the same way (`--parallel --fail-fast --before typecheck:gen`), so a lint, glossary or max-lines red ends the run in seconds instead of after the ~50 s typecheck (lead-c, 2026-10-04).
- `npm run check` runs its steps in parallel too (WP-1022): `steps.mjs --parallel --fail-fast --before typecheck:gen --after bench:harness check check:fast boundaries test:record`. `check:fast`, `boundaries` and `test:record` start together after the shared generation; the first red one kills the others. `bench:harness` runs **alone, after** the group is green (`--after <script>`, the mirror of `--before`: it times things, so it must not share the CPU with the tests; a red group skips it). `check:fast:run` runs `typecheck`, `lint`, `glossary`, `lint:ui-strings` and `lint:max-lines` in parallel the same way (fail-fast, generation first). The wall time of a full check is now about its longest step (`test:record`) plus the bench instead of the sum.
- Plants are invisible to whole-repo tools (WP-1022): `.prettierignore` and ESLint's global ignores skip `**/*.planted*` and `**/*.planted/`, so a whole-repo `eslint .` beside plant-writing specs cannot hit a file that vanishes mid-run; `npm run boundaries` passes depcruise the config exclude plus `\.planted` for the same reason. A spec that lints a plant on purpose passes `--no-ignore` (`scripts/guardrails.spec.ts`, `packages/server/src/log/console-rule.spec.ts`).
- `npm run check` blocks lint, type, glossary, boundary and test failures. The pre-commit hook (`scripts/ops/precommit.mjs`, WP-953) runs the reference/ guard, a conflict-marker refusal (a staged line starting with `<<<<<<<` or `>>>>>>>`, WP-977), prettier and eslint on the staged files only, glossary-lint (about 0.8 s) and ui-strings-lint (about 0.2 s) on the staged `docs/user` Markdown files (the step is skipped when none is staged), and no typecheck; the typecheck runs in `check:changed` and in the train's full check. The glossary lint splits identifiers (`ToolConfigSchema`, `field_values`) into words and also scans comments and strings; legitimate uses go in the `allow` list of `scripts/glossary-terms.json`, each with a reason.
- `npm run check` also covers `apps/*`: `typecheck:web` (`svelte-check` over `apps/web`, WP-980: the `.svelte` and `.ts` files of the app, with the repo root as workspace so it follows `.svelte` imports into `packages/ui`; the 3 warnings of `packages/ui` print but only errors fail it; about 45 s, the floor of the parallel typecheck; WP-985 measured it and found no faster variant that stays correct (`--incremental` and `--tsgo` with the root workspace do not report errors in `.svelte` files, and with the `apps/web` workspace they leave `packages/ui` untyped; the program is import-closure bound, so a narrower `include` does not shrink it); its `i18n` step and `svelte-kit sync` run once in `typecheck:gen` before it, WP-981), eslint, prettier, and `apps/*/src/**/*.spec.ts` unit tests. Playwright e2e is not in `check` (the land train runs the affected specs after it, WP-1019): run `npm run e2e` (`scripts/e2e/run.mjs`: builds apps/web, sets up Chromium's libraries via `bench/browser/lib/libs.mjs`, then runs every suite: `apps/web`, `e2e/a11y`, `e2e/participant`, `e2e/journeys` and the discovered component suites; a missing suite config fails the run; every run gets its own free ports and data dirs, so several runs in parallel are safe, see `docs/process/e2e.md`; needs the Playwright browsers installed, and on hosts without Chromium's system libraries those too: see "e2e setup" in `apps/web/README.md`, which points at `bench/browser/lib/libs.mjs` for fetching them without root).
- Paraglide message files (`packages/{ui,builder}/messages`, `packages/tools/*/messages`, `apps/web/messages`; the list is `catalogueDirs` in `scripts/messages-sort.mjs`) keep their keys sorted alphabetically, `$schema` first, so parallel branches adding keys with different prefixes do not conflict at the file end. The i18n specs fail on an unsorted file; `npm run messages:sort` fixes it.
- `reference/` is read-only on disk and denied in `.claude/settings.json`.
- Every work package lists `owns:` globs, and the reviewer fails any diff outside them.
- Contracts are merged before implementation starts, so parallel workers can't invent incompatible interfaces.
- Golden scenarios (`fixtures/golden/`) are executable. A behaviour change shows up as a failing scenario, not as a surprise.
- Every work package is written with explicit acceptance items that tests must prove. The implementer writes the tests first, and the reviewer rejects tests that assert nothing.
- When the lead writes a work package, it fills in the **Extensibility**, **Performance** and **UX** sections of the template. A work package without them isn't `ready`.
- `npm run typecheck` runs its five steps (`root`, `ui`, `builder`, `bench`, `web`) in parallel (WP-981: `steps.mjs --parallel --before typecheck:gen`), so it takes about as long as `web` plus the generation. `typecheck:gen` runs first and alone: the paraglide output of every package (ui, builder, the six tools, web) and `svelte-kit sync`, so no two parallel steps write the same generated dir (before, `web`'s i18n rewrote what `ui` and `builder` had just generated). Each step's output is buffered and printed whole, framed `── name (ok|exit n) ──`; the exit code is the first failing step's in the given order; a signal reaches every child's process group. `check:fast:run` stays sequential across typecheck, lint, glossary and so on.
- `bench/**/*.ts` is typechecked too (WP-159): `typecheck:bench` (`tsc -p bench/tsconfig.json`, DOM lib for the jsdom and browser benches) runs inside `npm run typecheck` (it needs the paraglide messages that `typecheck:gen` generates). A contract change that breaks a bench now fails `check:fast`. Guardrail: `bench/harness/typecheck.spec.ts`.
- `fixtures/**/*.ts` is typechecked by the root project (WP-908): the first step of `npm run typecheck` is `tsc -p tsconfig.json --noEmit`, and the root `tsconfig.json` includes `fixtures/**/*.ts`, so a type error in a fixture fails `check:fast`. Every tsc project (root, bench, `packages/ui`, `packages/builder`, `apps/web`) is `incremental` with a distinct `tsBuildInfoFile` under `node_modules/.cache/tsc/`; the svelte-check steps (`ui`, `builder`) run with `--incremental` and cache in `packages/{ui,builder}/.svelte-check/` (WP-912). Guardrail: `fixtures/golden/typecheck-config.spec.ts`.
- No wall-clock assertions in unit specs (WP-147): implementer note: put a budget in `bench/` with `defineBudget`; a spec under `packages/**` or `apps/**` asserts behaviour only, so do not write `expect(performance.now() - t).toBeLessThan(200)`. It is enforced by `scripts/guardrails.spec.ts` (heuristic in `scripts/guardrails/wallclock.ts`, rule in `docs/12-performance-budgets.md`). Guardrail specs plant violations in a temp root through `scripts/testing/plant.mjs`.
- Vitest's global setups skip unchanged codegen (WP-1004, `scripts/ops/codegen-stamp.mjs`, tested by `codegen-stamp.spec.ts`). The four `vitest.global-setup.ts` files each await one shared `runAllCodegen()`, which runs every step concurrently: the Paraglide compile of ui, builder, the six tools and the web app, and `svelte-kit sync`. A step stores the sha1 of its inputs (Paraglide: `settings.json`, the messages files its `pathPattern` names, the `@inlang/paraglide-js` package.json; sync: the web app's svelte and vite configs, `app.d.ts`, the route file names, the `@sveltejs/kit` package.json) in `node_modules/.cache/codegen-stamps/<step>` and is skipped while the hash matches and its output exists. The stamp write is atomic (temp file and rename); a per-step `mkdir` lock with a re-check after acquiring keeps two vitest processes in one checkout from compiling over each other. `UEB_CODEGEN_FORCE=1` forces every step; a failing compile still fails the run. Measured on one trivial spec at load about 25: 15.9 s per run before (five sequential steps, about 14 s of global setup), 1.1-1.2 s with everything up to date, 3.5 s after changing one ui message (ui recompiles alone), 5.3 s on a cold checkout (all steps in parallel). The Paraglide hash also covers the version (nearest package.json) of every inlang plugin module in `settings.json` `modules` (a URL module is hashed as its string). The lock goes stale after 60 s (the longest measured step is 4.0 s) and its holder refreshes the mtime while the step runs. `npm run typecheck:gen` is `node scripts/ops/codegen-stamp.mjs` (WP-1005, the same step list): `npm run -s typecheck:gen` took 9.5 s on every run before, now 0.4 s warm and 4.4 s cold (stamps removed).
- Vitest never removes its scratch directory `<tmpdir>/<21 random chars>/{client,ssr}` (about 25 MB per run). Every vitest start goes through `scripts/ops/vitest-scoped.mjs` (root npm scripts use its CLI, `test-record.mjs` and `bench/harness/cli.mjs` use `scopedTmp()`), which sets a `TMPDIR` it deletes afterwards, also on failure. Guardrail: `scripts/ops/tmp-leak.spec.ts`. Never call `vitest` directly in a script or shell: every vitest config imports `scripts/ops/vitest-scoped.guard.mjs`, which exits with "run tests with npm test -- <path>" unless `UEB_VITEST_SCOPED=1` is set (the wrapper sets it; setting it by hand is the explicit escape hatch, for example for an IDE plug-in, and then /tmp is yours to clean). Run one spec with `npm test -- <path>`.
- Vitest's file module cache (`node_modules/.cache/vitest-modules/<lockHash>`, WP-932, 220-420 MB per checkout) is on in every checkout, agent worktrees included (WP-993, `scripts/ops/vitest-cache.mjs`; WP-973 had turned it off there). Measured on 138 specs in a fresh worktree (two runs): cache off 210 s and 181 s, on and cold 198 s and 193 s (no real penalty), on and warm 127 s and 131 s (30-40% faster than cold, 207 MB), because transform is 87% of a run. It is off when the cache's filesystem has under 8 GB free (`statfs`), and `UEB_VITEST_FS_CACHE=1|0` overrides both. Housekeep removes the whole cache of a worktree whose newest cache file is older than 3 h or whose branch is merged, prints the MB freed, and keeps in main's and `<main>-land`'s cache only the current lockfile's hash dir and, while that dir is over 1 GB (`CACHE_SOFT_MB`), drops entries unused for 24 h, oldest first (WP-999; the land staging's dir had grown to 1.3 GB and 100 000 entries).
- A spec under `scripts/` that spawns a process must not inherit the `UEB_*` variables the land, the check gate and the steps runner export (WP-919): pass `env: specEnv()` from `scripts/testing/spec-env.mjs`, which is `process.env` minus every `UEB_*` key, then explicit overrides (a spec that needs a `UEB_*` var sets it there). Guardrail: `scripts/testing/spec-env.spec.ts` scans `scripts/**/*.spec.{ts,mjs}`; it fails on a spawn without `env` and on one that hands over raw `process.env` (a spread, `Object.assign`, a conditional or `process['env']`; a nested `{ env }` does not count).

## Implementer note: `npm run check` may wait
Commands wait for a free slot in one of two pools (`docs/process/lead-loop.md`, "The check gate", is the single source).

**Blanket triggers (WP-991).** `check:changed` runs every test only for the few real blanket triggers (lockfile, configs, a `package.json` key other than `scripts`/`description`, a golden or schema file nobody reads); the rest is narrowed to reader specs and the import graph (`lead-loop.md`, "The check gate"). `apps/web/src/hooks.server.ts` left the blanket list on 2026-10-03 (lead-c): no spec reads it by path, its spec imports it, and it changed 8 times in 3 days, each time making every agent check run all ~1 040 files. For a narrowed tree, `check:changed` also seeds every non-spec module whose text reads it (WP-1010, e.g. `packages/core/src/testing/golden.ts` globbing `fixtures/golden`), so specs that reach the data through a testkit are selected by the import graph; the selection line names these modules.

**Additive barrel edits (WP-992).** A barrel (a file of only `export ... from` lines, e.g. `packages/core/src/registry/index.ts`) that gained named re-exports of brand-new modules selects no importers: `scripts/ops/barrel-diff.mjs` parses the merge-base and current text with TypeScript's parser (`barrelDiff`), and `check:changed` prints `check:changed barrel <path>: N added exports -> no importers (their users are in the diff)`. The new modules are dropped from the selection too (vitest would walk from them back through the barrel to its ~700 importers); their own specs and importers are changed files, so they run anyway. A name added next to an `export *` is checked against that star's target (parsed one level deep, plus one nested star; WP-996): a local named export wins over the same name from a star, so an added name the target already offers would re-point every importer, and the barrel is selected (`check:changed barrel <path>: added 'foo' shadows export * from './a' -> importers`); a star target that cannot be resolved or parsed, or nests deeper, selects it too. A removed, re-pointed or `export *` line, a non-re-export statement, or an added line for a module that already existed selects the barrel as before. `npm run test:fanout -- --replay` applies the rule.

**Message catalogues in `check:changed` (WP-989).** A change to `<pkg>/messages/**` or `<pkg>/project.inlang/**` selects the importers of that package's compiled Paraglide entry. The packages are read from the tree (`messageEntries` in `scripts/ops/rerun-triggers.mjs`: every `apps/*`, `packages/*` and `packages/tools/*` directory with a `project.inlang/`; the entry is the `--outdir` of its `i18n` / `i18n:own` script plus `/messages.js`), so a new tool package needs no registration. Before `vitest related`, the package's own `vitest.global-setup.ts` compiles it, or, if it has none (the tool packages), `npm run i18n` in the package. An entry still missing runs every test; a `messages/` path outside any such package stays `trigger <file> (no compiled entry known) -> all tests`. Full pool (at most K = 6 at once, `<git common dir>/check-slots/K` or `UEB_CHECK_SLOTS`): `npm run check`, `npm run check:changed` and `npm test` without a path. Light pool (more slots): scoped `npm test -- <path>` (any argument that is not an option; `packages` or `.` still counts as scoped, so do not use it as a way around the gate), `npm run check:fast` (so pre-commit too) and `npm run deps:install` (use it instead of bare `npm ci`; it hardlinks main's install when the lockfiles match and main's install is current, else runs `npm ci` and prints why; WP-958). A command started inside a held full slot takes no second slot, so `check` runs its `check:fast` freely. Under heavy host load the test runner also caps vitest workers and says so. E2e pool (WP-1016): `npm run e2e` (scripts/e2e/run.mjs) takes one of K = 2 e2e slots for the whole run, build included (`<slot dir>/K.e2e` or `UEB_E2E_SLOTS`; `check-gate.sh --e2e`); a full or land slot covers a nested e2e run. Waiting is normal: leave the command running.

**Never bypass the check gate** (WP-140.2). Do not set `UEB_GATE_HELD`, and do not run the check steps by hand to dodge the queue: the gate ignores a hand-set value anyway, and doing it deliberately is a process violation. The queue is first come, first served, so a wait ends in bounded time. If a wait is long (over about 20 minutes, or a holder looks stuck in the wait report), stop and report it to your lead instead of working around it.

### Branch names and the stale-board backfill (WP-963)
`wp/<n>` and `wp/WP-<n>` are the same work package `WP-<n>` (ids with sub-numbers like `wp/WP-140.1` too). `wp_id_of_branch` in `scripts/orchestrate/land-lib.sh` is the one place that derives the id; the done commit, the `merged <sha>` event, the folding of pending events and the branch and worktree removal all use it. A letter suffix (`wp/609b`, `wp/WP-609b`) marks a partial branch of WP-609 (`wp_is_partial_branch`): it lands normally (merge, branch and worktree cleanup) but writes no done commit and does not set WP-609 to done; its events stay in WP-609's pending log until the unsuffixed branch `wp/609` lands and closes the package. Tested by `land-wp-branches.spec.ts`.

`node scripts/orchestrate/backfill-done.mjs` (run once by lead-c through `locked.sh`, never automatically) lists work packages that are landed but not `done`: a first-parent `Merge branch 'wp/<n>…'` on main, or a `wp/<n>` / `wp/WP-<n>` branch whose tip is on main while the package says `review`. A suffixed partial branch alone is no evidence. Dry run by default (prints the table); `--apply` (refused with exit 1 unless `UEB_LOCKED=1`, which `scripts/orchestrate/locked.sh` sets: run `scripts/orchestrate/locked.sh node scripts/orchestrate/backfill-done.mjs --apply`; and only on main) sets `status: done`, adds the `merged <sha>` event where none exists and makes one commit. A second run finds nothing. Tested by `backfill-done.spec.ts`.

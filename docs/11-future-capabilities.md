# 11 · Future capabilities: the extensibility horizon (binding)

None of these is built in v4.0. **Every design must leave room for them.** Before a work package fixes a shape (a schema, a contract, a table, a UI structure), check it against this list. If a choice would make one of these hard or impossible, **stop and report to the lead** (CLAUDE.md R13). The lead decides provisionally, keeps a seam, and records a later topic (`docs/decisions/later/`); the owner reviews it after the build.

| # | Capability | What it means | Keep open now (do not preclude) |
|---|---|---|---|
| H1 | **3D layers: CAD/BIM, point clouds, terrain** | View building models (IFC), 3D city models and scans next to 2D features, with good performance on a phone. Candidate standards: OGC 3D Tiles / I3S (streamed with levels of detail), glTF, IFC → 3D Tiles conversion. | Geometry keeps an optional **Z** coordinate end to end (RFC 7946 allows it). Never drop it. The view/layer model has a **renderer** field from a registry (`maplibre-2d` now, `3d` later), so the Style Spec is one renderer's style, not *the* layer format. Features can reference external assets (blobs, URLs). Don't hard-wire MapLibre into core or into the view model. |
| H2 | **Dispatch and realtime assignment** | An admin in the builder, in QGIS, or through an AI assistant creates, say, 30 work features that don't exist yet and assigns 10 each to three teams. Field devices see them within seconds. Think fire-brigade command centre. | Runs support **atomic batches** (one request, many runs, one transaction, one seq range). Assignment is a property (`participant`, and later `team` types). The sync doorbell must stay fast enough for "seconds, not minutes". OGC API Features Part 4 (create/update) must be mappable to runs, so that QGIS editing becomes runs. A **team / group** concept may come (open decision O12): don't hard-code "role = the only grouping". |
| H3 | **Role-specific apps** | Each role gets its own app: home view, tools, task shortcuts, presets, visible views and data, even its own look. Technicians see different tools than inspectors. | The project file has a **per-role app profile** section (views, tools, default view, presets, UI options). It must be in the schema from WP-010, even if minimal. Nothing in the participant UI may assume "every participant sees the same app". |
| H4 | **AI assistants: participant and admin** | The participant asks "show me my open tasks", and the map loads exactly those, even though no admin configured that view. An admin assistant plans and dispatches work. | **Views are data** that can be created at runtime (ephemeral views): a CEL filter plus a style, always clipped by the compiled permissions. Rule-language evaluation is safe for untrusted input (no I/O, total). An assistant **reads through views** and **writes only by proposing runs** that a human confirms (open decision O15). `explain` exists so the assistant can say *why*. Every capability the UI has must also be reachable through a typed API. The UI must not hold logic an API can't reach. |
| H5 | **Command-centre situational awareness** | A central office sees where teams are and what state their work is in, live. | Live positions and presence are **telemetry**, not observations. They are high-frequency and short-lived, and need a separate channel and store (open decision O14, privacy-sensitive). Don't route them through the observation log. |
| H6 | **External GIS as editor** | QGIS or ArcGIS read and write Überblick data directly. | OGC API Features conformance (docs/09). Every external write becomes a run with the caller's own actor (`admin`, `participant` or `import`), never a direct DB write. |

## How to apply this
- **Schema and contract work packages:** add a short "Extensibility check" to the work-package Log stating which of H1–H6 you touched and why your shape leaves room.
- **When in doubt, generalise the extension point, not the feature.** A registry entry beats a hard-coded case. Don't build H1–H6 early, just don't block them.

# Ein Projekt bereitstellen

Beim Bereitstellen prüft Überblick die Projektdatei und macht sie zur gültigen Konfigurationsversion. Die Seite **Versionen** zeigt die Ergebnisse (siehe unten).

1. **Vorschau.** Sie sehen, was sich gegenüber der laufenden Version ändert: neue, entfernte und geänderte Einträge mit ihrem Pfad. Änderungen, die Daten betreffen (entfernte Typen, Eigenschaften, Optionen, Rollen; geänderte Eigenschaftstypen), sind als kritisch markiert. Eine geänderte Reihenfolge ist eine Änderung, die den Besitzer nennt (Objektart, Aufgabe, Eigenschaft usw. mit seinem Namen, dann welche Reihenfolge), und nie kritisch. Für eine Objektart, die nur eine neue Reihenfolge hat, fragt die Vorschau nicht nach belassen oder verschieben: Eine Reihenfolge berührt kein Objekt.
2. **Prüfung.** Gibt es Fehler (unbekannte Schlüssel, falsche Ausdrücke, Verstöße gegen Sperren der Vorlage), wird nichts bereitgestellt. Jeder Fehler nennt den Pfad und einen Lösungsvorschlag.
3. **Bereitstellen.** Es entsteht eine neue, unveränderliche Version. Die bisherige wird archiviert, bleibt aber lesbar: Eingaben, die auf einem Gerät noch in der Warteschlange liegen, werden weiter gegen die Version geprüft, mit der sie erstellt wurden.

- Dieselbe Datei zweimal bereitzustellen erzeugt keine neue Version. Eine geänderte Reihenfolge allein ist eine Änderung: Sie erzeugt beim Bereitstellen eine neue Version. Wird eine ältere Datei erneut bereitgestellt, wird deren Version wieder aktiv.
- Eigenschaften mit `index: true` bekommen beim Bereitstellen einen Datenbankindex; entfällt die Angabe, wird er wieder entfernt. Etwas anderes verändert die Datenbank nie.

## Laufende Objekte: belassen oder verschieben
Hat eine Objektart sich geändert und gibt es **laufende** Objekte (Zustand *aktiv*), fragt die Bereitstellung einmal pro Objektart (so wie v3 pro Ablauf):

- **Laufende Objekte auf alter Version belassen** (`keep`). Jedes laufende Objekt dieser Art wird an die Version geheftet, die jetzt läuft. Es behält deren Aufgaben, Formulare und Stufen, bis es von Hand verschoben wird (**Auf aktuelle Version verschieben** auf der Seite Versionen) oder erledigt ist. Das Heften geschieht in der Bereitstellung selbst: ein Systemlauf je Objekt, alles oder nichts.
- **Laufende Objekte auf neue Version verschieben** (`move`, Voreinstellung). Die Objekte laufen mit der neuen Version weiter, und die Wertverschiebungen der Bereitstellung gelten für sie.

*Abgeschlossene* und *archivierte* Objekte werden nie geheftet: sie wandern immer mit. Neue Objekte bekommen immer die neueste Version. Bereits geheftete Objekte bleiben in beiden Fällen auf ihrer Version, und Wertverschiebungen berühren sie nicht.

Die Vorschau (`POST /api/admin/p/<Projekt>/plan`) nennt je geänderter Objektart mit laufenden Objekten drei Zahlen: `running_floating` (laufend, ungeheftet: so viele würde *belassen* heften), `already_pinned` (schon geheftet) und `settled_floating` (abgeschlossen oder archiviert, ungeheftet: wandern immer mit). Die Zahl `affected` an einem kritischen Eintrag zählt alle ungehefteten Objekte, unabhängig von der Wahl. Die Wahl steht im Parameter `versions`: `POST …/deploy?versions={"baum":"keep"}`; nicht genannte Arten bekommen *verschieben*. Eine Wahl für eine unbekannte, unveränderte oder leere Objektart (ohne laufende Objekte) lehnt die Bereitstellung mit einem Fehler am Pfad `versions.<Art>` ab. Beim ersten Bereitstellen gibt es keine Wahl.

## Die Deploy-Übersicht („Veröffentlichen“)
**Veröffentlichen** in der gelben Leiste (jede Projektseite) und in der Werkzeugleiste des Builders öffnet dieselbe Übersicht. Sie zeigt, was die Veröffentlichung tut, bevor etwas passiert:

- **Pro Objektart** eine Karte mit Abzeichen (**neu**, **Tiefgreifende Änderung — n entfernt** oder **Keine tiefgreifenden Änderungen**), der Zahl der Objekte und den Änderungen in Worten (zum Beispiel: Phase Maßnahme entfernt, Eigenschaft Vitalität hinzugefügt). Mehrere Änderungen an einer Aufgabe oder Eigenschaft erscheinen als eine Zeile. Beim ersten Veröffentlichen steht jede Objektart nur als **neu** da.
- **Laufende Objekte.** Hat eine geänderte Objektart laufende Objekte, wählen Sie **Laufende Objekte auf ihrer aktuellen Version belassen (Legacy)** oder **auf die neue Version verschieben** (Voreinstellung). Darunter stehen die drei Zahlen der Vorschau: laufend, schon auf älterer Version, abgeschlossen oder archiviert (wechseln immer). Ohne laufende Objekte erscheint die Wahl nicht.
- **verschieben nach.** Enthalten entfernte Phasen, Optionen oder Eigenschaften noch Werte, steht eine Zeile mit der Zahl der Objekte und einer Auswahl: **verschieben nach <Ziel>** oder **Werte verwerfen**. **Veröffentlichen** bleibt aus, bis jede Zeile eine Antwort hat. Zeilen, deren Werte kein Objekt mehr hält (oder nur laufende, die Sie belassen), brauchen keine Antwort und verwerfen nichts.
- **Behebe zuerst:** Probleme des Entwurfs mit **Gehe zu**, das den Builder an dieser Stelle öffnet. Solange es welche gibt, bleibt **Veröffentlichen** aus.
- **Hinweise** (zum Beispiel ein Zeitplan, der nie läuft) sperren nichts.
- **Vorschau-Logins.** Unter den Änderungen steht je Rolle des Entwurfs ein Link, dazu **Keine Rolle**. **Link kopieren** legt ihn in die Zwischenablage (danach steht dort **Kopiert!**). Wer den Link auf dem Telefon öffnet, ist als diese Rolle in der Vorschau angemeldet: Sie sehen den Entwurf mit Demo-Daten, ohne etwas Echtes zu ändern. Neue Rollen bekommen mit dem nächsten Speichern einen Link, bei entfernten Rollen hört er auf zu gelten. Die Links bleiben beim Veröffentlichen gültig, und die Objekte der Vorschau (Demo-Daten und was Testende eingetragen haben) bleiben erhalten: Sie ziehen mit denselben Zuordnungen um wie die echten Objekte. **Demo-Daten zurücksetzen** (mit Rückfrage) erzeugt neue Demo-Daten und verwirft die Testdaten; die Links bleiben, die Anmeldung muss erneut erfolgen. **Schon vor dem ersten Veröffentlichen:** Dieselben Links stehen auch unter Projekteinstellungen, **Status & Freigabe**; ein Projekt aus einer Vorlage hat sie sofort, ohne dass etwas live ist.

Nach **Veröffentlichen** läuft ein Fortschritt, dann erscheinen „Version n ist live.“ als Meldung und in der Leiste. Wurde der Entwurf inzwischen geändert, lädt die Übersicht sich neu. Auf dem Telefon ist die Übersicht ein scrollbarer Dialog, die Auswahlen sind die des Geräts.

## Die Seite Versionen
Öffnen Sie in der Seitenleiste eines Projekts **Versionen** (`/admin/projects/<Projekt>/versions`). Die Seite sieht aus wie v3s Releases-Liste: eine Zeile pro Version, die neueste oben, mit `v<Nummer>`, dem Status (**aktiv** für die laufende Version, **ersetzt** für ältere), der Zahl der Objektarten, der Vorlage und dem Datum. Ohne Versionen steht dort ein Hinweis, dass es noch keine gibt.

- **Zurückrollen.** Jede ersetzte Version hat die Schaltfläche **Zurückrollen**. Ein Dialog fragt einmal nach; dann wird die Datei dieser Version erneut bereitgestellt, mit denselben Prüfungen wie jede Bereitstellung. Die ältere Version ist wieder **aktiv**; die Liste behält alle Versionen. Würde das Zurückrollen Daten betreffen, die eine Zuordnung brauchen, sagt die Seite das und tut nichts.
- **Vergleichen.** Haken Sie zwei Versionen an und drücken Sie **Vergleichen**: Sie sehen unter der Liste jeden neuen, entfernten und geänderten Eintrag mit Pfad und jede geänderte Reihenfolge („Reihenfolge geändert“), gruppiert nach Stelle, und welche Änderungen **brechend** sind.
- **Vorlage aktualisieren.** Ist eine neuere Version der Vorlage veröffentlicht, die Ihr Projekt erweitert, steht über der Liste ein Angebot („Vorlage <Name>: Version <x> verfügbar“). Es zeigt, wie viele Änderungen von selbst gelten, und für jeden Schlüssel, den Sie und die Vorlage geändert haben, Ihren Wert neben dem der alten und der neuen Vorlage: **Meinen Wert behalten** oder **Wert der neuen Vorlage übernehmen**. Einträge, die die neue Vorlage entfernt hat, können Sie entfernen oder behalten (und von Hand korrigieren). Hat jeder Konflikt eine Wahl, sehen Sie die Änderungen und, für brechende Änderungen, eine Zuordnung („Werte verwerfen“ oder „Nach <Schlüssel> verschieben“); **Aktualisieren und veröffentlichen** stellt das Ergebnis bereit. Der Entwurf beginnt danach neu auf der neuen Vorlage.
- **Auf aktuelle Version verschieben.** Haben Sie Objekte mit *belassen* auf einer älteren Version gelassen, zeigt deren Zeile **<n> Objekte noch auf dieser Version** und die Schaltfläche **Auf aktuelle Version verschieben** (nur solange noch Objekte dort sind). Der Dialog nennt, wie viele Objekte von welcher auf welche Version wechseln, und fragt, wie bei der Veröffentlichung, für jede kritische Änderung, die Werte dieser Objekte betrifft: **verschieben nach <Ziel>** oder **Werte verwerfen**. **Verschieben** bleibt aus, bis jede Zeile eine Antwort hat. Alle Objekte dieser Version wechseln, auch abgeschlossene und archivierte. Jeder Wechsel ist ein Systemlauf im Verlauf des Objekts, alles oder nichts: lehnt irgendein Lauf ab, bleibt alles unverändert. Danach steht die Zahl nicht mehr dort; die Geräte laden die Objekte unter der aktiven Version nach. Es gibt keinen automatischen Wechsel, wenn ein Objekt abgeschlossen wird.
- **Entwurf verwerfen.** Oben rechts verwirft **Entwurf verwerfen** nach einer Rückfrage alle Änderungen im Builder, die noch nicht live sind. Der Entwurf entspricht danach wieder der aktiven Version.

Die Seite funktioniert auf dem Telefon: die Zeilen brechen um, die Auswahl der Zuordnung ist die Auswahl des Geräts.

Nicht auf dieser Seite: **Veröffentlichen** (siehe oben, die Deploy-Übersicht) und **Als Vorlage veröffentlichen** (kommt ins Projektmenü). Bis dahin: `npm run admin -- publish-template`. Für Assistenten und Skripte: `GET /builder-api/<Projekt>/plan?versions={…}` (die Vorschau des Entwurfs) und `POST /builder-api/<Projekt>/deploy` mit `{ revision, mappings, versions }`. Veröffentlicht wird immer mit Ihrem Klick: Builder und Assistenten bereiten nur vor.

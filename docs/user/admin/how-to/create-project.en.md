# Create a project

Any signed-in admin account can create a project in one step. You find it on the **Projects** page (the first page after sign-in).

**On screen:** the page shows one card per project with name, description (without one: the creation date after "Created") and **Open project**. **Create project** (top right) asks for project name, description and template; **Empty project** comes first. An empty name shows "Name is required". You then land on the new project's **Participants** page.

**Through the API** (the same steps the screen uses):

1. **Pick a template.** `GET /api/admin/templates` lists the published templates, the newest version per key, **Empty project** (`leer`) first, with German and English labels.
2. **Create.** `POST /api/admin/projects` with `{ "name": "Baumkataster Nord", "description": "…", "template": "leer@1" }`. The response (201) gives `id` and `key`. Überblick generates the key from the name (umlauts are spelled out, a duplicate name gets a number). An empty name or an unknown template gives 400 with the fields concerned. `GET /api/admin/projects` lists the projects you are a member of, newest first: `id`, `key`, `name`, `description`, `createdAt`, `template` (`key@version` of the deployed version, else `null`) and `published` (`true` only after the first deploy).
3. **Configure.** The project has a **draft** made from the template at once and you are a member. Nothing is live yet: the first **Publish** (see [Deploy a project](deploy.en.md)) turns it into the first version.

## Menu on the Projects page

The split button next to **Create project** and the ⋮ button on every card hold the project-file actions.

- **Import from file** (chevron next to **Create project**): pick a project file (`.yaml`, `.yml` or `.json`, up to 1 MB). A file that extends a published template becomes the new project's draft. A complete template file is published as a template version first and the project is built on it. The new project is not live until its first **Publish**. If the file has problems, a list shows each one with its place in the file and no project is created.
- **Export schema** (⋮ on a card): downloads the project's current draft, template and changes together, as one YAML file named after the project. Importing that file on another instance gives an equal project.
- **Publish as template** (⋮ on a card): needs a project that was published at least once. The dialog asks for the template name, a key (starts as the project key) and a version (starts as the next minor version of that key, or 1.0.0). The version then appears in the Template list of **Create project**. A version number can only go up, and inside a major version nothing may be removed.

- **Export full project (ZIP)** (⋮ on a card): downloads an archive with the project file, every object of every Objektart (in any state, archived and deleted included) and all attachments. It works for a project that was never published; the archive then holds the project file only. The participants come along too: with roles, custom columns, status and their **login token**, so existing logins and QR codes keep working on the new instance (admin accounts are not included). **The file contains login credentials: keep it confidential and do not share it.** The archive is a backup of today's state, not of the history: who changed an object and when is not in it. Personal data that was erased stays erased.
- **Export data (CSV)** (⋮ on a card, after the first publish): downloads a ZIP with one CSV file per Objektart, with the columns of the data page, a comma as the separator and the position as `lon` and `lat`. Deleted objects are left out, as on the data page.
- **Export GeoPackage** (⋮ on a card, after the first publish): downloads a GeoPackage with one layer per Objektart, in WGS84.
- **Import full project (ZIP)** (arrow next to **Create project**): choose an archive. The dialog names the file and its size and lets you give another name; **Import** uploads it and creates the project. If the archive holds objects, the project is published at once, because objects need a config version; without objects it stays a draft. A progress bar shows uploading and processing, you may close the dialog and the import goes on. If the archive holds participants, they are restored with their login tokens. A token exists only once per instance: if a token of the archive is already in use (for example in the original project on the same instance, when you make a copy), those participants get new login links and all others keep theirs; the dialog names the number ("n participants received new login links"). The original's logins stay as they are. If a token appears several times inside the archive itself, the archive is damaged and the import is refused. Archives without participants (older exports) import as before, without participants. If it fails, the dialog lists the reasons; a project begun by it stays, with incomplete data, under its key, and you delete it yourself. Unpacking is strictly limited (4 GB unpacked, 2 GB per file, 4 MB for the project file and the manifest, 4 MB per line of a data file); an archive that unpacks to more than it declares is refused at once. The template of the archive's file is published as a template of its own, `import_…`, when its name exists with other content. Largest file: 2 GB, but at most the instance's `UPLOAD_LIMIT` (default 50 MB); for larger archives set a higher value.

Through the API: `POST /api/admin/templates` (`project`, `key`, `version`, `label`), `GET /api/admin/projects/<project>/schema` and `POST /api/admin/projects/import` (multipart `file`); for the archives `GET /api/admin/p/<project>/export/zip`, `…/export/csv` (with `?type=<Objektart>` one single CSV file), `…/export/gpkg`, `POST /api/admin/projects/import-zip` (the ZIP as the request body, optional `?name=`) and `GET /api/admin/projects/import-zip/<job>` for the progress.

The operator can still create projects with `npm run admin -- create-project`.

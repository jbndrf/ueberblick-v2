# The builder at a glance

The builder edits your project file. It never writes data, only the file (more precisely, the overlay on top of the template).

## Where you are
You open the builder on a feature type's data page with the **Builder** button. It always edits one feature type of the project; you switch to the next one in the sidebar. Time-based rules (`elapsed`, `schedule`) are described in [Time-based rules](how-to/time-based-rules.en.md). Versions, rollback, compare and the template update are on the project's **Versions** page (see [Deploy a project](how-to/deploy.en.md)), the roles on the **Roles** page (see [Roles](how-to/roles.en.md)).

## The builder of one feature type
At `/admin/projects/<project>/types/<feature type>/builder` the builder of a single feature type opens in three columns, as in v3: the **catalog** on the left, the chosen view in the middle, the details of the selection on the right. A feature type that does not exist gives the error 404.

- **Toolbar.** "Save" writes the draft. "Publish" saves what is still open and opens the deploy overview (see *Deploy a project*); "Go to" in the overview opens the builder at the place of the problem (`?select=`). Next to it the view switch toggles between "Workflow", "Model" and "Code", followed by the gear "Feature type settings" (see below); the choice is in the address (`?view=`), so a reload stays in the view. On the right is the name of the feature type; change it in place and confirm with Enter or Tab. The "Code" view hides the catalog and the details.
- **On a phone (below 768 px).** The canvas takes the full width and the toolbar wraps. The **Catalog** button (toolbar) opens the catalog as a sheet from the left; the **Details** button opens the details of the selection as a sheet from the bottom, and without a selection it shows the "Default view". Choosing something in the catalog, on the canvas or in the problems list closes the catalog and opens the details; clearing the selection closes them. Closing a sheet (Escape, a tap outside) keeps the selection, so reopening shows the same entry. Both sheets have their own **Save** button at the top, so you can save without closing them. On a desktop nothing changes.
- **Problems badge.** Next to the view switch a small number shows the problems of this feature type (and those of the whole project). A click lists them, and a click on an entry selects the task, automatic action or property it is about. There is no separate problems panel.
- **Feature type settings (gear).** The gear in the toolbar opens the feature type's own settings on the right (as a sheet on a phone): its name, "Visible to roles" (empty means every role; create a new role right in the picker, it applies after "Publish") and "Private entries" (participants only see what they created themselves). These are the same settings as in the data page header and in the permission matrix; where visibility is set per property, a note points to the model. "Default filter & marker icons" is a link to the feature type's data page, where you set the property for filters and marker icons under "Icons".
- **Unsaved changes.** After an edit "Unsaved changes" appears next to "Save". Closing or leaving the page asks first. If the draft was changed elsewhere in the meantime, the reload message appears and your changes stay on screen.
- **Catalog.** Under "Structure", "Stage" and "Entry" add a stage or an entry (a task from the map). Under "Add action", "Button" and "Form" add an action that people carry out (a new one, like a new "Entry", is open to every role of the project and "Admin", like v3; the roles under "Who may use this" narrow it), and "Automatic" adds an automatic action. An **action** has a condition and an outcome and is carried out by people or automatically; an automatic action owns its outcome and never shows as a button. Below, "Actions" (with the filter "All", "People" and "Automatic") and "Field library" list what the feature type already has; a click selects the entry. "Stage" always works, also on a new feature type without stages: the first stage is the start and an end stage "End" is added, all as one change (one undo takes it all back). When the template locks adding one (for example the stages of the tree cadastre), the chip is greyed out and says "Locked by the template"; the same goes for any locked chip. On a phone the sidebar closes as soon as a new feature type is open. The column on the right has a width that fits what it shows (narrow for a task, wide for the form editor); the canvas shrinks beside it.

- **Field definition.** A click on a property in the "Field library" opens its field definition on the right (the column stays, only its content changes). From top to bottom: **Label** (saved when you leave the field), the **key** with "Copy key" (it never changes, not even when you rename), the **field type** (a different type is asked about when going live), **Required** and, for a select, the **options**: every option has a name you change by clicking it (the key stays), arrows to move it, "Remove", and at the bottom you add a new option. If you remove an option that objects still hold as a value, going live asks for the target (move to); the note under the options says so. For a reference you choose the target ("Points to").
- **Visible to roles / Editable by roles.** Right in the field definition you set which roles see and which edit the field. Empty means all. On a phone the choice opens as a full-screen dialog with search and "Done", on a desktop as a list under the field; type a name and press Enter to create a new role (it only applies after going live). If it says "Nobody", no role may currently edit the field. If the file sets who sees the objects of the feature type at all, "Visible to roles" is locked; change that first in the "Model" view under Permissions. The permission matrix shows the same settings as an overview.
- **The "Model" › "Fields" and "Tasks" views.** "Model" opens on "Fields" (next to "Permissions" and "Tasks"). **Fields** shows the layout of the object type's Data view as participants see it: one tab per data tab ("Data" first), the fields in their rows and columns, plus "Hidden" with the number of hidden fields, the library of hidden fields. Each card shows the label (a star for required), the type, the kind of value (single value, observation, computed), the key and where the field is used ("2 tasks, 1 automatic actions"; "Not used" otherwise; hover for the names). Click a card to open the field definition on the right. The eye hides a field, the arrow brings it from "Hidden" back to the data tab, the bin deletes it entirely (the dialog says how many forms it disappears from; the object type's phase field cannot be deleted). Change the layout by dragging a card by its grip (as in the form editor): onto a tab (also "Hidden"), onto the gap between two rows (a row of its own) or onto the left or right half of a single card (the two share the row). There are no move buttons; the arrange icon on the card still opens the selects "Left", "Right" and "Full width" (full width cannot be dragged) and "Move to tab" (also to "Hidden"). "Add field" creates a text field "New field" in "Hidden" and opens its field definition. The search box filters all fields by label, key and type. **Tasks** is the table of this object type's tasks: name, "Offered in stage", "Who may use this", start (manual or by a rule), number of form fields and target phase; click a row to open the task on the right. On a phone the tables scroll sideways and the name stays.
- **The "Model" › "Permissions" view (matrix).** The overview for changing many things at once: the roles are the columns, the rows are "Can see the objects of this object type" and below it, per field, a row with the field's name and, indented, "Can edit the value". A green icon means allowed, a pale red one not allowed, a dashed border means it applies to all roles (new ones too). Clicking an icon toggles that role in that row; taking out the last role leaves nobody, and when every role takes part it applies to all. "Advanced" also shows "Can create objects" and "Can delete objects"; "Simple" hides them again. The **Private objects** switch lets each person see only the objects they created themselves (it writes the object type's visibility condition; if a custom one is already set, the switch stays off and shows it, and it is changed in the "Code" view). Where the draft differs from the template, the cell shows a small arrow ↺; clicking it resets only that cell to the template. A locked icon (explained on hover) cannot be changed here because the file keeps that setting elsewhere. Save with "Save" like everything in the builder; the same settings are in the field definition (see above). If the project has no roles yet, a note says so. On a phone the table scrolls sideways and the row names stay in place.
- **Delete field entirely.** Asks first and names the forms the field will also disappear from; its roles go with it. The property that carries the process (the stage) cannot be deleted.
- **The "Workflow" view (canvas).** It draws the process of the feature type as v3 did: a card per stage (coloured left edge: green = start, pink = end, blue = in between) holding the buttons of its tasks, the "Global" box for tasks without a stage, a green entry (the task from the map) with a dashed arrow to the start stage, and an amber box per automatic action ("automatic", trigger and outcome in one line, for example Priority → high; the action's own task is not a button). A task that only the system runs and no single automatic action owns carries the same mark (bolt and "automatic"; tooltip "Only ever run automatically"). Each button shows its tools (form, quick edit) and a dot on the right from which the arrow leads to the target stage. An automatic action's arrow is dashed, an "otherwise" arrow dotted. A click selects a stage, task or rule (its details open on the right); a click on the background clears the selection; Tab and Enter work without a mouse. Rename a stage by clicking its name; rename a task by double-clicking its button (or F2). Enter keeps it, Escape cancels; **Save** writes the draft. Only the label in your language changes, the key stays. If the template locks the stages (`lock`), the document refuses the rename and the toolbar says so. Scroll, pinch or drag the background to pan and zoom. You can drag any box (stage, "Global", entry, automatic action) to another place with the mouse or a finger. The place is stored for this project (not in the project file, so it creates no new version) and is the same for every admin; after a reload the box is where you left it. Boxes you never moved are arranged automatically. **Editing on the canvas** (as in v3): "Add stage" at the top left adds a stage. Below the buttons of each stage and in the "Global" box, "Add button" adds a new task (in a stage it is tied to that stage). Draw an arrow from the dot on the right of a button to a stage; it says the button puts the feature in that stage. Select an arrow with a click (or Tab and Enter), **Delete** removes it (the button stays), and at the end of the selected arrow you drag it to another stage. If the arrow exists, the task's condition ties it to another stage, or the template locks the task, the reason shows at the bottom right and nothing changes. The same works without dragging in the task's "Outcome" tab ("Transition to"). Change the order of the buttons of a stage with the grip on the left ("Reorder") or with Alt+Arrow up/down on the button; it also applies to participants. Drag a tool icon (form, quick edit, location) onto another button to move it there; hold Alt to copy it. Without a mouse: Space on the icon picks it up, Enter on a button drops it there (with Alt it copies), Escape cancels. A form takes its fields along; a task has only one form, and only one step per task writes a property. A right-click (or the context key) on a button, stage or automatic action opens the menu "Copy key" and "Delete task/stage/automatic action"; before deleting you see what gets a problem. On an icon the entry is "Remove from task". A chip from the catalog ("Stage", "Entry", "Automatic", "Button", "Form") can be dragged onto the canvas and is created there. The entry and rules have no dot to draw from: the entry always leads to the start stage, an automatic action's arrow follows its outcome. On a phone everything works with a finger; the menu opens on a long press, otherwise delete in the details on the right. A feature type without stages shows only "Global". If a task leads to a linked entry of another feature type (for example a measure created on a tree), its button shows "linked" and the name of that feature type underneath; a click opens the builder of that feature type, which has its own process. There "Sub-process of:" and the name of the parent feature type at the top left link back. The page "Relations" stays the overview of all links.
- **Stage pane (right column).** A click on "Stage" in the catalog adds a stage and opens it here; with nothing selected the column shows v3's "Default view" (the data every participant sees). The header holds the stage name (click to rename; it edits the same label as the canvas, the key stays), the type "Start", "Intermediate" or "End" (written to the feature type's `process`: there is exactly one start and at least one end, so the start only moves by choosing another start), the role of the preview, a delete button (opens the confirm dialog, which lists what the deletion breaks, as the canvas delete does) and a close button. If the template locks its stages, name and delete are disabled and a lock says so. Below the header, the action bar shows the stage's buttons: the tasks pinned to this stage by their condition and the global ones (offered in every stage, with a globe mark). The plus button adds a button pinned to the stage and opens its task; a click on a button opens its task. Choose a role under "All roles" and the buttons that role is not offered here are dimmed, with the reason as a tooltip; the preview asks the same rules the app uses. The "Data" view lists the properties; for a chosen role, hidden ones are greyed out and read-only ones are marked. Tabs of the feature sheet (add, rename, drag) follow with the sheet's tab layout. **Daten tabs (as in v3).** Under the buttons sits the Data view with its tabs ("Data" first). "Add tab" (+) creates a tab "New tab"; a click on its name renames it (Enter commits; a name that already exists is refused), the cross next to it deletes it. Deleting asks first and says that the tab's fields stay and then sit without a tab in the "Data" tab. "Add fields to the active tab" opens the field library (the right column then grows from 520 to 720 px, as in v3, so the preview keeps its size): a click on a field (a hidden one too) puts it at the end of the active tab, fields already there are greyed out. Change the order by dragging a field by its grip (as in the form editor): onto the gap between two lines (a line of its own), onto the half of a single field (the two share the line) or onto a tab; a field of the library can be dragged the same way. There are no move buttons and no "Left", "Right", "Full width" choice any more; in a tab you made, "Remove from tab" stays. The tabs are the same as under "Model" > "Fields" (`display.tab`, `tab_order`); a new tab shows up there as soon as a field sits in it.

### The details of a task
Select a task in the catalog and its pane opens on the right. At the top are "Task", the name, the key with **Copy key**, and **Delete task**. Below are five tabs as in v3; a task always opens on "Definition".

- **Definition.** *Button text* is the name participants see (saved when you leave the field; it cannot be empty). *Description* explains the task. *Offered in stage* limits the task to features in one stage (every stage when nothing is chosen); if the condition is already on the "Condition" tab, the choice changes only that line. *Linked objects* names which other objects the task may read and change (for example the area a tree stands in). Each row has a *name* and a *relation* of the task's object type (only relations to exactly one object, with the target object type); "Add linked object" adds a row, × removes it. While form fields use that object ("Add linked field") it can be neither removed nor renamed; a dialog lists the form fields and the expressions that still depend on it, and you take those out first. If a step of the task still uses the object, the file reports the reason and does not apply the change. *Entry task* makes the task one that starts on the map at a position and creates a new feature of this type. *Colour* is a named colour (primary, success, warning, danger, neutral) or a hex value such as #3b82f6 (swatch or text); *Icon* is the name of an icon, for example `check` or `triangle-alert`. "Require confirmation" asks before the task runs; the *message* is the question. A value the file does not accept is reported in place with the reason and not applied.
- **Condition.** "Only available when…" is rows of field, comparison and value, joined by AND (or OR); "Add condition" adds a row, the cross removes it. Every change applies at once. If it causes a problem (for example a value that does not fit the field), the reason shows in place and the file stays unchanged. A condition the rows cannot express stays text and is changed there. **Who may use this** picks the roles ("Admin" is also an option): empty means no person may run the task, only its automatic actions; the task then carries the "Automatic" mark. For a task that creates features, the choice also writes the type's permission to create such features. You can create a new role right in the picker; it applies only once the draft is deployed. "Any feature" or "Own only" limits the button to features the user created themselves (the creator condition); it is not shown as a row, and the roles and rows stay untouched.
- **Form** (v3: "Tools"). The steps participants go through one after another; one submit at the end. Each row is a step with up and down arrows and a bin. "Form" is the task form (once only; if you remove the step, Überblick asks first and names the fields that go with it). "Quick edit" lets participants change chosen properties inline (an emptied value clears the property): you pick the properties in the picker. "Location" lets them move the pin or redraw the shape; you pick the geometry property. Each property is written by one step only (or the form). "Edit fields" (the pencil on the form step) opens the form editor, see below.
- **Outcome.** What happens after the form. "Transition to" sets the stage (it is the same arrow the canvas draws); "No transition" removes it. Below are the actions, in the order they run: "Set value" (a value or an expression; "Insert property …" and "Operators …" put text at the cursor), "Clear value", "Set status" (a select property and its option), "Create feature" (at most one per task; add another task for a second one) and "Set lifecycle" (active, completed, archived, deleted). Each action applies "always", "only if …" (condition rows as on the "Condition" tab) or "otherwise" (when no earlier conditional action ran). Arrows reorder, the bin removes. An expression the check rejects is not applied and the reason shows in place. Erasing personal values is edited on the "YAML" tab.
- **YAML.** The whole task as text. **Copy form** puts only the task's form (and its steps, if it has any) on the clipboard as YAML; the message "Form copied" confirms it. "Apply YAML" takes your change as the smallest change to the overlay (all or nothing); an error is named with its line.

On a phone the role picker opens as a full-screen sheet (with search and "Done (n)"), on a computer as a list under the field.

**Delete task** asks first. Rules that run the task are listed: they stay and then show a problem in the problems badge until you change or delete them.

### The details of a rule
Select an automatic action in the catalog (or on the canvas) and its pane opens on the right. At the top are "Automatic action", the name (type in the field to change it), the key with **Copy key** and **Delete automatic action**. Below are two tabs, the same as for a task: "Condition" (when it fires, the trigger, and its condition together) and "Outcome". Who may carry out a task is in its condition; the "Automatic" mark in the catalog shows an automatic action. An automatic action always opens on "Condition". **Automatic** under "Add action" in the catalog adds a new automatic action: it starts with v3's trigger "When created" (the feature type's entry; "On a value change" when it has none) and its own outcome that only it can run.

- **Trigger** (the first part of the "Condition" tab). "Trigger type" chooses when the automatic action runs: *When created* (an entry), *On a stage change* (from stage, to stage; "Any stage" means every one), *On a value change* (watched properties, none = all; plus "In stage"), *On a schedule* (a five-field cron; an error shows the reason in place, otherwise the next run in UTC), *After a time* ("After" N hours, days or months, "Since" created, last changed or enters stage; with "enters stage" "In stage" limits it to one stage), *When conditions become true* (fires the moment the conditions become true; they are rows below, as for a task, and at least one is required) and *After a task*. Time triggers run on the server. A choice the feature type cannot support (no entry, no process) is greyed with the reason. A hand-written trigger the picker cannot express is shown as such and stays unchanged until you choose a type. 
- **Condition** (the second part of the "Condition" tab). "Fires while these conditions hold": rows of field, comparison and value, as for a task. What the trigger writes itself (the stage, for example) does not appear twice here. A condition the rows cannot express stays text.
- **Outcome.** An automatic action runs a task as a system run; its steps are the outcome. When it has its own task (as "Automatic" adds it), you edit the steps here with the same list as the "Outcome" tab of a task: set value, clear value, set status, create object, set lifecycle, each "always / only if ... / otherwise" (that is v3's condition per step and its stopping at the first match). When the task of the automatic action is used elsewhere too (by people or by other automatic actions), the pane shows its name (the automatic action sits in that task, so it is not chosen here). An automatic run has no form: a "Set value" step of the task gives the values, and the builder reports a required field without a value as a problem. Open it with **Open task**; you change its steps there, so a shared task is never changed unnoticed.

**Delete automatic action** asks first and deletes the action's own task with it; a task with other actions or people stays (a template's automatic action is hidden, not deleted). An automatic action is stored inside its task (`auto:`); the "Condition" tab of the trigger *When conditions become true* has no second list of rows, because its condition is the trigger itself. A schedule always says how long an Objekt must have been idle: empty or 0 means every Objekt.

### The form editor
"Edit fields" in the "Form" tab opens the form editor in place of the task details (as in v3). At the top are the title, the task and the cross that goes back to the task; at the bottom **Delete form** (asks first and names the fields that go with it). On a phone the editor is the details sheet, with its own cross next to the sheet's.

- **Field library.** The properties of the feature type that the form can take (not the stage, no geometry and nothing another step of the task writes). A tap or click adds the field at the end of the open page; drag it and it lands where you let go. What is in the form already is greyed. Expanded (the arrow on the edge of the palette) the list shows the type and the number of uses.
- **Field types.** Short text, long text, number, email, date, file, dropdown, multiple choice: a tap creates a **new property** of that type in the feature type ("New field", writable by all roles as in v3) and adds it to the form. Long text and email are text fields with the appearance `multiline` and `email`. Smart dropdown and table selection place a choice field with a filter and a reference field respectively (see below).
- **Add linked field.** The dashed button below the field types takes a property of a **linked object** into the form, for example the name of the area a tree stands in. In the dialog you pick the relation first (the links the task names under "Linked objects" in its Definition; with none, the dialog says so), then the property (searchable; one already in the form is greyed). The card carries the mark "From <object type>". You set the width on the card like for any field. The field panel has **Placeholder** (this form only), **Help text** (applies in every form that has this field and changes the property's description on the linked object type), **Read-only** (on only shows the value, off (the default) saves the change to the linked object in the same run) and **Required**. If the linked object does not exist, the field is not shown. "Delete field entirely" does not apply: the property belongs to the other object type.
- **The preview.** The form as participants see it: page tabs, the page description, then the lines, each with one full-width field or two half-width ones. Each card shows the label (click to rename the property; Enter applies, Escape cancels), a star for required, the input itself and marks for "Has validation rules" and "Shown only under a condition". A click on the card opens the field's settings (see below; the back arrow: "Back to the form").
- **The card's bar** (with a mouse on hover and on the selected field, on a touch screen always): the bin (takes the field out of the form, the property stays) and `⋯` (also right click) with "Remove from form", "Delete field entirely" and "Copy key".
- **Dragging.** Drag the card's grip with a mouse or a finger: while you drag, drop zones appear before every line and at the end (left, full, right), at the empty side of a half-width line and beside a single card (it moves aside). The entries of the palettes can be dragged there too (with a mouse). Dragging onto a page tab moves the field to that page. Escape cancels. The card's arrows do the same without dragging.
- **Pages.** Order, width (full, half left, half right) and page of a field are set by dragging only. The first field of a page opens it; its tab carries the title (pencil on the open tab), the text field below it the description. `+` adds a page; it comes into being once you drag a field onto it. The cross on the open tab takes the page out, its fields move to the page before; no field is lost.
- **Width and line belong to the form.** Half or full width, the line and the order of the fields are part of this one form: changing them here leaves other forms and the Daten view unchanged. The Daten view has its own layout (Model › Fields).

#### A field's settings
A click on a card opens the settings of that field on the right (in place of the palettes and the preview). At the top are the back arrow, the icon and name of the field type and, below it, the name of the field; at the bottom **Remove from form** (the field leaves this form only, the property stays).

**Display in this form** ("Applies to this form only", with two exceptions, see Help text and Required):
- **Placeholder**: the grey text in the empty input, in the builder's language.
- **Help text**: the text under the field. It belongs to the property and applies in **every** form that has the field; the panel says so under the field.
- **Required**: applies in this form only. If the property is required itself (field definition) the switch is on and locked, with the reason.
- **Prefill**: Empty, Constant (a fixed value), Last value (the object's current value) or Computed (an expression, for example `today()`). For Date and Date and time, **Prefill with the current date/time** sets the prefill to today or now.
- **Require a change before submitting** (with any prefill but Empty): participants must change the prefilled value.
- An expression that does not hold (an unknown field, the wrong type) is **not** applied; the reason shows at the top of the editor.
- A computed field has no placeholder, no required and no prefill.

**Validation** (text: minimum and maximum length; multiple choice: minimum and maximum selection). The rule applies in this form and has a matching message. If the field already has a rule of its own (from the Code view) it stays as it is and a note says so. A text field also has a **Regex pattern** (for example `^[A-Z]{2}-[0-9]+$`; it must match somewhere in the text, anchor it with `^` and `$`); a pattern the checker cannot run safely (for example a look-ahead) shows its problem under the input and is not saved. A **whole-number** or **number** field has a **Step**: the value must be a multiple of it. For a whole number the step is a whole number of at least 1; for a decimal it is a number above 0 with at most 9 decimal places (for example 0.5 or 0.01; 0.3 is a multiple of 0.1, checked exactly). An invalid step shows its problem under the input and is not saved.

**Smart dropdown** (the "Smart dropdown" tile places a choice field whose options depend on an earlier answer). In the field settings the section shows for every choice field that has a filter:
- **Source field**: "Browse available fields" opens a dialog listing the choice fields **above this one in the form**, grouped by page, each with its options. A click picks the source field; the cross next to it removes it. Changing the source field starts with empty lists. While no source field is picked, every option is offered.
- **Conditional options** › **Configure options**: a dialog with a tab per value of the source field (a dot shows that the tab has options). On the tab you tick the options that are offered when the source field has that value; explanation texts show under the options. Type a new option at the bottom: it is added to the field and offered for the open tab. A value with no ticked option offers nothing. Every change is in the draft at once; **Done** closes the dialog.
- If the field has a filter you wrote yourself in the Code view, it shows read-only as a **Rule** and stays as it is.
- **Explanation text of an option** (answer plus explanation text in v3): in the field definition each option has an "Explanation (optional)" line under its name. Participants see it under the option. Removing the option removes its text.
- **Multiple choice**: set the field type to multiple choice in the field definition; the filter stays.

**Table selection** (the "Table selection" tile places a field that points at a table; if there is no table yet, a field for participants). The "Select from" section in the field settings:
- **Table**, **Participants** or **Roles**: this is the type of the property (a reference to the table, or a participant property). "Table" is disabled while there is no table. **Roles**: the field stores the key of a role of the project (the picker shows the role names). The dialog there has **Allow multiple selections**, **Self-select only** (these roles can only select roles they hold themselves) and **Can select anyone** (these roles can select any role). With neither set, every role can select any role; with one set, roles in neither list cannot select a role (the dialog says so). The form on the device offers only the roles allowed, and a run that picks another one is refused.
- **… Configure** opens the dialog; "Configured" shows that something is set. At the top is the switch **Allow multiple selections** (for Table and Participants): several entries can then be picked and the field stores a list. It stays when you switch between Table and Participants. If the project's template requires multiple selection, it cannot be turned off here because the stored values are lists. For **Table** you pick the table (with search, a full-screen list on a phone), the **Display field** and **Roles with visibility**. The **Display field** decides which property of the table (text, number or select) names the entries in the picker and in the data table; "Display name (default)" uses the table's first required text. If you choose another table, a display field that table lacks is dropped. **Roles with visibility**: only participants with one of these roles see the entries; **empty means all roles** (as in every role picker; v3 said that nobody sees anything here). It is the same setting as "Visible to roles" in the field definition.
- For **Participants**: **Self-select only** (these roles can only select themselves) and **Can select anyone** (these roles can select any participant). A line in the dialog says what holds for all other roles: with "Can select anyone" roles set, the others may only select themselves; with only "Self-select only" roles set, the others may select anyone. This applies in this form. If the field already has a validation rule of its own (Code view), it shows read-only as a **Rule**.

**Edit field definition** goes one step deeper (back arrow: "Back to the field settings"). It shows the field definition as described above plus, by type: for a number **Min** and **Max**; for Date, Date and time and Time the **date mode**; for a file the **allowed file types** (All files, Images only, Documents only) and the **maximum files**; and under **Advanced** the switch **Computed**. Computed means the value is calculated from other fields of the object and never entered (for example `self.hoehe_m * 2`); it is recalculated whenever a value it uses changes, and every calculation is in the history. The expression is saved with "Apply"; if it does not hold, the reason shows below and nothing is written. Below it is the list of the fields the expression reads (an unknown one in red). A field that is in a form cannot be computed: take it out of the forms first. **Hidden from Daten tabs** (checkbox under "Editable by roles"): the field appears in no Daten tab but under "Model" > "Fields" in "Hidden" (`display.hidden`); unticked, it is back where it was.

Every change is in the draft at once; **Save** writes it, and participants see it after "Publish". A changed order (fields, options, tasks, rules, tools, views) is a change too: the draft counts as changed and the overview says "order changed". If a type has only an order change, the overview counts no objects as affected: no object is touched. A change that would create a new problem at the task (a field no role of the task may write, say) is not applied and the reason shows at the top of the editor.

## Where it comes from: template, changed, added
When your project builds on a template, every field in the form editor and every task, at the top of its details, carries a small mark: **Template** (it is as the template has it), **Changed** (you changed it against the template) or **Added** (it exists only in your project). The same words are used in the margin of the Code view and in the matrix. For a changed field the **⋯** menu (or a right click on the field) has **Reset to template**; for a changed task it sits next to the mark. It restores everything you changed on that field or task. A field or task from the template cannot be deleted, only **hidden**: the entry then reads "Hide" (the confirmation, for a field a hide question with a **Hide** button, says it stays in the template and is hidden in this project) instead of "Delete field entirely" or "Delete task". When the template locks an element, the mark shows a lock with the reason, and reset and hide are switched off. A project without a template shows no marks. Hidden template elements appear at the end of the catalog lists "Actions" and "Field library", greyed; **Show again** brings them back. The same goes for automatic actions: the mark sits beside the key in their pane, with **Reset to template** and **Hide** in place of "Delete automatic action". In the Workflow view, stages, task rows and rules carry a small dot (its colour and tooltip name where the element comes from); their right-click menu has **Reset to template** (for a changed element) and **Hide** (for an element from the template), switched off when the template locks the element. The stage details show the same mark; a changed stage offers **Reset to template** there, a template stage **Hide** instead of delete, and a locked stage shows the lock.

## The Code view
The **Code** switch in the toolbar shows the whole feature type (Objektart) as YAML: the type and its tasks, with their automatic actions (`auto:` inside a task), written as in the template (`types:`, `tasks:`). The catalog and the right-hand pane are hidden in this view. The narrow margin next to the line numbers shows where each line comes from: an orange bar means "Changed by you", a green one "Added by you", no mark "From the template" (the legend under the editor explains it). **Copy** puts the text on the clipboard, **Reload** discards what you typed and shows the draft again.

Type as in any editor; the fold arrows collapse sections. On the value of a reference (for example `property:`, `start:`, `end:`, `roles:`, `run:`, `on:`, `creates:`, or `see`, `create`, `write` in `permissions`) the editor offers the properties, stages, roles, tasks and feature types of the project by name; the key is what gets inserted. Errors show while you type: a red mark on the line and the list "Line n: …" above the editor. A value the template locks (`lock`) is refused with its line.

**Apply** writes your change into the draft as the smallest change (all or nothing): a changed value overrides the template's, a new entry under `tasks:` or under a task's `auto:` is added, a deleted template entry is hidden. The text then shows the draft's own notation. As elsewhere nothing is saved yet: **Save** in the toolbar saves the draft. The feature type itself cannot be deleted or renamed here.

Two tabs sit above the editor: **Code** (the text above) and **Overlay**. Overlay shows only what this project changed, added or hid on this feature type compared with the template, as overlay text (read-only, with **Copy**). If the project changed nothing there it says "No overlay entries – everything comes from the template." A project on the empty template has no tabs, because there is nothing to compare with.

The same notation exists for a single element: select a field or a rule (or the feature type), switch the pane's toggle from **Form** to **YAML** and use the same editor and **Apply**. A task has its "YAML" tab for this.

## A choice that depends on an earlier answer (file format)

A choice field in a task's form can carry `choice_filter`: an expression that is true or false for each option; `option` is the option key and `form.<field>` the earlier answer. Example: `form.gruppe == 'laub' ? option != 'kiefer' : option == 'kiefer'`. Only true options are offered, and the server refuses any other answer (`invalid_input`). Write an explanation text per option on the property: `option_hints: { linde: Tilia cordata }`. A `choice_filter` on a field that is not a choice is reported as a problem (`choice_filter_invalid`). The screen for it is the smart dropdown in the field settings (see above); write a filter of any other shape in the Code view.

## Problems
The problem counter in the toolbar lists every problem in the project file with the explanation, the path and a hint how to fix it, in the builder's language (German or English, including the detail of an error inside an expression, such as the type check) (see [Problems in the project file](reference/problems.en.md)). Clicking a problem opens the feature type or task and puts the focus on the affected field.

## Keyboard
Everything works without a mouse. Tab moves through the toolbar, the catalog, the view in the middle and the details on the right. Enter opens an entry or jumps to a problem.

## Your draft is saved
Every project has one working draft. It is created from the deployed version the first time you open the builder, and every change you make is saved automatically (bottom right: "Saving …", "Saved"). Close the page and come back later: your edits are still there. The draft is not live until it is deployed.

If a colleague (or an assistant) changed the same draft in the meantime, the builder stops saving and shows "The draft was changed elsewhere. Reload to see the current version." Nothing you see is overwritten; press **Reload** to load the current draft.

If no version is deployed yet, the builder says "There is no project file to edit yet." Deploy a version first.

The draft and the problems are also available through the API: `GET` and `PUT /builder-api/<project>/draft`, `GET /builder-api/<project>/problems`.

## Language

The builder follows the admin area language (Account, Language): labels and texts are German or English.

When the draft refuses a change, the builder shows a short line in your language ("Locked by the template" when the template locks the element, otherwise the reason, for example "Not applied: the file would no longer fit the schema" or, when something was already set to a single value, the request to reset it first; "Not possible." stays only for an unknown reason), never a technical English message. The "Unsaved changes" note keeps its place in the toolbar, so the canvas does not move on your first edit, and the builder page itself does not scroll.

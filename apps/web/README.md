# apps/web

The SvelteKit 2 app (adapter-node): **the one server process**. It composes `packages/server` (SQLite adapters, auth, deploy), the builder, and the participant app (`packages/ui`, `packages/client`, the tools).

## Layout

- `src/hooks.server.ts`: resolves the two session cookies independently into `locals.admin` and `locals.participant` (`Auth.authenticate`, O(1) each; WP-705, as v3). `null` means no session of that kind.
- No `hooks.client.ts`: zod runs jitless because every zod import goes through `@ueberblick/core/zod` (the CSP forbids eval; WP-959, WP-975), so the participant shell never imports zod just to configure it.
- `src/lib/server/runtime.ts`: the composition root: `control.db`, the auth service, the control.db `TemplateSource` and lazily opened project databases (`<data dir>/project-<key>.db`), the preview refresher (`rt.previews`, WP-341) and the instance settings store (WP-638).
- `src/lib/server/handlers/*`: plain handlers `(call) -> Response`. **Routes hold no logic**: each `+server.ts` is one line that exports a handler (H4: everything reachable through the typed API).
- `src/lib/server/authz.ts`: admin authorisation for `/api/admin/p/<project>/*`: an admin principal with a membership in that project (provisional; roles are template-defined keys).
- `e2e/`: Playwright against the **built** process (`flow.spec.ts`, `rss.spec.ts`, `builder-draft.spec.ts` and others). The participant app has its own suite in `e2e/participant/` at the repo root (see "Participant app").

## API (JSON)

| Route                                                       | Who                  | Does                                                                                                                                                                                                 |
| ----------------------------------------------------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/health`                                           | anyone               | `{ ok, principal }`                                                                                                                                                                                  |
| `POST /api/auth/exchange` `{ token, device? }`              | anyone               | reusable QR token (no default expiry; revoked ones fail) -> session cookie; the consent gate comes first (403 `{ code: 'consent_required' }`, WP-638), then 401 `{ code }`                           |
| `POST /api/auth/login` `{ email, password, totp, device? }` | anyone               | admin login -> session cookie; 401 `{ code }`                                                                                                                                                        |
| `POST /api/auth/logout`                                     | anyone               | revokes the session, clears the cookie                                                                                                                                                               |
| `POST /api/admin/p/<project>/plan` (project file)           | admin of the project | dry run: `{ ok, diff }` or `{ ok: false, problems }` (422)                                                                                                                                           |
| `POST /api/admin/p/<project>/deploy` (project file)         | admin of the project | deploys (template or overlay); overlays resolve `extends` against the templates published in control.db                                                                                              |
| `GET /api/admin/p/<project>/versions`                       | admin of the project | config versions                                                                                                                                                                                      |
| `GET /api/admin/p/<project>/draft/status`                   | admin of the project | the project's draft state (E-13): `{ dirty, neverPublished, problems, revision, type }`; the admin shell reads it for the publish bar and the sidebar badge; not cached (`no-store`)                 |
| `GET /api/instance/consent`                                 | anyone               | the consent gate for the sign-in page (WP-638): `{ required, accepted, title, body, acceptLabel, rejectLabel, footerPages }`; an empty text is the page's built-in default in the visitor's language |
| `POST /api/instance/consent` `{ decision }`                 | anyone               | the decision (`accepted` or `rejected`); sets the one-year `consent` cookie and answers `{ ok }`                                                                                                     |
| `GET /api/instance/legal`, `GET /api/instance/legal/<slug>` | anyone               | the instance's legal pages: the list (`{ pages: [{ slug, title }] }`) or one page with its HTML `body`; 404 for an unknown or malformed slug                                                         |
| `GET` / `PUT /api/instance/settings`                        | any admin account    | the instance settings (`requireConsent`, the consent texts and labels); the instance has no project scope, so no membership is needed; 401 anonymous, 403 a participant                              |
| `PUT` / `DELETE /api/instance/legal/<slug>`                 | any admin account    | creates or replaces a legal page (the slug is 1 to 100 of `a-z0-9-`, the `body` is HTML, sanitised on display); `DELETE` removes it (204), 404 when absent                                           |
| `GET /api/admin/p/<project>/features`                       | admin of the project | the admin feature list: paged rows of one type, searched, sorted and filtered per column (`{ rows, next, total }`; full contract in docs/03 and `docs/user/admin/reference/features-api.md`)         |
| `GET /api/admin/p/<project>/features/distinct`              | admin of the project | the distinct values of a column with their counts (at most 500)                                                                                                                                      |

Errors: 400 malformed body or not a project file, 401 not signed in, 403 no access, 404 unknown project, 422 compile problems.

### Builder (admin, `src/routes/(builder)`)

| Route                                                    | Who                  | Does                                                                                                                                                                                                                                                                               |
| -------------------------------------------------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/builder/<project>[/<type>[/<task>]]` (`?lens=<key>`)   | admin of the project | the builder shell (`@ueberblick/builder`); the `[project]` layout holds it, the pages only select the location                                                                                                                                                                     |
| `GET /builder-api/<project>/problems` (`?locale=de\|en`) | admin of the project | the problems of the project's draft, the same list the panel shows: `{ revision, count, problems }`; 404 `no_draft` while the project has no draft (it is created by the first read of `/draft` or the builder page)                                                               |
| `GET`/`PUT /builder-api/<project>/draft`                 | admin of the project | the working draft (A-011): `GET` creates it from the deployed version on first read (404 `no_version` when nothing is deployed); `PUT { overlay, revision }` is compare-and-swap: 200 `{ revision }`, 409 `{ code, draft }` when stale, 400/413 for a bad or oversized (1 MB) body |
| `GET /builder-api/<project>/preview`                     | admin of the project | the state of the project's preview (WP-341, docs/08): `{ status, problems, version, updatedAt }`; `status` is `ready`, `stale` (the draft has problems) or `dropped` (no live preview); `version` and `updatedAt` are the deployed preview version or null                         |

`src/lib/admin/draft/draft-source.server.ts` is the one place the routes reach the draft store (`DraftStore` in `packages/server`): `loadDraft` reads without creating, `openDraft` creates it from the deployed version and returns `null` only when nothing is deployed, and `ensure`/`put` back the `/draft` handlers. The browser draft client sits beside it in `src/lib/admin/draft/` (WP-326): `draft-saver.ts` (the builder's `[project]` layout and the admin builder page `/admin/projects/<project>/types/<type>/builder`), `versions-client.ts` (the builder's `VersionsApi` over `fetch`) and, for the admin shell, `status-store.svelte.ts` and `publish-client.ts` (publish bar and sidebar badge). Builder code is loaded only by these routes (`participant-no-builder` in `.dependency-cruiser.cjs`; `e2e/builder-bundle.spec.ts` checks the build); the one non-route file that may import it is `src/lib/admin/draft/versions-client.ts` (it implements the builder's `VersionsApi` and is imported by `(builder)` routes only). The problems handler is `createProblemsHandler({ authorize, loadDraft })`, tested directly in `problems-handler.spec.ts`.

Run and sync routes are mounted by WP-105/WP-106 in their own folders. The participant surface (bootstrap, config, sync, runs, blobs, prefs) resolves `<project>` to a real project or its live preview (the served key `<key>__vorschau`) through `runtime().participantProject` (WP-341, docs/03); OGC, MCP, admin, export and the builder keep `runtime().project` and stay blind to previews.

## Participant app (`src/routes/(participant)`, `src/lib/participant`)

| Route                     | Does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/login`                  | v3's sign-in card (WP-609): token tab, QR tab (camera scanner loaded on first open, image upload), language and theme switch. `?token=` signs in with no tap, clears the address and goes to `/map`. Scanned links from another origin are refused as invalid codes. Refusal codes map to texts in `src/lib/participant/login/exchange.ts`. When the operator requires consent (WP-638), the consent modal opens before anything is sent: the operator's title, body and labels (the built-in defaults in the visitor's language when empty), the legal pages of the consent footer readable in place, and a `?token=` link waits behind it until the decision; while the gate is closed the server refuses `exchange` (403 `consent_required`). |
| `/map`                    | bootstrap, then the device runtime, then v3's map screen (`shell/MapScreen.svelte`: header, map, bottom bar, sheets through `shell/sheets.ts`). Without a session it goes to `/login`. Client-only (`ssr = false`): IndexedDB, MapLibre and the run queue have no server rendering.                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `/legal`, `/legal/<slug>` | the instance's legal pages without sign-in (WP-638): the list (an empty notice when none are published) and one page with its text, German or English (Accept-Language, English first); 404 for an unknown or malformed slug.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

The route composes packages and re-implements nothing (R1). `src/lib/participant`:

- **Shell chunk** (loaded first, must stay under the docs/12 row of 250 KB gzip and free of core geo, MapLibre, tools and builder): the screen of `/map` composed in `shell/` — `MapScreen.svelte` (orchestrator), `Header.svelte`, `BottomBar.svelte`, `MapCanvas.svelte`, `SheetHost.svelte` and the sheet registry `sheets.ts` (one lazy `import()` per slot; `layers`, `filter`, `settings`, `tools`, `create`, `recent`, `feature`, `cluster` and `chat` are registered, a slot without an entry opens nothing and its button stays) — plus the interim `FeatureSlot.svelte` (feature sheet with WP-624's `FormSheet.svelte`), `NoticeBar.svelte`, `ProblemBar.svelte`, `PreviewBanner.svelte`, and the pure helpers `bar.ts`, `panels.ts`, `apps/web/src/lib/participant/shell/progress.ts`, `standort.ts`, `badge.ts`, `status.ts`, `apps/web/src/lib/participant/map-view.ts`, `tools.ts`, `apps/web/src/lib/participant/messages.ts` (the typed accessor over the catalogue), `apps/web/src/lib/participant/http.ts`. They import types from the device chunk, never its code.
- **Device chunk** (`device.ts` and what it imports, loaded by dynamic import: `@ueberblick/client` with core geo, core.plan and core.form): `openDevice(bootstrap, ports, locale)` builds the store, config versions, run queue, sync and the readers; every side effect is a `DevicePorts` port, so it runs under test with fake-indexeddb and in the browser with `browser.ts`. Nothing is global, `close()` lets go (H4).
- **Sync is wired in one function**, `start-sync.ts` `startSync` (WP-567): it opens the sync host of `@ueberblick/client` (`openSyncHost`) in the mode the app picks, builds the run queue over the host's store (`queueFor`), passes the queue as the `PredictionRefresher`, calls `queue.onPulled(cursor)` after every pull, `resetBackoff` and `drain` on online and focus, and asks the queue to send again after a backoff (the queue never retries by itself). In the browser the host is a dedicated Web Worker (`browser.ts` starts `sync.worker.ts`, which is one line around `createWorkerSide`: the page transport and the page decoding run in the worker, the main thread keeps a read replica and the run queue); under test it is in-thread or a `MessageChannel` (`device.spec.ts` runs the same cases on both). The mode is `DevicePorts.sync`; a worker that cannot start is an error, never a silent fallback. Several tabs of one participant share one sync: the worker choice carries `tabs(name)` (`browserTabs`, WP-572), so only the tab holding the Web Lock runs the sync worker. Blobs stay main-only.
- `view-source.ts` is the map's `FeatureSource` over the device's `Facts` (synced state with queued predictions on top, the view's filters through core.expr; `changed.ts` feeds it the ids of a page or "all"); `reader.ts` reads each feature under its own config version (the `createFeatureConfigs` resolver the run queue's planner shares) and asks core.plan which tasks a role may start and which are offered on a feature (while a feature's version is not on the device yet the sheet is read-only without tasks, `awaitingVersion`), and builds the feature's Aktivität timeline (`warmActivity` loads the store's run rows and names; `activityOf` returns one `ActivityEntry` per run, newest first, the device's own queued and refused runs on top); `submitter.ts` is the task sheet's `RunSubmitter` over the queue; `blobs.ts` holds a tool's file bytes until their run is stored; `drafts.ts` keeps one draft per key in localStorage.
- **Tools** load through `ToolLoader`s (`tools.ts`): photo, file, draw, measure, search and chat are dynamic imports (`chat` is a factory with the device's dependencies, `apps/web/src/lib/participant/tools/chat.ts`). `fieldOptions` gives each field its tool options: the project's `tools.<key>`, the role's on top, and for `draw` the field's `geometry_type` and the map centre. Measure is offered only when the map can report taps by position (`apps/web/src/lib/participant/map-view.ts`, see Known gaps).

**Sign-in language.** The route's own strings are in its own Paraglide catalogue, `apps/web/messages/{de,en}.json` (keys `participant_*`, compiled by `npm run i18n -w @ueberblick/web` to `src/lib/participant/paraglide`; `apps/web/src/lib/participant/messages.ts` is only the typed accessor, no string table); the design system's follow the same language through its `PARAGLIDE_LOCALE` cookie, which the app sets from the person's pick (the `ub:locale` key, shared by the sign-in page switch and Optionen; `apps/web/src/lib/participant/login/locale.ts`), else the cookie of a former visit, else the browser language.

**Offline start (WP-631).** `src/service-worker.ts` (SvelteKit's native worker, routing in `src/service-worker/`) precaches the build, the static files and the `/map` and `/login` shells at install and serves them cache-first, so a start never waits for the network; `/api/**` and `/participant-api/**` are never answered from the cache. Install, update and the manifest: `docs/07-sync-and-offline.md` "Service worker and install".

### Known gaps (all logged in `work/WP-550-participant-app-route.md`)

- `mapToolPort(handle, style)` is the tool port over `MapHandle` (WP-576): Measure is offered while a map is mounted (`canTap`), Search centres it, and a tool's overlay is drawn under the id `tool` in the role's primary token. The e2e (`e2e/participant/map.spec.ts`, WP-585) covers the mounted map: Measure draws and clears its overlay, and Search centres the map on the found feature (asserted on the settled map centre, the `data-center`/`data-idle` seam `shell/MapCanvas.svelte` writes).
- The shell cannot open its task sheet from outside, so a task started from the feature sheet or a tool opens in a second `Sheet` of the route (the same `FormSheet`).
- Problems (`notices.ts`, codes in `APP_PROBLEM_CODES`: `style_unresolved`, `tool_setting_invalid`, `map_unavailable`, `sync_host_fault`, `stale_bundle`) are listed in the `ProblemBar` above the shell. `style_unresolved` and `tool_setting_invalid` cannot reach a device for an accepted config: compile embeds layer styles and rejects a bad `tools.search` setting (`tool_source_invalid`, WP-577). The runtime keeps both as guards until B-013 removes the dead paths. The one a user sees is `map_unavailable` (a map that fails to mount; the list stands in) and, since WP-656, a fault of the sync host (`host-fault.ts`): a worker fault is `sync_host_fault`, a page older than an update (host codes `bad_version`, `unknown_kind`, `ill_typed`) is `stale_bundle`, and a diverged replica is re-read, no problem. Both also show on the Profil sync card, where v3 shows a failed sync.
- Server replies are checked before use: `decode.ts` refuses a malformed bootstrap (the app says so), and the compiled config, from bootstrap and from `config/<version>`, goes through core `hydrate`, which throws on a mismatch. `config/<version>` serves only versions that were deployed (status deployed or retired); a draft is 404.
- The map source re-reads only the features a committed page names (`DeviceStore.onChange`), coalesced to 200 ms; a queued run walks the view's types once (O(features of those types), one user action). A view filter that reads a related feature can be stale for an unchanged feature until the next full walk.
- A tool's `blobs.put` keeps the file in memory until its run is stored; the run transport does not upload blobs yet.
- **MapLibre worker files** (WP-165): `vite.config.ts` (`maplibreWorkers`) copies `maplibre-gl-worker.mjs` and `maplibre-gl-shared.mjs` to `_app/immutable/maplibre-gl-<version>/` in the client build (served immutable, same URL in dev); `WORKER_URL` in `shell/MapCanvas.svelte` points there. The service worker precaches them (WP-717): SvelteKit's `build` list does not hold them, so `workerAssetsPlugin` writes the list of worker files to `_app/worker-assets.json` and the install caches it. The folder name carries the installed maplibre-gl version (Vite `define` `__MAPLIBRE_VERSION__`), so an upgrade gets a fresh path automatically.

## Configuration (environment)

`src/lib/server/config/` is the **only** reader of the environment: `loadConfig(env)` parses and validates every variable once (`config()` keeps the result; `init` in `hooks.server.ts` calls it at start, so a missing or bad value stops the start with one message naming the variable). `runtime.ts` and `routes/api/mcp/source.ts` import the parsed config; a new setting is declared in `config/vars.ts` and parsed in `config/parse.ts`.

- **Documented variables** (`DOCUMENTED` in `vars.ts`): exactly the variables of `.env.example` at the repo root, with defaults and explanations. A test compares the two lists. `PUBLIC_URL` is required, `LOCAL_HOSTS` is required with `HTTPS_MODE=direct`, and `ADMIN_EMAIL` and `ADMIN_PASSWORD` come as a pair. Empty counts as unset.
- **Internal variables** (`INTERNAL`): `DATA_DIR` (default `./data`; the image sets `/data`), `UEBERBLICK_LOG_LEVEL`, `UEBERBLICK_MCP_SECRET`, `UEBERBLICK_INSECURE_COOKIES` (`1` drops the `Secure` cookie flag; plain-http local runs and e2e only).
- **Wired by WP-940:** `DATA_DIR`, `TIMERS_INTERVAL_S`, `PUBLIC_URL` (the entrypoint derives adapter-node's `ORIGIN` from it, `scripts/tls/origin.mjs`, WP-954), `APP_PORT` (compose publishes it; inside the container the app listens on `PORT=3000`). The others are read by the HTTPS, security and backup steps.
- adapter-node itself reads `PORT`, `HOST`, `ORIGIN` and the `*_HEADER` variables before the app code runs.

## HTTPS (WP-941)

The app only speaks plain http; TLS ends at the admin's proxy (`HTTPS_MODE=proxy`) or at the front in the same container (`direct`).

- **The gate** (`src/lib/server/tls/gate.ts`, called first in `hooks.server.ts`): `X-Forwarded-For` and `X-Forwarded-Proto` count only when the socket peer is in `TRUSTED_PROXIES` (in direct mode: loopback, where the front sits; `TRUSTED_PROXIES` is ignored). The client is the first address from the right that is no trusted proxy; it replaces `getClientAddress()` for logs and rate limits. Direct mode redirects (308) every request that did not come through the front to `https://<host>:<HTTPS_PORT>` (host from `LOCAL_HOSTS` only; `/api/health` is exempt for the container probe). `url.origin` (the cross-site form check, WP-954) comes from adapter-node: in proxy mode `ORIGIN` = `PUBLIC_URL`, derived by `scripts/tls/origin.mjs` (the entrypoint evals it, the e2e config calls `originEnv`; nobody sets `ORIGIN` by hand). In direct mode there is no `ORIGIN`: `PROTOCOL_HEADER`/`HOST_HEADER` name the `X-Forwarded-*` headers that the front sets from the host the browser used, and the front answers 421 for a host that is not in `LOCAL_HOSTS`, so a form POST works on every `LOCAL_HOSTS` address and a foreign Origin is refused. This is safe because of the gate, not because the app port is hidden (compose publishes `APP_PORT` in every mode): forwarded headers count only from a loopback peer, and any other peer, forged `X-Forwarded-Host` and matching Origin included, gets the 308 above before any action runs (pinned in `scripts/tls/origin.spec.ts`). `ADDRESS_HEADER` stays unused.
- **Certificates** (`scripts/tls/cert.mjs`, `loadTlsMaterial`): local CA (EC P-256, 10 years) and a server certificate (397 days) for exactly `LOCAL_HOSTS`, in `$DATA_DIR/tls`. Reuses what is there; reissues the server certificate when the SAN differs, it has under 30 days left or it no longer chains to the CA. The one function is the seam for own certificate files later (`TLS_CERT_FILE`, `TLS_KEY_FILE`). `asn1.mjs` is a minimal DER writer (no openssl in the image).
- **The front** (`scripts/tls/front.mjs`): `node scripts/tls/front.mjs <app command>`; `scripts/docker/entrypoint.sh` prepends it when `HTTPS_MODE=direct`. It listens on 8443 inside the container (compose publishes `${HTTPS_PORT}:8443`), forwards to the app on loopback with `X-Forwarded-*`, and ends with the app.
- **Setup page** `/setup/zertifikat` (`src/routes/setup/zertifikat`, `src/lib/server/tls/{ca,downloads}.ts`): public; reads only `$DATA_DIR/tls/ca.crt` (never a key). Downloads `ueberblick-ca.crt` and `ueberblick.mobileconfig`; the QR code is inline SVG (`qrcode-generator`).

## Build, run, test

```bash
npm run build -w @ueberblick/web      # writes apps/web/build
npm run start -w @ueberblick/web      # node build/index.js
npm run e2e -w @ueberblick/web        # needs a build first
```

**e2e setup.** The specs run in real Chromium (`builder-draft.spec.ts` opens the builder). Install the browser once with `npx playwright install chromium`. Some sandboxes lack Chromium's system libraries (`libnss3`, `libnspr4`, ...); without root they are fetched as Debian packages and unpacked into a local directory that `LD_LIBRARY_PATH` then points at: `ensureLibs` in `bench/browser/lib/libs.mjs` does this for the benchmarks and documents the mechanism. Run `ldd` on the Chromium binary to see what is missing, and set `LD_LIBRARY_PATH` for the `npm run e2e` call.

`better-sqlite3` is a `dependency` of this package on purpose: adapter-node keeps `dependencies` external, and the native module must not be bundled.

## Measured

Idle RSS of the built process with 5 deployed projects: about 85 MB (budget 120 MB, docs/12). `e2e/rss.spec.ts` asserts it.

## e2e of the participant app

`e2e/participant/` (own Playwright config; fallback port 4175, overridden per run by `npm run e2e`, see `docs/process/e2e.md`): `npm run build -w @ueberblick/web`, then `npx playwright test -c e2e/participant/playwright.config.ts`. `participant.spec.ts` signs in with a QR token in a fresh browser context and covers the map screen, opening a feature, running a task offline and syncing it and a server refusal shown with its typed reason; `map-shell.spec.ts` the phone bar, Standort and tapping a feature. `bundle.spec.ts` reads the build and asserts the shell closure of `/map` against the docs/12 row and that core geo, MapLibre and the builder are lazy chunks. `offline.spec.ts` (WP-631) proves the offline cold start at phone and desktop size and that no data endpoint ever lands in a cache.
The Aktivität tab has its own component suite (`apps/web/src/lib/participant/feature/activity/e2e`): a Vite harness over the real tab at phone and desktop size, run with `npm run e2e -- --suite comp:web/lib-participant-feature-activity` (port `E2E_COMP_WEB_LIB_PARTICIPANT_FEATURE_ACTIVITY_PORT`, default 4183).

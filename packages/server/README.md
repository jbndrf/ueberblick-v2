# @ueberblick/server

Server adapters that implement core ports (docs/03-architecture.md). Exists so far: the SQLite layer (WP-100), blobs and the outbox worker (WP-107), the deploy pipeline (WP-112), timers and derived-edge recomputation (WP-108), import and GeoPackage export (WP-111), and the OGC API Features (WP-110).

## Database (`src/db`)

- `driver.ts`: the `Db` interface (`exec`, `prepare` -> `run/get/all/iterate`, `transaction`, `close`) and `openSqlite(path)`. It is the **only** file that imports `better-sqlite3` (A-001). Every connection gets WAL, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=5000`, an 8 MiB page cache.
- `migrate.ts`: `migrate(db, migrations)` applies pending, strictly ordered migrations, each in one transaction, and records them in `schema_migrations`. A second run does nothing. Migrations are safe across processes (WP-1032): each step runs in an IMMEDIATE transaction (write lock at BEGIN, waiting up to the 5 s busy timeout) and re-checks `schema_migrations` inside it, so two processes opening one file migrate it once and the returned ids are the ones this call applied. `migrationState(db, migrations)` is the read-only companion: it reports the `pending` (known, not applied) and `unknown` (applied, not known) migration ids and never creates or changes anything; the backup drill checks restored databases with it (`docs/process/backup.md`).
- `control-schema.ts`, `project-schema.ts`: the DDL of docs/04. CHECK lists are generated from core registries (`ACTOR_KINDS`, `RUN_OUTCOMES`, `CONFIG_VERSION_STATUSES`) through `inList`.
- `open.ts`: `openControlDb(path)`, `openProjectDb(dir, key)` (file `<dir>/project-<key>.db`), `projectDbPath`. `:memory:` works for tests. Project keys must match the config `Key` pattern.

```ts
const control = openControlDb(join(dataDir, 'control.db'));
const project = openProjectDb(dataDir, 'trees');
project.transaction(() => {
  /* one run */
});
```

Measured: opening 5 project DBs adds about 4 MB RSS.

## Auth (`src/auth`, WP-103)

`createAuth({ control, now, participantRoles })` implements the `Auth` contract (`auth/contract.ts`). Everything is stored in control.db (`credentials`, `sessions`, `accounts`, `memberships`).

- **Participant tokens (WP-606, C-002):** reusable and stored readable (`credentials.token`, unique in the whole instance; the token alone identifies participant and project). `issueCredential(projectId, participantId, expiresAt?)` generates `XXXX-XXXX-XXXX-XXXX-XXXX` (20 symbols of 32 unambiguous ones, 100 bits, `GENERATED_TOKEN`); `issueChosenCredential(..., token, expiresAt?)` takes an admin-chosen one (`TOKEN_RULES`: 8-128 characters of letters, numbers, `-`, `_`; refused `token_too_short | token_invalid | token_duplicate`). `exchange(token)` works any number of times on any device and sets `last_used_at`; refusals `credential_unknown | credential_revoked | credential_expired | participant_disabled` (`AUTH_ERRORS`). There is no one-time claim.
- **Admin view and replace (WP-607):** `currentCredential(projectId, participantId)` returns the newest non-revoked token readable (an expired one is still shown, with its date; `null` when none). `replaceCredential(projectId, participantId, token?, expiresAt?)` issues the chosen or a generated token and revokes the participant's other tokens in one transaction (sessions stay); setting the token that is already current only updates its expiry; a refusal (`token_too_short | token_invalid | token_duplicate`) changes nothing. The participants admin API builds on these (`http/participants/service.ts`).
- **Participant roles (WP-136):** `participantRoles(projectId, participantId)` is required (no silent empty roles). It returns the roles, or `null` for a disabled participant (`disabled_at`): no exchange (`participant_disabled`, the token is kept), and `authenticate` returns `null`. It runs on every `authenticate` with no cache, so a role change or disabling applies on the next request. `participantRolesOf(projectDb, id)` reads `participants.roles`; the web runtime wires it. `participantRolesOf` returns `null` for a missing or disabled roster row: the token exchange is refused (`participant_disabled`, 401) and `authenticate` returns `null` for an existing session (A-025, supersedes A-014).
- **Sessions:** the cookie value is a 256-bit random id, stored as a hash. `authenticate(id)` is one indexed lookup, `null` when unknown, expired or revoked. `toActor(principal)` maps onto the core `Actor`. Lifetimes: participant 90 days, admin 12 hours (`params.ts`). A participant session slides: when its last renewal is 24 h or more ago, `authenticate` writes `expires_at = now + 90 days` and returns `renewedExpiresAt` (epoch ms) so the HTTP layer can re-set the cookie (WP-608). Inside 24 h there is no write and no extra query. Admin sessions never slide.
- **Revocation:** `revokeParticipant` (all credentials + sessions), `revokeSession`, `revokeAccountSessions`.
- **Admins:** `createAdmin` (scrypt, 32 MiB), `verifyPassword`, `enrolTotp` (refuses when already confirmed) / `resetTotp` (admin path, ends sessions) / `verifyTotp` (RFC 6238, SHA-1, 6 digits, +-1 step, a step is usable once), `loginAdmin(email, password, code)`. An admin without confirmed TOTP cannot log in (`mfa_not_enrolled`). The TOTP secret is stored in `accounts.mfa` as JSON; encrypting it at rest is a follow-up.
- **Cookies (WP-705):** one per session kind (`SESSION_COOKIES` in `params.ts`: `participant` is `ub_session_participant`, `admin` is `ub_session_admin`), so an admin and a participant session live side by side in one browser (v3 had two cookies too). `sessionCookie(kind, session)`, `clearSessionCookie(kind)` and `readSessionCookie(request, kind)` take the kind at every call; a read looks at that kind's cookie only, and only `participant` falls back to an API token. `HttpOnly; Secure; SameSite=Lax`. A cookie holding the other kind's session counts as absent. There is no alias for the old shared `ub_session`: admins sign in once again after the deploy of WP-705.
- **Which session an endpoint reads (WP-705, fix round 3):** the caller states it, `authorizeProject(deps, req, key, kinds)`. Device endpoints (runs, run batch, blobs, prefs, chat, packs, tiles, OGC, and `sync` / `sync/events` through `principal` then `fallback`) use `DEVICE_KINDS = ['participant', 'admin']`: the participant session or API token first, so with both cookies a participant's run is recorded as the participant; the admin session answers only when no participant session may act in the project (an admin using the preview or the builder sync). Admin, builder, `api/admin` and `api/mcp` routes read `locals.admin` only.
- All tunables are in `params.ts`; all secret comparisons go through `safeEqual` (`crypto.ts`).

### OIDC admin login (`src/auth/oidc`, WP-532)

`createOidc({ auth, control, providers, fetch, env, now, store? })` implements `Oidc` (`oidc/contract.ts`). `beginLogin(providerKey)` returns the redirect URL (code flow, PKCE S256, state, nonce). The pending login sits in an `OidcStateStore` (in memory by default, single use, 10 min). `completeLogin({state, code, error})` returns a `Session` from `Auth.openAdminSession` (same kind as a password + TOTP session) or an `OidcError` (`OIDC_ERRORS`). ID tokens: RS256/ES256 only (`OIDC_ALGORITHMS`; `none` and HS* refused). JWKS comes through an injected `fetch`, cached 10 min, with one rate-limited refetch on an unknown `kid`. iss, aud/azp, exp, iat and nonce are checked. `accounts.oidc_sub` holds `<issuer>#<sub>`; `linkSubject` links, `provision: {claim, value}` (off by default) creates accounts without password. The client secret is read via `env(clientSecretEnv)`, never from config. Routing is WP-113. `oidc/test-issuer.ts` is a mock provider for tests.

## Blobs (`src/blobs`)

- `BlobStore` is the port for the bytes (`write`, `read`, `has`, `delete(ids)`: async, idempotent). `fileBlobStore(root)` keeps `<root>/<ab>/<cd>/<sha256>`; S3 would be a second implementation.
- `createBlobs({db, store, clock})` -> `put(stream, mime, expectedSha256?)`, `get(sha)`, `has(sha)` (satisfies core's `Blobs` port). The `blobs` table holds mime and size.
- Streams only: bytes are hashed and written chunk by chunk to a temp file, then renamed. A 200 MB upload adds well under 80 MB RSS (tested).
- HTTP (`src/http/blobs`, WP-604): `PUT | HEAD | GET /api/p/<project>/blobs/<sha256>` through `blobHandlersFor(runtime())`; `createBlobAccess` decides who may download (admin; a blob the deployed config names — `branding.icon`, `configBlobs`, A-036 — readable by every participant of the project; the author of a run naming the sha; or the sync scope via `blob_refs`). The run store (`store/run/blob-refs.ts`) refuses `blob_missing` and records `blob_refs` in the run transaction; `collectShas` (`erasure/shas.ts`) is the one reader of file values. **Who owns a hash (WP-757):** PUT always reads and hashes the body (the server never says whether it already held the bytes: 201 either way) and then records the caller in `blob_uploads` (`store/blobs`, migration 25; two uploaders of identical bytes both count). A participant's submitted run may name a hash only when its actor uploaded it, an accepted run of that actor already named it, it is already on the run's feature, or the actor may already read it (the same `BlobAccess` GET and HEAD use, injected into `createBlobRefs`, judged on the state before the run; WP-774); else `not_permitted` (after `blob_missing`). Admin, import and system actors and rule runs are not asked (R3 trusted writers). HEAD answers 200 only for a file the caller uploaded or may download, else 404 like a missing file. Upload limit: `BlobLimits` (`RuntimeOptions.blobLimits`).
- Thumbnails (`src/blobs/thumbs.ts`, WP-618): `GET .../blobs/<sha256>?thumb=<size>` returns a WebP made once with `sharp` (EXIF orientation applied, all metadata incl. GPS stripped) and cached as `<dataDir>/blobs/<project>/thumbs/<sha256>.<size>.webp`. Sizes come from the core registry `THUMB_SIZES` (`list`: 80x80 centre-cropped square, `preview`: 800 px wide, aspect preserved — the sizes v3 asked for); any other size, a non-image (SVG included) is 404. An image whose bytes do not decode, or a folder that cannot be written, makes `get` reject with `ThumbnailFailed` (`code` `decode_failed` / `write_failed`); the handler answers the JSON error `thumbnail_failed` (500, `HTTP_ERRORS`; never a misleading 404) and logs the declared event `blob.thumbnail_failed` once (fields `code`: `decode_failed` / `write_failed`, and the blob `id`; level `error`, no personal data, WP-720), so the cause is in the log; the app then shows the original. `BlobsDeps.log` / `BlobRuntimeDeps.log` is required. `blobHandlersFor` needs the runtime's `dataDir` (WP-708: `Runtime` lacked it, so every `?thumb` was a 404). Authorisation is the original's; the response carries `ETag` `"<sha>-<size>"` and answers 304 to an exact `If-None-Match` match, checked after authorisation and without generating or reading any file. Concurrent first requests share one generation (libuv thread pool, off the event loop). A 12 MP JPEG (4000x3000, 6.5 MB) takes about 100 ms (`list`) to 190 ms (`preview`) once; later requests are sub-millisecond file reads. `sharp` ships prebuilt binaries per platform (`@img/sharp-*`), so the Docker runtime stage must copy them with `sharp`.
- Same bytes twice = one file and one row. A declared hash that differs rejects with `BlobHashMismatch` and stores nothing.

## Outbox (`src/outbox`)

- `defineEffect({key, description, handler})` and `effectRegistry([...])`: one entry per effect kind. `webhookEffect(fetch)` is the built-in; e-mail comes later. (Core has no `defineEffect` yet, so the registry lives here. Move it when a work package owns `packages/core/src/registry` again.)
- `runOutbox({db, effects, clock})` does one pass: claims due rows (compare-and-set on `attempts`, with a lease), runs handlers with **no transaction open**, then marks `done_at` or schedules `next_at = now + base * 2^(attempt-1)`. Defaults: 8 attempts, 1 s base, 1 h cap, 5 min lease, batch 50. Delivery is at least once, so handlers should be idempotent per `runId` (the webhook sends it as `idempotency-key`).
- An unknown kind counts as a failed attempt. A row out of attempts stays in the table with `done_at` empty.
- Handlers **must be idempotent per `runId`**: delivery is at least once. If marking a row done fails after the effect succeeded, the effect is retried.

## Deploy (`src/deploy`, WP-112)

- `plan(db, file, {clock, templates?})` is the dry run: compiles the effective file and returns `{ok, diff, warnings}` against the deployed version, or `{ok: false, problems}`. It writes nothing. `warnings` (`TimerWarning`: `path`, `code` from `TIMER_WARNING_CODES`, `message`, `hint`) never block: today `schedule_never_runs`, a `schedule` rule with no run inside `CRON_HORIZON_DAYS`. `deploy` returns the same `warnings`.
- `deploy(db, file, by, deps)` does the same and then, **in one transaction**, retires the deployed row, inserts a `config_versions` row (`compiled` = `serialize(config)`, `hash` = content hash of the effective file, `overlay` = the overlay JSON or `{}`) and reconciles the indexes. Problems write nothing.
- `deployProject(db, file, by, {clock, templates, afterDeploy})` (`deploy/deploy-project.ts`, WP-169) is the **only** production caller of `deploy`: it deploys and, when the running config changed (`created` or a non-empty `diff`), calls `afterDeploy` (`ProjectServices.afterDeploy`: rings the doorbell once, timers `rebuild` plus `syncSchedules`). The admin API (`POST /api/admin/p/<project>/deploy`) and the builder (deploy, rollback, upgrade via `createVersionsService`'s `afterDeploy` dep) all use it, so a deployed rule change never leaves stale timers or cron rows until a restart. A grep test in `deploy-project.spec.ts` fails if another caller appears.
- `file` is a template file or an overlay; an overlay needs `deps.templates.resolve('template@major')` (a missing template is a `dangling_reference` at `extends`). Lock violations come back as Problems.
- Same hash: no new version (`created: false`, empty diff). A hash that belongs to a retired version reactivates that version.
- SQL application functions: `openSqlite` registers core's `SQL_APP_FUNCTIONS` (`ub_lower`, `ub_upper`, `ub_add_months`) on every connection, which `toSql` needs for Unicode `lower`/`upper` and calendar `months()` (docs/06). A new driver must register them too.
- Index DDL (`index-ddl.ts`): one `cfg_idx_<len(type)>_<type>_<property>` index on `features (type, json_extract(properties, '$.<property>'))` per `index: true` property (not `geometry`), and for a text property a second `cfg_idx_nc_<len(type)>_<type>_<property>` on the same expression with `COLLATE NOCASE` and the id (the admin feature list sorts text by exactly that expression, so `sortSql` and the DDL share `noCase`; ids and timestamps sort binary and use the plain index). Indexes with that prefix that the file no longer asks for are dropped; platform indexes are never touched. The property read is `propertySql('', property)` from core, the same text `toSql` uses, so generated filters hit the index (the filter must also constrain `type`).
- Reading: `versions(db)`, `deployedVersion(db)`, `loadConfig(db, version?)` (the deployed one by default; any stored number for queued runs). A stored form with an older `format` is recompiled from the stored file (A-005).
- Breaking diff entries are reported but do not block; mappings for them belong to the builder.
- Measured (bench/deploy, 500 entities, 100 indexes): first deploy 157 ms, unchanged 51 ms, changed 90 ms; budget 2 s.

## Templates (`src/templates`, WP-113)

- `publishTemplate(control, file, clock)` validates, compiles and stores a template in `control.db` (`templates`: `source` = the file as JSON, `compiled` = `serialize(config)`). The same content again is a no-op (`created: false`); other content under a published `(key, version)` is refused (`{ok: false, error}`), so versions stay immutable. Compile problems come back as `{ok: false, problems}`.
- `publishTemplateVersion(control, controlCatalog(control), clock, yamlText)` (`templates/publish-version.ts`, WP-395) is the one publish gate: it reads the text, runs core's `checkPublish` against the highest published version below it, then `publishTemplate`; it answers a core `PublishOutcome`. `POST /api/admin/templates`, the template-file import and the builder's Versions publish all call it.
- `controlTemplateSource(control)` implements the deploy `TemplateSource` port: `key@major` resolves to the highest published version of that major, `key@1.2.3` to exactly that version.

## Builder draft (`src/builder-draft`, WP-213)

- The one working draft per project (A-011), table `builder_draft` (migration 2, docs/04): the overlay source text (a draft in progress may not compile), the pinned `template` and `template_version`, and a `revision` that starts at 1 and counts accepted writes.
- `DraftStore` (`contract.ts`) is the port: `get()`, `seed(draft)` (stores the first draft when none exists, returns the stored one either way) and `reset(draft)` (replaces template, version and overlay with a new base, e.g. after a template upgrade, and advances the revision so an open editor is refused; creates the draft when none exists) and `putIf(expected, overlay, by, at)` — one UPDATE guarded on `revision = expected`, so the test and the write cannot be split by another writer; a stale write returns `{ ok: false, draft }` with the draft as it is now (`draft` undefined when the row does not exist). `createDraftStore(db)` is the SQLite adapter.
- `ensureDraft(db, clock, by)` returns the stored draft or creates it from the deployed version (its template and overlay; a plain template without an overlay starts as an empty overlay on that template's major); nothing deployed yet is `{ ok: false, code: 'no_version' }`. `draftSources(draft, templates)` resolves the pinned template as source text plus the overlay text.
- `draftStatus(db, { clock, templates })` (`status.ts`, WP-326): the draft's state against the deployed version (E-13); it reads only and never creates the draft. `dirty` (the draft differs from the deployed version, or, before the first publish, there is a draft to publish), `neverPublished` (nothing is deployed yet), `problems` (how many keep the draft from deploying), `revision` (the one a deploy must name; `null` when there is no draft), `type` (the feature type to open for those problems or a value move: the first problem's, else the first one; `null` when none is known). Used by `GET /api/admin/p/<project>/draft/status` in apps/web (the admin shell's publish bar and sidebar badge).
- Used by `GET`/`PUT /builder-api/<project>/draft` in apps/web (docs/08); assistants and the MCP server (H4) use the same endpoints and get the same 409.

## Store, read side (`src/store`, WP-104.1)

Contract: `store/contract.ts`. Exported from `src/index.ts`.

- `createFacts(db, inverse)` returns core's `Facts` and `FeatureAccess` over the project database. `inverse` is `inverseRelations(config)` (`<type>.<relation>` to `{key, from}`: the stored key and the source type); `related(id, relation)` reads a stored relation forwards (references and derived edges) or, for an `inverse_of` relation, the same edges backwards. All statements are prepared once and hit an index (`features` PK, `edges` PK and `edges_by_to`, `observations_by_feature`). `history` is newest first and capped by `limit`.
- `createFoldWriter(db).apply(batch)` (statements prepared once per connection; the projector and `createDerive` each create one) writes `core.fold` output (features, edge puts and removes) in one transaction. A feature row that is not older than the stored `updated_seq` is skipped, so replays change nothing. `features.geometry` is the type's first geometry property as stored (Z kept); `feature_bbox` (rid = `features.rowid`) holds the union bbox of all geometry properties, and no row for an archived or deleted feature. Every edge it removes leaves an `edge` tombstone (`tombstones.id` = `edgeKey`, see the run transaction below).
- `bboxQuery(db, bbox, type?)` lists live features intersecting a viewport (from core `viewportFrom`: the R*Tree drives; with a config index on `features` 59 to 70 ms became 1 to 11 ms for 1 % to 10 % viewports at 60k); `createDerivedLookup(db, schema, geo, condition)` is the adapter side of `Fold.recomputeDerived` (`condition` is the caller's expr.condition over its Facts).
- `Facts.near(type, bbox)` (part of the `Facts` port) returns the live features of one type whose bbox intersects `bbox`, from the same R*Tree as `bboxQuery` (edge contact counts; features without geometry never match). Measured at 60k: p95 0.02 ms for small boxes (budget 2 ms).
- `related` follows core's SQL translation (`expr/sql/values.ts` `relationFrom`): the far end must exist in `features` (inner JOIN) and be live (`lifecycle IN ('active','completed')`), so dangling and deleted ends never appear. `edgesFrom`/`edgesTo` apply the same rule (`store/facts/edges.ts`, core's `liveEdgeJoin` from `@ueberblick/core/expr/compile`, the same text `relationFrom` and `related` use), so they return no edge to a never-created or deleted feature; the derived-edge lookup of the fold reads the stored rows instead (`storedEdges`), dead ends included, or it could not remove them. `related.conformance.spec.ts` executes core's `toSql` relation SQL against the same database and compares, and `describeFactsConformance` (`@ueberblick/core/testing`, run from `facts.spec.ts` and from core's `MemoryStore` spec) holds both stores to the same cases. Measured at 60k (`bench/server-facts/edges.bench.ts`): edgesFrom p95 0.007 ms unchanged, edgesTo(relation) on hub targets p95 0.5 ms before, 0.8 to 1.0 ms after (one `features` PK probe per returned edge, up to 400 on the busiest hub of the generator). WP-179: migration 9 widens `edges_by_to` to `(to_id, relation, from_id, derived)`, so the edge side is a covering search already in `ORDER BY from_id` order (no temp sort); edgesTo(relation) p95 0.6 to 0.7 ms under `BENCH_STRICT=1` at load 20 to 30 (was 0.86 ms at load 17 in the same profile).
- An inverse read filters on the source type (`InverseRelation.from`), so two types that store edges under the same key never mix. Known gap in core (follow-up): `sqlInverse` and the SQL translation of an inverse relation still key on the stored key only; the conformance test therefore uses a schema without shared keys.

Measured at 60k features (`bench/server-facts`): feature + related lookup p95 0.016 ms (budget 1 ms); bbox query for a 10 % x 10 % viewport (about 590 hits) p95 about 2 ms (budget 100 ms); an inverse read (`sources` path, about 61 sources) p95 0.43 ms (budget 1 ms).

## Store, run transaction (`src/store/run`, WP-104)

Contract: `store/run/contract.ts`. `createStore(db, deps)` returns `{ facts, access(version), submit(run), submitBatch(runs) }`. `deps` = `{ clock, log, ids, geo, limits, config(version), versions, form, hooks?, erasure?, onOrphanedBlobs? }` (`config` is `loadConfig(db, version)`; `versions` is the project's shared LRU of compiled configs, `versionCacheFor(db)`, default 8, so the store, sync and blob access compile a version once; `form` is core's `formApi`). It is the only write path (R3): imports, admin edits, rules and OGC writes all arrive through `submit` / `submitBatch`.

One submitted run, or one batch, is **one transaction**: ledger, `core.plan` (`planFor` with the server's `configFor`: each feature under its pin, else the deployed version; creates under the deployed one — a database without a deployed version refuses with `NoDeployedVersion` before anything is written), append `runs` and `observations`, fold, edges, hooks. Plan reads through `store.facts` (the pre-batch state) and layers its own output, so later runs of a batch see earlier ones.

- **Ledger.** `runs.id` is the idempotency key; `runs.result` (migration 3) stores what the run came to. A repeated id by the same actor with the same payload (task, input, feature; client time and key order do not count) returns the stored `SubmitResult` unchanged and writes nothing, so an offline retry stays idempotent. Any other use of a stored id (another actor, a changed payload, a rule run's id) is refused `id_taken` with no observations and writes nothing (WP-754, `ledger.binding`, which applies core's one `sameRunBinding`, the same rule the SimServer uses, WP-781). A batch whose submitted run reuses the id of a rule run planned by an earlier run of it is refused `id_taken` too. A refused run writes its `runs` row (`outcome = rejected`, `refusal_code`, the refusal in `result`) and nothing else. Because the refusal is stored, a retried refused run is refused again, identically. A refused batch writes a rejected row per run (the failing one with its refusal, the others `batch_failed`) and returns `{ outcome: 'refused', index, runId, refusal }`. A malformed batch (duplicate run id, a run with `causedBy`, mixed config versions) is refused `invalid_input` and writes nothing. A run against a config version that is gone throws `ConfigVersionGone` before anything is written (the caller shows the run for review, docs/07).
- **Seq.** Observations of the batch take `max(observations.seq, tombstones.seq) + 1, +2, ...` in plan order: the submitted run, the rule runs it caused (depth-first, `caused_by` set, actor kind `system`), then the next run. `SubmitResult.seq` is the inclusive range of the run and its rule runs; `BatchResult.seq` the range of the batch. `runs.seq` is the last seq of that run's own observations. Edge tombstones take the seqs after the batch's observations, so the server head is `max(observations.seq, tombstones.seq)` and `SeqRange` covers observations only. `features.updated_seq` is the seq of the feature's last observation; edge puts carry the last observation seq of the batch.
- **Fold.** `createProjector` folds the observations per touched feature with `core.fold` on top of the stored row, each under its own version (its pin, else the deployed; derived values are restored from the stored geometry first), calls `createFoldWriter().apply` once, then `recomputeDerived` for every feature whose geometry or derive input changed (R*Tree prefilter, exact predicate, derive `condition` through core's `condition` over `featureAccess`). Only the touched features are read (R14).
- **Edge tombstones.** `createFoldWriter().apply` writes an `edge` tombstone (`id` = `edgeKey`, the sync protocol form) for every edge it actually removes, each at its own seq (`tombstones.seq` is the primary key). A pull must apply tombstones before edge rows: an edge removed and later put again keeps its old tombstone, and the put has the higher `updated_seq` (WP-106).
- **Hooks.** `deps.hooks` run inside the transaction after the fold with `{ db, config, seq, runs, features }`; a throw rolls the whole run back. Outbox rows (effects) and timers are written by hooks (WP-107, WP-108): core plan produces no effects or timers yet, so the store writes none itself.
- `store.access(version)` returns `Facts` + `FeatureAccess` with the inverse relations of that config version.
- All runs of a batch must share one `configVersion`. `PLAN_MAX_RULE_DEPTH` (8) is a core constant; a deeper chain refuses the submitted run with `depth_exceeded` and leaves only the rejected ledger row.

Measured at 60k features (`bench/server-run`, in-memory database): a single run including rules (`kontrolle` with a rule run that creates a measure, and `verschieben` that recomputes derived edges) p95 5.4 ms, median 1.7 ms (budget 50 ms); a batch of 30 new features p95 37 ms (budget 150 ms).

## Sync service, endpoint and doorbell (`src/sync`, `src/http/sync`, WP-106)

## Timers (`src/timers`, WP-108)

Contract: `timers/contract.ts`. `createTimers(db, { clock, ids, geo, current, submit })` returns `{ hook, scheduleFor, syncSchedules, rebuild, tick }`. Time-based rules (`elapsed`, `schedule`) are server-only (decision 0020); each is a row of `timers (feature_id, rule, due_at)` and fires as a system run through `store.submit` (R3), so plan, permissions, rules and seq apply as for any run.

- **Scheduling is a `TransactionHook`.** Put `timers.hook` in `StoreDeps.hooks`. In the run's transaction, for each feature the run created or changed, every `elapsed` rule of its type (the type(s) of the rule's task) gets `due_at = from + after + offset` (one expression, evaluated by core on the folded state) written over the row of the same `(feature_id, rule)`. A rule is re-evaluated only when the run created or restored the feature or wrote a property its expressions read (`self.<property>`), so a fired timer does not come back after an unrelated edit. A null `from`, or an archived or deleted feature, removes the row.
- **`schedule` rules** have no feature: `feature_id = ''` (`SCHEDULE_SUBJECT`). `syncSchedules()` adds missing rows (call it at start and after a deploy); after a firing the next time is the first cron match after the tick's `now`, so a server that was down fires once, not once per missed slot. Cron (`@ueberblick/core/rules/timing`): five fields, UTC, `*`, lists, ranges, steps, day of week 0 and 7 = Sunday, day of month and day of week OR-ed when both are set.
- **`tick(now, limit = 500)`**: the rows with `due_at <= now`, oldest first. Per row, in ONE transaction: delete the row, evaluate `when` and `with`, submit the run. A row fires exactly once, at the first tick at or after `due_at`. `when` false, a feature that is gone or a rule that left the config consume the row without a run; a refused run consumes it too (its refusal is in the ledger); a throw rolls that row back and leaves it for the next tick without stopping the others. Returns `{ fired, refused, skipped, failed }`. `startTimersLoop` (`timers/loop.ts`) calls `syncSchedules()` once per project and `tick(now)` on a beat; the runtime starts it and a deploy calls `rebuild()` (see "Runtime wiring" below).
- `rebuild(rule?)` after a deploy: schedules the rule (or all) for every live feature of its types and removes rows of rules the config no longer has. `scheduleFor(feature, rule)` schedules one.
- Times are UTC, and a `date` value means midnight UTC. Project migration 5 adds `timers_by_due (due_at)`; without it an idle tick scanned the table (5.5 ms at 52k rows, 0.09 ms with the index).
- **Seams to remove** (both are gaps in core, in the WP-108 Notes): `timeRules`, `elapsedDueAt` and the cron code live in core (`@ueberblick/core/rules/timing`, WP-573); an unusable rule is listed in `TimeRules.unusable` and never scheduled. `fireRules` is internal to core, so `timers/fire.ts` evaluates `when` and `with` again.

- **Declared log events (WP-163):** `run.committed` / `run.refused` come from the run store (`StoreDeps.log`, required; `ProjectStoresDeps.log` passes it): one line per submitted run (a replay logs nothing), after the transaction, from the outcome only. An erasure run is an ordinary run and is logged like any run. A refused batch logs the failing run with its refusal code and the others as `batch_failed`. `sync.served` comes from `createSyncHandlers` (`SyncHttpDeps.log`, required), once per served page. `packs.failed` (a pack layer that gave up building, `code` `build_failed` — the `pack_builds` row keeps the reason — or a pack drain that threw, `drain_threw`) is logged by the apps/web runtime's pack wiring (WP-351); the next deploy or rebuild queues it again. `http.error` (`logHttpError`, server errors >= 500 only) and `auth.failed` (`logAuthFailure`, from a 401 answer or a 429 throttle of the two sign-in routes) live in `http/shared/observe.ts`; `apps/web/src/hooks.server.ts` calls them from `handleError` and `handle`. `logAuthFailure` writes `actor: anonymous` (the caller of a failed sign-in is unknown); the TOTP confirm (`apps/web/src/lib/server/handlers/admin-totp.ts`) logs `auth.failed` too, with the admin id (`throttled`, `totp_rejected`). Tests use `logSpy()` and `expectDeclaredFieldsOnly()` (`store/run/log.testkit.ts`).
- A `schedule` rule with no run inside the horizon is never dropped silently: `syncSchedules` and the re-schedule after a firing log one `timer.dropped` line (`ruleId`, `code`) per rule per config version through `TimersDeps.log` (required; the composition root passes the one process logger, `runtime().log`, level from `UEBERBLICK_LOG_LEVEL`, default `info`; see `docs/process/logging.md`). `blob.delete_failed` and `timers.failed` are error lines with codes only.

## Guest self-join, quota and expiry (`src/join`, `src/timers/guest-expiry.ts`, WP-639, B-016)

- **The link.** A role can admit guests through a public link `/join/<slug>`. `enabled` and `slug` are roster-side state, not config (owner Q14: a switch applies at once and is not part of a draft): table `join_links (project_id, role, slug UNIQUE, enabled)` in the control database (control migration 6), so one indexed lookup (`resolveSlug`) resolves a link, whose slug is unique across the instance, to its project and role. Only the quota is config (below). Admin API (in `http/participants/handlers.ts`): `GET /api/admin/p/<project>/roles/self-join` lists the links, `PUT /api/admin/p/<project>/roles/<role>/self-join` takes `{ enabled, slug? }` (no slug: a generated one is kept; `slug_invalid` 400, `slug_taken` 409, `JOIN_ERRORS`). A changed slug ends the old link at once.
- **Joining (B-016).** `joinAsGuest(deps, slug, principal)`: a system roster write like an admin's, not a run (R3 covers feature data). It inserts a participant `gast-<8 hex>`, name `Gast`, the link's role, `self_joined = 1`, `created_at` and `attrs {"created_by":"system","join_slug":…}` (project migration 17), issues a generated token (no placeholder e-mail, v3 bug B7) and opens a session through `auth.exchange`. A caller who already holds a participant session of the same project gets `existing` and no second guest. `isJoinable` / `resolveSlug` only read.
- **Web (`apps/web/src/routes/join`).** `GET /join/<slug>` creates nothing (v3 bug B12: link previews): 404 "Nicht gefunden." for an unknown or switched-off slug, a redirect for a device that already has a session, else a page that submits a form by itself; `POST /join/<slug>/start` calls `joinAsGuest`, sets the session cookie and redirects (303) to `?next=` (a path of this app, not `//`) or `/map`. Throttled like the sign-in routes (an unknown slug is a failure). Consent comes first (WP-638 `consentRefusal`): without it GET redirects to `/login?returnTo=<link>` (the login page returns there after Accept) and POST answers 403 `consent_required`; no guest is created.
- **Quota (core).** `roles.<role>.quota` (positive integer): the most features a participant may create, all types together (v3's `max_instances`); with several roles the highest quota counts; admin, system and import actors are never limited. `core.plan` refuses a create with `quota_exceeded` (`plan/quota.ts`), so device and server agree. The count is `Facts.createdBy(actorId, limit)`, which stops at `limit` (the quota minus this batch's own creations), so the cost is bounded by the quota: server SQL counts live `features WHERE created_by = ?` via index `features_by_creator_any` (project migration 17; the audit column of WP-306, set from `creatorOf(run)`; no table of its own) and is measured in `bench/server-facts/created-by.bench.ts` (60k features: p95 0.027 ms against the 1 ms budget, `server-facts-created-by-p95`); `MemoryStore` reads `FeatureState.createdBy`. A deleted feature frees its place. The device store (`packages/client`) still answers 0 for `createdBy`, so only the server refuses until it reads `FeatureState.createdBy` (follow-up).
- **Expiry.** `expireGuests` (`timers/guest-expiry.ts`) deactivates guests after 90 days without activity (`GUEST_INACTIVITY_DAYS`, owner 2026-10-06, WP-1073): a `self_joined` participant who joined over 90 days ago and has no live session (`Auth.hasLiveSession`; every authenticated use renews the 90-day session at most daily, so a live session means used within 90 days) is deactivated through `removeParticipant` (disables the row, revokes tokens, ends sessions; their runs keep the actor). `startTimersLoop` calls it per project on every beat (`TimersLoopDeps.guests`); one read of the partial index `participants_guests` plus one lookup per old guest in `sessions_by_subject` (control migration 9).

## HTTP: run endpoints (`src/http`, WP-105)

Handlers are Web `Request -> Response` functions (`shared/contract.ts`: `Handler`, `HttpLimits`, error envelope `{error: {code, message, issues?}}` with codes from the `HTTP_ERRORS` registry); SvelteKit route files only delegate.

- `createRunHandlers({auth, project, store, limits?})` returns `submit` (`POST /api/p/<project>/runs`) and `batch` (`.../runs/batch`). `runHandlersFor(runtime)` memoises them on the runtime; `projectStoresFor(runtime)` gives one `Store` per project database (one `composeProjectStore` per project, with `runtime.hooks?`), and is what sync and timers must share.
- Order: session (401), project access (403: a participant of another project, an admin without membership, an unknown project), body cap (413, streamed, also without content-length), Zod parse (400 with dotted paths), store.
- The actor is always the session principal (an admin's roles are its memberships). The body is a strict schema: `actor`, `causedBy` and typos are 400.
- Status: 200 accepted, 422 refused, 409 `review` (`ConfigVersionGone`: the run is kept for review, docs/07). A repeated run id answers the stored result with the same status.
- **Protocol version (WP-144).** Every reply of both handlers, accepted, refused, review and every error (401, 403, 400, 413), carries a top-level `v: SYNC_PROTOCOL_VERSION` (the one device-to-server version of `@ueberblick/core/sync`; there is no second constant). All replies leave through the `versioned` wrapper in `runs/handlers.ts`, so no path can omit it; the response schemas require `v` (inside a batch, only the envelope has it). The client refuses a missing or different `v`.
- Limits (`DEFAULT_HTTP_LIMITS`, overridable): 256 KiB per run, 8 MiB per batch, 500 runs per batch.
- The Zod schemas (`runs/schema.ts`: `RunRequestSchema`, `BatchRequestSchema`, `RunResponseSchema`, `BatchResponseSchema`) are the typed API (H4). User reference: `docs/user/admin/reference/run-api.md`.
- Benchmark `bench/server-run/http.bench.ts` (60k features): end to end p95 7.9 ms against 50 ms; handler overhead over `store.submit` p95 0.7 ms against 5 ms.

## OGC API Features (`src/http/ogc`, WP-110)

`createOgcHandlers(deps: OgcDeps)` (`handlers.ts`) answers the standard OGC API Features endpoints; `ogcHandlersFor(rt, seams?)` (`wiring.ts`) memoises one set per runtime, and `apps/web` delegates to it in `routes/api/p/[project]/ogc/[...path]`. Rows are clipped by `SyncService.visible` and properties by the compiled permissions (R1); a collection is a feature type the caller may see (`visibleTypes`).

- **Read.** Keyset paging over `rowid` (`cursor`, `limit` 1 to 1,000, default 100); `bbox` (four or six numbers, no antimeridian crossing) and `bbox-crs` prefilter on `feature_bbox` (core `viewportPageFrom`, a plain join: SQLite walks `features` in rowid order and stops at the `LIMIT`, so paging a whole layer costs 0.4 ms a page where `viewportFrom` needs about 45 ms; `viewportFrom` would be faster only for narrow viewports); `crs` defaults to CRS84, EPSG:4326 is served lat/lon, and the projected CRSs are the projected members of the core registry `GEO_SOURCE_CRS` (25832, 25833, 31466-31469); `f` accepts `json` and `geojson` (the body is `application/geo+json`). The CQL2 `filter` (`filter-lang` `cql2-text` or `cql2-json`, `filter-crs` only CRS84) is read with `fromCql2` against the type's check environment (`checkEnvFor`); the terms `toSql` translates join the WHERE, the rest are a residual that core `condition` evaluates on the candidates, always bounded by a bbox (the request's or one derived from a spatial term); above `RESIDUAL_SCAN_CAP` (5,000, overridable as `residualScanCap` in `OgcDeps`) candidates the request is refused `filter_too_broad` (422). Unknown query parameters are a 400 `invalid_query`.
- **Write (Part 4).** POST/PUT/PATCH/DELETE on items are written by the caller (an admin session or a participant session or API token, A-043, WP-402) and become runs with the caller's own actor (kind `admin` or `participant`) through `store.submit` (R3), planned and stamped under the version the feature follows (its pin, else the deployed one; A-029, WP-316); core `plan` applies the caller's role, `when`, field-write permissions and rules like in the app, the OGC handler holds no second check. The task is the `?task=` hint or the unique task the caller may run (`resolveWriteTask`, `write-task.ts`); a participant's permission refusal (task, property, `when`) answers 403 `forbidden` with core's refusal path, and none or several tasks a 422 `no_write_task` with the candidates (a delete runs the task whose only effect is `lifecycle: deleted`, A-028). PUT and PATCH send only the changed properties; an unchanged feature answers 204 without a run, a created one 201 with a `location` header. A refused run is stored like any other (the run transaction above).
- **Discovery.** `discovery.ts` builds the landing page, the collections and `/conformance` (generated from `conformanceClasses`, which claims only what is wired). What is claimed, and how to connect QGIS: the OGC section of docs/09 and `docs/user/admin/how-to/connect-qgis.md`.
- Measured at 60k (`bench/server-ogc`): items with bbox p95 1.8 ms (budget 100 ms). Specs: `ogc.spec.ts`, `filter.spec.ts`, `write-task.spec.ts`, `write-participant.spec.ts`, `write-oracle.spec.ts`, `ogc-filter-crs.spec.ts`; e2e `apps/web/e2e/ogc.spec.ts`.

## Subject data export (`src/export-subject`, WP-535)

`exportSubject(project, subjectId, actor)` returns an `AsyncGenerator<Uint8Array>` with a ZIP (Art. 15 access, Art. 20 portability; B-005, `docs/research/gdpr-erasure.md` section 9). It is a read, not a run. `project` is a `ProjectExport` (`key`, `db`, `blobs`, `config`, `configVersion`, `clock`, `accessLog`). The subject is a participant id or, for `personal: { subject: feature }` properties, a feature id.

- **Access log:** when `exportSubject` is called (the log means "export requested", not "delivered"; a stream nobody reads still leaves one row), `accessLog.record({ at, actor, action: 'export_subject', subject })`. Ids and times only, never a value. `sqliteAccessLog(db)` writes the `access_log` table (project migration 7).
- **Streaming:** the ZIP is written by a small streaming writer (`zip.ts`: stored entries, data descriptors, no ZIP64, so at most 65,535 entries and 4 GiB; `ZipLimitError` beyond that, `ZipNameError` for a duplicate or unsafe name). Rows are read with `iterate` and emitted in about 64 KiB chunks; only the per-feature latest values (for `features.geojson`) and the blob hashes are held in memory. Benchmark `bench/export-subject` (budget 5 s for 10,000 observations).
- **What is in it:** every observation of the subject's own runs (all properties, current and history); the observations of personal properties about the subject that other actors wrote (`property:<key>`: while the named participant was the subject; `feature`: on the subject feature), without those actors' runs; the subject's runs incl. refusals; the participant row. Nothing about other subjects (property test with a tagged oracle). The subject's own writes are filtered the same way: a personal property is kept only if its subject is the exporting subject (`actor` kind: the author; `feature` kind: the feature is the subject; `property:<key>`: `<key>` named the subject at that moment). In `runs.ndjson`, `input` fields (keyed by property, or `alias.property`) that hold such a value about someone else, or whose subject cannot be told (a refused run has no observations), are replaced by the marker `{ "$redacted": "other_subject" }` (`EXPORT_REDACTIONS` in `registry.ts`); a refusal `message` in `result` is replaced too when the input was redacted.
- **Format (version 1):**

| File                   | Content                                                                                                                                                                                                                                              |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `participant.json`     | `id`, `name`, `roles`, `attrs`, `disabled_at` (only for a participant)                                                                                                                                                                               |
| `runs.ndjson`          | one run per line: `id`, `task`, `config_version`, `input`, `client_time`, `received_at`, `outcome`, `refusal_code`, `result`, `caused_by`, `seq`                                                                                                     |
| `messages.ndjson`      | one chat message per line (the subject's own, and those mentioning them or a feature that is the subject): `seq`, `id`, `author`, `at`, `body`, `removed`, `mentions`, `via` (`author` or `mentioned`)                                               |
| `observations.ndjson`  | one observation per line: `seq`, `feature`, `property`, `value`, `phenomenon_time`, `via` (`run` or `named`); `run`, `task`, `received_at` for `via: run`                                                                                            |
| `features.geojson`     | RFC 7946 FeatureCollection: per touched feature the latest exported values as `properties` (plus `$type`), the latest exported geometry-property value as `geometry`                                                                                 |
| `blobs/<sha256>.<ext>` | attachments referenced by any exported value or run input                                                                                                                                                                                            |
| `manifest.json`        | last entry: `format` (`ueberblick-subject-export`), `version`, `project`, `config_version`, `generated_at`, `subject`, `files` (path, kind, records, bytes, sha256, mime), `properties` (the personal properties with their labels), `missing_blobs` |

`manifest.schema.json` is the JSON Schema of the manifest, generated from `ManifestSchema` (`manifestJsonSchema()`); a test keeps it current. Reads of `runs(actor)` scan `runs` once (via `runs_by_actor`, migration 6).

## Erasure (`src/erasure`, WP-534, B-005)

`createErasure(db).erase({subject, purge, erasureRun, at})` is the guarded purge of an erasure run: called inside the run transaction that appended the null observations of core's `planRedaction`, it blanks (to JSON `null`) the superseded results of the purged (feature, property) pairs and the `runs.input` of the runs that wrote them, keeps the erasure run's own input, emits a `redaction` tombstone per affected pair, deletes blob rows nothing references any more (a `blob` tombstone each; the caller deletes the bytes, `orphanedBlobs`) and records the subject in `erasure_subjects`. It sets `PRAGMA secure_delete = ON` on the connection. Calling it again with the same pairs changes nothing.

- Migration 8 adds `erasure_runs (run_id, subject, erased_at)`, primary key (run_id, subject) because one run may erase several subjects: `erase` inserts the row in its own transaction (rolled back with it) and always upserts `erasure_subjects.erased_at` for its subject, even when every pair was already blanked. The backup journal (`scripts/backup/journal.mjs`, WP-536) selects erasure runs from it and never infers them from a run's input.
- Migration 6 adds `erasure_subjects`, `runs(actor)`, a one-row `erasure_guard` and triggers: any other UPDATE or DELETE of `observations`, and any UPDATE of `runs.input`, is refused; with the guard open only blanking to `null` passes. Normal runs only INSERT, so the run path pays nothing.
- Run path (A-021): a run of a task with a `redact` step is an ordinary run. The run transaction (`submit`, `submitBatch`) calls `erase` for every planned run whose `PlannedRun.purge` is non-empty, once per `PlannedRun.erased` entry (one per redact step) with that entry's own pairs (`erase` always upserts the subject's `erased_at`, so a subject with nothing left to blank is still recorded), after the fold and in the same transaction (if `erase` throws the run rolls back; ordinary runs never call it). After the commit it calls `deps.onOrphanedBlobs(ids)` once with all orphaned blobs of the batch; the caller deletes the bytes with `BlobStore.delete`. Who may erase is the task's `when` rule, checked by plan. `Store.submitErasure` and `POST /api/admin/p/<project>/erasure` are gone. Crash recovery: `createBlobSweeper({db, store}).sweep()` at startup deletes the bytes of every `blob` tombstone whose blob row is gone (a re-uploaded blob has a row and is kept). `http/shared/stores.ts` wires both because `ProjectStoresDeps.blobs {store, onError}` is required (the runtime passes `fileBlobStore` under `<dataDir>/blobs/<project>`): `onOrphanedBlobs` deletes the bytes, and the sweep runs once when a project's store is created. Benchmark `bench/erasure`: 1,000 pairs in 200k observations, 23 ms (budget 2 s).

## Import and export (`src/io`, WP-111)

`importFile(store, source, mapping, deps, { mode })` reads CSV, GeoJSON or a GeoPackage and submits the file as runs of the mapped creating task with actor kind `import` (no direct writes, R3): mode `atomic` (default) is one `submitBatch`, `skip` one `submit` per run. A bad row refuses the whole file with its row number (`atomic`) or is reported and left out (`skip`); the atomic check stops after 1000 problems. `planImport` plans without writing; `planRows` takes rows already read (the seam for the v3 converter, WP-301). Geometry: the source CRS comes from the file (GeoPackage srs, GeoJSON `crs` member) or the mapping's `sourceCrs`, else a `crs_undeclared` problem; reprojected to WGS84 with `core.geo` (Z kept). Export: `buildGpkg`/`exportGpkg(src, types)` write one GeoPackage with one table per feature type, rows through `SyncService.visible`, columns through `Perms.readable` (one filter, R1). Details: `src/io/README.md`. User page: `docs/user/admin/how-to/import-export.md`. Benchmark `bench/server-import`: 10k CSV import 2.5 s (limit 30 s, derived from the run endpoint row).

The web runtime (`apps/web/src/lib/server/runtime.ts`) refuses to start when the data dir holds `*.restoring` files (an unfinished backup restore, docs/process/backup.md); it creates nothing. Root scripts: `npm run backup:journal`, `npm run backup:restore`.

## Offline packs (`src/packs`, `src/http/admin-packs`, WP-350)

The server side of the offline packs (the device side: docs/07 "Offline packs on the device"; the config: docs/05 "Offline packs"): one PMTiles v3 file per (pack, layer) of the deployed config, built in the background from the project's `pmtiles` sources, never inside a run transaction.

- **`pack_builds`** (project migration 19, docs/04): one row per (pack hash, layer). `state` from the core registry `PACK_BUILD_STATES` (`queued`, `building`, `ready`, `failed`); `tiles_done`/`tiles_total` the persisted position in the sorted tile list (the resume point), `bytes` the spool size, `sha256`, `max_zoom` and `tiles` of the finished file, `error` the failure reason. Files live at `<blobs>/packs/<project>/<pack_hash>/<layer>.pmtiles`.
- **Queueing.** `deployProject` (the deploy side effects, "Deploy" above) calls `enqueuePacks` on every deploy that changes the running config: it queues every (pack, layer) whose hash has no row; a `failed` row is queued again, `ready`, `queued` and `building` rows are left alone, so a redeploy with the same hash enqueues nothing.
- **Build worker.** `createPackBuilder({ db, clock, dir, file, fetchRange, pinned? })` returns `{ enqueue, drain, rebuild, sweep }`; `drain()` builds until nothing is queued, one layer at a time (a stop signal leaves the row `building`). `buildLayer` lists the pack's tiles in tile-id order (core `tileRanges`, PMTiles order via `packTileIds`), capped at the archive header's max zoom (`layerMaxZoom`), and copies the stored bytes without decoding them: `archive-read.ts` locates each tile's offset in the remote PMTiles v3 archive by range, near ranges (64 KiB apart or less, 8 MiB per request or less) merge into one fetch, and the bytes go through the `fetchRange` port — `httpFetchRange` (concurrency 2, an identifying User-Agent, relative URLs resolved against `baseUrl`) wrapped in `withRetries` (3 retries, 500 ms base, doubling). The spool next to the result (`.part` + one 24-byte `.idx` record per tile) grows in batches of 512, the row stores the position after each batch, and a restart cuts the spool back to that point: no tile twice, none missing. `archive-write.ts` writes the finished clustered archive (header, root directory, metadata, leaf directories, tile data; gzipped directories) to a temp name and renames it, so a half file is never served. A fetch that still fails after the retries ends the row `failed(reason)`; `rebuild(packKey)` re-queues the pack's failed layers.
- **Garbage collection.** `sweep()` deletes the directory and rows of every hash that no deployed config (or a `pinned()` hash, the version-pinning seam, A-029) references; it runs at the start of every `drain` (O(hashes)) rather than in the blob sweeper (a deviation from A-032, docs/03).
- **Admin API** (`createAdminPackHandlers`, mounted by apps/web behind `authorizeAdmin`): `GET /api/admin/p/<project>/packs` answers, per pack of the deployed version, the definition, the estimate and the per-layer state, progress, `max_zoom`, `tiles` and `sha256` (`PackStatus`, `status.ts`; a pack is `failed` when a layer failed, else `building`, `ready` or `queued`), and `POST /api/admin/p/<project>/packs/<key>/rebuild` re-queues the failed layers (`{ queued: n }`; 409 unless the pack's state is `failed`, 404 for an unknown key). The estimates reuse core's `estimatePack` (R1, docs/05). User reference: `docs/user/admin/reference/packs-api.md`.
- The `pmtiles` dependency serves the header and directory parsing and the tile-id math; the estimate (`estimatePack`) and the tile list (`tileRanges`) are core, so the config checker, the admin dialog and the build job share them (R1).
- Bench `bench/packs` (docs/12 `pack-build-20k`): the build copies a 21,845-tile fixture pyramid at at least 2,000 tiles/s (measured about 100 to 170 ms).

## Audit times (WP-724)

`Store.submit` and `submitBatch` are the one intake of every run. A run without `clientTime` gets the server clock's time before planning, so core folds `createdAt` and `changedAt` for it (R4). A client-supplied time is kept. The ledger's `client_time` is the client time, or the server's receive time when the client sent none.

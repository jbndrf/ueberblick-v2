# @ueberblick/ui

Design system: tokens, themes, SVG icons and the field-proof primitives every screen builds on (Svelte 5). Depends on `@ueberblick/core` only. The props are the contract: `src/contract.ts`.

## Tokens and themes

`src/tokens.ts` holds two typed themes, `NORMAL_THEME` (WCAG 2.2 AA, at least 4.5:1 text) and `OUTDOOR_THEME` (pure black on white, at least 7:1). A theme is data: `themeVars(theme)` flattens it to `--ub-*` custom properties (`--ub-color-primary`, `--ub-space-md`, `--ub-radius-md`, `--ub-elevation-raised`, `--ub-type-size-md`, `--ub-target-primary`), and `themeToCss(theme, selector)` renders them as CSS text. The app shell injects `themeToCss(THEMES.normal)` on `:root` and `themeToCss(THEMES.outdoor, '[data-theme="outdoor"]')`. The builder can later edit a theme object to re-theme a project (UX principle 10). Components only read the variables, never literal colours.

`textPairs(theme)` lists every text-on-background pair the primitives use. `tokens.spec.ts` computes the contrast of each pair from the tokens, so a new colour that breaks AA or the 7:1 outdoor bar fails the test. Dark mode is out of scope; the mechanism (another theme object) already allows it.

Touch targets (`TARGET_SIZE`): primary actions (Button primary and danger, TextField input) are 56 px, everything else 44 px. The components set `min-height` and `min-width` inline, and tests read them from computed styles.

## v3 design system (B-015)

The look of the app is v3's: shadcn-svelte components on Tailwind 4 and bits-ui, copied from `reference/` into `src/components/ui/<name>/`. Dialog content (WP-663): `dialog-content.svelte` sets `contain-none!` once, because bits-ui puts `contain: layout style` inline on the content, which clips popovers on phones (v3 had no containment). The content also sets a context (`dialog/modal-context.ts`); the kit MultiSelect, Popover, DropdownMenu and Tooltip content read it and render in place inside a dialog (the dialog overlay would otherwise cover their body portal), because the modal makes a body portal inert (an explicit `disablePortal` prop still wins). Proof: `src/components/ui/dialog/e2e` (phone and desktop, axe). Kit: sortable (below), button, card, tabs, input, label, sheet, drawer, dialog, alert-dialog, badge, switch, separator, tooltip, sonner, progress, skeleton, dropdown-menu, textarea, checkbox, radio-group, popover, scroll-area, spinner.

- **Sortable list (WP-408, `components/ui/sortable`):** the one drag-order list of the admin. `Sortable` takes `items`, `key`, `onreorder({ keys, moved })`, the accessible names (`label`, `handleLabel`, `upLabel`, `downLabel`) and a `row` snippet that receives `grip` (a focusable drag handle: ArrowUp/ArrowDown move the row and keep focus on it) and `moves` (up and down buttons, shown below the `sm` breakpoint and on coarse pointers: HTML5 drag has no touch, so a phone orders with the buttons). `announce` feeds a polite status line after a move; `disabled` locks every path while a save runs. A list that builds its own rows (the admin sidebar) uses `SortableState` and `SortableItem` directly: the whole item is draggable and Alt+ArrowUp/ArrowDown moves it. The pure functions `moveWithin`, `moveBy`, `arrange` have property tests (`reorder.spec.ts`). axe: `Sample.testing.svelte` mounts a `Sortable`, so `ui.a11y.spec.ts` scans it. The owner saves the order through its own path and passes it back as `items`; the kit holds no order.
- **Import one component** (no barrel, so unused ones are tree-shaken): `import { Button } from '@ueberblick/ui/components/ui/button'`, `import * as Sheet from '@ueberblick/ui/components/ui/sheet'`. `cn()` is `@ueberblick/ui/utils`.
- **Theme.** `src/app.css` is v3's `app.css` (Tailwind, `tw-animate-css`, the CSS variables for light and dark, `.admin-theme`). `apps/web/src/app.css` imports it once (`@import '@ueberblick/ui/app.css'`) and `apps/web/src/routes/+layout.svelte` loads it. Dark mode is the `dark` class on `<html>`, set before first paint by mode-watcher's `ModeWatcher` in the root layout. The CSS variables are the only colour source (the seam for admin theming); components use `bg-primary`, `text-muted-foreground` etc., never literal colours.
- **Tailwind scanning.** `@source './'` in `src/app.css` makes the app build generate every class used in this package.
- **Old primitives** (`Button.svelte`, `Sheet.svelte`, `TextField.svelte` and the `--ub-*` tokens above) stay until the last screen using them is replaced (R11).
- **Test helpers for other packages** (WP-628): specs outside packages/ui import `@ueberblick/ui/testing` (axe helper `axeViolations`; importing it installs the jsdom shims), never a relative path into `packages/ui/src`. `no-testing-helpers-in-prod` bans production code from it, and `apps/web/src/ui-testing-imports.spec.ts` fails on a deep import.
- **Tests.** Svelte libraries of the kit are inlined in `vitest.config.ts`; `src/components/ui/jsdom-shims.testing.ts` stubs `ResizeObserver` and `matchMedia`. `Sample.testing.svelte` mounts every component.

## Primitives

| Component      | Purpose                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------- |
| `Button`       | `variant` primary / secondary / danger, `loading` (busy, spinner, status text, ignores clicks)                      |
| `IconButton`   | icon-only control; `label` is required and becomes the accessible name                                              |
| `TextField`    | label, `hint`, `error` (sets `aria-invalid`, linked by `aria-describedby`), `required` shown as text                |
| `ErrorSummary` | list of `{fieldId, message}`; takes focus when errors appear, each link focuses its field                           |
| `Sheet`        | modal bottom sheet; closes by button, Escape or backdrop, never drag-only (WCAG 2.5.7); traps focus and restores it |
| `StatusBadge`  | honest state `online` / `offline` / `pending` / `refused`: icon and text, never colour alone                        |
| `Icon`         | renders an `IconDef` as inline SVG with `currentColor`; `aria-hidden` unless `label` is given                       |

Enum values (`THEME_NAMES`, `BUTTON_VARIANTS`, `STATUS_KINDS`) are registries in `packages/core/src/registry/ui.ts`, imported from `@ueberblick/core`.

## Participant app shell

`src/shell/` renders what a role's app profile (`roles.<key>.app`) declares (H3). `deriveShellModel({ file, roleKey, locale, userTheme?, allowedTasks? })` is pure: it returns the role's views, home view, tools, shortcuts, task list, theme and the navigation graph (`stepsFrom`, `navDepth` are the tests' probes: at most 2 levels, every frequent action at most 3 taps). A role without `app` gets every view in file order, the first as home, every declared tool and no shortcuts. Unknown keys are dropped. Theme precedence: the user's setting, then `app.ui.theme`, then `normal`. `allowedTasks` comes from core perms; the shell has no permission logic.

`AppShell` takes `model`, `status` (a `StatusModel`: online, lastSyncedAt, pending, oldestPendingAge, refused, storage), `onexport` and slots: `map`, `taskSheet`, optional `featureSheet`, `me`, `assistant` (H4, empty by default). It imports no map or form code. `StatusIndicator` is always in the header: kind text and icon, unsent count as text, "Data at risk" for `storage: 'at_risk'`; tap opens the details sheet with the queue export button. Registries added for it: `STORAGE_STATES`, `NAV_NODE_KINDS`, `ME_SECTIONS`. Journey and graph: `docs/ia-map.md`.

## Icons

Each icon is a plain object (`name`, `paths` on a 24x24 grid) in its own module under `src/icons/`, re-exported by name from `src/icons/index.ts`. The package declares `sideEffects: false`, so unused icons are dropped by the bundler.

## Strings

All user-visible strings come from Paraglide: `messages/en.json` and `messages/de.json`, compiled to `src/paraglide/` (generated, git-ignored, excluded from Prettier and ESLint) by `npm run i18n -w @ueberblick/ui`. `npm run typecheck` and the Vitest config compile them automatically. Components import `m` from `../paraglide/messages.js`. `src/i18n.spec.ts` fails on literal text in a component, on a locale missing a key and on unsorted message files (`npm run messages:sort` fixes them). Project content is different: it uses `LocalizedString` (decision 0019).

**Language (WP-394):** the compiled runtime resolves the language from the `PARAGLIDE_LOCALE` cookie, then the base locale `en`. An app with its own language setting (the admin: the `ub_locale` cookie) calls `setUiLocale(locale)` (exported from the package root; `undefined` restores the runtime default) and never imports the generated runtime. The setting is module-wide, so on the server call it in the same synchronous pass that renders (the admin layout does, in a `$derived` read by `{#key}`; Svelte's server render has no `await` between), and remount what is on screen after a switch (message calls are not reactive).

## Adding a primitive

1. Add its props type to `src/contract.ts` and, if it has enum values, a registry to `packages/core/src/registry/ui.ts`.
2. Write the spec first: keyboard and screen-reader behaviour, target size, axe (`src/testing/axe.ts`), no literal strings.
3. Add every new text/background pair to `textPairs` in `tokens.ts`.
4. Add the strings to both message files, the component under `src/components/`, and an export in `src/index.ts`.
5. Keep it independent of any app shell (role apps differ, H3) and free of literal colours.

## Form renderer (`src/form`)

A task's `form:` becomes a `FormModel` (`buildFormModel({ form, properties })`), a `FormSession` (`createFormSession(model, { task, config, ctx, type?, initial, locale })`) and the `FormRenderer` component (`session`, `onsubmit`, `oncancel?`, `ondraft`, `choices`, `tool`). Contract: `src/form/contract.ts`. Exports: `src/form/index.ts`. A runtime language switch calls `session.setLocale(locale)` (WP-790): `session.locale` is a getter, subscribers are notified, the open form re-labels and keeps the typed values; the session is never rebuilt. A session for a frozen record (the admin Protokoll) implements it as a no-op.

- **Inputs** come from `INPUT_KIND_BY_TYPE`, total over the property type registry (a spec fails when a type has none). `file` and `geometry`, and any field with a `tool` key, render the `tool` snippet (`ToolSlot`: field, value, set, id); without it the slot says it is not available. `participant` and `reference` take their options from `choices[fieldKey]`. An unknown type or a form field without a property throws `FormModelError` (`code`, `fieldKey`).
- **Form rules** (`relevant`, `required`, `readonly`, `constraint`, `calculate`, submit values) come only from `core.form` (`formApi`, R1); the session is the one caller. `config` is the compiled project, `ctx` the `EvalContext` (`self`, `actor`, `now`, ports); core binds `form` and `value`. After an edit the session asks `formApi.dependents` which fields can change. A `no-twin.spec.ts` guard fails if an evaluator port or expression evaluation returns. A property's `required` is plan's create-time rule; the form uses only the form entry's `required` flag. A `file` field's value is a list of `{ sha256, name, mime }` (core's type check). `form/form.testing.ts` has `formWorld`, `evalContext` and `sessionOptions` to compile a test form. `*.testing.ts` files are exempt from `participant-core-subpaths` and banned from production code by `no-testing-helpers-in-prod`.
- **Localized text (WP-676):** a `localized_text` property has its own input kind `localized_text`; `FieldInput` (used by the task form and quick edit) shows `localizedShown(value, locale)` (core `localize`, the read view's chain) and writes `localizedWith(value, locale, text)` (`form/localized.ts`): `{ ...existing, [locale]: text }`, an empty text removes only that locale, nothing left is `null` (cleared like any emptied field).
- **Choice fields (WP-642):** `select`, `multiselect`, `participant` and `reference` all draw the kit's `MultiSelect` (`components/ui/multi-select`, v3's `mobile-multi-select`; no native `<select>`, no checkbox group). `FieldInput` passes `id`, `describedby` and `invalid` so the field label, help text and error attach to the trigger; a single choice gets the placeholder `form_choose`. Browser proof at phone 390x844 and desktop 1280x800: `components/ui/multi-select/e2e` (`npx playwright test -c packages/ui/src/components/ui/multi-select/e2e/playwright.config.ts`).
- **Non-relevant fields** are hidden, skipped by validation and left out of `submitValues()` (decision 0015). `draft()` returns every current value, hidden ones included, for the run queue; the renderer never persists it.
- **`calculate`** prefills once, and only when no initial value exists (draft, assistant proposal, role preset). Editing is never overwritten. A `readonly` calculated field follows its inputs.
- **v3's form look (WP-624):** drawn with the design kit (`components/ui`). `PageTabs` shows one tab per page (the page title, or "Seite n" without one; WP-672) with the red missing count once Submit was tried; tabs jump freely and Next never blocks. Submit validates every page and jumps to the first page with an issue. `appearance: multiline` draws a textarea. **Clearing guard (owner Q5):** `session.clearing()` lists the form fields whose stored value (read from `ctx`: `self` and the features port) this submit would erase, either because the field is no longer relevant or because the user emptied it; `ClearingDialog` asks first and `session.submitValuesCleared()` is the submit after "Leeren & speichern" (an explicit `null` per field). Plain `submitValues()` still drops non-relevant fields (decision 0015).
- **Form chrome (WP-643):** the footer is v3's (`FormFillTool.svelte:407-445`): Abbrechen (when `oncancel` is given) or Zurück with a ChevronLeft, Weiter with a ChevronRight, Absenden with Send; `onsubmit` may return a promise, and while it is pending the form is *submitting* (Loader, "Wird gesendet…", every button disabled, a second tap ignored). A form with no fields says so and the button reads "Eintrag erstellen". The footer is `sticky bottom-0` inside the shell's scroll area. `FormField.column` and `.row` come from the property's `display` (`buildFormModel`); `formLines` and `COLUMN_CLASS` (`form/layout.ts`) lay a page out in lines, `left`/`right` cells of one row at `w-[calc(50%-0.5rem)]`, also on a phone. The `email` appearance token draws `type=email` (`EMAIL_TOKEN`). The form sits in `ModuleShell` (the app's `form/FormShell.svelte`). Browser proof at phone 390x844 and desktop 1280x800: `src/form/e2e` (`node scripts/e2e/run.mjs --suite comp:ui/form`).
- **Choice filter and option hints (WP-392, A-039):** a field over a select whose form entry has `choice_filter` offers only what core.form lets through: `session.offered(key)` is the offered option keys (`FieldState.options`), or `undefined` without a filter (then every option of `field.options`). `FormRenderer` hands it to `FieldInput` as `offered`; the static list stays the fallback. An option's explanation text (`FormField.optionHints`, the property's `option_hints`) is the `description` of the `MultiSelect` row, under the name (v3 `mobile-multi-select.svelte:548-551`), on the phone sheet and the desktop dropdown. An answer the filter removes is cleared at once (`sweep` in `session.ts`) and counts as an edit, so a stored value it erases is listed by `clearing()` and the "Felder werden geleert" dialog asks before the submit. Without a filter and without hints, rendering is unchanged.
- **Record view (WP-372, `readonly` prop):** `FormRenderer readonly` draws a filled form that cannot be changed (a past run's Protokoll). Inputs get the `readonly` attribute and `aria-readonly="true"`, never `disabled` (`disabled` stays for a field core.form marks `readonly` in the editable form, which greys out). A select, multiselect, participant or reference field shows its chosen labels as a read-only text input; the checkbox uses bits-ui `readonly`. There is no submit, cancel, error summary, required mark or clearing dialog, Enter submits nothing, and the footer holds only Zurück / Weiter on a form with several pages. Absent, the form is exactly as before. The caller supplies a `FormSession` over the values (`FormRenderer.readonly.spec.ts`).
- **Validation** per page: the issues of core.form (`required`, `type`, `constraint`, `readonly`); a `type` issue reads as `min`, `max` or `integer` in the message when that is the cause. A constraint applies only to a non-empty value; the message is the localized `constraint_message`. After a failed Next or Submit, ErrorSummary takes focus and each link focuses its field.
- **Paging (WP-672):** a form entry with `page: { label?, hint? }` starts a new page at that field (`page: {}` is an untitled page); there is one page otherwise. `FormModel.pageInfo` carries each page's title and description, drawn as the tab title and an h4 heading with the description under it (v3 `renderPageGroup`). Values stay when going back. `FormField.placeholder` is the localized placeholder of an empty input (an `email` field defaults to `email@example.com`, as v3). `appearance` is a space-separated token list validated against the core registry `FORM_APPEARANCES` (`multiline`, `email`).
- Timing (50 fields, one keystroke, at most 16 ms) is measured in `bench/ui-form`; `src/form/session.perf.spec.ts` holds the relevance re-evaluation.

### Gallery (`src/form/gallery`, WP-630)

`MediaGallery` (props `files`, `mode` `fill`|`view`, `size` `list`|`preview`, `onRemove(index)`) draws the files of a `file` value as the kit carousel (`components/ui/carousel`, v3 shadcn-svelte on Embla; prop `columnPosition` `full`|`half`|`third`|`quarter` sets 3, 1.5 or 1 items visible, arrows only when more items than visible; wheel, swipe and re-init on first width in `gestures.ts`): images as thumbnails that open the `Lightbox` (v3's dialog: previous/next, counter, arrow keys, Esc), other files as a file row with the name, an x per entry in `fill` mode. `FieldInput` shows it above the tool for `file` fields (removing writes the shorter list, or `null` when it was the last); the feature sheet shows it read-only in Daten. `fileRefs(value)` is the one reader of a `file` value (the sheet formatter uses it too). Image URLs come from the app: it calls `providePhotoUrl(resolve)` once (Svelte context), `resolve(sha256, size)` returns a URL or a promise of one (`apps/web/src/lib/participant/photo-url.ts`); without a provider every file is a file row. Adding files stays in the photo tool.

## Task sheet (`src/task-sheet`)

`TaskSheet` is the content of the shell's task sheet slot: it wraps `FormRenderer` and talks to two ports (`contract.ts`). It renders no `Sheet` of its own; the shell does, and unmounting the content is "closing".

- **`RunSubmitter`** (implemented by the run queue, WP-511): `submit(RunDraft)` resolves `'queued'` once the run is stored on the device, `outcome(runId, listener)` reports `RunProgress` (`queued`, `accepted`, `refused` with `reason`; registry `RUN_PROGRESS_STATES` in core). **`DraftStore`**: `get`, `put`, `drop` by key. Run ids come from the `ids` port (`Ids.runId()`, UUIDv7), minted once per submit so a retry after a failed local save is the same run.
- **Submit** builds one `RunDraft` per target feature (`featureIds`; none = a task that creates one; several = H2 batch) with `session.submitValues()`. A synchronous guard makes a double tap create one run.
- **Drafts:** the values are written 1 s after the last change (`TimerPort`, `DRAFT_SAVE_DELAY_MS`), on unmount and when the page is hidden, but only if they differ from what was last saved; reopening restores them (a stored draft wins over `initial`, which is where an assistant proposal, H4, or a role preset goes). Submit drops the draft; a refusal offers "Reopen draft", which stores the values again and reopens the form. Default key: task key plus feature ids.
- **Outcome text** never says done before the server accepted: "Saved on this device..." (offline: "will be sent when you are online"), then "Accepted by the server", or the refusal reason.
- **Tools:** the `tool` snippet receives `{ field, value, id, produce }`; `produce(value)` sets the field.
- `TaskSheet.perf.spec.ts` holds the jsdom open-time check (50 fields; jsdom inflates DOM cost). The binding number is the real-browser scenario `task-sheet-50` (`npm run bench:browser -- --only task-sheet-50`): tap to next paint, CPU x4, limit 200 ms (docs/12 INP); about 160 ms (WP-549). `testing/` has in-memory ports.

## Map (`src/map/`)

`contract.ts` is the contract: `ViewRenderer.mount(el, view, source)` returns a `MapHandle` (`ready`, `onFeatureTap`, `onMapTap`, `centerOn`, `showOverlay`, `clearOverlay`, `addMarker`, `moveMarker`, `markerPosition`, `removeMarker`, `onMarkerDrag`, `setDoubleClickZoom`, `project`, `unproject`, `onMove`, `extent`, `onExtentChange`, `zoomBy`, `setView`, `setBasemaps` (optional), `destroy`). Renderers are looked up by their `RENDERERS` registry key with `getRenderer(createRendererMap(), key)`; an unknown key throws `UnknownRendererError`. A second renderer (3D, H1) registers through `createRendererMap(extra)` and touches nothing in `maplibre/`.

- **Features in:** a `FeatureSource` delivers `FeatureChange` deltas (add, update, remove). `toMapFeature(folded, geometryProperty)` builds a `MapFeature` with the anchor from `derived.pointOnSurface`; Z stays in `geometry` and `anchor`. `queryChunks(bbox, size)` gives the same features as `query` lazily in slices (WP-848): the renderer reads the values of a new style key slice by slice with a yield between each (`maplibre/key-values.ts`; a newer walk ends the older one), and a filtered source reapplies a filter change the same way. A live-positions layer (H5) is just another source.
- **Clustering** runs in a Web Worker (`cluster/worker.ts`, Supercluster). The main thread posts deltas (id and anchor only) and receives cluster output for the viewport. `ClusterClient` takes a `ClusterTransport`, an optional `YieldToMain` and an optional chunk size (default `CHUNK_SIZE`, injectable for tests); `createInProcessTransport()` runs the same handler in tests and `bench/map-cluster`. Supercluster cannot change a built index, so the worker keeps one small `HeldPoint` per feature by id (id, anchor, style values; `cluster/feed.ts`, about half the heap of GeoJSON wrappers) and rebuilds lazily: the first query builds; changes after that wait in a pending set and are overlaid on the query result (results at the highest zoom are exact; at lower zoom the cluster totals lag a fresh build by at most the number of points changed since the last rebuild). A build hands Supercluster the points through one reused feature object, so it allocates no wrapper per point. At start the worker also runs `warmUp()` (`cluster/warm.ts`: a synthetic index of 4000 points, about 75 ms) while it waits for the first delivery, so the engine has compiled the build loops when the real points arrive; it changes no output (`cluster/identical.spec.ts`). When the data is already there at worker start there is no idle time: warm-up plus build is about equal to the cold cost (no loss beyond about 70 ms of worker CPU). Once more than max(200, 0.5 % of the points) are pending, the next query rebuilds. `ClusterIndex.builds` counts builds. Numbers: `bench/map-cluster`.
- **Un-cluster (WP-666):** the Cluster tool's capped query. `ClusterClient.queryCapped(bbox, zoom, cap)` sends the `cap` with the `query` (the `query` method is the uncapped form); the answer is a `ClusterAnswer` (the `items`, and with a cap `stats` of `CappedStats`: `inView` and `single`). It is two-phase: the clustered answer at the zoom counts the features in view in O(clusters in view), and only when that total fits the cap is the index asked again above its max zoom, which returns the (at most the cap) features singly — never a pass over all points. On the handle, `setUncluster(cap | null)`: with a number the features in view are drawn singly while there are at most that many, more stay clustered; `null` clusters as usual, and clustering itself stays on. `onUnclusterStats(fn)` reports, after each query while un-clustering is on, how many features are in view and whether they are drawn singly (`UnclusterStats`: `inView`, `single`), and calls the listener at once with the last report, if any. Both are optional: a renderer without clusters (3D) omits them. Numbers: `bench/map-uncluster`.
- **Loading:** `createRendererMap()` loads the `maplibre-2d` renderer (and with it the style validator and MapLibre) on the first `mount`, so the shell chunk stays small (`renderers.ts` 34.7 to 1.1 KB gzipped). The handle is usable at once; `ready` resolves when the map is drawn. The renderer delivers features to the worker in chunks of `CHUNK_SIZE` (4000) items with a yield to the main thread between chunks (`yieldToMain` port, `maplibre/chunk.ts`); later changes queue behind. Markers appear after the first chunk and the picture completes after the last, with no spinner. What remains of long tasks on load is MapLibre's own work (module evaluation, shader compile, first render), not feature delivery.
- **Selected feature and pointer (WP-733):** `setSelected({ id, color } | null)` marks the feature whose sheet is open (v3 `selectedInstanceId`): a ring (two strokes, 70 % and 20 %, behind the marker) around a point, a 4 px (area) or 6 px (line) stroke and a 15 % fill on a shape. The colour is a token value the caller passes (the app gives `color.focus` of the role's theme). It is four `setFilter` calls on the layers `ub-select-halo`, `ub-select-ring`, `ub-select-fill`, `ub-select-line` (filtered on the feature id; not tappable, not replaceable by a view style); the data is never rewritten, so it is O(1) (bench `map-select`). A redraw of the layers re-applies the held selection, and a selection made before the map loads is applied once it has. A feature inside a cluster shows no ring. Over a tappable layer the canvas cursor is `pointer` (`maplibre/hover.ts`; desktop only). Optional on the handle: a renderer without it (3D) omits it.
- **`maplibre/`** is the only place that names MapLibre. `api.ts` is the slice of the library used and the dynamic `import('maplibre-gl')`, so the ui entry never loads it. Polygons and lines are drawn from a GeoJSON source updated by `updateData` diffs; anchors of all features go through the cluster source. A view layer's `style` (renderer `maplibre-2d`) is applied over the default layers by `style.ts` (`resolveLayers`): the style is `{ "layers": [...] }`, a layer whose `id` is a default (`ub-shape-fill`, `ub-shape-line`, `ub-cluster`, `ub-cluster-count`, `ub-single`) replaces it verbatim; other ids are appended before the cluster layers, which are drawn last so the counts stay readable. An added layer on `ub-clusters` draws single features only: the renderer adds `['!', ['has', 'clusterId']]` to its filter (via `all` if it has one), so its own filter must use expression syntax (e.g. `["==", ["get", "art"], "x"]`); MapLibre refuses to mix the two filter syntaxes. Each layer is validated with `@maplibre/maplibre-gl-style-spec`; an invalid one throws `MapStyleError` with `layerId` (from `ready` at mount, or synchronously from `setView`). Layers may only use the sources `ub-clusters` (clusters: `clusterId`, `count`; single points: `featureId` plus exactly the feature properties the style reads with `["get", key]` or `["has", key]`, found by walking the expressions in `pointPropertyKeys`; the worker gets only those keys, and a style change adding a key sends values for that key alone through one `keys` message, never the anchors again; the values of a new key travel in chunks of `CHUNK_SIZE` with a `yieldToMain` between them, the first chunk inside the `keys` message and the rest as `values` messages, so no main-thread task is longer than one chunk (60k features: about 1.4 ms unthrottled). `ClusterClient` queues later posts behind a delivery in flight, so the worker sees call order and a query answers after the last chunk) and `ub-geometry` (polygons and lines; their feature properties and `id`, read with `["get", key]`). Every layer on those two sources is tappable, whatever its id. `$ref` styles must be resolved by the caller first. `MapHandle.setView(view)` swaps the style on a live map without re-sending features. The style never enters the view model (H1). **One tap, one target (WP-688, `maplibre/tap.ts`):** the map has one click handler, not one per layer. A tap asks MapLibre once for the features of every tappable layer in a box of `HIT_PAD_PX` (12 px, v3's touch tolerance, `MapCanvas.svelte:634-670`) around the point, and `pickHit` takes the first class that has a hit: a point or cluster (circle and symbol layers), then a line, then an area (fill layers), the topmost within a class (v3's order: markers first, then `[L_LINE, L_FILL]`). No hit is a tap on empty map. A layer's class comes from its MapLibre type. Cost is O(hits under the box); bench `map-tap`. Specs: `renderer-tap.spec.ts` (fake map) and `maplibre/e2e` (real MapLibre). One tap on a cluster reports its members (`MapHandle.onClusterTap`, from the worker's `leaves` message) and `MapHandle.isolate` draws only some of them (v3's drill-down); a second tap within 300 ms fits the members (WP-653).
- **Map backgrounds (WP-614):** `maplibre/basemaps.ts` draws the project file's `map` section (docs/05): `basemapSpecs(config, selection)` builds one source `bm-<key>` and its layers per selected layer (the base first, then overlays in draw order; a vector source draws fill, line and point layers, a raster one a single layer, and an `advanced` key applies only to the layers whose type it names); `applyBasemaps(map, config, prev, next, beforeId)` moves a live map between choices — sources added before layers, every basemap layer below `beforeId` (the lowest feature layer), layers that stay untouched; `resolveSelection(config, choice)` keeps a choice that still fits the config (a base the config no longer declares falls back to `defaultSelection`; overlays keep only the declared ones). The core registry (`MAP_LAYER_KINDS`, `MAP_SOURCE_TYPES`, `MAP_PRESETS`) plus `layersForRoles`, `defaultSelection` and `orderedLayerKeys` decide which layers a participant sees; the module draws what it is given. `basemapErrors(config, spec)` checks each layer's `advanced` against the Style Spec, like view styles, because core may not import it; a key that fits no layer is reported too. `pmtiles` sources use `pmtiles://` URLs, which the app must register. **Tile proxy (WP-689, A-033):** `basemapSpecs(config, selection, packs?, proxy?)` and `applyBasemaps` take `proxy: TileProxy = { project, origin }`; every `proxied` source type then draws from `<origin>/api/p/<project>/tiles/<layer>/{z}/{x}/{y}` (wms: `/wms/<layer>?bbox=…&width&height&crs`; a remote pmtiles archive as a `raster` or `vector` tile source) and the pack protocol's network leg reads the same URL. Self-hosted paths and `geojson` stay direct. The renderer takes it as the `proxy` option (`RendererMapOptions`).
- **E2E read-back seams (WP-740, WP-745):** the highlight, the clusters and the marker icons are canvas pixels, so the renderer writes what MapLibre holds onto the map element: `data-select-filter` (the highlight layer's filter) and `data-map-state` (`maplibre/probe.ts`: JSON of `zoom`, `minZoom`/`maxZoom` from `map.getMinZoom()/getMaxZoom()`, the rendered cluster and single counts from `queryRenderedFeatures`, the `ub-single` `icon-image` expression and the `ub-look-*` image ids from `listImages()`). `data-map-state` exists only in the e2e build (R14: it queries the map on every settle): `apps/web/vite.config.ts` defines `__UB_MAP_PROBE__` as true when `UB_MAP_PROBE=1` is set for the build, and `scripts/e2e/run.mjs` sets it. A production build never sets it, so the renderer attaches no `idle` listener at all (`createProbe` returns `undefined`); specs use the renderer option `probe: true`. When on, it is written on each `idle` and only when the JSON changed. Journeys that read it: `apps/web/e2e/participant/real-map.spec.ts` (zoom limits, Cluster tab, marker looks of two Objektarten, child create from the relation menu).
- **Stylesheet and camera (WP-592):** `maplibre/renderer.ts` imports `maplibre-gl/dist/maplibre-gl.css`, so the stylesheet ships with the lazy renderer chunk (shell unchanged; `e2e/participant/bundle.spec.ts` checks both) and reaches the builder preview too. Without it the map container is `position: static` and the canvas is blank. The view's `camera` (`View.camera`, schema `Camera`) is read by the renderer, not the contract: `MapHandle` is unchanged. The map opens at it, and `setView` with a different camera eases there (jumps with reduced motion); the same camera again leaves the map where the user put it. `maplibre/camera.ts` maps `center`, `zoom`, `bearing` and `pitch` one to one; with no `zoom`, a Z (metres above the ellipsoid, `center[2]`) gives `zoom = log2(1.5 * 40075016.686 * cos(lat) / Z)` (MapLibre's camera sits 1.5 map heights above the ground; straight down, clamped to 0..24), for example Z 14677 m at the equator is zoom 12. A 3D renderer uses Z directly. A camera with neither `zoom` nor Z opens at zoom 14. With no camera the map fits the extent of the first features the view delivers, once per view (a no-camera `setView` fits the first delivery of that view), in one pass over that delivery (the source is not scanned a second time; an empty first delivery waits for the first non-empty one; non-finite anchors are ignored, and a delivery without a finite anchor does not fit, a later one does); with none known it keeps the default (Germany, zoom 5).
- **Tool ports (WP-576):** all renderer-neutral (Position, Bbox, Geometry; a 3D renderer implements them from the same types, H1). `onMapTap(fn)`: a tap on empty map, WGS84 `[lon, lat]`; a tap on a feature fires `onFeatureTap` only, a tap on a cluster `onClusterTap` only (a second tap on the same cluster within 300 ms fits the members instead); neither fires `onMapTap` (the renderer asks which of its feature layers are under the point; tool overlays do not count, so Measure can tap across its own line). `captureTaps(on)` (WP-698, v3 `isEditingLocation`): a tool that owns the tap (the placement pin, the draw tool) switches it on: while on, every tap is a `mapTap` with its position, also over a feature, an area or a cluster (a tree inside an area can be moved); off by default, a renderer without taps omits it. `centerOn(point | bbox, { zoom?, minZoom?, offset? })`: a point eases (zoom stays unless given; `minZoom` only zooms in and `offset` lands it in the middle of the part the sheets leave free), a bbox is fitted; when the user prefers reduced motion (`reducedMotion` renderer option, default the `prefers-reduced-motion` media query) the view jumps (duration 0). `showOverlay(id, geometry, style)` / `clearOverlay(id)`: one overlay source and three layers (`ub-overlay-*`, `packages/ui/src/map/maplibre/overlay.ts`) above the view's layers; the same id replaces; `OverlayStyle` is `{ color, fillColor?, width? }` in design-token values the caller passes (the app uses `THEMES[theme].color.primary`), the renderer has no colours of its own. Overlays are re-sent whole (they are few), never the features; `setView` only moves them back on top; `destroy` removes their layers and source. Calls before MapLibre has loaded are kept and replayed (lazy wrapper in `renderers.ts`, and inside the renderer for calls before `load`). The list alternative needs none of this: `FeatureList` works without a map. H5 live positions use overlays.
- **Markers and projection (WP-632):** `addMarker(id, at, { element, draggable? })` pins a caller-built DOM element at a WGS84 position (same id replaces; `maplibre/marker.ts`). Markers are not features: they never reach the cluster worker, and a drag moves one element and calls `onMarkerDrag(id, at)` (every move, and once at the end), so a drag re-draws nothing else. `moveMarker` does not fire `onMarkerDrag`; `markerPosition(id)` reads it back; `removeMarker` drops it. `project(at)` / `unproject({x, y})` convert between WGS84 and px in the map's box (undefined until the map is drawn). `onMove(fn)` fires every frame the view moves, unlike `onExtentChange` (when it settles). `OverlayStyle` also takes `opacity` and `dashed` (a dashed line has its own layer, `ub-overlay-dash`). The + flow's draggable pin and dashed connector use these (`apps/web/.../sheets/create/PinPlacement.svelte`).
- **Map controls (WP-554.3, WCAG 2.5.1 and 4.1.2):** `MapHandle.zoomBy(delta)` eases the zoom (jumps with reduced motion; ignored before the map is drawn). The map has no zoom buttons, as v3: double-tap, wheel and the keyboard (MapLibre's `+`/`-` and arrows) zoom and pan. Standort lives in the app's bar and reads the device only through the `PositionPort`, then `centerOn` at `POSITION_ZOOM`. `describeMap(el, labels)` gives the map element `role="region"`, an `aria-label` and an `aria-describedby` description that says the same features are in the list; it returns an undo. All text is `MapDescriptionLabels` from the app. The participant app's map screen (`apps/web/src/lib/participant/shell/MapCanvas.svelte`, WP-620) calls `describeMap` on mount. `MapControls` and `startTitle` were removed in WP-656.
- **Drawing on the map (WP-635):** `draw/` is the renderer-neutral port of v3's `reference/src/lib/components/map/geometry-draw-tool.svelte` (it uses only the `MapHandle`). `createSession(kind, multi)` keeps the parts (a line 2, an area 3 vertices; `MIN_VERTICES`), the active part and the per-part undo/redo. `createDrawController(handle, session, colors)` binds the session to the map: each part is one overlay (an unfinished area's outline is dashed), each vertex a draggable marker, a tap on the map adds a vertex, a tap on the first vertex closes an area — so a change re-draws one overlay source, never a feature (R14). `DrawOnMap` is the control stack (its strings come from `DrawLabels`, no literal text) and the confirm gate: `evaluate(geo, parts, kind, multi)` runs the finished shape through `core.geo` (`repair` fixes orientation, closing and rounding; a repair that changes the geometry type is a refusal with the reason). While it is mounted it turns `setDoubleClickZoom` off (two quick taps add two vertices), captures the taps (`captureTaps`, so a vertex inside an area is still a vertex, WP-698) and puts the `ub-drawing` class on the body (crosshair cursor).
- **List alternative:** `FeatureList` (a table, sortable by column button, `aria-sort`, every row a button opening the same `featureTap`). `inExtent(features, extent)` selects what the map shows; `sortFeatures` applies a view's `sort`. Strings come in through the required `labels` prop, so the component has no literal text.

## Feature sheet (`src/feature-sheet/`)

`buildFeatureSheetModel(input)` (pure) turns a `FoldedFeature`, its feature type, edges in and out, `availableTasks` (decided by perms, an input) and an `activity` list (one `ActivityEntry` per run: task label, actor name or the neutral label, time, changed values and status; newest first) into a `FeatureSheetModel`; `FeatureSheet` draws it in a `Sheet` (props: `open`, `model`, `clock`, `onclose`, `onStartTask(key)`, `onOpenFeature(id)`); a `file` row draws the read-only `MediaGallery` (see Gallery below). Contract: `contract.ts`. `buildActivity(input)` (pure, the same input) builds the sheet's Aktivität timeline: a segment per stage visit (the tappable "Verschoben nach: …" header, the visit counter when a stage repeats, the green "Erstellt" header of the creating run or, when that run is not on the device, the sync row's audit fields) and one line per run (smart label: one field, the location, several fields, or the task; plus the task, the actor and the time, expandable to the changed values, photos as thumbnails). Types: `ActivityView`, `ActivitySegment`, `ActivityRun`, `ActivityField`, `ActivityLabel`.

- **Values** go through `FORMATTERS`, total over the property type registry. Names of participants and features come from the `lookups` input (`undefined` shows the id). Geometry shows `derived.areaM2` or `lengthM`, never coordinates. A value that does not match the property type shows like an unset one (structural check, no coercion; a `console.warn` in dev). Locale: `en` or `de` strings via Paraglide with the model's locale; numbers, dates and relative times via `Intl`, with formatters cached.
- **Selector (H3):** `properties` narrows and orders the shown properties (a data view's `properties`); history of hidden properties is dropped too. Permissions are not decided here.
- **Relations** are grouped by relation and direction (an incoming group's label ends with the localized "incoming"). The group is named by the picked property's label (a property with the relation's key on this type), else the label of the type on the other side, else the key. The relation's own optional `label` (in `RelationSchema`) is accepted by the schema but not read by the sheet yet.
- **History** is one row per changed value of the `activity` entries, in their order (the reader supplies them newest first), at most `HISTORY_CAP` (10) rows per property. Times are relative to `clock.now()` (a `Clock` port).
- `sheet.perf.spec.ts` holds the budget test (50 properties, 10 relations, at most 50 ms).

## Tool host (`src/tool-host/`, WP-527)

Public tool API (decision 0017, extracted from photo, draw, measure and search in WP-553): tools are made with `defineTool` and import from `@ueberblick/ui/tool-api` (authoring surface without the design system); authoring guide in `packages/tools/README.md`. `createToolHost({ loaders, ports, locale?, person?, optionsFor? })` mounts first-party tools by key. `loaders` are lazy (`() => import(...)`), the ui package never imports `packages/tools/*` (a spec checks it). Tool API 2 (WP-613): a tool declares `contributes` (registry `TOOL_CONTRIBUTIONS`), optional `settings` and `preferences` option schemas, and gets `ctx.settings`, `ctx.preferences`, `ctx.setPreference`; the optional `person` port (`ToolPersonPort`) supplies availability (`offered` / `active`, registry `TOOL_AVAILABILITY`), the project and role settings, the person's switch and preferences, and the host refuses a tool that is off (`tool_off`). `form-field` tools (`mountField`) get one field, its value, options (from the project file's `tools.<key>` settings via `optionsFor`; per-field overrides are a later question), the ports (`blobs`, `hash`, `position`), `produce(value)` and `clear()` (an explicit clear: the form empties the field; a `null` value is refused); the host checks the tool's `produces` against the field type and the value's shape (`file`, `geometry`), and refuses values after unmount. panel tools (the other points, `mountPanel(el, { toolKey, point, ... })`) get `startTask`, the same `ports`, `map` (`centerOn(position, zoom?)`, `showOverlay(geometry)`, `clearOverlay()`, `onTap(handler)` returning the unsubscribe function: a temporary overlay and map taps, never a write), `openFeature(id)` (opens the feature sheet), `searchText(sources, query, limit)` (the device store's index lookup) and `feature(id)` (read one feature to label a result); the app passes these per mount (`MountPanelInput`), the host adds `locale`. Errors are `ToolHostError` with a registry code (`unknown_tool`, `wrong_point`, `tool_off`, `invalid_preference`, `wrong_field_type`, `invalid_value`, `unmounted`, `invalid_option`, `invalid_definition`, `unsupported_api`); the registries `TOOL_CONTRIBUTIONS`, `TOOL_AVAILABILITY` and `TOOL_HOST_ERROR_CODES` live in `packages/core/src/registry/ui.ts`). `ToolMount` renders a form `ToolSlot` through the host (use it in the `FormRenderer` `tool` snippet). The host runs `assertTool` on every loaded tool, so an object that did not come from `defineTool` (or targets another `TOOL_API_VERSION`) is refused. `browserPosition` is the `PositionPort` over the Geolocation API; `@ueberblick/ui/tool-testing` holds the contract suite `describeToolContract` every tool spec must call, and `testPorts`/`testMap`. Tool API 3 (WP-683, B-020): a panel tool may declare `data: true` and then gets `ctx.data` (`ToolDataPort`: `items()`, `subscribe`, `append(body)` returning the pending item at once, `cursor`, batched `markRead(seq)`, `retry(id)`, `discard(id)`), the tool's own data stream on the device; the app supplies the streams through the host option `data: ToolDataSource` (`forTool(key)`), and a tool that did not declare `data`, or has no stream for the person, gets no `ctx.data`. The tool never calls the network. Extending: H1 viewers and H4 assistants are `form-field` tools, H5 live layers are `layer-section` tools; a new contribution point is a registry entry.

View style subpath (WP-570): `@ueberblick/ui/view-style` is the narrow entry the builder uses to check a maplibre-2d view style without the ui barrel or MapLibre GL. It exports `validateViewStyle(style): Promise<ViewStyleResult>` (`{ ok: true }` or `{ ok: false, errors }`, each error `{ path, message, layerId? }`; the type is renderer-neutral, other renderers add their own validators), the constants `SOURCES` and `LAYER_IDS` (the ones the renderer draws with; `map/maplibre/layers.ts` re-exports them) and `viewStyleErrors(style, spec)`, the synchronous check the renderer's `resolveLayers` shares (`spec` carries the Style Spec's `validateStyleMin` and `isExpressionFilter`). The Style Spec is loaded by a dynamic import on the first `validateViewStyle` call only. A style layer must name a source from `SOURCES`; a layer added over `ub-clusters` needs an expression-syntax filter, refused by a `layers[i].filter` error.

## BaseTable (`src/components/admin/`, WP-322)

v3's one list component (`import { BaseTable } from '@ueberblick/ui/components/admin'`). It takes `rows` and `columns` and fetches nothing. Built on `@tanstack/table-core` (models) and `@tanstack/svelte-virtual` (only the rows in view are in the DOM: 10 000 rows draw a few dozen), with the kit's `ui/table`.

- **Columns** (`TableColumn`): `key`, `label`, `kind` (`text`, `number`, `date`, `boolean`, `array`, `dropdown`, `custom`; registry `CELL_KINDS`), `sortable` and `filterable` (default on), `editable` (default off), `copyable`, `copyValue` (what the copy button puts on the clipboard when it is not the shown value, e.g. the login link for a token), `live` (a `boolean` switch that works outside Edit mode), `minWidth`, `options` (dropdown and array), `dateMode`, `emptyLabel` (name of the "no value" filter entry), `cell` (snippet for `custom`). A new property type adds one renderer to `cells/registry.ts` (`CELL_RENDERERS`).
- **Callbacks:** `onEdit(rowId, key, value)` (cells are editable only in Edit mode, only for `editable` columns, and only when `onEdit` is set; a rejected promise shows a failure toast, or the page's own message when it throws `CellRefusal` (exported from the same entry), and the cell keeps the typed value), `onRowSave(rowId, values)` (row editing, WP-370: in Edit mode the cell edits of a row are collected, the check in the row's last cell saves them with ONE call, the x discards them, leaving Edit mode drops unsaved ones; with the focus on the edited row Enter saves it and Escape discards it (the cell editors keep their own keys), the buttons are 44 px targets; throw a `RowRefusal(message, { <columnKey>: reason })` to mark the named cells and keep the edits; `live` columns still save at once through `onEdit`), `onAdd(values)` with `addRow: { requiredKeys, excludedKeys, defaultValues }` (shows the add row; `createAreaPrefix` renders before its confirm button), `onDelete(ids)` (row menu "Delete"), `rowMenu: { header, onEdit, items }`, `onRowClick`, `selectable` with `onSelectionChange(ids)` (shift-click selects a range; `shiftSelect: false` turns it off), `getRowId` (default `row.id`), `columnManagement: { label, onOpen }` (the "+" of the last header opens the page's column manager), `locale` (`de` or `en`, the language of the table's own texts). Toolbar: `showToolbar`, `showEditMode`, `editModeLabel`. Empty state: `emptyMessage`, `emptySubMessage`.
- **Query mode:** pass `onQueryChange` and the table neither filters nor sorts: it calls `onQueryChange({ search, sort, filters, page })` on mount and after every change (`filters` maps a column key to the ticked values; the empty-value entry is `__empty__`; `page` is the `page` prop, the parent owns paging; the search is not debounced, the parent does that). The rows you pass are shown as they are. `initialQuery` seeds the initial `search`, `sort` and `filters` (read once when the model is created; the data page passes the query it left behind when opening a detail).
- Filter counts are computed once per row set and column, not per keystroke or scroll. Strings: `table_*` in `messages/{de,en}.json`.
- jsdom has no layout, so a spec must give the `[data-scroll]` element an `offsetHeight` (see `base-table.spec.ts`), or the virtualiser has no window and draws no rows.

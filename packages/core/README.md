# @ueberblick/core

All domain logic lives here, and **none of it does I/O**. Storage, clock, IDs and blobs arrive through `src/ports.ts`. This package runs unchanged on the device, the server, the builder simulator and in tests.

## plan/bind resolver (WP-807)

`bindVars` (`plan/scope.ts`) is the one place a task's `bind` expressions are evaluated, under the actor's visibility guard (pointers kept, so a hidden id is refused loudly later). `scope()` uses it and refuses `bind_unresolved` on a `null`; the device asks `createPlan(form).bindsFor(task, target, actor, configFor, ports)` (same result, never refuses; `null` = no Objekt) and `boundTypes(config, task)` for the label and properties of the Objektart behind each `<bind>.<property>` form field. The participant form (`apps/web/.../form/binds.ts`), `buildStepViews` and the builder preview take that `bound`; none of them evaluates a bind itself (R1).

The device reads a task form's expressions (visibility, required, computed display, filters) through `createPlan(form).contextFor(target, actor, configFor, ports)`: `guardedContext`, the context `scope()` uses, so an Objekt the participant may not see reads as absent and drops out of relation lists (WP-816). The device can hold such Objekte: queued runs predict features on top of the synced ones, and a pull learns of a visibility change only at the next sync.

## plan/participant-choice (WP-756)

A submitted `participant` value is checked in plan with `participantChoice` (`schema/property-select.ts`), the function the web form uses to offer people (B-022): without `select` a participant may choose only themselves, a role in `select.all` any member, a role in neither list nobody; an empty value clears. A breach is refused `not_permitted` (`form.<key>`). Imports, rules and the system are not held to it. Membership is checked through the optional port `PlanPorts.isParticipant`; the server passes it, a device leaves it out (it does not know all members) and the server stays authoritative.

## schema/ (WP-010)

Zod schema of the project file. Entry points: `parseProjectFile` (template or overlay, precise error paths), `TemplateFileSchema`, `OverlayFileSchema`, `ProjectFileSchema`, `ViewSchema` (standalone, also for ephemeral views), `MapSchema` (the `map` section: background layers), `GeoJsonGeometrySchema` (Z allowed). Enum values (property types, geometry kinds, renderers, task offers, audiences, schema versions) come from `registry/`. `npm run gen:schema` writes `schema/ueberblick-1.schema.json`; a spec fails when it is stale. Fixtures: `src/schema/__fixtures__` (valid YAML and `invalid/cases.yaml` with expected error paths). Semantic checks are `schema/compile` (`compile(file, { assets })`: `assets` is required: the project bundle as an `AssetResolver` at ingestion, `NO_ASSETS` for a self-contained stored file (B-013); every layer style `$ref` is embedded in the compiled config and `tools.search.sources` is validated, WP-577; the single `$ref` walker `embedRefs(value, resolve)` is exported here and used by `scripts/embed-refs.mjs` (e2e and demo ingestion) and by the test helpers `goldenAssets`, `embedGoldenRefs`, `embedGoldenSource` in `testing/golden.ts`) (WP-013: `compile`, `diff`, `serialize`, `hydrate`, see docs/05 "compile()"), expressions WP-020. `schema/index` re-exports them (`compile`, `diff`, `hydrate`, …); participant code imports the `@ueberblick/core` subpaths instead (WP-122).

## form/ (WP-044)

`formApi` (`initial`, `evaluate`, `submitValues`, `hiddenClears`, `dependents`) is the one implementation of relevant, required, readonly, constraint and calculate (decision 0015). Expressions come from `CompiledConfig.expressions` (`tasks.<task>.form.<field>.<attr>`); a declared one without a compiled expression throws `FormConfigError` (fail closed). The caller's `EvalContext` carries `self`, `actor`, `inputs`, bind names; the module binds `form` and `value`. Empty means `undefined`, `null`, `''` or `[]`; a constraint runs only on a non-empty value. `evaluate` recomputes readonly calculated fields and reports a supplied value that differs (`readonly` issue), so a caller must not feed a stale readonly value back in. Expression errors count as false and land in `FieldState.errors` (constraint errors are also a `constraint` issue). `submitValues` drops non-relevant fields; `hiddenClears` names the non-relevant fields a run sends as an explicit null (owner Q5), and plan writes that null as a cleared observation only for a field that holds a value (a non-null value for a hidden field is still dropped). `dependents` is transitive through readonly calculated fields and includes the field itself. The `type` issue covers type fit, declared select options, integer, min/max and geometry kind, checked against the property of the task's target type (`creates`, else the single `on` type; `evaluate`'s optional `type` argument when `on` lists several, else `FormConfigError`).

## expr/sql liveEdgeJoin (WP-571)

`liveEdgeJoin({ edge, feature, direction })` (from `@ueberblick/core/expr/compile`) is the one text of "an edge counts only if its far end is a live feature". It returns `{ join, live, near, far }`: `join` is `JOIN features <feature> ON <feature>.id = <edge>.<far>`, `live` is `<feature>.lifecycle IN ('active','completed')` (`servedSql`) (AND it into the `WHERE`), `near` is the edge column that holds the known id. `direction: 'out'` goes from `from_id` to `to_id`, `'in'` the reverse. `relationFrom` and the relation subqueries of `toSql` are built from it, and so are the server's `Facts.edgesFrom/edgesTo`: `FROM edges e ${j.join} WHERE e.${j.near} = ? AND ${j.live}`. An edge to a never-created or deleted feature is excluded in both directions.

## expr/sql viewportFrom (WP-590)

`viewportFrom({ feature, box })` (from `@ueberblick/core/expr/compile`) is the one text of "features inside a viewport": `from` is `FROM feature_bbox <box> CROSS JOIN features <feature> ON <feature>.rowid = <box>.rid`, `near` the four-`?` intersection condition (AND it into the `WHERE`), `args(bbox)` its values for `[west, south, east, north]`. `CROSS JOIN` pins SQLite's join order, so the R*Tree drives and `features` is fetched by rowid. With a plain `JOIN` a filter that matches most rows (`hoehe_m > 15`, a 16k-term `IN`) made the planner walk the expression index and probe the R*Tree once per match. At 60k features: viewport plus filter 72 to 24 ms, viewport plus 16k-term list 100 to 52 ms. Results are identical (property test against the plain join). No extra index or DDL.

`Facts.ofType(type)` (WP-594) lists every live feature of a type, with or without geometry, in unspecified order: O(features of the type), for one user action or one changed feature. The participant's own-lists read it because `near` never returns a feature without geometry.

`viewportPageFrom({ feature, box })` is the second shape (WP-591): `FROM features <feature> JOIN feature_bbox <box> ON <box>.rid = <feature>.rowid`, same `near` and `args`, same rows. It is for a rowid-ordered, limited read (keyset paging, `ORDER BY rowid LIMIT n`): SQLite may walk `features` in rowid order and stop at the `LIMIT`, so paging a whole layer costs a page each (0.4 ms at 60k), where `viewportFrom` would sort every match first (about 50 ms per page). Over a narrow viewport `viewportFrom` is faster (1.2 against 11.7 ms per page with a config index). Use `viewportFrom` for every other viewport read. The server's `store/facts` (`bboxQuery`, `Facts.near`, the derived lookup) uses `viewportFrom`, `http/ogc/items.ts` uses `viewportPageFrom`.

## expr/evaluate (WP-127)

`evaluate` and `condition` compile a `TypedAst` once (cached per AST, the last one also in a variable) into closures; nothing that depends only on the expression is redone per feature. A chain of binary operators runs a fast path that holds only values; a fault or a non-bool operand abandons it and the chain is evaluated again on the general path (faults as values, CEL absorption). The retry restores the iteration budget and sets `Run.safe`, so nested faulting chains are retried at most once per level. `condition` returns shared results for the no-error cases. The `EvalContext` contract is unchanged.

## rules/timing (WP-573)

Time-based rules in one place, for the server timers, the builder simulator ("advance time") and later the device. `parseCron(expr)` returns `{ ok: true, cron }` or `{ ok: false, error: { message, position } }`. `nextAfter(cron, from)` is the first matching minute strictly after `from`; it steps by day up to `CRON_HORIZON_DAYS` (8 years, at most 2,929 day checks), never by minute, and returns undefined when the cron never matches. `timeRules(config)` lists the `elapsed` automatic actions (by id `<task>.<name>` and by feature type) and the `schedule` ones, read from `config.autos`; compile guarantees every entry is usable, so a hand-built config with a bad cron or a missing `elapsed.from` makes it throw an invariant error naming the id. `elapsedDueAt(rule, ctx)` is `from + after + offset` from the expressions compile stored under `tasks.<t>.auto.<n>.elapsed.*`; `ctx.vars` needs `self` and `inputs`. Calendar months clamp to month end. Undefined while `from` has no value.

## locale/ (WP-588)

`localize(value, locales)` is the only resolver of a `LocalizedString`: requested locales in order (exact tag, then base language), then the first key. No default-locale parameter: the caller appends its default to `locales`. `localizeExact(value, locale)` serves editing one language (no fallback). `acceptLocales(header)` parses `Accept-Language`. Subpath `@ueberblick/core/locale`. `displayName(type, feature, locales)` is the one name of a feature for people (WP-593): the first `required` `text` or `localized_text` property with a value, in the order the type declares (an optional text is a finding or a note, never a name; [B-014](../../docs/decisions/later/B-014-feature-display-name.md)), else the type label plus `shortId(id)` (`Baum #4f2a`). The list row, the feature sheet title and relation links all call it; it reads one row, never a fold. A guard spec (`locale/guard.spec.ts`) fails when another file picks a language itself.

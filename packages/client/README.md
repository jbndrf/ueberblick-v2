# @ueberblick/client

Device runtime (`docs/03-architecture.md`). Implements the core ports on the device.

## Device store (`src/store`, WP-510)

`openDeviceStore(name, { env, marker, onIssue })` opens one IndexedDB per participant and project and returns a `DeviceStore` (contract: `src/store/contract.ts`). It implements the core `Facts` and `Blobs` ports.

- **Synchronous ports over async storage.** Features, edges and blob keys are held in memory, loaded once at open, and updated only after the IndexedDB transaction committed. History (last 10 per feature and property) is loaded on demand: `await store.warmHistory(ids)` before `store.facts.history(...)`. A cold feature throws `history_not_warm`, never an empty answer. The history cache is bounded (4,000 features). `warmActivity(id)` is `warmHistory` plus the run rows of that history, so `observationsOf(id)` (all warm history, newest `seq` first), `runMeta(runId)` (the run row of a synced run, absent when unknown on this device) and `personName(id)` (the name the sync shipped for an actor, absent when the role may not see names) answer synchronously; `queuedRunsOf(id)` lists the device's queued runs that name the feature or whose prediction touches it, oldest first, in every state. The run rows are a bounded memory cache (`RUN_META_CACHE`, 20,000; older ones reload from the `runMeta` store on `warmActivity`), and the queued runs are mirrored in memory on `appendRuns`, `settleRuns` and `removeRuns`, so the Aktivität timeline of a feature answers without further I/O.
- **`facts.near(type, bbox)`** answers from an incremental grid index (`src/store/spatial.ts`) kept on every put and delete of the mirror; it never scans all features. It ignores Z and includes edge contact, and predictions (overlay) supersede committed features. Measured at 60k: p95 0.12 ms (x4 phone factor 0.5 ms; budget 1 ms); the index adds about 2 MB to the mirror.
- **`applyPage(rows, cursor)`** writes the page (with its run rows and names) and the cursor in ONE transaction, issued in chunks of `WRITE_CHUNK` (200) requests (`src/store/chunked.ts`): `IDBObjectStore.put` clones synchronously, so the next chunk is issued from the success callback of the previous chunk's last request. The transaction stays alive, the event loop gets a task boundary between chunks, the cursor is put last, and an abort at any chunk leaves the previous page and cursor. Only the scheduling is chunked, so the store can still move into a worker. A row with a lower `updatedSeq` than the stored one is skipped; feature and edge tombstones apply unless the row was re-created later. Edge tombstone `id` must equal `edgeKey(edge)` from core.
- **`indexText(type, property)` and `searchText(sources, query, limit)`** (`src/store/text-index.ts`) search text and number properties without a scan: per (type, property) a sorted array of word tokens (NFD, diacritics stripped, lower-cased) with postings, kept on every put and delete (tombstones drop out; `clearCache` empties it). The app calls `indexText` once per `tools.search.sources` entry at open or config load: that is a bulk build (postings first, one sort of the distinct tokens). `searchText` on an unregistered source throws `DeviceStoreError` `text_source_not_indexed`. A query splits into words; every word must be the prefix of a word of a searched value. The most selective word (fewest postings, priced with a cap) drives the index walk, the rest are checked on the feature. Predicted features of queued runs are found too. In memory only. Measured at 60k distinct names (bench/client-store): keystroke worst 1.0 ms (x4: 4.2 ms, budget 50 ms), build at open 156 ms (x4: 624 ms, budget 1000 ms derived from cold-start-60k), one incremental add 0.02 ms, index heap 5.1 MB.
- **Runs are the irreplaceable data.** `appendRun(run, blobs)` stores run and blobs in one transaction (idempotent per run id, ordered by a device counter, not a clock). `QuotaExceededError` rejects with `quota_exceeded` and nothing is queued. `clearCache()` drops features, edges, history, the run rows (`runMeta`), the names (`people`) and the cursor, never runs, blobs or predictions.
- **Uploaded files (WP-803).** `RunSettlement.uploaded` replaces the run row's optional `uploaded` list (sha256 of the blobs already PUT); the queue writes it after each successful PUT and a retry skips those. Absent keeps the old value.
- **Purges.** `deleteBlob(sha256)` drops a blob's bytes and key; `dropHistory(featureId, properties)` drops cached history rows by key range (no scan) and releases the run rows no history row references any more. Both are transactional and idempotent.
- **Predictions** (`putPrediction`, `dropPrediction`) overlay the server state until dropped. The states come from `core.fold` in the run queue. A prediction also carries `observations` (`featureId`, `property`, `result`: what the run's plan wrote, rule runs included, in plan order); `plannedChangesOf(runId, featureId)` reads them, and the Aktivität entry of a waiting run is built from them, so it matches the synced entry (WP-854). A prediction stored before this field existed has none (pre-release, no shim).
- **Open failures never delete the database.** `open_failed`, `blocked`, `terminated` and `version_change` are typed (`STORE_ERROR_CODES`); `exportRuns()` still reads the queue when the connection is lost.
- **Eviction guard.** `marker` (localStorage in the app) says "this device was initialised". A new empty database with the marker set opens as `origin: 'evicted'` and stays so until `acknowledgeEviction()`.
- **Storage health.** `readStorageHealth(browserStoragePort(globalThis))` gives `{ persisted, usageBytes, quotaBytes, standalone, atRisk }` for the honest-state header.
- **Platform ports.** The store needs no DOM typings: pass `{ factory: indexedDB, keyRange: IDBKeyRange }` as `env`; tests pass fake-indexeddb. The sync host (`src/host`) can run the store's writes in a worker (see below).

Benchmark: `bench/client-store` (`npm test -- -c bench/vitest.config.ts client-store`).

## Sync worker (`src/sync`, WP-512)

`createSyncWorker({ store, transport, meta, predictions, clock })` is the one engine that pulls the `core/sync` protocol (contract: `src/sync/contract.ts`). HTTP is the `SyncTransport` port, the snapshot head is kept by the `SyncMeta` port, and the run queue plugs in as `PredictionRefresher`.

- **`pull()`** runs a snapshot (no cursor) or a delta (stored cursor) to the end of the server's data. Each page is written with its cursor in one `applyPage` transaction; the next page is requested while the current one is written. It is single-flight: a call during a pull waits and then pulls once more. Typed errors reject (`SyncProtocolError` such as `version_mismatch`, `DeviceStoreError`); `status().lastError` says `transport`, `protocol` or `store`. Nothing falls back.
- **Access value (WP-793).** The worker keeps the last `header.access` of the server (the first is the baseline). A page whose value differs sets `PullResult.accessChanged`; the host rings `onAccessCheck` (the one role-refresh path, WP-784). A server without the field never flags it.
- **Resume.** During a snapshot the store cursor is the paging cursor and `SyncMeta` holds the pinned head; the request carries `after` and `pin`. When the last page lands the cursor becomes `{ delta, head }`, so writes made during the snapshot arrive through the first delta (the store's stale guard makes replays harmless). Without a stored head the snapshot restarts.
- **Resets.** A different scope fingerprint, a server head behind the cursor, or a changed pinned head clears the cache (never runs, blobs or predictions), re-snapshots and calls `predictions.rederive(reason)`. A first sync calls it too. More than 3 restarts in one pull is a typed `malformed` error.
- **Purges.** A `redaction` tombstone calls `store.dropHistory(featureId, [property])` and the page's feature row replaces the blanked value; a `blob` tombstone calls `store.deleteBlob(sha256)`. Both run before the page is applied (idempotent, so a crash repeats them). The store's page plan ignores these two kinds.
- **Auto sync.** `createAutoSync({ worker, timers, doorbell, online, visible })` pulls on start (`open`), on `online` and on `visibilitychange`, and after the doorbell with a 500 ms debounce, so a burst is one pull.
- **Paging and pinning** are part of `core/sync` (`SyncRequest.after`/`pin`, `SyncPageHeader.head`, docs/07). The store cursor holds one number, so `SyncMeta` keeps the pinned head while a snapshot runs.

Benchmark: `bench/client-sync` (60k features, 60 pages: about 1 s on fake-indexeddb; budget 20 s).

## Sync host: in-thread or in a Web Worker (`src/host`, WP-567, B-012)

`openSyncHost({ mode, ... })` returns a `SyncHost`: a `DeviceStore` to read through, a `SyncWorker` (`pull`, `status`, `subscribe`) and `dispose()`. The app picks the mode; a worker that cannot start is an error, never a silent fallback.

- **`in-thread`**: `openWriterStore` plus `createSyncWorker` on the calling thread (Node, tests).
- **`worker`**: the app starts `new Worker(...)` whose entry calls `serveSyncHost(self, factory)` (the factory builds the worker's adapters: `env`, `transport` with inline decode, `clock`). `openSyncHost({ mode: 'worker', port, config, predictions })` opens a **read replica** on the main thread and proxies `pull`. Cache writes on the replica (`applyPage`, `clearCache`, `dropHistory`) reject with `not_writer`; the run queue's writes (`appendRun`, `putPrediction`, `putConfigVersion`, ...) work on it and go straight to IndexedDB through the main thread's own connection.
- **`DeviceStore.onChange(listener)`** (both hosts): one call per committed change: `page` (changed feature ids and the stored cursor), `cleared`, `history_dropped`, `blob_deleted`, and `reloaded` (a replica re-read the database). A `page` listener already sees the page through `facts`.
- **Consistency.** The worker commits to IndexedDB, then to its memory, then posts a notice `{ from, commit }`; `commit` for a page is the applied `PagePlan`. The replica applies it with `commitPlan` only when `from` equals its own cursor, one notice at a time and in order. Otherwise it reports `replica_diverged` (`onFault`) and re-reads the database (`reloaded`). Startup: the replica hydrates, the worker opens and reports its cursor, the replica re-reads if they differ, and only then does the worker accept `pull`.
- **Protocol** (`src/host/protocol.ts`): versioned (`HOST_PROTOCOL_VERSION`), kinds `init start pull rederived close` to the worker and `ready pulled status change rederive issue fault` back. An unknown kind, another version or an ill-typed field is a `HostProtocolError` (`bad_version`, `unknown_kind`, `ill_typed`, `out_of_order`, `replica_diverged`) and faults the host. Typed errors travel as `{ kind, code, message }` and are rebuilt as `SyncProtocolError` or `DeviceStoreError`.
- **Run queue.** It reads the replica through the port. It re-predicts through `PredictionRefresher.rederive`, which the sync worker calls only after the whole pull; it does not read `pageInFlight()` or subscribe to `onChange`. `rederive` runs on the main thread: the worker asks for it with a `rederive` message and waits for `rederived`.
- **`blobs` is main-only.** It is queue data (a queued run's bytes), so the worker's store never writes it. On a blob tombstone the worker's `deleteBlob` only announces the purge (a `blob_purge` notice with the ids); the main thread applies it on its own connection (`purgeBlobs`, also what `deleteBlob` does on the replica and in-thread), in one transaction with the check that no queued run still references the sha. A referenced blob survives the purge. Each blob dropped is heard once as `blob_deleted`.
- **`pageInFlight()`** is true while the mirror is not a whole, consistent state: a page is half applied (slices arrived, the last did not), or a re-read of the database (`rehydrate`) is under way, when features may be loaded but the cursor is not. Wait for `onChange` (a `reloaded` after a re-read) before reading. It is a hook for other readers (UI, map, `facts` readers); nothing in the run queue consults it. Always false in-thread.
- **Slices.** The replica applies a page in slices of about `SLICE_ROWS` (600) rows, each in its own task (`sliceNotice`), because a whole 1,000-feature page measured 50-110 ms on the main thread at the x4 factor. The cursor and the one `page` notification follow the last slice, so between the first and the last slice a reader can see part of the page, but only whole feature groups: a slice holds a feature with the edges from it and its history rows, never one without the other (an oversized single group is one slice; a group is never split). The page's run rows and names belong to no feature and travel with the first slice. The edges that travel are those FROM the feature, so between slices `edgesFrom(a)` may return an edge whose `to` feature has not arrived yet, and `edgesTo(x)` shows an edge only once its source's group has arrived. Readers must tolerate a missing endpoint while `pageInFlight()` is true; the run queue never sees a half-applied page, because it re-predicts through `rederive` after the whole pull (in worker mode the `rederive` message follows the last slice on the same port). After a `replica_diverged` the rest of that page's slices are discarded and the replica re-reads once. What crosses is the applied plan without its write bookkeeping (`PageEffects`); history rows travel too, because `facts.history` on a warm feature must see them.
- **Sync head.** In the worker `SyncMeta` is the `syncHead` key of the meta store (`idbSyncMeta`), because a worker has no `localStorage`. The same meta store keeps `lastSynced` (WP-678: `SyncMeta.readLastSynced/writeLastSynced`): written when a pull completes, read once by `SyncEngine.restore()` at host start so `SyncStatus.lastSyncedAt` survives a reload; a snapshot restart (cache cleared) forgets it. The UI turns it into "Zuletzt synchronisiert" / "noch nie synchronisiert" / the 7-day stale line (v3 `freshness.ts:11-37`).
- One host per store name (one participant and project).
- **Several tabs (WP-572).** Pass `tabs: browserTabs(name)` (worker mode; `src/host/tabs.ts`, `tabs-browser.ts`). The tab that holds the Web Lock `ueberblick-sync:<name>` runs the worker and pulls; the other tabs open only their replica (no worker is started, no sync work) and follow the holder: the holder relays its worker's `change`, `status` and `rederive` messages over a `BroadcastChannel` of the same name, and a follower feeds them through the same in-order apply (a follower that missed a notice re-reads the database via `replica_diverged`). A follower's `sync.pull()` (the doorbell) is forwarded to the holder and answered with its `PullResult`. Followers queue for the lock; when the holder closes or the tab dies, the browser releases it and the next tab starts its worker, checks its replica against the stored cursor and resumes the pull from it. Takeover order: lock granted, `holder` flag set, replica checked against the stored cursor (re-read if it moved), worker `start`, then `holder` is announced. `Tabs.pull()` on the new holder in that window waits for the start and then runs; all pulls of the window (including doorbells and forwarded pulls) share one worker pull, so none faults with `pull arrived while the host was ready` and none is dropped. `DeviceStore.pageInFlight()` also covers a replica re-read: it stays true until `hydrate` has restored features and cursor, and the `reloaded` notice fires after it is false. Both ports are structural (`SyncLockManagerLike`, `BroadcastChannelLike`, `TabCoordination`): tests pass `FakeLocks` and `FakeBus` (`test-tabs.ts`). A page that is not a secure context (plain http) throws the typed `InsecureContextError` in `browserTabs`, checked before anything else; a secure platform without Web Locks throws the plain error; pass `SINGLE_TAB` deliberately for a single tab (`tabs` is required). Not covered: the run queue's own lock (`webQueueLock`) is separate.

## Config versions and schema versions (`src/config`, `src/store`, WP-514)

`openConfigVersions({ store, fetcher })` returns `ConfigVersions` (contract: `src/config/contract.ts`): the compiled configs the device holds for its queued runs, hydrated with core's `hydrate` (no compiler on the device) and kept in memory.

- **`get(version)`** is synchronous and returns the config or `'refetching'`. A stored version whose `format` differs from the running core's `COMPILED_FORMAT` (older after an app update, newer after a rollback), and any version never seen, is wanted and fetched through the `ConfigFetcher` port (single flight per version). The readable copy is stored (`putConfigVersion`) and survives `clearCache`. A copy this core still cannot read is not stored and stays `'refetching'` with `lastError(version)`.
- **Runs are never touched.** `awaiting()` lists the versions the queue is waiting for; runs recorded against them stay queued and visible. `refresh()` retries every awaiting version.
- **IndexedDB schema versions** are the `MIGRATIONS` list in `src/store/schema.ts`; `DB_VERSION` is its last version. A step only adds stores or indexes and is never edited; opening an older database runs the missing steps and keeps runs, blobs, predictions and the cursor (test from a v1 fixture: `migrate.spec.ts`). v2 added the `configVersions` store, and v3 the `runMeta` and `people` stores and the `history.runId` index.
- **Page decode in a worker** (`src/sync/decode.ts`). `decodingTransport(encodedTransport, decoder)` makes the `SyncTransport` for the sync worker: it asks the HTTP adapter for a page with the cap `SYNC_PAGE_MAX_ROWS` (1,000 feature rows; sent as `SyncRequest.limit`) and hands the raw JSON text or tuples to a `PageDecoder`. `createWorkerDecoder(port)` posts it to a worker that runs `serveDecoder` (entry file: `src/sync/decode-entry.ts`); typed errors come back as `SyncProtocolError`. `inlineDecoder` decodes on the calling thread (tests, hosts without workers). A page over the cap is a `malformed` error. Only the structured-clone hand-back and `applyPage` remain on the main thread.
- **Live versions (WP-669).** The sync host reports each page header's `versions` and each completed pull to a `VersionsSink` (`config/sink.ts`): `follow` sets `deployed` and wants every live version; `synced` calls `retain(queued)`, dropping stored and in-memory versions outside it (`ConfigStorePort.deleteConfigVersion`). A failed pull prunes nothing. `get` stays synchronous. In the worker host the worker posts the host message `versions` (protocol 2) and the main thread applies it; the in-thread host calls the sink directly (`versions` option of both hosts, `lateVersionsSink` while `ConfigVersions` is not open yet; `device.ts` wires it).

Benchmark `bench/client-sync` (real `worker_threads` decode): the judged long-task line is the main-thread work the store does per page on a device: plan, the structured clone of the puts (IndexedDB clones synchronously) and the in-memory commit, worst of 59 pages of 1,000 features (after one warm-up page), at the x4 device factor against 100 ms. `planPage` and the spatial index allocate no per-row key strings or tuples (WP-858). The worst page is the one that crosses 32,768 features: every `Map` of the index (features, by type, slots, edges, adjacency) doubles and rehashes there, about 2 ms each, so the number cannot fall far below one page of work plus that doubling. The longest event-loop stall during the 60k pull is printed as info only: fake IndexedDB runs its transactions in JS on the same thread, which a browser's IndexedDB does not. Node cannot show a throttled phone's numbers; the browser bench is the authority for those.

## Run queue (`src/queue`, WP-511)

`createRunQueue(deps)` returns the `RunQueue` (contract: `src/queue/contract.ts`). It talks to the store only through the `QueueStore` slice (async, plus the sync `facts` port `core.plan` needs, B-004), so the store may later live in a worker (B-012).

- **Store first.** `submit(runs)` plans with `core.plan` over `store.facts` (which layer earlier predictions), then stores the runs with `appendRuns` (one transaction, an atomic batch H2 shares a `group` and is one entry and one request) and then `putPrediction`. A device refusal stores the batch as `refused` drafts and returns `{ ok: false, refusal }`. `quota_exceeded` rejects, nothing is stored. `warmHistory` runs first for the runs' features and their neighbours.
- **Created features** (WP-681). `submit`/`enqueue` answers `{ ok: true, orders, created }`: `created` maps each submitted run id to the features its own local plan created (the `created` list of `core.plan`, i.e. the `$type` observations), `[]` for a run that creates nothing; a feature only a rule created is not listed. Ids come from `seededIds` in `@ueberblick/core/plan` (`plan/seeded-ids.ts`), so a rebase or re-plan gives the same ones. `createdBy(runId)` answers the same later (latest plan, last 200 runs of the session, also after accept and pull; `[]` after a refusal). A form for a create without a map position (`on: $none`) opens the new feature's detail with it.
- **Prediction** (`predict.ts`): `core.fold` over the planned observations, one `Prediction` per submitted run (rule runs folded in). Limit: only added reference edges; removed reference edges and derived edges are not layered until the next pull.
- **Order and sequence.** The store's device counter orders the runs; no clock is read. `drain()` is single-flight per tab and per `QueueLock` (`webQueueLock(navigator.locks, name)`), sends one entry at a time, and stops on the first entry that is not settled.
- **Files first** (WP-605). `blobTransport` is a required dependency (`has(sha256)`, `put(sha256, bytes, mime)` in `src/queue/contract.ts`): before `transport.send` the queue uploads every file of the entry whose bytes are in the store with `put` (idempotent on the server, so no `has` probe first, which would log a 404 console error, WP-785) and asks `has` only for a file whose bytes are gone, one file at a time (`src/queue/upload.ts`), so the server never receives a run that references bytes it lacks. A thrown transport error is transient: the run is not sent, capped backoff. A `mismatch` or `too_large` answer, or a file whose bytes (or mime) are no longer in the store while `has` says the server lacks it too, refuses the entry locally (`blob_mismatch`, `blob_too_large`, `blob_lost`); the bytes stay in the store for "Bearbeiten" and resubmit. The mime of every blob is stored with the run row (`StoredRun.blobMimes`) and is required on every `BlobInput`.
- **Typed refusal only.** `decodeRunReply(status, body, expectedVersion = SYNC_PROTOCOL_VERSION)` turns an HTTP answer into a `RunReply`: only a body that matches the run endpoint envelope on its own status (200 accepted, 422 refused, 409 review) settles a run; 401 is `unauthenticated`; a body naming another protocol `v`, or none on a 200/409/422 (every run reply carries `v` since WP-144), is `incompatible`; everything else is `transient`. `incompatible` sets the hold `incompatible_protocol`: no retry, no backoff (`resetBackoff` does not clear it), no run lost, `QueueStatus.serverProtocol` says which version answered; the app must be updated. Transient: backoff 2 s doubling to 5 min on a monotonic clock, `resetBackoff()` on `online`/focus/sign-in. **Self-retry:** in a backoff the queue arms one timer on the injected `timers` port for `retryInMs` and drains again by itself; `resetBackoff`, a settled drain and `close()` cancel it, a repeated status never double-schedules, and `incompatible_protocol` / `auth_expired` never arm one. A retry that throws goes to the required `deps.onError`. The app calls `close()` on stop and keeps no retry timer of its own. A hung request times out (30 s) as transient. The `code` of a refusal travels unchanged into `QueueStatus.refused`.
- **Rebase.** After a refusal the entry's prediction is dropped and every QUEUED entry is re-planned in order; an entry that now fails is refused, the rest is kept. **Dependent runs (WP-767, v3 `dependent_rejected`):** when the failing entry names a feature whose creating run is refused (`createdBy` of a refused or dependent run), it is stored with the registry state `dependent` instead of `refused`, carrying the culprit's refusal (same `code`) with `depends on refused run <id>: …` as developer message. A registry state, not a flag, so the stored row says it without parsing and `isRefusedRunState` (registry) is the one test for "refused or dependent". It is listed in `QueueStatus.refused`, can be resubmitted and discarded like a refused run, and is never sent. A run refused for its own reason stays `refused`. Accepted entries are not re-planned: they were sent after every earlier entry had settled, so their prediction is already current. A run that was refused on the device at enqueue (because a predecessor's prediction made it invalid) stays a refused draft when that predecessor is later refused by the server; the user re-enters it. A `review` reply (server has no such config version) is kept, never dropped, and rebases the same way. `rederive(reason)` (the `PredictionRefresher` of the sync worker) re-plans every live entry without refusing: a run that fails then stays queued and the server decides, and it is listed in `QueueStatus.unpredicted` ("not previewed"), never dropped silently. `createRunQueue` re-derives once at start.
- **After a pull.** `onPulled(seq)`: accepted runs the pull covers lose their prediction and leave the queue. Wire it to the sync worker status.
- **Drafts.** `resubmit(runId)` (new run ids, the old draft is removed after the new one is stored) works on `refused`, `dependent` and `review` runs and then drains at once, like a new local run (WP-764); offline the attempt fails transiently and the run waits for the next trigger. `discard(runId)` also takes a `queued` run that is not being sent (WP-627): it drops the run, its batch, its prediction and its parked bytes (bytes another run still references stay) and re-plans the later waiting runs; a run in flight is `not_discardable` until the send settles. `exportQueue()` reads through `store.exportRuns()`, also when the store is unavailable.
- **Feature configs (WP-675).** `createFeatureConfigs({ versions, facts, fallback })` (`config/resolver.ts`) is the one feature-to-config resolver: `of(id)` (undefined while the version is not on the device), `configFor` (throws `AwaitingConfig`), `versionFor`. The planner and the web participant reader both use it (R1); `FeatureState.version` is the stored version's one type.
- **Planner (WP-319).** `queue/planner.ts` plans with `planFor` and a `configFor` that resolves a feature to the `version` the sync sent with it (else `config.deployed`, else the run's own `configVersion`), a create to `deployed`. A version that `ConfigVersions.get` answers `'refetching'` for makes `plan()` return `{ kind: 'config', version }`. `PlanOutcome.planned` holds the planned runs, stamped with the version they were planned under; a prediction keeps the `version` of its feature.
- **Ids of created features** (`seededIds` in `@ueberblick/core/plan`): `core.plan` itself derives the ids of what a submitted run creates from the run's id (n-th feature id, n-th rule-run id), whatever `ids` port the caller passes and whatever batch the run is in. Re-planning (rebase, re-derivation, restart) and the server's plan mint the same ids (WP-748): a queued run that refers to a created or rule-created feature stays valid, there is no ghost twin, and a created feature the form opened is the one the server stores.
- **Known limits.** (1) Upload blobs are stored with their run but are not part of the run envelope: blobs of settled runs are not garbage-collected (a later work package). (2) Two tabs: only the tab holding the lock drains and settles; the other tab's in-memory prediction overlay refreshes on its next `rederive`/`onPulled`, not when the holder settles a run.
- **Store additions** (`src/store/runs.ts`): `appendRuns`, `settleRuns`, `removeRuns`; `StoredRun` has `state`, `group`, `refusal`, `acceptedSeq`, `blobMimes` (mime per blob sha256, written for every blob). Rows written before read as `queued`.

Benchmark: `bench/client-queue`.

## Simulation against the real adapters (`src/simulation`, WP-513)

Test-only (`*.testing.ts`, never imported by production code). `simulateReal(workload, makeBackend, options)` runs N devices built from the real adapters (`RealDevice`: fake-indexeddb store, run queue, sync worker) against a `SimBackend` (contract: `contract.testing.ts`) under seeded faults, drains fault-free and checks the three invariants of docs/07 (`invariants.testing.ts`). The package may not import `packages/server`, so the server is the `SimBackend` port; `fixtures/golden/simulation/backend.ts` implements it with the real SQLite run store and the real run and sync handlers.

- `net.testing.ts`: `Faults` wraps a transport call: lost request, lost reply (the server applied), duplicate, late duplicate, offline. Decisions come from the seeded `Rng`, in call order.
- `sim.testing.ts`: the tick loop (offline flips, restarts, runs, atomic batches from a `verwaltung` device, admin batches straight to the server), the drain, the oracle (a fresh device's snapshot per actor). `simulateRealWorld` returns the end state for tests that tamper with it.
- `repro.testing.ts`: `shrink` and `formatRepro` turn a failing seed into a minimal `SIM_SEED=... npm run sim` command; `fromEnv` and `toEnv` are the two directions of it.

Profiles, the SQLite backend, the specs and the accepted limits: `fixtures/golden/simulation/README.md`. Budget: `bench/simulation-real` (short profile at most 30 s).

## Photo thumbnails (`src/blobs`, WP-667)
`ThumbCache` (`get`, `has`, `put`, `count`, `bytes`, `keys`, `remove`, `clear`) is the device's Offline-Bilder store: `idbThumbCache(env, name)` keeps `{ sha256, bytes, mime }` rows in its own IndexedDB (not the run queue's `blobs` store); `undefined` env gives an unsupported cache that stores nothing. `downloadThumbs({ shas, cache, transport, signal, onProgress })` is bounded (`THUMB_FETCH_CONCURRENCY` 3, `THUMB_CACHE_MAX_BYTES` 256 MiB) and returns `{ stored, failed, stopped }`. `fetchThumbTransport(project, fetch)` asks `?thumb=preview` (`CACHED_THUMB_SIZE`). Specs: `blobs.spec.ts` (memory and fake IndexedDB, property test).

## Offline packs (`src/packs`, WP-662)

Device side of contract A-032. `createPackManager({ storage, transport })` diffs the server manifest, downloads changed layers by Range into OPFS (`deviceOpfsStorage(navigator, { project, participant })`; `memoryPackStorage` in tests), verifies sha256 and keeps `progress` (a store-compatible signal for the Offline tab) and `counts()`. `fetchPackTransport(project, fetch)` is the browser transport; it runs the server's answer through `decodePackManifest` (`@ueberblick/core/sync`, which also owns the manifest types so the server's builder types against the same definition) and a bad manifest fails the refresh with the path of the wrong field. `manager.files` is what the map protocol reads (`packages/ui/src/map/maplibre/packs.ts`). Details: `docs/07-sync-and-offline.md`. Specs use `fake-server.testing.ts` (fake manifest and Range server). Benchmark: `bench/client-packs`. `manager.remove(keys)` deletes packs and their files (a pack the server still lists becomes `absent`), `manager.hasLayer(layer)` answers synchronously from the ready packs after `load()` (the map protocol routes by it), `counts()` also carries each pack's `built_at`. **Scope (WP-773):** packs sit in `packs/p-<project>/u-<participant>/` of the OPFS, so another project or person on the browser never sees or deletes them; `clearPackScope(navigator, scope)` removes that person's directory (WP-769's sign-out can call it; it is not wired yet). **Safari:** OPFS `createWritable` is missing on its main thread, so `deviceOpfsStorage(navigator, scope, writer)` takes a `PackFileWriter`: `workerPackWriter(port)` posts the writes to a small dedicated worker that runs `serveWriter(self, root)` (sync access handle). The manager and the map protocol stay on the main thread; `mainThreadCanWrite(globalThis)` says when the worker is needed. The app wiring is `apps/web/src/lib/participant/offline/browser.ts` and `pack-writer.worker.ts`. **Pack file (WP-668):** `bundle.ts` holds the `.ubpack` format (B-017); `manager.packFile(key)` gives the stored pack as a lazy Blob and `manager.importPack(chunks, onProgress)` streams a file into the store, verifying each layer's sha256 (`streamChunks(file.stream())` adapts a web stream); see docs/07.

## Tool data (`src/tooldata`, WP-683, B-020)

The device side of the tool host's `ctx.data`: `createToolData({ store, transport, available, self, clock, newId, timers, doorbell, kick?, onError })` over `openToolDataStore(idbBackend(env, name))` (`memoryBackend()` in tests). `pull(tool)` and `pullAll()` mirror the streams of the available tools; `drain()` sends the outbox in creation order; `flushReads()` sends the batched read marks; `handle(tool)` is what a tool sees (`items()`, `subscribe`, `append`, `cursor`, `members()`, `markRead`, `retry`, `discard`). `httpToolDataTransport(project)` speaks the routes of WP-682, `sseToolDoorbell` turns `event: tool` into a ring with the key, and `createAutoSync({ tools })` (`src/sync`) pulls on open, `online`, `visible` and each ring. The outbox and the mirror live in their own database `<name>-tooldata`. The routes speak the server's shapes (WP-682); `tooldata/http.ts` maps them to the domain shapes of `tooldata/contract.ts` (a page has `records`, `removed` ids, `last`, `more`, the read `cursor` and the `members`, names only, which the store keeps per tool for the person picker); the mirror upserts by id, because erasure re-delivers a changed message under a new seq. `handle.cursor` is `max(acknowledged, pending)`: a read mark counts at once, also offline. The device boots it once (`apps/web/src/lib/participant/tools/device-data.ts`): one service per device, the keyed doorbell, `available` from core's `toolAvailabilityFor`, and `startSync` hands it to `createAutoSync({ tools })`. Behaviour: docs/07 "Tool streams on the device".

## Personal preference record (`src/prefs`, WP-612, WP-695)

`createPrefsClient` caches the person's record and keeps offline edits (`set`, `sync`, `subscribe`). Besides the tool switches, Kartenlayer choice and saved filter views, it holds the look: `ui.theme`, `ui.font_size`, `ui.locale`. The app reads and writes them through `PrefsPort` (`apps/web/.../settings/prefs-record.ts`), with the device storage underneath as the pre-paint and sign-in cache. Device-only: tile pack, install, remembered tab.

## Testing: fakes copy what they store (`src/testing`, WP-702)

IndexedDB structured-clones every value it stores, so a Proxy (a Svelte `$state` object), a function or a DOM node in a run input throws `DataCloneError` on a phone (the WP-696 blocker). An in-memory fake that keeps the object as is hides this. Every fake that stands in for the device store, the run queue or the servers behind them copies what it keeps through the one helper `deviceClone` (`src/testing/clone.testing.ts`, a `structuredClone`): `FakeRunServer` and `FakeBlobServer` (`queue.testing.ts`), the scripted queue of `submitter.spec.ts` and `readRuns` of `fakeDevice` (Einstellungen specs). A new fake of this kind uses `deviceClone` too; never a spread or a second copy helper. The real queue and store specs already run on fake-indexeddb, which clones.
